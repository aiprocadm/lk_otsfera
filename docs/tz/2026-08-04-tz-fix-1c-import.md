# ТЗ: починка загрузки выгрузки из 1С (Excel) — организации не создаются, экран молчит

**Проект:** `aiprocadm/lk_otsfera` (main)
**Дата:** 2026-08-04
**Тип:** bugfix + доработка функциональности
**Статус:** к реализации

---

## 0. Симптом от пользователя

> «Несколько раз пытался загрузить выписку из 1С в Excel — ничего не произошло. Пробовал из кабинета администратора, менеджера и руководителя. Новые организации не добавились.»

**Короткий диагноз (простыми словами):**

1. **Организации из Excel в принципе не создаются — так написан код.** Это не сбой, это незаконченная функция. Лист «Контрагенты» читается из файла и молча выбрасывается.
2. **Заказы и оплаты по неизвестному ИНН тоже не создаются** — они «прикрепляются» только к уже существующим в базе организациям. Нет организации → строка пропущена.
3. **Экран ничего не показал**, потому что в форме нет `catch`: если серверное действие упало (превышен лимит тела запроса, редирект гарда, ошибка БД), состояние не меняется и кнопка просто «отщёлкивает».
4. **Из кабинетов менеджера и руководителя этих страниц нет вообще** — они лежат под `requireAdmin()`.

Ниже — точные места в коде и план работ.

## 0.1. Решения владельца продукта (зафиксировано 2026-08-04)

| № | Вопрос | Решение |
|---|---|---|
| 1 | Организация без партнёра | **Допустима как прямой клиент.** Партнёр есть не всегда. У одного партнёра может быть несколько организаций (уже поддержано схемой: `Partner.organizations Organization[]`) |
| 2 | Кто импортирует | **Администратор и руководитель.** Обычный менеджер — нет |
| 3 | Ключ контрагента | **Синтезируем из ИНН**, отдельного кода/GUID из 1С не ждём |
| 4 | Откат импорта | **Нужен.** Добавляется как отдельный этап (Т-32…Т-40) |
| 5 | Создание организации из выписки | **Только ручное подтверждение**, автосоздание запрещено |
| 6 | Список блокирующих откат связей (Т-36) | **Принят предложенный минимум:** акт комиссии, пользователи организации, документы заказа |
| 7 | Срок отката (Т-40) | **30 дней** |
| 8 | Привязка новой организации к `Company` | **Вариант A (§0.2).** Клиент — это `Organization`. Отдельная `Company` на клиента **не** создаётся; `Organization.companyId` = компания-продавец импортёра |

**Хорошая новость по схеме БД:** миграции для решений 1 и 2 **не нужны** —
`Organization.partnerId` уже `String?` (nullable), `Partner.inn` уже существует и `@unique`,
`Organization.inn` и `Organization.externalId` — `String? @unique`. Правится только код-гард в writer'е.
Миграция нужна **только** под откат (новые таблицы `OneCImportBatch` / `OneCImportRow`).

## 0.2. Привязка организации к компании — принят вариант A

**Решение (2026-08-04): клиент — это `Organization`. Отдельная `Company` под клиента не создаётся.**

Обоснование — инвариант терминологии из `docs/ARCHITECTURE.md:15-17`:

> `Company` — компания-**продавец** (контур сотрудников, граница изоляции C8),
> `Organization` — **клиент** (заказчик обучения). Не путать: почти все правила scope построены на этой паре.

`Organization.companyId` отвечает на вопрос «**какой продавец ведёт этого клиента**», а не «как называется клиент».
Поэтому импорт из 1С обязан ставить туда компанию импортёра, а не минтовать новую.

### Что было бы при обратном решении (зафиксировано как отвергнутое)

Если бы каждый контрагент получал собственную `Company`:

- каждый импортированный клиент становился бы отдельным продавцом-арендатором;
- руководитель со скоупом `{ kind: 'company', companyId: свой }` **не увидел** бы ни одну импортированную организацию;
- заказы и оплаты этих организаций из того же файла отбивались бы как `out_of_scope`;
- ломался бы инвариант C8 (№5, `invariants.company-isolation.integration.test.ts`).

### Дефект, который это чинит

`writers.ts:344` — ветка создания организации сейчас делает:

```ts
const company = await tx.company.create({ data: { name: input.name } });
await tx.organization.create({ data: { ..., companyId: company.id } });
```

На каждого нового контрагента из 1С минтуется **новая компания-продавец с названием клиента**.
Клиент попадает в собственный пустой тенант, невидимый для менеджеров и руководителей.
Дефект действует и в сетевой синхронизации (`adapter-rest` идёт через тот же writer), не только в файловом импорте, — значит осиротевшие записи в базе, возможно, уже есть (см. Т-42).

### Требования

- **Т-41.** Убрать `tx.company.create` из ветки создания в `upsertOrgRecord`. Новая организация получает `companyId`:
  - скоуп `company` (руководитель) → его `companyId`;
  - скоуп `global` (admin) → компания, выбранная в форме импорта; при единственной компании в системе — она же по умолчанию, без вопроса;
  - воркер без скоупа → компания из конфигурации синхронизации (`oneCSync/config.ts`); если не задана — импорт организаций не выполняется с явной ошибкой в журнале, а не с молчаливым созданием тенанта.
- **Т-42.** Скрипт-бэкфилл `scripts/backfill-orphan-companies.mjs`: находит `Company` без пользователей, у которых ровно одна `Organization` с совпадающим названием, — это осиротевшие тенанты от прошлых прогонов. Перепривязывает их организации к целевой компании, пустые `Company` удаляет.
  Обязательно: режим `--dry-run` по умолчанию, отчёт списком, применение только с явным флагом. Перед запуском на проде — бэкап (`docs/runbook-backups.md`).
- **Т-43.** После Т-41 `mayCreateOrg` (`writers.ts:44`) расширяется на скоуп `company`: новая организация создаётся **внутри** компании актора, поэтому C8 не нарушается. Обновить комментарий-обоснование над функцией (он сейчас прямо описывает старое поведение) и тест инварианта.
- **Т-44.** Guardrail-тест: импорт любого файла **не должен** создавать ни одной записи `Company`. Проверяется счётчиком `company.count()` до и после прогона в integration-тесте.

## 1. Разбор причин (по коду)

### П-1 (главная). Адаптер файла намеренно возвращает пустой список организаций

`src/lib/services/oneCSync/adapter-file.ts:56-61`

```ts
// Excel import only ATTACHES to existing orgs (resolved by INN); it never creates orgs or documents.
async pullOrganizations(cursor: SyncCursor): Promise<OneCOrgDto[]> {
  void cursor;
  return [];
}
```

`src/lib/services/import/parse-workbook.ts` честно парсит лист «Контрагенты» в поле `orgs`, но `src/lib/services/import/index.ts:33,40` вызывает только `pullOrders()` и `pullPayments()`. Поле `orgs` не используется нигде.

**Следствие:** сколько бы контрагентов ни было в файле — 0 организаций.

### П-2. Даже при включении организаций писатель их отбросит

`src/lib/services/oneCSync/writers.ts:281-301` — `upsertOrgRecord`:

- организация без `partnerExternalId` → `skip: 'no_partner_external_id'`;
- партнёр ищется как `db.partner.findUnique({ where: { slug: input.partnerExternalId } })`, а в колонке-источнике (`ORG_COLS.partnerInn = 'ИНН партнёра'`) лежит **ИНН**, а не slug → `skip: 'partner_not_found'`.

То есть механическое «включим `pullOrganizations`» даст 100% пропусков. Требуется отдельная ветка «прямой клиент без партнёра».

### П-3. Заказы и оплаты по неизвестной организации молча пропускаются

`src/lib/services/oneCSync/resolve-org.ts` ищет организацию по `externalId`, затем по `inn`; не нашёл → `null`. Далее `writers.ts:60-61,200-201,213-214` → `skip: 'organization_not_found'`.

**Следствие:** первый импорт в пустую базу всегда даёт `создано: 0` по всем сущностям.

### П-4. Молчаливое падение UI (это и есть «ничего не произошло»)

`src/components/import/import-form.tsx:126-151` и `src/components/import/payment-import-form.tsx` — оба обработчика:

```ts
try {
  const result = await previewImportAction(form);
  setPreview(result as PreviewResult);
} finally {
  setIsPreviewing(false);
}
```

`catch` отсутствует. Любое исключение внутри server action или на транспортном уровне → промис отклонён → `setPreview` не вызван → на экране ноль изменений.

### П-5. Рассинхрон лимита размера файла

- `next.config.mjs`: `experimental.serverActions.bodySizeLimit: '10mb'`
- `src/server-actions/import.ts:7`: `IMPORT_MAX_XLSX_BYTES = 20 * 1024 * 1024`
- текст в UI: «не более 20 МБ»

Файл 10–20 МБ отвергается Next.js **до** входа в server action → исключение → П-4 → пустой экран. Выгрузка «Карточка счёта 51» за год легко перешагивает 10 МБ.

### П-6. Доступ по ролям

- Обе страницы (`/admin/settings/integrations/1c/excel`, `.../1c/payments`) вызывают `requireSettingsSection('integrations.oneC', 'admin')` → `requireAdmin()`. Менеджер и руководитель → redirect `/forbidden`. Зеркал в `/leader/*` и `/manager/*` нет.
- В сервисе `src/lib/services/import/index.ts:20` `isStaff()` разрешает `admin | manager`, но **не** `leader` — рассинхрон с `importScope()`, который отдельно обрабатывает manager-leader.
- Раздел закрыт feature-флагом (`SETTINGS_SECTIONS[integrations.oneC].flag`); при выключенном `FEATURE_SETTINGS_HUB` HTTP-редиректы из `next.config.mjs` не регистрируются, а страница нового хаба может отдать `notFound()`. **Проверить `.env` первым делом.**

### П-7. Карта колонок помечена как непроверенная

`src/lib/services/import/column-map.ts:2-3`:

```
// SAMPLE-LOCKED: confirm against the real export before go-live
```

Сопоставление заголовков — точное строковое равенство (`colIndex.get(label)`). Оно ломается от:
- неразрывного пробела (`\u00A0`) в шапке 1С;
- «ё» vs «е» («ИНН партнёра» / «ИНН партнера»);
- регистра и двойных пробелов;
- переноса строки внутри ячейки шапки;
- других имён листов («Контрагент», «Реализация товаров и услуг», «Поступление на расчётный счёт»).

Плюс внутренняя несогласованность: `ORDER_COLS.orgInn = 'ИНН организации'`, а `PAYMENT_COLS.orgInn = 'ИНН'`.

Если имя листа не совпало — `readSheet` возвращает `[]` **без единой ошибки**. Итог: `pulled = 0` → `error: 'empty'` → «Файл пуст или нет валидных строк», что для пользователя выглядит как «файл не тот», хотя файл нормальный.

### П-8. Формат файла

- Страница «Загрузка Excel» принимает только `.xlsx` (`accept=".xlsx"` + проверка расширения). 1С по умолчанию отдаёт `.xls` (BIFF8) или `.mxl`.
- Проверка идёт по **расширению**, а не по сигнатуре. Переименованный `.xls` → `.xlsx` → ExcelJS падает → `parse_failed`.
- Модуль выписки (`read-spreadsheet.ts`) умеет оба формата через `xlsx` (SheetJS), модуль «чистого» импорта — нет.

### П-9. Нет диагностики

`previewImport` / `commitImport` (`src/lib/services/import/index.ts:57-60,72-75`) ловят исключение пустым `catch {}` и возвращают строку `'parse_failed'`. Ни лога, ни имени листа, ни нераспознанного заголовка. Отладить по продовому инциденту невозможно.

### Этап 2. Устойчивое распознавание листов и колонок (P1)

- **Т-8.** Ввести нормализацию заголовка перед сравнением: `trim` → замена `\u00A0` и переносов на пробел → схлопывание пробелов → `toLowerCase()` → `ё` → `е`.
- **Т-9.** Перевести `SHEET_NAMES`, `ORG_COLS`, `ORDER_COLS`, `PAYMENT_COLS` со строк на **массивы алиасов**: `{ inn: ['ИНН', 'ИНН организации', 'ИНН контрагента'] }`. Первый совпавший — победитель.
- **Т-10.** Лист искать не по точному имени, а по нормализованному вхождению: «Контрагенты» матчит «Контрагент», «Реализации» матчит «Реализация товаров и услуг».
- **Т-11.** Если ни один лист не распознан — возвращать не `'empty'`, а `'sheets_not_recognized'` с перечнем фактических имён листов в отчёте (Т-3).
- **Т-12.** Если лист найден, но обязательная колонка (ИНН / Номер / Сумма) не найдена — возвращать `'columns_not_recognized'` с перечнем фактических заголовков.
- **Т-13.** Поддержать `.xls` на странице «Загрузка Excel»: вынести `readSpreadsheet()` из `oneCAccountCard/read-spreadsheet.ts` в общий `src/lib/services/import/read-spreadsheet.ts` и использовать в `parse-workbook.ts`. `accept` в input → `.xls,.xlsx`.
- **Т-14.** Проверять сигнатуру файла, а не только расширение: `PK\x03\x04` → xlsx, `\xD0\xCF\x11\xE0` → xls. Несовпадение → `'format_mismatch'` с подсказкой «Файл назван .xlsx, но внутри старый формат .xls — пересохраните из 1С в «Лист Excel 2007-…(xlsx)»».

### Этап 3. Импорт контрагентов = создание организаций (P0, ядро задачи)

- **Т-15.** Реализовать `FileOneCAdapter.pullOrganizations()`: возвращать DTO из уже парсящегося `sheets().orgs`. Схема `OneCOrgSchema`, поля: `externalId`, `name`, `inn`, `kpp`, `partnerExternalId?`.
- **Т-16.** `externalId` контрагента **синтезируется детерминированно** из нормализованного ИНН по формуле `1c-inn:<ИНН>` (решение №3). Колонки «Код»/«GUID» из 1С не используются. Требования:
  - формула вынесена в одну экспортируемую функцию `synthOrgExternalId(inn: string): string` — единственная точка правды, её же использует откат;
  - строка **без ИНН** не может получить ключ → `invalid: 'no_inn'`, организация не создаётся (в таблицу ошибок с наименованием контрагента, чтобы оператор завёл вручную);
  - префикс `1c-inn:` обязателен — он отличает синтетический ключ от настоящего `externalId`, пришедшего по сети из `adapter-rest`;
  - если организация уже найдена по `inn` и у неё **есть** свой `externalId` — синтетический **не** записывается поверх (логика backfill в `upsertOrgRecord` уже такая, сохранить).
- **Т-17.** В `src/lib/services/import/index.ts` в `run()` добавить **первым** батчем организации (до заказов и оплат), чтобы заказ из того же файла нашёл свою организацию в live-режиме. Порядок: `orgs → orders → payments`.
- **Т-18.** Расширить `ImportReport` до `{ orgs, orders, payments }` и вывести карточку «Организации» в `import-form.tsx` наравне с «Заказы»/«Оплаты».
- **Т-19.** В `upsertOrgRecord` (`writers.ts:288-301`) снять жёсткое требование партнёра (решение №1). Новая логика:

  | Что в строке «ИНН партнёра» | Поведение |
  |---|---|
  | пусто | организация создаётся как **прямой клиент**, `partnerId: null` |
  | заполнено, партнёр найден | `partnerId = partner.id` |
  | заполнено, партнёр **не** найден | `skip: 'partner_not_found'` — не угадываем и не создаём партнёра молча |

  Код `no_partner_external_id` удаляется полностью.
  Миграция не требуется: `Organization.partnerId` уже nullable.
  > ⚠️ Правка затрагивает **и** сетевую синхронизацию (`adapter-rest` идёт через тот же writer), не только импорт из файла. Это ожидаемо и согласовано, но пункт обязателен к упоминанию в CHANGELOG.

- **Т-19а.** «У партнёра может быть несколько организаций» — уже поддержано схемой (`Partner.organizations Organization[]`, `Organization.partnerId` — обычное поле без `@unique`). Требование к реализации: **не** делать `findUnique` по `partnerId` и не предполагать 1:1 нигде в новом коде. Покрыть тестом: две строки контрагентов с одинаковым «ИНН партнёра» → создаются две организации, обе с одним `partnerId`, ошибок нет.

- **Т-20.** Поиск партнёра вести по ИНН, а не по `slug`:
  `db.partner.findFirst({ where: { OR: [{ inn: normalizedInn }, { slug: raw }] } })`.
  Миграция не нужна — `Partner.inn String? @unique` уже есть в схеме (`prisma/schema.prisma:646`).
  ИНН партнёра нормализуется тем же кодом, что и ИНН организации (Т-22).

### Этап 6. Откат импорта (P1, решение №4)

Требуется откатывать **импорт из Excel** (лист-файл 1С). Откат выписки (карточка 51) — вне объёма, там уже есть `PaymentImportBatch` и очередь разбора.

- **Т-32.** Миграция: новые модели по образцу `PaymentImportBatch`.

  ```prisma
  model OneCImportBatch {
    id           String            @id @default(cuid())
    createdAt    DateTime          @default(now())
    importedById String?
    importedBy   User?             @relation("OneCImportBatchBy", fields: [importedById], references: [id])
    companyId    String?
    fileKey      String?
    fileName     String
    counts       Json
    status       String            // committed | rolled_back | rollback_partial
    rolledBackAt DateTime?
    rolledBackById String?
    rows         OneCImportRow[]
    @@index([companyId, createdAt])
  }

  model OneCImportRow {
    id        String          @id @default(cuid())
    batchId   String
    batch     OneCImportBatch @relation(fields: [batchId], references: [id], onDelete: Cascade)
    entity    String          // organization | order | payment
    entityId  String          // id созданной/обновлённой записи
    action    String          // created | updated
    before    Json?           // снимок изменённых полей ДО (только для action=updated)
    reverted  Boolean         @default(false)
    @@index([batchId, entity])
    @@index([entityId])
  }
  ```

- **Т-33.** `commitImport` пишет батч и по строке `OneCImportRow` на каждую запись. Для `action: 'updated'` в `before` кладётся снимок **только тех полей, которые импорт трогает** (`name`, `inn`, `kpp`, `externalId`, `partnerId` для организации; `totalAmount`, `paidAmount`, `financialStatus`, `executionStatus` для заказа; сумма/дата/назначение для платежа). Полный снимок записи не хранится — это ПДн и лишний объём.
- **Т-34.** Writer'ы (`upsertOrgRecord`, `upsertOrderRecord`, `upsertPaymentRecord`) должны **возвращать** `{ entityId, action, before }`, а не только инкрементить счётчики. Сейчас они возвращают `void` — это обязательная предварительная правка.
- **Т-35.** Логика отката:
  - `action: 'created'` → удалить запись;
  - `action: 'updated'` → восстановить поля из `before`;
  - порядок обратный порядку импорта: **платежи → заказы → организации** (иначе внешние ключи не дадут удалить организацию).
- **Т-36. Защита от разрушительного отката (обязательно).** Откат **не выполняется** и возвращает список конфликтов, если хотя бы одна созданная запись уже «обросла» связями:
  - платёж входит в `CommissionStatementItem` или имеет `CommissionCorrection` → **откат заблокирован** (иначе поедет уже согласованная комиссия партнёра);
  - у заказа появились `OrderStatusChange`, документы, зачисления, или платежи не из этого батча;
  - у организации есть пользователи (`OrganizationUser`), заявки, сделки, сертификаты, студенты или заказы не из этого батча.

  UI показывает список: «Нельзя откатить: 3 платежа уже в акте комиссии №…, организация «…» имеет 2 пользователей». Оператор разбирается вручную.
- **Т-37.** Частичный откат: если часть строк откатить нельзя, дать выбор — «откатить только безопасные» (статус `rollback_partial`, у откаченных строк `reverted: true`) или отменить целиком. По умолчанию — **отменить целиком** (безопаснее).
- **Т-38.** Откат выполняется в одной транзакции Prisma. Права — те же, что на импорт (Т-25). Обязательная запись в `recordAudit` с `action: 'one_c_import.rollback'` и перечнем затронутых id.
- **Т-39.** UI: на странице «Загрузка Excel» блок **«История импортов»** — таблица последних 20 батчей (дата, файл, кто, счётчики, статус) с кнопкой «Откатить». Кнопка требует подтверждения во втором диалоге с явным текстом «Будет удалено: N организаций, N заказов, N платежей».
- **Т-40.** Срок отката ограничить **30 днями** с момента импорта. Более старые батчи показываются, но кнопка неактивна с подсказкой — чем дольше живут данные, тем выше риск, что на них уже что-то завязано.

## 4. Критерии приёмки

1. Загрузка файла с 3 листами в **пустую** базу создаёт организации, затем заказы, затем оплаты; в отчёте по каждой сущности `создано > 0`.
2. Повторная загрузка того же файла: `создано: 0`, `обновлено: N`, ошибок нет.
3. Файл с неверными именами листов даёт красный блок с перечнем фактических имён листов, а не «Файл пуст».
4. Файл 15 МБ загружается (при лимите 25 МБ). Файл 30 МБ отвергается **до** отправки, с понятным текстом.
5. Файл `.xls` из 1С загружается на обеих страницах.
6. Отключённая сеть / упавший сервер → красный блок «Сервер не принял файл», а не пустой экран.
7. Предпросмотр не меняет ни одной записи в БД (проверяется сравнением дампа до/после).
8. Обычный менеджер получает `/forbidden`; администратор и руководитель видят страницу и успешно импортируют.
9. Контрагент **без** «ИНН партнёра» создаёт организацию с `partnerId: null`. Два контрагента с одним «ИНН партнёра» создают две организации с одним `partnerId`.
10. Контрагент с указанным, но несуществующим партнёром → `skip: partner_not_found`, организация не создана.
11. Контрагент без ИНН → строка в таблице ошибок с кодом `no_inn`, батч не падает.
12. **Откат:** после импорта в пустую базу откат возвращает базу к исходному состоянию — 0 организаций, 0 заказов, 0 платежей; батч в статусе `rolled_back`.
13. **Откат заблокирован**, если платёж из батча попал в акт комиссии: показан список конфликтов, ни одна запись не удалена.
14. Откат батча старше 30 дней недоступен.
15. Строка выписки с новым ИНН **не создаёт** организацию автоматически — уходит в очередь разбора.
16. Импорт **не создаёт** ни одной новой `Company` (вариант A). Организации, созданные руководителем, видны ему же сразу после импорта, и их заказы/оплаты из того же файла не отбиваются как `out_of_scope`.
17. Тест инварианта изоляции компаний (`invariants.company-isolation.integration.test.ts`) проходит без ослабления проверок.

## 5. Тесты

**Unit (vitest, без Postgres):**
- `parse-workbook`: алиасы листов и колонок, `\u00A0`, «ё/е», регистр, отсутствие листа, отсутствие колонки.
- `adapter-file.pullOrganizations`: маппинг строки → DTO, синтетический `externalId`, нормализация ИНН с ведущими нулями.
- валидатор ИНН: 10/12 знаков, контрольная сумма, мусор.
- сниффер формата: сигнатуры PK / OLE / мусор.

- `synthOrgExternalId`: стабильность (один ИНН → один ключ), префикс, отсутствие ИНН → ошибка.

**Integration (с Postgres):**
- полный прогон 3-листового файла в пустую базу → счётчики.
- повторный прогон → идемпотентность.
- `shadow` не пишет: снапшот таблиц `Organization`/`Order`/`Payment` до и после.
- организация без партнёра создаётся с `partnerId: null` (Т-19).
- два контрагента с одним «ИНН партнёра» → две организации, один `partnerId` (Т-19а).
- указанный, но несуществующий партнёр → `skip: partner_not_found`.
- скоуп: руководитель создаёт организации внутри своей `companyId` (Т-26а); руководитель другой компании не может изменить чужую организацию.
- обычный менеджер получает `forbidden` от сервиса, даже если обойти UI.
- **откат:** импорт → откат → снапшот базы совпадает с исходным.
- **откат заблокирован:** импорт → платёж включён в `CommissionStatementItem` → откат возвращает конфликты, база не изменилась.
- **частичный откат:** статус `rollback_partial`, `reverted` проставлен только у откаченных строк.
- откат чужого батча (другая компания) → отказ.

**Компонентные:**
- `import-form`: отклонённый промис server action → отрисован блок ошибки.
- превышение размера на клиенте → запрос не уходит.

**Фикстуры:** положить обезличенный реальный файл 1С в `src/lib/services/oneCSync/fixtures/` (папка уже есть). ИНН/наименования заменить на вымышленные.
