## 0. Зачем и главный риск

Сейчас руководитель — пометка на менеджере (`role='manager'` +
`managerRole='leader'`). Каждое правило пишется «для менеджера», про
руководителя вспоминают отдельно — и иногда не вспоминают (карточка
организации, PR #273; **свежий пример 17.08: поиск из палитры доверял клиенту
флаг «я руководитель» — рядовой менеджер мог получить выдачу по всей
компании; закрыто хотфиксом** до начала программы). Выделение роли делает
«забыть» невозможным: система сама потребует решения в каждой развилке.

Риск двусторонний: (1) руководитель теряет доступ — заметно, чинится;
(2) **менеджер получает лишнее — не заметит никто**. Поэтому программа
строится вокруг проверок «лишнее закрыто», а не только «нужное работает».

## 2. Решения (Р-Л-1…Р-Л-5) — предложены, ждут «да»

- **Р-Л-1. Модель:** `enum Role` получает значение `leader`
  (`admin manager leader partner organization student`); данные —
  `UPDATE User SET role='leader' WHERE role='manager' AND managerRole='leader'`.
  Колонка `managerRole` остаётся на переходный период и снимается последним
  PR (иначе нечем откатывать).
- **Р-Л-2. Старые токены — переходная совместимость, без разлогина:**
  `getSession` до последнего PR считает руководителем и `role='leader'`, и
  старую пару `manager+managerRole='leader'`. Токены живут 7 дней; рычаг
  `sessionVersion` держим в резерве на случай инцидента.
- **Р-Л-3. «Играющий тренер» сохраняется:** `/manager/*` открыт роли `leader`
  (`protectedPrefixes: '/manager': ['manager','leader']`), мосты меню
  остаются. Поведение не меняется — меняется только модель.
- **Р-Л-4. Правило разбора ≈99 мест — три шаблона:**
  «сотрудник менеджерского контура» → новый хелпер `isStaffManagerSide()`
  (manager ∨ leader); «именно рядовой менеджер» → `role==='manager'` как есть;
  «руководитель» → `role==='leader'`. Хелпер обязателен — без него 99 мест
  превращаются в 99 независимых решений.
- **Р-Л-5. Приёмка — «менеджер не получил лишнего»:** расширенная
  guard-матрица (см. этап 0) + регресс прав обеих ролей + миграционный тест +
  тест переходного периода + **ручная проверка стенда всеми шестью ролями до
  снятия совместимости**.

## 4. Что НЕ входит

- Изменение прав руководителя по сути (что видел — то и видит).
- Отделы (`Department`), новые правила доступа.
- Перевод `AccessProfile` на новую роль сверх механического (`leader`
  управляет профилями, как сейчас).
- Одноимённые «лидеры» других контуров (`OrganizationUser.roleInOrg`,
  `PartnerUser.roleInPartner`) — не трогаются.
