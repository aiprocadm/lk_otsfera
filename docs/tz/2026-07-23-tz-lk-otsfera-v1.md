# Техническое задание на развитие платформы lk_otsfera

**Проект:** Личный кабинет «ОТ Сфера» (Промтехносфера) — B2B-платформа услуг охраны труда и обучения.
**Репозиторий:** `aiprocadm/lk_otsfera`, ветка `main`.
**Стек:** Next.js 15 (App Router), React 19, TypeScript strict, Prisma 5 + PostgreSQL, S3-совместимое хранилище, BullMQ + Redis, Vitest + Playwright.
**Версия документа:** 1.0 от 23.07.2026.

Документ является постановкой задачи для реализации через Claude Code. Исполнитель обязан соблюдать проектные конвенции `CLAUDE.md`: слои `app → server-actions → services → lib`, Result-тип сервисов, RBAC в три слоя (middleware → route guard → service scope), sibling-pattern компонентов по ролям, палитра в примитивах `src/components/ui/`, user-facing строки на русском, спека в `docs/superpowers/specs/` и план в `docs/superpowers/plans/` перед каждым этапом, зелёные `typecheck` / `lint` / `npm test` после каждого этапа, запрет на правку применённых миграций.

## 1. Цели

1.1. Разделить клиентский и внутренний контуры: партнёр и организация подают **заявки** и получают **результат** (заказы, документы, удостоверения); лиды, сделки, воронки, задачи — **исключительно внутренние** инструменты сотрудников (admin, manager, leader).
1.2. Сделать клиентский путь очевидным без обучения: как подать заявку на обучение, где следить за статусом, где скачать сканы удостоверений и документов.
1.3. Дать сотрудникам единую точку приёмки («что поступило в работу») и формальный протокол выдачи результата («передано клиенту»).
1.4. Перенести настройку всех внешних сервисов (почта, IMAP, телефония, Telegram, Max, WhatsApp, 1С, DaData) из env-файлов сервера в интерфейс администратора.
1.5. Убрать ручной труд: автоотправка приглашений, автогенерация счетов/актов, массовые операции, экспорты, подсказки по ИНН.

## 2. Термины и определения (обязательный словарь UI)

| Термин | Определение | Кто создаёт | Кто видит |
|---|---|---|---|
| **Заявка** (ClientRequest) | Обращение партнёра или организации «нужна услуга / привёл клиента». Входная точка клиентского контура. | Партнёр, организация | Податель (свою), сотрудники (все в scope) |
| **Заявка на обучение** (EnrollmentRequest) | Заявка на зачисление слушателей: направление + список слушателей. | Партнёр, организация, сотрудники | Податель (свою), сотрудники |
| **Лид** (Lead) | Внутренняя карточка потенциальной продажи. Клиентам не виден никогда. | Только сотрудники | Только сотрудники |
| **Сделка** (Deal) | Внутренняя карточка активной продажи (КП, счёт, переговоры) до заказа. | Только сотрудники | Только сотрудники |
| **Заказ** (Order) | Принятая в исполнение услуга. | Сотрудники (в т.ч. конверсией из сделки) | Сотрудники; организация и партнёр — свои, в клиентском представлении |
| **Удостоверение** (Certificate) | Результат обучения слушателя: номер, срок действия, скан. | Сотрудники | Сотрудники; организация — по своим сотрудникам; партнёр — по своим организациям |
| **Документ** (Document) | Файл по заказу или вне заказа: договор, счёт, акт, скан удостоверения и т.д. | Сотрудники, система, клиенты (загрузка входящих) | По принадлежности контрагенту |
| **Обращение** (InboundMessage) | Входящее сообщение из внешнего канала или из кабинета («Задать вопрос»). | Внешний мир, клиенты | Сотрудники |
| **Входящие в работу** (Intake) | Агрегатор всех неразобранных единиц для сотрудников. | — | Только сотрудники |

Слово «Заявки» в интерфейсе допустимо только для ClientRequest. Текущий пункт меню менеджера «Заявки» (`/manager/leads`) переименовывается в «Лиды». Завести файл `docs/glossary.md` с этой таблицей; все спеки ссылаются на него.

## 3. Роли и модель доступа

JWT-роли: `admin`, `manager`, `partner`, `organization`, `student`. `leader` — не роль, а `manager` с `managerRole='leader'`. Admin работает через зеркало `/admin/*` (Model A), в чужие кабинеты не входит.

Подроли (существующие, сохранить):
- Партнёр: `PartnerUser.roleInPartner` = `admin` (вся команда, приглашения, все организации партнёра) | `manager` (только организации из `assignedOrgIds`).
- Организация: участник с ролью admin / leader / member (`orgAdminOrLeaderOnly` в навигации); мультиорганизационность через `memberships` с переключателем активной организации.

Scope менеджера — существующие правила `managerPolicy` (teamMode C8 / AccessProfile) распространяются на новые сущности ClientRequest, Deal, Intake без исключений.

### 3.2. Правило чистоты клиентских кабинетов

В кабинетах partner и organization отсутствуют: ссылки и экраны лидов, сделок, воронок, задач, intake; поля «назначенный менеджер лида», внутренние заметки, стадии воронки; любые данные других партнёров/организаций. Требование обеспечивается на всех трёх слоях RBAC и подтверждается интеграционными тестами (см. раздел 8).

## 4. Целевая бизнес-модель: сквозной поток

```
ИСТОЧНИКИ                     ВНУТРЕННИЙ КОНТУР                        РЕЗУЛЬТАТ КЛИЕНТУ
─────────────                 ────────────────────                     ─────────────────
Заявка партнёра     ┐
Заявка организации  ├─→ INTAKE ─→ ЛИД ─→ СДЕЛКА ─→ ЗАКАЗ ─→ чек-лист ─→ «Передано»:
Заявка на обучение  │  (триаж)  (квалиф.) (продажа) (исполн.) готовности    удостоверения,
Обращение (письмо,  │                                                       документы,
  чат, «Вопрос»)    │                                                       уведомление
Звонок              ┘
```

4.1. Каждая единица из «Источников» попадает в Intake и не может «потеряться»: у неё всегда есть статус (не разобрано / в работе / закрыто) и, после триажа, ответственный.
4.2. Конверсии сохраняют ссылки на источник по всей цепочке: `ClientRequest → Lead (sourceRequestId) → Deal (leadId) → Order (dealId)`; податель заявки видит только контрольные точки своей заявки: подана → принята / отклонена (с причиной) → по заявке создан заказ №X → результат передан.
4.3. Существующий путь `Lead.promotedOrderId` (лид → заказ напрямую) сохраняется для обратной совместимости; основной новый путь в UI — через сделку.
4.4. SLA: заявка/обращение без реакции дольше порога (настройка компании, дефолт 24 ч; подсветка с 4 ч) эскалируется уведомлением руководителю.

## 5. Функциональные требования

Нумерация ФТ-<модуль>.<номер>. Каждый пункт — проверяемое требование.

### Модуль 1. Заявки клиентов (ClientRequest)

- **ФТ-1.1.** Новая модель Prisma `ClientRequest`: податель (`submittedByUserId`, `submitterRole`), принадлежность (`partnerId?` / `organizationId?`), данные клиента (название, ИНН, контактное лицо, телефон, email), тема, желаемая услуга (`ServiceType`), примечание, вложения (модель по образцу `LeadAttachment` со scan-статусом), статус `submitted | accepted | rejected | converted`, `rejectedReason?`, `convertedLeadId?`.
- **ФТ-1.2.** Партнёр: раздел «Мои заявки» (`/partner/requests`) — форма подачи (переработка `lead-create-form.tsx` под ClientRequest), список со статусами и причинами отклонения, вложения, отзыв неразобранной заявки. Существующие маршруты `/partner/leads*` и API `api/partner/leads*` выводятся из эксплуатации (redirect на requests).
- **ФТ-1.3.** Организация: раздел «Мои заявки» (`/organization/requests`) — подача заявки на услугу (обучение, разработка документов и др.), список со статусами. Поток «Заявки на обучение» (Модуль 2) остаётся отдельным.
- **ФТ-1.4.** Сотрудники: раздел «Заявки» (`/manager/requests`, зеркала leader/admin) — список входящих, действия: «Принять → создать лид» (предзаполненная форма, `Lead.source='partner_request'|'org_request'`, `sourceRequestId`), «Отклонить» с обязательной причиной (податель видит причину).
- **ФТ-1.5.** Модель Lead: `partnerId` становится nullable (миграция без потери данных); новые поля `source` (`partner_request | org_request | call | inbound_message | manual | website`), `sourceRequestId?`, `sourceCallId?`, `sourceInboundId?`. Создание Lead — только роли admin/manager/leader (сервисный запрет, Result-код `forbidden`).
- **ФТ-1.6.** Ручное создание лида сотрудником: форма «Новый лид»; из карточки звонка и обращения — действие «Создать лид» с автоподстановкой контакта (существующие `Contact`/`ContactChannel`).
- **ФТ-1.7.** Меню менеджера: пункт `/manager/leads` переименован «Заявки» → «Лиды». Feature-флаг `partner_leads` заменён на `client_requests` (route-флаг: middleware + nav + page-гейт).
- **ФТ-1.8.** Уведомления: `new_client_request` менеджерам при подаче; подателю — при каждом изменении статуса его заявки.

### Модуль 2. Заявки на обучение (мастер подачи)

- **ФТ-2.1.** Форма подачи заменяется мастером в 2–3 шага: (1) направление — выбор из активных `TrainingDirection` (не свободный текст); (2) слушатели — чекбоксы из сотрудников организации (`listOrgStudents` по активной организации) + добавление новых строками (ФИО, email, должность) + импорт из Excel («Скачать шаблон», построчная валидация с русскими сообщениями об ошибках); (3) проверка и примечание.
- **ФТ-2.2.** Модель: `EnrollmentRequest` (шапка: податель, направление `directionId`, статус) + новая `EnrollmentRequestItem` (позиция: `studentId?` либо ФИО+email нового слушателя, индивидуальный статус). Миграция: существующие однострочные заявки → шапка с одной позицией; поле `courseTitle` сохраняется как `legacyCourseTitle`.
- **ФТ-2.3.** Деталка заявки у подателя: статусная лента «подана → принята → зачислены → идёт обучение → удостоверения готовы»; на финальном шаге — прямые ссылки на удостоверения (Модуль 6).
- **ФТ-2.4.** Дашборды организации и партнёра: заметная кнопка «Подать заявку на обучение» + последние 5 заявок со статусами.
- **ФТ-2.5.** Уведомление подателю `enrollment_status_changed` на каждый переход.
- **ФТ-2.6.** Пустые состояния и инлайн-подсказки объясняют процесс без отдельной страницы документации.

### Модуль 3. Лиды и воронка (внутренние)

- **ФТ-3.1.** Существующая воронка (`FunnelStage` поверх `LeadStatus`, доска `funnel-board`) сохраняется; лиды отображают источник и ссылку на исходную заявку/звонок/обращение.
- **ФТ-3.2.** Карточка лида: блок «Задачи» (Модуль 7) и действие «Создать сделку».
- **ФТ-3.3.** Передача лида, возврат «в новые», пуш в 1С — без изменений (реализовано Треком B).

### Модуль 4. Сделки и канбан сделок (внутренние)

- **ФТ-4.1.** Новая модель `Deal`: `companyId` (граница C8), `leadId?`, `organizationId?`, `contactId?`, `title`, `amount Decimal?`, ответственный менеджер, `status` enum `DealStatus (open | won | lost)`, `stageId?`, `expectedCloseAt?`, `lostReason?`, `orderId?`.
- **ФТ-4.2.** Словарь стадий `DealStage` по паттерну проекта (companyId, name, position, statusAnchor, color, isTerminal) с настройкой руководителем — зеркало настройки колонок задач.
- **ФТ-4.3.** Канбан `/manager/deals` (свои) и `/leader/deals` (команда, фильтр по менеджеру) с drag-and-drop по образцу `funnel-board`/`task-board`; клиентские роли — 404 на всех трёх слоях RBAC.
- **ФТ-4.4.** Конверсии: Лид → «Создать сделку» (`Lead.promotedDealId`, лид получает статус promoted); Сделка → «Выиграна → создать заказ» (`Deal.orderId`). Лента активности сделки — переиспользование паттерна `deal-activity`/`DealNote` (решение о привязке DealNote к Deal — в спеке этапа).
- **ФТ-4.5.** Аналитика руководителя: сумма выигранных сделок в план/факт (`SalesTarget`) — отдельным подэтапом после стабилизации модели.
- **ФТ-4.6.** Feature-флаг `deals_pipeline` (route-флаг).

### Модуль 5. Заказы: чек-лист готовности и передача результата

- **ФТ-5.1.** На деталке заказа (менеджер/руководитель) блок «Готовность к передаче»: для `ServiceType.training` по каждой позиции `OrderItem` — обучение завершено / удостоверение создано / скан загружен; для `document_development` — итоговые документы (`direction=outgoing`) загружены. Блок расширяет существующий «список несоблюдённых условий завершения» (Трек A).
- **ФТ-5.2.** Кнопка «Передать результат клиенту»: активна только при полной готовности; фиксирует `resultDeliveredAt` на заказе; отправляет организации (и партнёру, если заказ его) уведомление `order_result_delivered` со ссылкой на реестр удостоверений/документы.
- **ФТ-5.3.** Массовая загрузка сканов удостоверений на заказе: мультизагрузка с сопоставлением файла позиции (выбор слушателя; опциональная автоподстановка по совпадению ФИО в имени файла с обязательным ручным подтверждением). Каждый файл проходит антивирус-скан как обычный Document.
- **ФТ-5.4.** Клиентское представление заказа (степпер `humanStage`) дополняется финальной точкой «Результат передан» с датой.

### Модуль 6. Удостоверения: витрина и реестры

- **ФТ-6.1.** Раздел организации `/organization/certificates`: реестр — сотрудник, направление, номер, выдано, действует до, статус-бейдж (действует / истекает ≤ 60 дней / истекло); «Скачать скан» через `Certificate.documentId` (presigned); фильтры (направление, статус), поиск по ФИО; строка без скана — пометка «скан готовится».
- **ФТ-6.2.** Раздел партнёра `/partner/certificates`: sibling-версия с колонкой и фильтром «Организация»; scope — организации партнёра (для partner-manager — с учётом `assignedOrgIds`).
- **ФТ-6.3.** Карточка сотрудника `/organization/students/[id]`: удостоверения + история обучения (позиции заказов, `trainingStatus`); ссылки из реестра и таблицы сотрудников.
- **ФТ-6.4.** Дашборды организации и партнёра: карточка «Истекают удостоверения: N» со ссылкой на отфильтрованный реестр. В `OrgKpiGrid` карточка добавляется к существующим четырём.
- **ФТ-6.5.** Экспорт реестров в Excel (Модуль 12).
- **ФТ-6.6.** Документы: метка «новый» для непросмотренных, группировка по заказу; проверка, что `document_uploaded` реально доставляется клиенту при загрузке менеджером, письмо содержит прямую ссылку.

### Модуль 7. Задачи (внутренние)

### Модуль 8. Intake — «Входящие в работу»

- **ФТ-8.1.** Экран `/manager/intake` (зеркало leader): агрегатор неразобранных единиц — ClientRequest (submitted), EnrollmentRequest (pending), InboundMessage (unresolved), звонки без привязки. Колонки: тип, от кого, суть, время ожидания (подсветка: > 4 ч жёлтая, > 24 ч красная — пороги в настройках компании), ответственный, действия.
- **ФТ-8.2.** Действия триажа: «Взять в работу» (по образцу `claimOrder`), «Создать лид», «Создать задачу», «Привязать к организации/контакту», «Отклонить». Единица покидает Intake при наличии ответственного и целевой сущности.
- **ФТ-8.3.** Руководитель: вся команда, фильтр по менеджеру, секция «без ответственного», сортировка по ожиданию.
- **ФТ-8.4.** Счётчик Intake — бейдж в меню; единый агрегирующий эндпоинт счётчиков (см. ФТ-14.2).
- **ФТ-8.5.** SLA-эскалация руководителю (см. 4.4) — джоб воркера.

### Модуль 9. Реквизиты и автогенерация документов

- **ФТ-9.1.** Расширение моделей реквизитами: `Organization` (есть inn, kpp) и `Partner` (есть legalName, inn) дополняются: ОГРН, юридический адрес, банк (р/с, к/с, БИК, название), подписант (должность, ФИО, основание); `Company` (исполнитель) — полный аналогичный набор.

## 8. Нефункциональные требования

- **НФ-1. RBAC.** Каждый новый защищённый маршрут — во всех трёх слоях: `protectedPrefixes` (middleware), route/action-guard, service-scope. Менеджерский teamMode (C8) прокидывается во все новые резолверы ClientRequest/Deal/Intake.
- **НФ-2. ПДн (152-ФЗ).** Новые сущности с ПДн (ClientRequest, EnrollmentRequestItem, реквизиты) включаются в скраббер логов (`lib/logging/scrub`); доступ сотрудников к ПДн-спискам и экспортам — через `recordPiiAccess`; вложения — через существующий антивирус-скан; файлы — в РФ-совместимом S3 (без изменений).
- **НФ-3. Аудит.** Мутации заявок, сделок, передач результата, реквизитов, настроек интеграций, приглашений — в `AuditLog` (без секретов и лишних ПДн в payload).
- **НФ-4. Надёжность.** Уведомления/очереди — degrade gracefully (ошибка фан-аута не блокирует основной путь); SLA-джобы и генерация документов — идемпотентны; счётчик номеров счетов — безопасен при конкуренции.
- **НФ-5. Производительность.** Списки (Intake, реестры, канбаны) — с пагинацией и индексами под основные выборки (`companyId+status+createdAt` и аналоги); агрегирующий эндпоинт бейджей — один запрос на поллинг.
- **НФ-6. Тесты.** Проект держит 100 % coverage-гейт на логические слои — новые сервисы, экшены, роуты и компоненты обязаны попадать под порог; для каждого модуля — unit + integration, для RBAC — негативные сценарии из раздела 7; e2e-визуал по ключевым новым экранам.
- **НФ-7. Локализация.** Все user-facing строки — русский; коды ошибок — стабильные английские строки Result-контракта.
- **НФ-8. Доступность.** Модалки — через общий `Dialog` (нативный dialog); новые интерактивы — с клавиатурной навигацией и aria-атрибутами по образцу существующих.

Для каждого этапа: (1) прочитай соответствующие модули ФТ и существующий код по указанным файлам-якорям; (2) напиши спеку в `docs/superpowers/specs/` — решения, альтернативы, тест-стратегия, открытые вопросы; (3) дождись подтверждения заказчика; (4) напиши план с чекбоксами в `docs/superpowers/plans/`; (5) реализуй инкрементально с объяснениями на русском простым языком и предупреждениями перед ломающими изменениями; (6) прогони typecheck, lint, полный npm test, обнови CHANGELOG.md. Начни с этапа 1.
