## §0. Главное условие заказчика

> **Пользователь должен легко ориентироваться в функционале проекта.**

Это не пожелание к одному экрану, а **приёмочный критерий всего ТЗ**. Любое требование ниже считается невыполненным, если после его реализации новый пользователь не может за 30 секунд ответить на три вопроса:

1. **Где я?** — заголовок экрана, хлебные крошки, подсвеченный пункт меню.
2. **Что здесь делают?** — подзаголовок из одной строки под заголовком на каждом экране.
3. **Что делать дальше?** — либо видимая главная кнопка, либо пустой экран с подсказкой и кнопкой.

Правило распространяется и на уже написанные экраны: этап 7 проходит по всем 287 маршрутам и добивает те, где этих трёх ответов нет.

## §1. Зачем это ТЗ

Программа починки импорта 1С закрыта 07.08.2026 (44 требования `Т-N`, PR #310…#328). Код дисциплинирован: 100% coverage-гейт, dependency-cruiser, spec-first процесс. Но приёмка заказчиком показала, что **проблема не в качестве кода, а в двух других вещах**:

1. **Функциональные пробелы**, из-за которых система не может работать на реальных данных. Главный — записи `Student` (сотрудники клиента) не создаются нигде в приложении, только в `prisma/seed.ts`. От этого рушится цепочка «сотрудник → заявка на обучение → удостоверение».
2. **Расхождения между кабинетами**, из-за которых интерфейс выглядит как шесть разных продуктов, а не один.

Оба класса проблем решаются в этом ТЗ.

### Что НЕ пересматривается

Архитектура (`app → server-actions → services → lib`), правила `CLAUDE.md` §1–13, coverage-порог 100%, spec-first процесс §8. Все они действуют поверх этого ТЗ. При противоречии — спросить заказчика.

## §3. Что нашёл аудит (доказательная база)

Каждое требование ниже опирается на конкретное место в коде. Раздел нужен, чтобы исполнитель не тратил время на повторную разведку.

### 3.1. Сотрудники не создаются нигде

Поиск по всему репозиторию (`prisma.student.create`, `tx.student.create`, `student.upsert`, `createStudent`, `ensureStudent`) даёт **ноль совпадений** в `src/lib`, `src/server-actions`, `src/worker`. Единственное создание — `prisma/seed.ts`.

Последствия, наблюдаемые заказчиком:

- В портфеле партнёра вкладка «Сотрудники» (`org-employees-tab.tsx`) — read-only список без кнопки добавления.
- В мастере заявки на обучение чекбоксы «выбрать из сотрудников» (`/api/enrollments/students`) всегда пустые.
- Слушатель, вписанный руками в мастере, оседает в `EnrollmentRequestItem` со `studentId = null` и сотрудником **не становится** — в следующий раз его снова придётся вписывать вручную.
- Реестр удостоверений (`Certificate.studentId`) не с чем связывать.

### 3.2. Заявка на обучение — одно направление на всю заявку

`prisma/schema.prisma`: `directionId` лежит на **шапке** `EnrollmentRequest`. У позиции-слушателя `EnrollmentRequestItem` поля направления **нет вообще**. Физически невозможно ни «разное обучение у разных слушателей», ни «несколько обучений у одного сотрудника».

Правильный образец лежит в том же файле — `OrderItem` с `@@unique([orderId, studentId, directionId])`.

### 3.3. Партнёр назначает себе комиссию

`PUT /api/partner/portfolio/[orgId]/rate` пропускает `requirePartnerAdmin` и пишет `Organization.partnerCommissionRate`. Партнёр-администратор ставит ставку себе сам; история `OrganizationCommissionRateChange` фиксирует его же как автора изменения.

Хорошая новость: у администратора экран уже есть — `AdminRateOverrideForm` на `/admin/organizations/[id]`. Работа — чистое вычитание, новый экран не нужен.

### 3.4. Значков в меню партнёра нет — по двум причинам сразу

1. `src/lib/navigation/cabinet.ts` — у ролей `partner` и `student` в пунктах меню **отсутствует поле `icon`** (у `admin`, `manager`, `leader`, `organization` оно есть).
2. `src/components/dashboard/app-shell.tsx` (шелл партнёра) рисует серую точку `<span className="w-1.5 h-1.5 rounded-full bg-gray-300" />` и **игнорирует `item.icon` полностью**. Даже если добавить иконки в конфиг, они не появятся.

### 3.5. Значки не согласованы между кабинетами

| Название | Где | Значок |
|---|---|---|
| Организации | `/manager/organizations`, `/leader/organizations` | 🏢 |
| Организации | `/admin/organizations` | 🏛 |
| Партнёры | `/admin/partners` | 🏢 *(тот же, что «Организации» у менеджера)* |
| Настройки / Команда / Кабинет руководителя | все кабинеты | ⚙ *(один значок на три разных раздела)* |
| Входящие в работу / Загрузка Excel / Загрузка из 1С / Импорт оплат | admin, manager | 📥 *(один значок на четыре раздела)* |
| Обращения клиентов | `/manager/requests` | 📮 |
| Обращения | `/manager/inbox` | 📨 |

### 3.6. Мобильной версии нет ни у одного кабинета сотрудников

Подсчёт адаптивных классов (`md:`, `sm:`, `lg:`):

| Файл | Кол-во |
|---|---|
| `admin-sidebar.tsx` | 0 |
| `manager-sidebar.tsx` | 0 |
| `leader-sidebar.tsx` | 0 |
| `org-sidebar.tsx` | 0 |
| `dashboard/app-shell.tsx` (партнёр) | 0 |

Сайдбар `w-60` (`w-56` у партнёра — ширина ещё и разная) висит на телефоне всегда, бургер-меню нет. Нижняя панель есть только у партнёра и организации. У администратора, руководителя и менеджера мобильной навигации нет вовсе: на экране 380 px сайдбар съедает 60% ширины.

### 3.7. Доступ к организации показан не на своей вкладке

`src/app/partner/portfolio/[orgId]/page.tsx`: компонент `<CustomerAccessSection>` вынесен **за пределы** переключателя вкладок — он рендерится под всеми вкладками сразу, поэтому и виден под «Комментариями». Настройки организации (`/settings`) при этом содержат **только форму ставки комиссии**.

Поля реквизитов у `Organization` в схеме уже есть (`legalName`, `ogrn`, `legalAddress`, `bankName`, `bankAccount`, `corrAccount`, `bic`, `signerName`, `signerPosition`, `signerBasis`), есть сервис `lib/services/organization/requisites.ts`, готовый компонент `RequisitesCard` и экшен `setOrgRequisitesAction`. Работа — переиспользование, не разработка с нуля.

### 3.8. Интеграции: ключи вводятся, каналы не включаются

`/admin/settings/integrations` даёт формы для Telegram, Max, WhatsApp, Mango, IMAP, 1С, DaData с кнопкой «Проверить подключение» — это работает. Но **включение самих каналов** возможно только через переменные окружения (`FEATURE_MAX_CHANNEL=1`, `FEATURE_WHATSAPP_CHANNEL=1`, `FEATURE_TELEPHONY_MANGO=1`), а страница `/admin/settings/system/feature-flags` в коде прямо подписана `Read-only матрица (ФТ-14.6)`.

Итог для заказчика: ключ ввести можно, включить канал — нельзя без SSH на сервер.

### 3.9. Почему «загрузил файл с 1С — ничего не происходит»

Заказчик грузит через вкладку **«Карточка счёта 51»**. Этот импорт по замыслу тянет **только платежи**. В `src/lib/services/import/oneCAccountCard/create-org.ts` записано прямым текстом: *«автосоздание запрещено решением владельца №5»*. Несопоставленные строки падают в «Очередь ручного разбора», где организацию надо создавать по одной.

Организации создаёт **соседняя вкладка «Загрузка Excel»** (лист «Контрагенты») — там же история импортов и откат.

Дополнительно парсер выписки хрупкий:

- колонки прибиты индексами: `COL = { date: 0, document: 1, analyticsCr: 3, debit: 5, corr: 7, credit: 8 }`;
- при отсутствии строки «Сальдо на начало» `parseAccountCard()` молча возвращает `[]` → пользователь видит только «Файл пуст или нет строк-операций»;
- диагностического блока «что система увидела в файле» на этой вкладке, в отличие от Excel-вкладки, **нет**.

### 3.10. Каналов обмена с 1С — четыре, и они разбросаны

`/admin/sync` (автообмен) · `/admin/settings/integrations/1c/excel` · `/admin/settings/integrations/1c/payments` · блок «Обмен с 1С» на странице интеграций (креды). У каждого своя история или её отсутствие.

## §4. Требования

Идентификатор — `У-N` (улучшение). Нумерация сквозная. Требование существует, только если у него есть номер здесь.

### Блок A. Безопасность денег (хотфикс)

- **У-1.** Убрать `RateOverrideForm` со страницы `/partner/portfolio/[orgId]/settings`. Компонент удалить.
- **У-2.** `PUT /api/partner/portfolio/[orgId]/rate` отвечает `403` для роли `partner` независимо от `partnerRole`. Роут остаётся только для внутренних ролей либо удаляется целиком, если внутренние вызовы идут через `AdminRateOverrideForm`.
- **У-3.** Партнёр видит действующую ставку **только на чтение** — строкой в карточке организации, с пометкой «назначает учебный центр».
- **У-4.** Тест-страж: попытка партнёра изменить ставку через API возвращает `403` и **не создаёт** запись в `OrganizationCommissionRateChange`.

### Блок B. Единый визуальный язык кабинетов

- **У-5.** Завести `src/lib/navigation/icons.ts` — единственный источник правды по значкам. Ключ — **семантика раздела**, а не роль: `dashboard`, `orders`, `organizations`, `partners`, `employees`, `team`, `settings`, `documents`, `finance`, `messages`, `enrollments`, `certificates`, `requests`, `intake`, `import`, `sync`, `search`, `tasks`, `calendar`, `analytics`, `audit`, `roles`, `security`.
- **У-6.** `navByRole` в `cabinet.ts` берёт значок из реестра по семантическому ключу. Поле `icon: string` заменяется на `iconKey: IconKey`.
- **У-7.** Добавить значки ролям `partner` и `student` — сейчас их нет вовсе.
- **У-8.** Разделить конфликтующие значки: «Настройки» ≠ «Команда» ≠ «Кабинет руководителя»; четыре разных раздела не могут делить 📥; «Организации» одинаковы во всех кабинетах.
- **У-9.** Тест-страж (unit): для любых двух пунктов меню в любых двух ролях — одинаковый `label` ⟹ одинаковый `iconKey`, и одинаковый `iconKey` ⟹ одинаковый `label`. Падение теста = красная сборка.
- **У-10.** `src/components/dashboard/app-shell.tsx` рендерит значок вместо серой точки.
- **У-11.** Единый `AppShell` для всех шести кабинетов: один компонент, роль-специфичное берётся пропсами (заголовок, реестр меню, роль колокольчика). Пять существующих шеллов схлопываются в один. Существующие тесты каждого шелла переписываются на общий.
- **У-12.** Ширина сайдбара едина — `w-60` во всех кабинетах.

### Блок C. Мобильная версия — одинаковая во всех кабинетах

- **У-13.** Сайдбар на экранах < `md` скрыт (`hidden md:flex`).
- **У-14.** В шапке на экранах < `md` появляется кнопка-бургер, открывающая выдвижную панель с полным меню. Панель использует существующий примитив `Dialog` (`CLAUDE.md` §9): фокус-ловушка, Escape, восстановление фокуса.
- **У-15.** Нижняя панель — во **всех** шести кабинетах, а не только у партнёра и организации. Состав берётся из общего реестра, максимум 5 пунктов, пятый — «Ещё» (открывает бургер-панель).
- **У-16.** Существующие `partner/bottom-tab-bar.tsx` и `organization/bottom-tab-bar.tsx` заменяются одним общим компонентом.
- **У-17.** Отступ снизу `pb-16 md:pb-0` применяется в общем шелле один раз, а не в каждой странице.
- **У-18.** Все таблицы шире четырёх колонок на мобильном превращаются в карточки. Образец уже есть — `team-table.tsx` + `team-card-list.tsx` в партнёрском кабинете; шаблон распространяется на остальные списки.
- **У-19.** Playwright-проект `mobile-*` с viewport 390×844: вход в каждый из шести кабинетов, снимок главной страницы, проверка что сайдбар скрыт и нижняя панель видна.

### Блок D. Справочник сотрудников (решение Р-1)

Фундамент для блоков E и F. Раньше них не делать нечего.

- **У-20.** Расширить модель `Student`: `snils String?`, `birthDate DateTime?`, `phone String?`, `note String?`. Поле `position` уже есть.
- **У-21.** Сделать `Student.email` **необязательным** (`String?`). Обоснование: в охране труда обучают рабочих без корпоративной почты, а сейчас email обязателен и блокирует ввод. Существующий `@@unique([organizationId, email])` с nullable-полем в PostgreSQL допускает много `NULL` — ограничение остаётся рабочим.
- **У-22.** Ключ дедупликации при любом создании сотрудника: СНИЛС (если указан) → иначе `ФИО + дата рождения` → иначе `ФИО + email`. Совпадение показывается пользователю как «Такой сотрудник уже есть», с кнопками «Использовать существующего» / «Всё равно добавить».
- **У-23.** Сервис `src/lib/services/students/` с операциями: `createStudent`, `updateStudent`, `deactivateStudent`, `findDuplicates`, `importStudents`. Result-тип по контракту `CLAUDE.md` §3.
- **У-24.** Кнопка «Добавить сотрудника» в кабинете организации (`/organization/students`) — доступна `admin` и `leader` организации.
- **У-25.** Кнопка «Добавить сотрудника» в портфеле партнёра (`/partner/portfolio/[orgId]`, вкладка «Сотрудники») — доступна партнёру с доступом к этой организации.
- **У-26.** Кнопка «Добавить сотрудника» в карточке организации у менеджера (`/manager/organizations/[id]`) и администратора (`/admin/organizations/[id]`).
- **У-27.** Импорт сотрудников списком из Excel/CSV. Шаблон скачивается с экрана. Колонки: ФИО, должность, СНИЛС, дата рождения, email, телефон. Обязательна только ФИО.
- **У-28.** Импорт сотрудников работает в два шага, как импорт 1С: предпросмотр («будет создано N, обновлено M, дубликатов K») → подтверждение.
- **У-29.** При переводе заявки на обучение в статус `approved` каждая позиция со `studentId = null` **создаёт запись `Student`** в организации заявки и проставляет `studentId`. Дедупликация — по У-22.
- **У-30.** Карточка сотрудника (`/organization/students/[id]`, `/manager/students/[id]`) показывает: реквизиты, историю обучений (позиции заявок), выданные удостоверения и сроки их действия.
- **У-31.** Все операции над сотрудником пишутся в `AuditLog`. Просмотр СНИЛС и даты рождения — в `PiiAccessEvent` (журнал 152-ФЗ, механизм уже есть).
- **У-32.** Права: партнёр и организация ведут сотрудников **только своих** организаций. Проверка — на уровне сервиса, а не только UI (`CLAUDE.md` §4, defense-in-depth).

### Блок E. Заявка на обучение: много слушателей × много обучений (решение Р-5)

- **У-33.** Перенести направление обучения с шапки на позицию: у `EnrollmentRequestItem` появляется `directionId String` (обязательное) и связь с `TrainingDirection`.
- **У-34.** Миграция данных (решение Р-8): у существующих заявок направление шапки копируется во все позиции. Заявки, где направление вписано текстом (`directionId = null`, заполнен `legacyCourseTitle`), **разбираются вручную** — служебное направление «Без указания» не заводится.
- **У-34а.** Порядок разбора, обязателен к соблюдению — иначе миграция не пройдёт:
  1. Скрипт `npm run report:legacy-enrollments` выводит список таких заявок: номер, организация, текст курса, дата, число слушателей.
  2. Экран разбора в кабинете администратора: список этих заявок, у каждой — выбор направления из справочника. Экран одноразовый, после разбора убирается.
  3. Только когда список пуст, накатывается миграция, делающая `EnrollmentRequestItem.directionId` обязательным.
  4. Страж миграции: если незакрытые заявки остались, миграция падает с внятным текстом, а не с ошибкой ограничения БД.
- **У-35.** Ограничение целостности: `@@unique([requestId, studentId, directionId])`. Один и тот же сотрудник может быть в заявке **несколько раз** с разными направлениями, но не дважды с одним и тем же.
- **У-36.** Поле `EnrollmentRequest.directionId` после бэкфилла помечается устаревшим и удаляется **отдельной миграцией следующего этапа** — не в одном PR с бэкфиллом.
- **У-37.** Мастер подачи (`enrollment-wizard.tsx`) перестраивается: шаг 1 — организация; шаг 2 — слушатели и обучения; шаг 3 — проверка. Выбор направления уезжает с шага 1 на строку слушателя.
- **У-38.** На шаге 2 строка выглядит как «сотрудник + направление». У одного сотрудника кнопка «+ ещё обучение» добавляет вторую строку с тем же сотрудником.
- **У-39.** Массовая операция: отметить чекбоксами нескольких сотрудников → «Назначить всем обучение …». Повтор операции с другим направлением добавляет второй набор строк, а не заменяет первый.
- **У-40.** Список сотрудников на шаге 2 подгружается из справочника блока D и содержит поиск. Рядом — кнопка «Добавить нового сотрудника», не выкидывающая из мастера.
- **У-41.** В шаблоне импорта слушателей появляется колонка «Направление обучения». Значение сверяется со справочником `TrainingDirection`; нераспознанное — ошибка строки с подсказкой допустимых значений.
- **У-42.** Шаг 3 показывает сводку: «N слушателей · M обучений» и разбивку по направлениям.
- **У-43.** Экраны просмотра заявки во всех пяти кабинетах группируют позиции **по направлению** и показывают статус каждой позиции отдельно.
- **У-44.** Уведомления о заявке (`services/enrollments/notify.ts`) в тексте перечисляют направления, а не одно.

### Блок F. Обмен с 1С: один экран (решения Р-2 и Р-3)

- **У-45.** Раздел «Обмен с 1С» становится **одним экраном** с четырьмя вкладками: **Загрузка Excel** · **Выписка по счёту 51** · **Автообмен** · **История**. Маршрут — `/{кабинет}/settings/integrations/1c`. Старые адреса редиректят на нужную вкладку (механизм `legacyHrefs` в `settings.ts` уже это умеет).
- **У-46.** Пункт «Синхронизация (авто)» уезжает с верхнего уровня меню внутрь этого экрана вкладкой. Группа «Обмен с 1С» из сайдбара администратора убирается — вместо трёх пунктов один.
- **У-47.** Первое, что видит пользователь на экране — **навигатор задачи**, а не форма загрузки. Три карточки-вопроса вида «Что вы хотите сделать?»: «Завести клиентов и заказы из 1С» → Excel · «Разнести оплаты из банка» → Выписка 51 · «Настроить постоянный обмен по сети» → Автообмен. Формулировка — по задаче пользователя, не по формату файла.
- **У-48.** Вкладка «История» — **общая для всех трёх каналов**, с фильтром по каналу, датой, автором, итогами и кнопкой отката там, где откат поддержан.
- **У-49.** Автосоздание организаций по валидному ИНН при импорте выписки счёта 51. Условия: ИНН прошёл проверку контрольной суммы (`isValidInn`, функция уже есть) **и** организации с таким ИНН ещё нет. Решение Р-9: **включается сразу для всех**, отдельного флага постепенной раскатки не заводится. Страховкой служат обязательный предпросмотр (У-52) и откат (У-59) — оба обязаны уехать в том же этапе, что и это требование.
- **У-50.** Компания новой организации: у руководителя — своя из скоупа; у администратора — выбранная в форме. Если у администратора компаний несколько и выбор не сделан — импорт отказывает с текстом `company_required` (текст уже есть в словаре ошибок).
- **У-51.** Строки без ИНН или с невалидным ИНН идут в очередь ручного разбора, как сейчас. Поведение очереди не меняется.
- **У-52.** Предпросмотр импорта показывает отдельной строкой «Будет создано организаций: N» **со списком названий и ИНН** до применения.
- **У-53.** В очереди ручного разбора появляется пакетное действие «Создать организации по всем строкам с валидным ИНН» — на случай накопленных строк. Решение Р-10: действие **обязательно двухшаговое**. Первый шаг — список того, что будет создано: название, ИНН, компания привязки, сумма платежей по строке. Строку можно снять галочкой. Второй шаг — подтверждение. Создание без показа списка запрещено.
- **У-54.** Каждая автосозданная организация помечается в аудите источником: `source: 'payment_import_auto'` либо `'excel_import_auto'`. В карточке организации видна плашка «Создана автоматически из выгрузки 1С от <дата>».
- **У-55.** Тесты матчера, стоящие стражем прежнего запрета автосоздания (решение владельца №5), переписываются под новое правило. Прежнее решение отменено — см. Р-2.
- **У-56.** Парсер выписки ищет колонки **по заголовкам**, а не по жёстким индексам `COL`. Индексы остаются запасным вариантом, если заголовки не распознаны.
- **У-57.** Если маркер «Сальдо на начало» не найден — парсер не возвращает молча пустой список, а пытается распознать таблицу по заголовкам колонок и сообщает, что именно не нашёл.
- **У-58.** Блок диагностики «Что система увидела в файле» появляется на вкладке выписки. Реализация уже есть на Excel-вкладке (`services/import/diagnostics.ts`) — переиспользовать.
- **У-59.** Откат импорта распространяется на выписку счёта 51. Сейчас откат есть только у Excel-импорта (`services/import/rollback.ts`).

### Блок G. Кабинет партнёра — перестановки

- **У-60.** Пункт «Команда» уходит из главного меню в «Настройки». Настройки партнёра получают вкладки: **Профиль и реквизиты** · **Команда** · **Уведомления** · **Безопасность**.
- **У-61.** Блок «Доступ к организации» (`CustomerAccessSection`) убирается из общей области карточки организации и переносится на вкладку **«Настройки»** этой организации.
- **У-62.** На вкладку «Настройки» организации добавляются **реквизиты организации** через существующий `RequisitesCard` + `setOrgRequisitesAction`. Права на правку — партнёр-администратор.
- **У-63.** Вкладка «Сотрудники» получает кнопку добавления (дублирует У-25) и поиск по списку.
- **У-64.** Состав вкладок карточки организации после перестановки: **Сотрудники · Документы · Комментарии · История · Настройки**. Ничего лишнего под вкладками не рендерится — компоненты живут **внутри** переключателя.

### Блок H. Управление системой из интерфейса

- **У-65.** Флаги функциональности становятся **редактируемыми** из `/admin/settings/system/feature-flags`. Значения хранятся в таблице `Setting` (механизм уже используется для кредов интеграций).
- **У-66.** Приоритет источников: **база → переменная окружения → значение по умолчанию**. На экране у каждого флага видно, откуда взято текущее значение.
- **У-67.** Каждое переключение флага пишется в `AuditLog`: кто, когда, из какого значения в какое.
- **У-68.** Флаги, влияющие на доступ и деньги (`role_constructor`, `pii_access_log`, `commission_*`), требуют подтверждения в диалоге с явным текстом последствия.
- **У-69.** Каналы уведомлений (Max, WhatsApp, телефония Mango) включаются **с той же страницы, где вводятся ключи**, — а не отдельным env на сервере. Сейчас ключ ввести можно, канал включить нельзя.
- **У-70.** Страница интеграций показывает для каждого сервиса светофор: **работает** (проверка прошла, дата) · **не настроено** · **ошибка** (текст последней ошибки).

## §5. План работ (порядок PR)

Этапы строго последовательны. Каждый — отдельная спека в `docs/superpowers/specs/` и отдельный PR, по процессу `CLAUDE.md` §8.

| Этап | Объём | Требования | Почему в этом месте |
|---|---|---|---|
| **1** | Хотфикс комиссии | У-1…У-4 | Дыра в деньгах. Работа на полдня, ждать нельзя |
| **2** | Реестр значков + единый шелл | У-5…У-12 | Дёшево, видно сразу, ничего не ломает. Даёт базу для этапа 3 |
| **3** | Мобильная версия | У-13…У-19 | Опирается на единый шелл из этапа 2. Раньше — переделывать пять раз |
| **4** | Перестановки в кабинете партнёра | У-60…У-64 | Замечания заказчика напрямую; кроме У-63 не зависит от справочника |
| **5** | **Справочник сотрудников** | У-20…У-32 | Фундамент. Без него этап 6 делать не из чего |
| **6** | **Заявка: много слушателей × много обучений** | У-33…У-44 | Обязан идти после этапа 5: выбор сотрудников опирается на справочник |
| **7** | **Обмен с 1С: один экран + автосоздание по ИНН** | У-45…У-59 | Самостоятельный, самый крупный. Ставится после этапа 5 — автосозданные организации сразу получают куда класть сотрудников |
| **8** | Управление флагами и интеграциями из UI | У-65…У-70 | Снимает зависимость от SSH. Не блокирует остальное |
| **9** | Ориентирование и приёмка §0 | У-71…У-77 | Финальный проход по всем экранам; имеет смысл, когда экраны уже перестали меняться |

### Порядковые ограничения (нарушать нельзя)

1. **Этап 2 до этапа 3.** Мобильную версию делать в пяти разных шеллах — это пять раз одна работа и пять источников расхождений.
2. **Этап 5 до этапа 6.** Мастер заявки выбирает сотрудников из справочника. Без справочника список пуст, и проверить нечего.
3. **У-34 (бэкфилл) и У-36 (удаление поля) — в разных PR.** Удалять колонку в том же PR, что и переносить из неё данные, — значит остаться без отката.

### Оценка

Этапы 1–4 — короткие, укладываются в неделю суммарно. Этапы 5–7 — по 3–5 дней каждый: там миграции схемы, бэкфилл и обязательные integration-тесты против живого Postgres (`npm run gate`). Этапы 8–9 — по 2–3 дня.

## §6. Что НЕ входит в объём

Перечислено, чтобы исполнитель не расширял границы «заодно»:

- Выделение руководителя в самостоятельную роль JWT (лежит в «Заделе на будущее» `STATUS.md` — отдельная программа со своим ТЗ).
- Перевод загрузки документов на API-роут вместо server action (известный хвост про `bodySizeLimit`; сюда не входит).
- Отделы (`Department`).
- Визуальные тесты в CI (кроме нового мобильного проекта У-19, который остаётся ручным).
- Переработка модуля сделок, воронки и задач.
- Смена дизайн-системы, палитры и типографики. Оранжевый `#F97316` и тёмная шапка `#111111` остаются.

## §7. Приёмка

ТЗ считается выполненным, когда:

1. Все требования `У-1` … `У-77` отгружены в `main` и отмечены в `STATUS.md`.
2. Зелёные `npm run typecheck`, `npm run lint`, `npm run test:unit`, `npm run gate`, `npm run boundaries`.
3. Coverage-порог 100% на логические слои держится (`CLAUDE.md` §6) — понижение только отдельным решением заказчика.
4. **Сценарная приёмка на стенде** — заказчик проходит вживую:
   - завести организацию загрузкой выгрузки 1С → организация создалась автоматически по ИНН;
   - добавить в неё трёх сотрудников (одного руками, двоих импортом);
   - подать заявку, где первый сотрудник учится по двум направлениям, а двое других — по одному разному;
   - повторить весь путь **с телефона**;
   - включить канал уведомлений из интерфейса, не заходя на сервер.
5. Чек-лист §0 пройден по шести кабинетам (У-77).
