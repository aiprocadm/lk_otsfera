## 2. Разведение прода и стейджинга

Прод и стейджинг не делят ничего, кроме образа приложения: один и тот же тег сначала проходит
стейджинг, потом без пересборки идёт на прод.

| Ресурс | Прод | Стейджинг |
|---|---|---|
| Сервер | Отдельная VM, агента разработки на ней нет | Отдельная VM; можно рядом с агентом |
| PostgreSQL | Managed-база, PITR, доступ только с IP прод-VM | Своя база |
| S3 | Свой бакет, ключ только на него, versioning | Свой бакет и ключ |
| Redis | Внутри compose прода | Внутри compose стейджинга |
| Секреты | Генерируются отдельно, хранятся в менеджере паролей | Свои; никогда не копируются с прода |
| Домен | `lk.otsfera.ru` | `stage.lk.otsfera.ru`, закрыт паролем, `noindex` |
| 1С | `ONE_C_ADAPTER=rest`, боевая база | `ONE_C_ADAPTER=mock` или тестовая копия 1С |
| Почта | Боевой отправитель | Песочница или только тестовые адреса |
| Telegram, MAX, Wazzup, Mango | Боевые боты и аккаунты | Отдельные тестовые (у бота один адрес вебхука) |
| Sentry | `SENTRY_ENVIRONMENT=production` | `SENTRY_ENVIRONMENT=staging` |
| Данные | Живые | Сид или обезличенный дамп; живых ПДн нет (152-ФЗ) |
| Кто деплоит | Только человек | Человек или агент (`npm run deploy:stand`) |

Обезличенный дамп нужен для репетиции миграций: имена, телефоны, email, паспортные данные и
файлы заменяются до того, как дамп покинет прод-контур; структура и объёмы сохраняются.

## 3. Фаза A. Инфраструктура (один раз для каждой среды)

1. **VM.** Пользователь `deploy`, SSH только по ключу, вход под root и по паролю выключен. Порт
   22 открыт только с IP администраторов, снаружи — только 80 и 443. RAM от 6 ГБ (ClamAV
   занимает 2–3 ГБ).
2. **PostgreSQL.** Managed-база, доступ только с IP своей VM, `sslmode=require`. Автобэкапы и
   PITR. У приложения отдельная роль без прав суперпользователя.
3. **S3.** Отдельный бакет, ключ с правами только на него, versioning, публичный доступ
   закрыт. Файлы — только presigned-ссылками на 10 минут.
4. **Домен и DNS.** A-запись на VM. Сертификат Caddy выпускает сам.
5. **Реестр образов.** Приватный registry. Прод-VM читает образы, писать может только
   сборочная машина.
6. **Интеграции.** Для стейджинга — отдельные тестовые боты Telegram и MAX, тестовый канал
   Wazzup и тестовая АТС Mango, если нужны. У каждого вебхука свой секрет.
7. **Наблюдение.** Проект в Sentry, внешний uptime-монитор, алерт на место на диске.

## 4. Фаза B. Сборка релиза

Релиз собирается один раз на чистой машине без агента; стейджинг и прод получают один и тот же
тег образа. CI GitHub Actions сейчас не запускается (исчерпаны минуты), поэтому этот прогон —
единственная независимая проверка.

1. Влить хотфиксы блокеров 1 и 4 отдельными PR от `main`.
2. Чистый прогон на свежем клоне: `npm ci`, `npm run verify`, `npm run gate`, `npm run build`,
   `npm run audit:prod` (0 high, 0 critical), `npm run schema:drift`.
3. Образ: каждый merge в `staging` собирает `staging-<sha>`, прод получает этот же образ под
   тегом `vX.Y.Z` без пересборки. Вручную, если runner недоступен: `git tag vX.Y.Z && git push
   --tags`, `docker build -t registry/lk-otsfera:vX.Y.Z .`, `docker push …`.
4. В `CHANGELOG.md` для релиза — блок «Миграции и совместимость»: какие миграции входят, к
   какой фазе expand / migrate / contract относится каждая, нужен ли скрипт данных и можно ли
   откатить образ.

## 5. Фаза C. Конфигурация

Четыре правки: версия образа в compose, сервис ClamAV, `.env` на каждую среду, закрытый Caddy
для стейджинга. Правки compose и Caddy — отдельным PR.

**Версия образа.** Сейчас в `docker-compose.prod.yml` жёстко задан `image: lk-otsfera:prod`,
откат требует пересборки. В сервисах `migrate`, `web`, `worker`:

```yaml
image: registry.example/lk-otsfera:${IMAGE_TAG:?IMAGE_TAG is required}
```

**ClamAV:**

```yaml
clamav:
  image: clamav/clamav:1.4
  volumes: ['clamdb:/var/lib/clamav']
  healthcheck:
    test: ['CMD', 'clamdcheck.sh']
    interval: 60s
    timeout: 10s
    retries: 3
    start_period: 300s # базы сигнатур грузятся несколько минут
  restart: unless-stopped
```

В `worker.depends_on` — `clamav: { condition: service_healthy }`, в `volumes:` — `clamdb:`.

**Переменные окружения.** `.env.production` собирается по `.env.production.example`, права
`600`, владелец `deploy`. Каждый секрет генерируется заново (`openssl rand -base64 48`). Если
остался плейсхолдер, `src/lib/env.ts` не даёт приложению стартовать.

| Переменная | Прод | Стейджинг |
|---|---|---|
| `APP_URL`, `APP_DOMAIN` | `https://lk.otsfera.ru`, `lk.otsfera.ru` | `https://stage.lk.otsfera.ru`, `stage.lk.otsfera.ru` |
| `DATABASE_URL` | прод-база, `sslmode=require` | база стейджинга |
| `REDIS_URL` | `redis://redis:6379` | `redis://redis:6379` |
| `S3_BUCKET` и ключи | прод-бакет | бакет стейджинга |
| `JWT_SECRET` | новый | другой новый |
| `STUDENT_BRIDGE_JWT_SECRET` | новый, не равен `JWT_SECRET` | свой |
| `STUDENT_BRIDGE_SHARED_SECRET` | новый | свой |
| `CLAMAV_HOST`, `CLAMAV_PORT` | `clamav`, `3310` | `clamav`, `3310` |
| `FEATURE_STAFF_2FA` | `1` | `1` |
| `EMAIL_ENABLED`, `RESEND_API_KEY` | `true`, боевой ключ | ключ песочницы |
| `ONE_C_ADAPTER` | `rest` + `ONE_C_API_URL`, `ONE_C_API_TOKEN` | `mock` |
| `SENTRY_DSN`, `NEXT_PUBLIC_SENTRY_DSN` | проект Sentry | тот же проект |
| `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE` | `production`, `$IMAGE_TAG` | `staging`, `$IMAGE_TAG` |
| `TRUSTED_PROXY_HOPS` | `1` | `1` |
| `SHOW_DEMO_LOGINS` | не задавать | не задавать |

Имена `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE`, `NEXT_PUBLIC_SENTRY_DSN` — стандартные; сверить,
читает ли их `src/instrumentation.ts`.

**Caddy.** Для прода текущий `Caddyfile` подходит без изменений (Caddy по умолчанию не доверяет
входящему `X-Forwarded-For`, поэтому лимиты по IP не обойти при `TRUSTED_PROXY_HOPS=1`). Для
стейджинга — отдельный файл, всё закрыто паролем, кроме вебхуков и публичной формы:

```caddy
{$APP_DOMAIN} {
	@private not path /api/integrations/* /api/public/*
	basic_auth @private {
		stage <хеш из `caddy hash-password`>
	}
	header X-Robots-Tag "noindex, nofollow"
	reverse_proxy web:3000
	encode gzip
}
```

## 6. Фаза D. Первый запуск

Сначала на стейджинге, затем тем же тегом на проде:

```bash
export IMAGE_TAG=v0.12.0
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml logs migrate web worker clamav
```

`migrate` отрабатывает первым, `web` и `worker` ждут его успешного завершения. Первый
администратор: `docker compose -f docker-compose.prod.yml run --rm web npm run db:create-admin`.
**На проде никогда не запускать `npm run prisma:seed`** — он создаёт демо-учётки с известными
паролями.

**Смоук-проверка:**

- `/api/health/live` отвечает 200, сертификат выпущен, HTTP перенаправляется на HTTPS;
- в логах `web` нет ошибок проверки env; `clamav` в состоянии healthy;
- вход админом: приходит код 2FA, вход проходит;
- сброс пароля: письмо приходит, ссылка ведёт на домен своей среды;
- загруженный документ становится `clean` и скачивается;
- тестовый файл EICAR получает `infected`, скачивание отвечает 410;
- вебхуки подключены с секретами своей среды, диагностика вебхуков в админке видит входящие;
- один ручной прогон синхронизации 1С из центра управления (прод);
- тестовая ошибка появилась в Sentry с нужным релизом и окружением;
- уроненная задача очереди дала алерт;
- бэкап базы восстановлен на стейджинге и приложение на нём стартует;
- сделан бэкап тома `caddy_data` (сертификаты и ACME-аккаунт).

## 7. Фаза E. Регламент релизов и откат

Каждый релиз идёт одним путём, откат — запуск предыдущего образа без отката схемы (возможно
только при соблюдении правил совместимости, раздел 8).

1. Задачи вливаются в `staging` и автоматически разворачиваются на стейджинг.
2. Стейджинг: репетиция миграций на обезличенном дампе, замер времени, смоук, **тест отката**
   (предыдущий образ на новой схеме), приёмка.
3. Релизный PR `staging → main`, merge commit, тег `vX.Y.Z`, переподпись протестированного
   образа.
4. Прод: снапшот базы → `deploy.sh vX.Y.Z` → смоук.
5. 24 часа наблюдения: новые группы ошибок в Sentry по тегу релиза, проваленные задачи очередей,
   p95 ответов.
6. При P0 — откат на предыдущий тег:
   `IMAGE_TAG=<прошлый> docker compose -f docker-compose.prod.yml up -d web worker`.

Миграции при откате не отменяются. Восстановление базы из снапшота — крайняя мера. Деплой на
прод выполняет только человек; агент может готовить PR и деплоить на стейджинг.

### Воркфлоу разработки: ветки, PR, ревью

Три уровня веток: ветка задачи → `staging` → `main`. Всё, что влито в `staging`, автоматически
разворачивается на стейджинг. В `main` — только принятый на стейджинге код через релизный PR и
срочные хотфиксы; только из `main` ставятся теги для прода. Прямой push в `staging` и `main`
запрещён всем. Незаконченная функция вливается в `staging` за выключенным флагом. **Схема
меняет правило CLAUDE.md §14 «PR всегда открывается с `base: main`» — пока владелец не поправил
CLAUDE.md, агент действует по старому правилу.**

Путь задачи: issue в бэклоге (нет issue — нет ветки) → ветка от свежего `staging`
`<тип>/<номер issue>-<короткое-описание>` → Conventional Commits, хуки не обходятся
`--no-verify` → PR в `staging` с `Closes #N` и шаблоном → проверки сервера (`typecheck`,
`lint`, `test:unit`, `gate`, `boundaries`, `deadcode`, `audit:prod`, страж миграций) → ревью
человека (обязательно, агентское ревью — только предварительное) → squash merge в `staging` →
автодеплой → автор проверяет на стенде → релиз.

| Ветка | Откуда код | Слияние | Деплой | Кто мержит |
|---|---|---|---|---|
| `feat/*`, `fix/*` и др. | от `staging` | — | не деплоится | — |
| `staging` | PR из веток задач; back-merge из `main` | squash для задач, merge commit для back-merge | автоматически на стейджинг | владелец или назначенный ревьюер |
| `hotfix/*` | от `main` | — | образ сначала на стейджинг | — |
| `main` | релизный PR из `staging`; PR из `hotfix/*` | merge commit для релиза, squash для хотфикса | прод по тегу `vX.Y.Z`, вручную | только владелец |

Релизный PR и back-merge — **merge commit, никогда squash**. Ветку стейджинга один раз создать
из `main`: `git push origin origin/main:refs/heads/staging`.

**Деплой стейджинга** — одинаковый скрипт на каждой VM, разница только в `.env.production`:

```bash
#!/usr/bin/env bash
# /srv/lk/deploy.sh <IMAGE_TAG> — одинаковый на стейджинге и проде
set -euo pipefail
export IMAGE_TAG="${1:?usage: deploy.sh <image-tag>}"
cd /srv/lk
docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d --wait   # ждёт healthy
curl -fsS http://127.0.0.1:3000/api/health/live
echo "$(date -Is) $IMAGE_TAG" >> deploy.log              # история для отката
```

Автоматизация — workflow на self-hosted runner сборочной машины (только SSH-ключ к стейджингу,
прод-ключей нет):

```yaml
# .github/workflows/deploy-staging.yml
name: deploy-staging
on:
  push:
    branches: [staging]
concurrency: deploy-staging
jobs:
  deploy:
    runs-on: [self-hosted, build]
    environment: staging
    env:
      IMAGE: ${{ vars.REGISTRY }}/lk-otsfera:staging-${{ github.sha }}
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run verify
      - run: docker build -t "$IMAGE" . && docker push "$IMAGE"
      - run: ssh deploy@${{ vars.STAGING_HOST }} "/srv/lk/deploy.sh staging-${{ github.sha }}"
```

Ручной запасной путь — те же три шага со сборочной машины. **Сейчас в проекте есть `npm run
deploy:stand` — сверить с этой схемой и либо перевести на `deploy.sh`, либо заменить.**

**Релизный PR `staging → main`.** Перед открытием: все задачи приняты на стейджинге (неготовое —
за флагом или откачено revert-PR); пройдены смоук, репетиция миграций и тест отката; в
CHANGELOG — блок «Миграции и совместимость» и список флагов; в `main` нет хотфиксов, которых
нет в `staging`. Шаги: заморозка `staging` → `gh pr create --base main --head staging` → ревью
владельцем, «Create a merge commit» → тег `vX.Y.Z` на merge-коммите → образ без пересборки
(проверить `git rev-parse origin/main^{tree}` = `origin/staging^{tree}`, перетегировать
`staging-<sha>` в `vX.Y.Z`) → прод только человек с отдельной машины (снапшот,
`ssh deploy@lk.otsfera.ru "/srv/lk/deploy.sh vX.Y.Z"`) → смоук, флаги, 24 часа наблюдения →
снять заморозку. Прод намеренно не автоматизируется.

**Имена веток:** `feat/`, `fix/`, `hotfix/` (P0/P1), `chore/`, `docs/`, `refactor/`, `migrate/`;
`release/` не используется.

**Правила:** одна задача — одна ветка — один PR (до ~400 строк боевого кода); ветка живёт не
дольше недели; стек PR через `base` на чужую ветку запрещён; после мержа проверять, что код в
целевой ветке; непринятая задача уходит revert-PR или за флаг; Renovate — в `staging`
(`baseBranches: ["staging"]`), мажоры только по решению владельца.

**Хотфикс прода** (только P0/P1): ветка от `main` с тестом-стражем → PR в `main`, ускоренное
ревью, squash → патч-тег → образ сначала на стейджинг, потом прод → в тот же день back-merge
`main → staging` merge commit.

**Защита `main` в GitHub** (два ruleset, нужен платный тариф — Pro/Team): `main` — только PR,
без push/force-push/удаления, одобрение владельца через `CODEOWNERS`, обязательные проверки CI
и `source-branch` (джоб падает, если источник PR не `staging` и не `hotfix/*`), линейная
история выключена; `staging` — только PR, одно одобрение человека, `CODEOWNERS` для
чувствительных путей; новый push сбрасывает одобрение; теги `v*` — только владелец; обход
правил — только владелец в аварии. `CODEOWNERS` для чувствительных путей: `prisma/`,
`src/lib/auth/`, `src/middleware.ts`, `src/app/api/integrations/`, `docker-compose*.yml`,
`Dockerfile`, `Caddyfile`, `.github/`, `CLAUDE.md`, `package.json`, `package-lock.json`.

**Серверные проверки.** Без CI обязательные проверки нечем требовать. Варианты: оплатить минуты
Actions или поднять self-hosted runner на отдельной сборочной машине (не на агентском сервере и
не на проде). `ci.yml` — на `pull_request` и `push` для `main` и `staging` плюс джоб
`source-branch`; новый `deploy-staging.yml` (CLAUDE.md §11 запрещает новые workflow без
обсуждения — нужно решение владельца); шаги workflow вызывают те же npm-скрипты, что и хуки.

**Агент в этом процессе:** отдельная учётная запись GitHub (machine user) с правами только на
push в свои ветки и создание PR; ответвляется от `staging`, PR только в `staging`; релизный PR,
хотфикс в `main`, back-merge, теги и деплой прода делает человек; каждая сессия — в своём
worktree и своей ветке; PR помечаются меткой `agent`; агент не мержит и не меняет настройки
репозитория.

**Шаблон PR** (`.github/pull_request_template.md`): связанный issue и `У-N`; что и зачем, как
проверить руками; вывод локальных проверок; безопасность (гард и скоуп у нового роута, нет
секретов и ПДн в коде и логах); чек-лист совместимости пройден; флаг — все три точки чтения;
UI — скриншоты десктопа и 390×844, три вопроса понятности и правило зеркала; запись в
`CHANGELOG.md`.

## 8. Совместимость с легаси-данными и функционалом

Главное требование: версия N работает со схемой и данными N−1, а версия N−1 — со схемой N.
Развивает действующие «схема только аддитивно» (`Р-ПМ-5`) и «применённую миграцию не
редактировать».

**Разрушающее изменение — только в три релиза** (между фазами минимум один релиз на проде без
отката):

| Фаза | Схема | Код | Данные | Откат |
|---|---|---|---|---|
| 1. Expand (N) | Добавить новое: столбец nullable или с default, новая таблица, новое значение enum | Пишет в старое и новое, читает старое | — | Свободный |
| 2. Migrate (N+1) | Без изменений | Читает новое (со старым как запасным), пишет в оба | Скрипт переноса: отчёт → исправление пачками → повторный отчёт = 0 | Свободный |
| 3. Contract (N+2+) | Удалить старое, NOT NULL, ограничения | О старом не знает | Бэкап и архив старого | Только до N+1 |

Contract — отдельное решение владельца, не смешивается с другими изменениями в одном PR.

**Схема (Prisma и PostgreSQL):** переименование поля Prisma генерирует как `DROP + ADD` —
имя в коде меняется через `@map`/`@@map`; каждую `migration.sql` читать глазами; новое
обязательное поле — nullable → заполнение скриптом → `NOT NULL` в следующем релизе; смена типа
— через новый столбец по трём фазам, не `ALTER COLUMN … TYPE`; enum — значения только
добавляются, код читает неизвестное значение без падения; индексы на больших таблицах —
`CREATE INDEX CONCURRENTLY` отдельной миграцией, ограничения — `NOT VALID`, затем
`VALIDATE CONSTRAINT`; удаление данных — признак архива; исторические заказы, документы,
платежи, комиссии и журнал аудита не удаляются и не пересчитываются задним числом; перенос
данных — парой скриптов по образцу `report:document-numbers` / `fix:document-numbers` (отчёт
без изменений, идемпотентное исправление пачками, запись в аудит).

**«Статичные» модели:** JSON-поля (значения настраиваемых полей, `AuditLog.after`, профили
доступа, настройки интеграций) читаются через Zod-схему с версией `{ v: 2, … }`, запись без `v`
— версия 1, переходник при чтении; новые клеймы JWT опциональны (эталон — `sessionVersion`,
отсутствие = 0), удаление клейма — по трём фазам с интервалом ≥ 7 дней, клеймы токена для
портала слушателя — только по согласованию с порталом; задачи BullMQ — новый воркер принимает
прежние формы payload (`removeOnFail: false`, задачи могут быть перезапущены через месяц),
очередь не переименовывается, пока старая не разобрана; стабильные строки (коды ошибок,
статусы, `action`/`entity` журнала аудита, ключи `IntegrationSetting` и флагов) не
переименовываются.

**Внешние контракты:** ссылки из отправленных писем (приглашения 7 дней, сброс пароля 2 часа,
уведомления — бессрочно) и закладки ведут на новое место или на «раздел переехал»
(`removedPaths.ts`); адрес и форма ответа вебхуков (Telegram, MAX, Wazzup, Mango, публичная
форма) не меняются без смены настройки у провайдера в том же окне; 1С — внешние идентификаторы
и номера документов неприкосновенны, изменение формата обмена проверяется на тестовой копии 1С;
файлы в S3 — старые ключи читаемы, ключ берётся из базы; новое поведение на старых данных —
за флагом (выключен на проде в первом релизе, остаётся аварийным тормозом).

**Механические проверки:**

1. **Страж миграций** (unit-тест в стиле проекта): падает, если в новой `migration.sql` есть
   `DROP TABLE`, `DROP COLUMN`, `RENAME`, `ALTER COLUMN … TYPE`, `SET NOT NULL` или ограничение
   без `NOT VALID`, и в файле нет пометки `-- contract: <ссылка на решение и релиз expand>`.
   Проверяется мутацией. Дополнительно можно подключить линтер миграций PostgreSQL (squawk).
2. **Фикстуры легаси-данных** в integration-слое: JSON старых версий, старые значения enum,
   строки с NULL в поздно добавленных полях, заказы из 1С и миграции Битрикс24, payload задач
   очередей, токены без новых клеймов — через ключевые сценарии (просмотр, скачивание,
   экспорт, расчёт комиссии).
3. **Репетиция на стейджинге** на обезличенном дампе с замером времени и контрольными суммами
   (число заказов, документов, платежей, суммы комиссий по месяцам).
4. **Тест отката:** после миграции на стейджинге запускается предыдущий образ и проходит смоук.
5. **Дрейф схемы:** `npm run schema:drift` и `prisma migrate status` на проде перед деплоем.

**Чек-лист для каждого PR:** меняет ли PR схему, JSON-форму, клейм, payload очереди, ключ
настройки, код ошибки, адрес или формат обмена (если да — указана фаза); предыдущий релиз
работает на новой схеме; код читает старые записи без нового поля, фикстура добавлена;
`migration.sql` прочитана глазами; перенос данных — отдельные идемпотентные скрипты; новое
поведение на старых данных за флагом; в CHANGELOG заполнен блок «Миграции и совместимость».
Чтобы правила стали обязательными — внести в CLAUDE.md, шаблон PR и добавить страж миграций
(решение владельца).

## 9. Обратная связь и бэклог

Большинство проблем ловится автоматически, кнопка «Сообщить о проблеме» добавляет то, что
логи не видят. Всё стекается в один бэклог с автоматическим предложением приоритета, решает
человек.

| Сигнал | Как ловим | Режим |
|---|---|---|
| Ошибки сервера и воркера | Sentry, `release` = тег образа | Авто |
| Ошибки в браузере | Sentry в клиенте + `clientLog` | Авто |
| Медленные ответы сервера | Sentry Performance: p95 по роутам, порог 3 с | Авто |
| «Не откликается» в браузере | Web Vitals (INP, LCP), таймауты `useFetchSubmit` | Авто |
| Сайт недоступен | Внешний uptime-монитор на `/api/health/live` раз в минуту | Авто |
| Фоновая работа не дошла | Проваленные задачи BullMQ → `monitoring.evaluateAlerts` | Авто |
| Молчат интеграции | Диагностика вебхуков: давно нет входящих → алерт | Авто |
| Жалоба пользователя | Кнопка «Сообщить о проблеме» в шапке и на страницах ошибок | Полуавто |
| Звонок, письмо, мессенджер | Менеджер заводит обращение той же формой от имени клиента | Вручную |

Форма обращения спрашивает одно: «что делали и что пошло не так». Адрес страницы, роль,
релиз, браузер, `x-request-id` последних ошибочных запросов и ID события Sentry подставляются
сами. Человек сразу видит номер обращения и получает уведомление, когда задачу закроют.

**Бэклог** — GitHub Issues и GitHub Project с полями «Приоритет», «Источник», «Релиз». Sentry
создаёт issue сам через интеграцию. Само обращение (текст, пользователь, организация) хранится
в базе ЛК; в GitHub уходят только номер и ссылка, роль, страница, релиз, request-id и текст
после `scrub()`. Sentry — свой (Sentry или GlitchTip на сервере в РФ) либо облачный строго с
`sendDefaultPii: false`, `scrubSentryEvent` и выключенным Session Replay. Выбор — владелец с
учётом 152-ФЗ.

**Приоритеты:** P0 — не работает вход, лёг сайт, утечка или дыра в доступе, потеря данных,
всплеск 5xx после релиза (алерт в Telegram дежурному сразу; откат или хотфикс в тот же день);
P1 — ключевой сценарий роли сломан и обхода нет (до 2 рабочих дней); P2 — сломано, но обход
есть, или затронут один пользователь (ближайший плановый релиз); P3 — косметика, неудобство,
пожелание (копится; пожелания уходят заказчику как вопрос).

Автооценка порядка внутри приоритета:
`балл = тяжесть × охват × частота × вес_сценария × (2, если регрессия)`; тяжесть: исключение 3,
таймаут 2, жалоба без ошибки 1; охват — уникальные пользователи за 24 часа (для жалоб — число
склеенных дублей); вес сценария: вход, документы, оплаты 3, клиентские кабинеты 2, служебные 1;
регрессия — ошибка впервые появилась в последнем релизе. Дубли склеиваются по отпечатку Sentry
или по request-id; жалоба с привязанным событием Sentry наследует его охват.

**Триаж:** ежедневно 10–15 минут (дежурный подтверждает приоритеты, склеивает дубли);
классификация: баг (расхождение с `У-N`) → хотфикс, пожелание → сверка с `docs/NOT_DOING.md` →
вопрос заказчику → спека, вопрос пользователя → ответ и правка подсказки на экране;
еженедельно — разбор P2 и P3, сводка заказчику; 24 часа после релиза — регрессии по тегу.
Агент может делать черновую классификацию, но текст обращений пишут пользователи — это канал
prompt-инъекции: агент триажа работает только на чтение, без `bypassPermissions` и
прод-доступов, его предложения применяет человек.

**Что требует разработки:** Sentry, алерты, uptime-монитор и GitHub Project — настройка.
Кнопка обращения, модель в базе, экран в админке, отправка в GitHub и уведомление о закрытии —
новая функция (спека). Сначала проверить, что уже делает существующий `api/support`.

## 10. Агентский сервер и доступы

Сервер с Claude — самый вероятный путь взлома: агент в режиме `bypassPermissions`, управление с
телефона, десятки плагинов и сотни сторонних скиллов, MCP `fetch`/`filesystem`. Одной
prompt-инъекции из веб-страницы, issue или файла достаточно, чтобы выполнить любую команду.

- на агентском сервере нет prod `.env`, SSH-ключей к проду, строки подключения к прод-базе,
  S3-ключей прода, права записи в registry;
- токен `gh` агента не может мержить в `main` и менять настройки репозитория (fine-grained,
  только PR); для `main` включена защита ветки;
- `bypassPermissions` снят или агент работает в изолированном контейнере без сетевого доступа
  к проду;
- удалены неиспользуемые и непроверенные наборы скиллов и плагинов, в первую очередь ≈750
  скиллов по кибербезопасности;
- пересмотрены разрешённые команды в `settings.local.json`;
- `chmod 700 ~/.claude` (история разговоров — возможны секреты и ПДн — и `.credentials.json`);
- агент может деплоить только стейджинг; прод — только человек с отдельной машины.

## 11. Открытые вопросы программиста

- Сверить план с `README.md` §«Финальный release checklist» и `scripts/stand/update-stand.sh`.
- Где размещается Sentry: свой сервер в РФ или облако со строгим фильтром ПДн (152-ФЗ).
- Какой registry и какая машина собирает образы, пока CI GitHub Actions не работает.
- Кто дежурный по P0 и куда приходят алерты.
- Решение владельца по nodemailer 10 (С-9) — блокер выхода.
- Принять ли правила совместимости как обязательные (CLAUDE.md, шаблон PR, страж миграций).
- Что уже делает `api/support` и модуль внутренних задач — перед спекой обратной связи.
- Тариф GitHub: защита веток и обязательный `CODEOWNERS` в приватном репозитории требуют Pro
  или Team. Кто заводит отдельную учётную запись для агента.
- Переход на ветку `staging`: владелец правит CLAUDE.md §14 и §11 (разрешить
  `deploy-staging.yml`), а также `renovate.json`. До этого агент следует старому правилу.
