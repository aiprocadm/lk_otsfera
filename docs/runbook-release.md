# Ранбук выкладки: стейджинг и прод

**Требование:** `У-343` (ТЗ 28.10.2026). **Источник:** [документ программиста](tz/sources/2026-10-28-release-plan.md), ДП §2–§8.
**Кто выполняет:** фазы A и выкладку прода — только человек (владелец или назначенный им инженер). Агент готовит
PR, может выкладывать стейджинг, прод не трогает.
**Главный документ выкладки.** Прежние ранбуки ([prod-infra-rf](runbook-prod-infra-rf.md),
[launch-deploy](runbook-launch-deploy.md), [RUNBOOK §3](RUNBOOK.md)) остаются справочниками по своим темам и
ссылаются сюда; при расхождении верен этот файл.

Один принцип на всё: **прод и стейджинг не делят ничего, кроме образа приложения.** Один и тот же тег образа
сначала проходит стейджинг, потом без пересборки идёт на прод. Откат — запуск прежнего образа без отката базы.

| Ресурс | Прод | Стейджинг |
|---|---|---|
| Сервер | отдельная VM, агента на ней нет | отдельная VM |
| PostgreSQL | managed, PITR, доступ только с прод-VM, `sslmode=require` | своя база (сид или обезличенный дамп) |
| S3 | свой бакет, ключ только на него, versioning | свой бакет и ключ |
| Домен | `lk.otsfera.ru` | `stage.lk.otsfera.ru`, за паролем, `noindex` |
| 1С | `ONE_C_ADAPTER=rest`, боевая база | `ONE_C_ADAPTER=fake` (в коде нет значения `mock`) |
| Почта | боевой отправитель | песочница / только тестовые адреса |
| Боты, Wazzup, Mango | боевые | отдельные тестовые (у бота один адрес вебхука) |
| Sentry | `SENTRY_ENVIRONMENT=production` | `SENTRY_ENVIRONMENT=staging` |
| Секреты | свои, в менеджере паролей | свои, никогда не копируются с прода |
| Данные | живые | без живых ПДн (152-ФЗ) |

Тестовый стенд `lk.ptsfera.online` — **не стейджинг**: он собирается из исходников (`npm run deploy:stand`,
[runbook-test-stand](runbook-test-stand.md)) и нужен для показа. Стейджинг и прод выкладываются только образом
через `scripts/deploy/deploy.sh`.

## Фаза A. Инфраструктура — один раз для каждой среды

Это действия владельца `Н-1`…`Н-7` из §6 ТЗ. Агент их не выполняет, только проверяет результат.

| Шаг | Что сделать | Действие владельца |
|---|---|---|
| A1 | VM: пользователь `deploy`, SSH только по ключу, вход root и по паролю выключен; порт 22 — только с IP администраторов, снаружи только 80/443; RAM от 6 ГБ (ClamAV берёт 2–3 ГБ) | `Н-1` |
| A2 | PostgreSQL: managed, доступ только с IP своей VM, `sslmode=require`, автобэкапы и PITR, у приложения роль без суперпользователя | `Н-2` |
| A3 | S3: свой бакет, ключ только на него, versioning, публичный доступ закрыт | `Н-3` |
| A4 | DNS: A-записи на VM; сертификат Caddy выпустит сам | `Н-4` |
| A5 | Реестр образов: приватный; прод-VM только читает, пишет только сборочная машина (не агентский сервер и не прод) — либо оплата минут GitHub Actions | `Н-5` |
| A6 | Интеграции: для стейджинга — отдельные тестовые боты Telegram/MAX, канал Wazzup, АТС Mango; у каждого вебхука свой секрет | `Н-6` |
| A7 | Наблюдение: проект Sentry (размещение — с учётом 152-ФЗ), внешний uptime-монитор, алерт на место на диске, дежурный по P0 | `Н-7` |
| A8 | Папка стека на VM, например `/srv/lk`: клон репозитория **на теге релиза** (нужны `docker-compose*.yml`, `Caddyfile*`, `scripts/deploy/`) | — |

Подробности провижна (S3-адаптер, compose-топология, TLS) — [runbook-prod-infra-rf](runbook-prod-infra-rf.md);
бэкапы и проверка восстановления — [runbook-backups](runbook-backups.md).

## Фаза B. Сборка релиза

Релиз собирается **один раз**, на чистой машине без агента. Пока CI GitHub Actions не запускается (исчерпаны
минуты), этот прогон — единственная независимая проверка.

1. **Свежий клон и проверки** (заменяют README «Финальный release checklist», шаги 1–5 и 7):
   ```bash
   git clone <репозиторий> lk && cd lk && git checkout main
   npm ci
   npm run verify          # typecheck · lint · boundaries · deadcode · dup · format · unit
   npm run gate            # integration против одноразового Docker-Postgres (миграции с нуля + сид)
   npm run build
   npm run audit:prod      # 0 high, 0 critical — иначе релиз не собирается
   npm run schema:drift    # схема Prisma совпадает с миграциями
   ```
   Шаг 6 README (запуск `npm run dev` и поиск ошибок маршрутизации) по-прежнему полезен: `next build` не видит
   конфликт имён сегментов вроде `[id]`/`[orderId]`.
2. **CHANGELOG.** У релиза — блок «Миграции и совместимость»: какие миграции входят, к какой фазе
   (expand / migrate / contract) относится каждая, нужен ли скрипт данных и можно ли откатить образ.
   Страж `docs.changelog-compat-block` не пропустит релиз без блока.
3. **Тег и образ.**
   ```bash
   git tag vX.Y.Z && git push origin vX.Y.Z
   docker build -t <реестр>/lk-otsfera:vX.Y.Z .
   docker push <реестр>/lk-otsfera:vX.Y.Z
   ```
   После перехода на ветки `staging → main` ([заготовки](../.github/staging-switch/README.md)) образ собирается на
   каждый merge в `staging` как `staging-<sha>`, а прод получает **тот же** образ, перетегированный в `vX.Y.Z`,
   без пересборки.

## Фаза C. Конфигурация

1. **`.env.production`** — собрать по [`.env.production.example`](../.env.production.example) (у строк пометки
   «прод / стейджинг»). Права `600`, владелец `deploy`. Каждый секрет — заново: `openssl rand -base64 48`.
   Осталась заглушка (`replace_with…`/`replace_me`/`changeme`) в **любой** строке — приложение не стартует и в
   журнале назовёт переменную. `SHOW_DEMO_LOGINS` не задавать никогда. `DIRECT_URL` обязательна наравне с `DATABASE_URL`
   (прямой адрес базы для миграций; без неё сервис `migrate` падает, и приложение не стартует).
2. **`.deploy.env`** рядом со стеком — какие compose-файлы и какой реестр:
   ```bash
   # прод
   IMAGE_REPO=<реестр>/lk-otsfera
   # стейджинг — ещё и надстройка с паролем
   IMAGE_REPO=<реестр>/lk-otsfera
   COMPOSE_FILE=docker-compose.prod.yml:docker-compose.staging.yml
   ```
3. **Пароль стейджинга** — файл `caddy-staging-users` рядом со стеком, одна строка `логин хеш`:
   ```bash
   docker run --rm caddy:2-alpine caddy hash-password --plaintext '<пароль>'
   ```
   Без файла Caddy стейджинга не стартует — сайт не откроется без пароля. Без пароля открыты только вебхуки
   (`/api/integrations/*`) и публичная форма (`/api/public/*`).
4. **Прод** — текущий [`Caddyfile`](../Caddyfile) подходит как есть (Caddy не доверяет входящему
   `X-Forwarded-For`, лимиты по IP не обойти при `TRUSTED_PROXY_HOPS=1`).

## Фаза D. Первый запуск

Сначала на стейджинге, затем **тем же тегом** на проде.

```bash
cd /srv/lk
./scripts/deploy/deploy.sh vX.Y.Z          # pull → migrate → web/worker → проверка здоровья → deploy.log
docker compose logs migrate web worker clamav
```

`migrate` отрабатывает первым, `web` и `worker` ждут его успешного завершения; `worker` — ещё и здорового
`clamav` (базы сигнатур грузятся несколько минут). После выкладки служебные команды compose работают без тега:
`deploy.sh` запомнил его в `.env` стека.

**Первый администратор** (пароль — через переменные, не в истории shell):

```bash
docker compose run --rm -e ADMIN_EMAIL=<email> -e ADMIN_PASSWORD=<от 8 символов> web npm run db:create-admin
```

**На проде никогда не запускать `npm run prisma:seed`** — он создаёт демо-учётки с известными паролями.

### Смоук-проверка (go / no-go)

- [ ] `/api/health/live` отвечает 200; сертификат выпущен; HTTP перенаправляется на HTTPS.
- [ ] В журнале `web` нет ошибок проверки окружения; `clamav` — `healthy`; `worker` — `healthy`.
- [ ] Вход администратора: приходит код 2FA (`FEATURE_STAFF_2FA=1`, `Н-8`), вход проходит.
- [ ] Сброс пароля: письмо приходит, ссылка ведёт на домен **своей** среды.
- [ ] Загруженный документ становится `clean` и скачивается.
- [ ] Тестовый файл EICAR получает `infected`, скачивание отвечает 410.
- [ ] Вебхуки подключены с секретами своей среды; диагностика вебхуков в админке видит входящие.
- [ ] Стейджинг: без пароля — 401 на любой странице; вебхуки и форма заявки — без пароля.
- [ ] Прод: один ручной прогон синхронизации 1С из центра управления.
- [ ] Тестовая ошибка появилась в Sentry с нужными релизом (тег образа) и окружением.
- [ ] Уроненная задача очереди дала алерт.
- [ ] Бэкап базы восстановлен на стейджинге, и приложение на нём стартует ([runbook-backups](runbook-backups.md) §4).
- [ ] Сделан бэкап тома `caddy_data` (сертификаты и ACME-аккаунт).

Флаги кабинетов, дедупликация и перевод 1С в live при первом боевом запуске —
[runbook-launch-deploy](runbook-launch-deploy.md) §0.1–§3.

## Фаза E. Регламент релизов и откат

Каждый релиз — один путь. Откат возможен только потому, что релизы соблюдают правила совместимости
(CLAUDE.md §2c, страж миграций `prisma.migrations-compat`).

1. Задачи вливаются (до `Н-9` — в `main`, после — в `staging`) и выкладываются на стейджинг: клон стека на
   коммит (`git -C /srv/lk checkout --detach <sha>`), затем `./scripts/deploy/deploy.sh staging-<sha>`.
2. **Стейджинг:** репетиция миграций на обезличенном дампе с замером времени; смоук; **тест отката** — прежний
   образ на новой схеме (`./scripts/deploy/deploy.sh <прежний тег>`, смоук, обратно на новый); приёмка.
3. Тег `vX.Y.Z` на проверенном коммите; образ — тот же, что прошёл стейджинг.
4. **Прод (только человек):** снапшот базы → клон стека на тег (`git -C /srv/lk fetch --tags && git -C /srv/lk
   checkout vX.Y.Z` — compose-файлы и `deploy.sh` должны совпадать с образом) → `./scripts/deploy/deploy.sh vX.Y.Z`
   → смоук. Для отката клон возвращают на прежний тег так же.
5. **24 часа наблюдения:** новые группы ошибок в Sentry по релизу, проваленные задачи очередей, p95 ответов.
6. **Откат при P0:**
   ```bash
   tail -5 deploy.log                         # история: дата и тег
   ./scripts/deploy/deploy.sh <прежний тег>   # или: IMAGE_TAG=<прежний> docker compose up -d web worker
   ```
   Миграции при откате не отменяются. Восстановление базы из снапшота — крайняя мера ([RUNBOOK](RUNBOOK.md) §3.2).

`deploy.sh` при осечке (сервисы не стали здоровыми, не отвечает проверка здоровья) не пишет тег в журнал и
печатает команду отката на прежний тег; сам не откатывает — решение за человеком.

### Хотфикс прода (только P0/P1)

1. Ветка от `main` (после `Н-9` — `hotfix/<описание>`), исправление **с тестом-стражем**, проверенным мутацией.
2. PR в `main`, ускоренное ревью, squash.
3. Патч-тег `vX.Y.(Z+1)` → образ **сначала на стейджинг** (смоук), потом прод по пунктам 4–5 выше.
4. После `Н-9`: в тот же день back-merge `main → staging` merge commit-ом (не squash).

### Переход на ветки `staging → main`

Схема веток, защита `main`, `CODEOWNERS`, автодеплой стейджинга — выключенные заготовки в
[`.github/staging-switch/`](../.github/staging-switch/README.md). Включаются только после `Н-9` (тариф GitHub с
защитой веток, ветка `staging`, разрешение владельца на правку CLAUDE.md §11/§14 и `renovate.json`) и `Н-11`
(отдельная учётная запись агента). До этого действует правило CLAUDE.md §14: PR с `base: main`.
