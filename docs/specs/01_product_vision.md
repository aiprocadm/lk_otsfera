# Видение продукта

**Для кого файл:** заказчик и Claude Code. Это рамка: что строим, что нет, по каким правилам решаем спорное. Требования с номерами — в файлах `02`…`13`.

## 1. Что строим

`lk_otsfera` — **одна система для четырёх аудиторий** учебного центра по охране труда:

1. **CRM для сотрудников** (администратор, руководитель, менеджер): клиенты, контакты, лиды, сделки, заказы, задачи, документы, коммуникации, отчёты.
2. **Кабинет заказчика**: заказы, обращения, заявки на обучение, сотрудники, удостоверения, документы, счета и оплаты, переписка с менеджером.
3. **Кабинет партнёра**: портфель организаций, заказы и обращения по ним, комиссия, документы, материалы.
4. **Коммуникационный центр**: e-mail, Telegram, MAX, WhatsApp, телефония, форма с сайта, кабинет — в одном экране у сотрудника, с привязкой к контакту, организации, сделке и заказу.

Плюс **обмен с 1С** (1С — источник истины по оплатам и реализациям, ADR-0004) и **миграция из Битрикс24** как одноразовый, но критичный проект.

Продукт уже существует (см. [00_project_audit.md](00_project_audit.md) §4) — эта программа **достраивает** его до состояния, в котором Битрикс24 можно выключить.

## 2. Для кого продукт

| Аудитория | Кто это в жизни | Роль в системе | Главная боль сегодня |
|---|---|---|---|
| Отдел продаж | 3–10 менеджеров, звонят, пишут, выставляют КП | `manager` | клиенты и переписка в Битриксе, документы в ЛК — два окна |
| Руководитель | владелец / РОП | `leader` (+ кабинет менеджера) | план/факт в Excel, нет картины по коммуникациям |
| Администратор | сам заказчик (владелец-«вайбкодер») и 1 техспециалист | `admin` | всё должно включаться из интерфейса, без сервера |
| Заказчик | специалист по ОТ или кадровик клиента | `organization` (`admin`/`leader`/`member`) | «где мой акт, оплатили ли счёт, когда обучение» |
| Партнёр | агент, приводящий организации | `partner` (`admin`/`manager`) | видеть статусы своих клиентов и комиссию |
| Слушатель | работник клиента, проходит обучение | `student` | попасть в СДО одной кнопкой |

## 4. Что не копируем из Битрикс24

1. **Живую ленту, соцсеть, лайки, бейджи.** Нет сценария.
2. **«Дела» как отдельную сущность.** Звонок, письмо, встреча, диалог — уже свои сущности со своими экранами; «дело» дублировало бы их.
3. **Бизнес-процессы с графическим редактором.** Правила «если событие → действия» из короткого списка (`У-222`) закрывают 90 % потребностей отдела продаж без визуального конструктора.
4. **Отдельные модули «Компании» и «Контрагенты» с двойным вводом реквизитов.** Реквизиты — на `Organization`, приходят из ЕГРЮЛ и 1С.
5. **Портальный дизайн с десятками пунктов меню.** Меню сотрудника — 9 групп, «Настройки» внизу (`У-113`); клиенту — 11–12 пунктов. Новый раздел без ответа «а где он у соседней роли» не проходит ревью (правило зеркала).
6. **Пользовательские поля везде.** Настраиваемые поля уже есть только там, где нужны (организация, заказ); в контакты и диалоги их не тащим.
7. **Внутренние чаты в каждой сущности.** Внутренний чат сотрудников — один (`StaffConversation`); в сущностях — заметки, а не чаты.

## 5. Главные пользовательские сценарии

Каждый сценарий — критерий приёмки программы (`У-268`). Формулировка «на стенде вживую».

1. **Входящее → сделка.** Клиент пишет в Telegram-бота / письмо / форму сайта → строка во «Входящих в работу» → менеджер берёт, видит контакт и историю, отвечает из диалога (шаблоном), создаёт лид → сделка → КП → заказ. Ничего не переписывается вручную.
2. **Миграция.** Администратор подключает Битрикс24 по вебхуку → предпросмотр: «компаний 412, контактов 980, сделок 1 230 (открытых 87), задач 340, файлов 1 100» → применение в фоне → отчёт сверки → две недели параллельной работы → повторный импорт без дублей → Битрикс выключен.
3. **Рутина без рук.** Счёт выставлен → через 5 дней задача «проверить оплату» у ответственного менеджера; КП без ответа 7 дней → задача «позвонить»; заказ перешёл в статус «в работе» → задача «подготовить документы». Правила включает руководитель галочкой.
4. **Заказчик сам находит ответы.** Заходит впервые → «Первые шаги» → видит заказы, счета со статусом оплаты, документы, ответ менеджера на обращение, переписку — и пишет менеджеру из кабинета; ответ приходит и в кабинет, и в бот.
5. **Руководитель управляет по цифрам.** Открывает «Аналитику»: план/факт по каждому KPI по менеджерам, время первого ответа по каналам, просроченные задачи, дебиторка; выгружает XLSX для собственника.
6. **Партнёр приводит клиента и видит всё по нему.** Портфель → организация → заказы, статусы, документы; раздел «Материалы» с актуальным прайсом и презентацией; уведомление о начислении.

## 6. Принципы интерфейса

Наследуются из действующих правил репозитория и обязательны для каждого PR программы:

1. **Три вопроса** — «где я / что здесь делают / что делать дальше» за 30 секунд (CLAUDE.md §15).
2. **Правило зеркала** — один объект, одно название, одно место во всех кабинетах; исключения — только в `mirrorExceptions.ts` с причиной (`У-121`).
3. **Ничего не включается на сервере** — всё, что нужно администратору и руководителю, настраивается из интерфейса (`У-122`).
4. **Лишнего для роли нет.** Клиент не видит внутренних терминов, кодов, чужих данных; страж стоп-слов `У-266`.
5. **Мобильный экран — не потом.** 390×844 проверяется на каждом новом экране.
6. **Ошибка — на русском и с выходом.** Коды — в API, человек видит строку из `errors/messages.ts`.
7. **Термины — из глоссария.** Новое слово в UI = строка в `docs/glossary.md` тем же PR.
