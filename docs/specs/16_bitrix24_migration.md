# Миграция из Битрикс24

**Этап дорожной карты:** 2 «Миграция из Битрикс24» · **Требования:** `У-188`…`У-203` · **Приоритет:** MVP (критический путь программы) · **Оценка:** 8–10 дней.
**Зависимости:** этап 1 (контакты, `OrganizationNote`). **От него зависят:** приёмка «Битрикс выключен» (`У-269`).
**Решения заказчика 12.09.2026:** `Р-Б-1` — источник: REST через входящий вебхук (основной) **и** CSV/XLSX-выгрузки (запасной); `Р-Б-2` — выигранные сделки переносятся **и** как история `Deal won`, **и** как заказ, с защитой от дублей с 1С; `Р-Б-11` — `bitrixId` отдельными колонками.

## 1. Цель

Перенести из Битрикс24 в `lk_otsfera` всё, чем пользуется отдел продаж: компании, контакты, лиды, сделки (со стадиями, ответственными и комментариями), задачи, файлы — так, чтобы после двух недель параллельной работы Битрикс можно было выключить. Механика — как у импорта 1С: **предпросмотр → применение в фоне → отчёт сверки → откат**.

## 2. Как есть

Кода миграции нет (`grep -rli bitrix src` → 0). Есть всё, во что переносить: `Organization` (ИНН, `nameKey`, `externalId` занят 1С), `Contact`/`ContactChannel` (этап 1), `Lead` (`LeadSource`), `Deal`/`DealStage` (стадии по компании), `Task`/`TaskColumn`, `DealNote`, `OrganizationNote` (этап 1), `Document` (`direction incoming`, `upload-core`, антивирус), `Order` (`externalId`, `OrderStatusDefinition`). Образцы механики: `OneCImportBatch`/`OneCImportRow` (предпросмотр, применение, откат `import/rollback.ts`, история `import/history.ts`), `PaymentImportBatch`/`PaymentImportWrite` (журнал записей для отката), fake-адаптеры `FAKE_ONEC_*`, `services/import/column-map.ts` (сопоставление колонок по заголовкам).

## 3. Решения

| Решение | Суть |
|---|---|
| `Р-Б-1` | Два адаптера одного интерфейса `BitrixSource`: `rest` (входящий вебхук) и `file` (выгрузки). Выбор — в форме пакета. Один пакет = один источник |
| `Р-Б-2` | Сделка `won` → `Deal` со стадией `won` (история, дата закрытия, сумма) **+** заказ: ищется заказ 1С той же организации с суммой ±1 % и датой закрытия ±30 дней → `Deal.orderId`; не найден → создаётся `Order` (`externalId = bitrix:deal:<id>`, статус «завершён» по `OrderStatusDefinition`, без строк, пометка «из Битрикса»); в предпросмотре колонка «Заказ: найден в 1С / будет создан» |
| `Р-Б-11` | `bitrixId String? @unique` на `Organization`, `Contact`, `Lead`, `Deal`, `Task`, `Document`; `externalId` остаётся 1С. Организация может иметь оба ключа |
| Идемпотентность | Повтор с тем же порталом обновляет по `bitrixId`; пустое из Битрикса не затирает заполненное; поля, правленные в ЛК после импорта, не перезаписываются (сравнение с `before` последней записи журнала) |
| Файлы | Через `upload-core` + `docs.scanDocument`; без сырых копий ответов API (ПДн не копим) |
| Пользователи | Ответственный Битрикса → `User` по e-mail; несопоставленные → «менеджер по умолчанию» из формы; таблица сопоставления сохраняется в `settings` пакета |

## 4. Модель данных

```prisma
model BitrixImportBatch {
  id            String   @id @default(cuid())
  companyId     String
  importedById  String
  source        String   // 'rest' | 'file'
  status        String   // preview | applying | applied | rolled_back | failed
  settings      Json     // фильтры, сопоставление пользователей/стадий, менеджер по умолчанию
  counts        Json     // { organizations: {create,update,skip}, contacts: {...}, ... , progress }
  errors        Json?    // построчные ошибки (первые 500)
  createdAt     DateTime @default(now())
  appliedAt     DateTime?
  rolledBackAt  DateTime?
  reportPath    String?  // XLSX сверки в S3
  @@index([companyId, createdAt])
}
model BitrixImportWrite {
  id        String   @id @default(cuid())
  batchId   String
  entity    String   // organization | contact | lead | deal | task | note | document | order
  entityId  String
  bitrixId  String
  action    String   // create | update | link
  before    Json?    // снимок изменённых полей для отката
  reverted  Boolean  @default(false)
  @@index([batchId, entity])
}
```

Секрет: `IntegrationSetting` ключи `bitrix.portalUrl`, `bitrix.webhookUrl` (`isSecret`, шифрование `APP_ENCRYPTION_KEY`), `bitrix.defaultManagerId`, `bitrix.userMap`.

## 5. Адаптеры

**`rest`** (`src/lib/services/bitrix/adapter-rest.ts`): URL вида `https://<портал>/rest/<userId>/<token>/<method>`; методы (уточняются спекой этапа по документации Битрикс24): `profile` (проверка), `user.get`, `crm.company.list` (+`crm.requisite.list` для ИНН `RQ_INN`), `crm.contact.list`, `crm.lead.list`, `crm.deal.list` (+`crm.dealcategory.list`, `crm.status.list` для стадий), `crm.timeline.comment.list`, `tasks.task.list`, `disk.attachedObject.get`/`disk.file.get` (ссылка скачивания); пагинация по `start`/`next` (50 за страницу), лимит ~2 запроса/с с backoff на `QUERY_LIMIT_EXCEEDED`, `batch` для сокращения вызовов; таймаут 30 с; ретраи 3.
**`file`** (`adapter-file.ts`): CSV/XLSX-выгрузки Битрикса по сущностям (компании, контакты, лиды, сделки, задачи); сопоставление колонок по заголовкам (образец `column-map.ts`), предпросмотр «колонка → поле»; файлы-вложения — ZIP с именами по id (необязательно).
**`fake`** (`adapter-fake.ts`, `FAKE_BITRIX=1`): фикстура в памяти для тестов и стенда — 5 компаний, 8 контактов, 6 лидов, 6 сделок (2 `won`, 1 `lost`), 4 задачи, 3 файла, 10 комментариев.

## 6. Сопоставление сущностей

| Битрикс24 | ЛК | Ключ / правило |
|---|---|---|
| Компания | `Organization` | ИНН из реквизитов → существующая; без ИНН → `nameKey` (`У-84`); нет → создать с «ИНН не указан»; `bitrixId`; ответственный → `OrganizationManager` |
| Контакт | `Contact` + каналы | телефоны/e-mail нормализуются (`resolveContactByChannel`); совпадение канала → существующий контакт; `COMPANY_ID` → организация; должность → `position` |
| Лид | `Lead` | `LeadSource.bitrix` (новое значение enum); статус `NEW/IN_PROCESS` → активная стадия (таблица сопоставления в предпросмотре), `CONVERTED` → конвертирован (связь со сделкой по `bitrixId`), `JUNK` → закрыт |
| Сделка | `Deal` | стадия по таблице «стадия Битрикса → `DealStage` компании» (предпросмотр показывает все стадии портала, для каждой выбирается стадия ЛК; `WON`/`LOSE` → `won`/`lost`); сумма, дата, ответственный, контакт, организация; `won` → `Р-Б-2` |
| Комментарий таймлайна сделки | `DealNote` | автор по e-mail (иначе «импорт из Битрикс24»), дата оригинала |
| Комментарий компании/контакта | `OrganizationNote` | то же; для контакта — с префиксом «О контакте …» |
| Задача | `Task` | статус → колонка (`2/3 → в работе`, `5 → done`, `6 → отложено`); ответственный/постановщик по e-mail; `UF_CRM_TASK` → связи с организацией/сделкой |
| Файл | `Document` | `direction incoming`, `type other`, контрагент — организация; размер ≤ лимита; скан; имя файла сохраняется |
| Выигранная сделка → заказ | `Order` | `Р-Б-2` |
| Дела, лента, соцсеть, CRM-формы | — | не переносятся (`01` §4); учитываются в счётчике «пропущено: не поддерживается» |

## 7. Предпросмотр, применение, откат, сверка

**`У-193` предпросмотр:** форма (источник, период по дате создания, «только открытые сделки/задачи» или «вся история», файлы да/нет, менеджер по умолчанию, таблица стадий, таблица пользователей) → dry-run в воркере (те же вызовы, без записи) → сводка по сущностям «создать / обновить / уже есть / пропустить (причина)», список конфликтов (ИНН у другой компании, канал у контакта другой организации, стадия без сопоставления), оценка объёма и времени. Пакет > 50 000 сущностей → предупреждение и разбиение по периодам (`У-200`).
**`У-194` применение:** кнопка «Применить» → очередь `bitrix.import` (конкурентность 1, прогресс в `counts.progress`); экран обновляет прогресс; ошибка строки — в `errors`, пакет продолжает; итог — статус `applied`.
**`У-196` откат:** все `BitrixImportWrite` в обратном порядке: `update` → вернуть `before`, `create` → удалить, если нет новых ссылок (иначе строка отчёта «нельзя откатить: заказ … ссылается»), `link` → снять; аудит `bitrix_import_rolled_back`.
**`У-198` сверка:** после применения — XLSX (листы по сущностям: id Битрикса, id ЛК, действие, конфликт) в S3, кнопка «Отчёт»; история пакетов (дата, кто, источник, итоги, статус, кнопки «Отчёт», «Откатить»).
**`У-195` параллельный период:** повторные запуски по расписанию из UI (еженедельно) или вручную — обновляют только по `bitrixId`, не трогают правленные вручную поля; runbook (`У-201`) — 2 недели, критерий отключения.

## 8. Безопасность (`У-199`)

Только `admin`; вебхук зашифрован, в логах/аудите — домен портала; ПДн в отчёте — просмотр отчёта пишет `recordPiiAccess` (контекст `bitrix_report`); файлы — антивирус, MIME allow-list; сырые ответы API не хранятся; rate-limit к порталу; флаг `bitrix_migration` (поведенческий, `У-202`) закрывает раздел, действия и очередь.

## 10. Критерии приемки (`У-203`)

- [ ] На fake-адаптере: предпросмотр показывает верные счётчики; применение создаёт 5 организаций (2 совпали по ИНН с существующими и обновились без затирания), контакты с каналами, лиды/сделки на правильных стадиях, задачи в колонках, заметки с датами оригинала, файлы после антивируса.
- [ ] 2 `won`-сделки: одна привязана к существующему заказу 1С (сумма/дата в допуске), для второй создан заказ `bitrix:deal:<id>`; предпросмотр показал это заранее.
- [ ] Повторное применение — 0 созданных, обновления только по изменившимся полям; поле, правленное в ЛК, не перезаписано.
- [ ] Откат возвращает базу к снимку (интеграционный тест сравнивает выборки до/после); незатрагиваемый заказ блокирует откат с понятной строкой.
- [ ] Отчёт сверки скачивается; просмотр пишет журнал ПДн; чужая компания/роль → 404/403.
- [ ] Файловый адаптер: CSV из фикстуры даёт тот же результат, что REST-фикстура.
- [ ] REST-адаптер: rate-limit и пагинация покрыты unit-тестами на мок-транспорте (без сети); `QUERY_LIMIT_EXCEEDED` → backoff.
- [ ] Флаг `bitrix_migration` выключен → раздел 404, очередь не обрабатывает.
- [ ] Документация и runbook на месте; глоссарий: «Миграция из Битрикс24», «Пакет миграции».
- [ ] Покрытие 100 %, стражи проверены мутацией.
