# CRM-ядро

**Этап дорожной карты:** 1 «Контакты и внутренние заметки» · **Требования:** `У-178`…`У-187` · **Приоритет:** MVP · **Оценка:** 4–5 дней.
**Зависимости:** этап 0 (`У-177`). **От него зависят:** миграция из Битрикс24 (этап 2), диалоги в карточках (`У-210`), задачи из карточки контакта (`У-220`).

## 1. Цель

Дать отделу продаж то, чего нет в `lk_otsfera`, но есть в Битрикс24 и без чего миграция не имеет смысла: **справочник контактов (физлиц) с карточкой** и **внутренние заметки по организации**, невидимые клиенту. Всё остальное ядро CRM уже есть (см. [00 §4](00_project_audit.md)).

**Что найдено в коде.** `Contact`/`ContactChannel` (`prisma/schema.prisma:2291-2347`) с полями `companyId`, `organizationId?`, `userId?`, `name`, `position`, `note`, `isArchived`, каналы `phone/email/telegram/whatsapp/max` с `normalizedValue` и `@@unique([companyId, type, normalizedValue])`; связи на `InboundMessage`, `MessengerDialog`, `Call`, `Order.primaryContact`. Сервисы: `contacts/backfill.ts`, `contacts/resolveContactByChannel.ts`, `inbound/createContactFromInbound.ts`, `manager/contacts.ts`. Экрана и API-роутов нет; флаг `contacts` выключен. `DealNote` (`:2410`) — заметки по сделке с упоминаниями (`notifications` `deal_note_mention`). `Comment` (`:1515`) — разговор клиент↔менеджер по заказу, **не** внутренняя заметка (CLAUDE.md §5). `SavedView` (`:643`) — мёртвая модель, сохранённых фильтров в UI нет.

## 2. Сущности

Соответствие сущностей промпта и проекта. **Столбец «Действие» — единственное, что меняет программа.**

| Contact | `Contact` + `ContactChannel` | экран, карточка, объединение — `У-178`…`У-181` |

| Deal / Order / Project | `Deal` (продажа) → `Order` (исполнение; из 1С или из выигранной сделки) | без изменений; заказы из Битрикса — `У-197` |
| Task | `Task` + `TaskColumn` + `TaskAssignee` | комментарии/чек-листы — этап 4 |

## 3. Карточка клиента (организации)

Существует по реестру `orgCardTabs.ts`. Программа добавляет три вкладки (все — только сотрудникам ЦО; у партнёра и заказчика отсутствуют — исключение зеркала с причиной «внутренние данные продавца»):

| Ключ | Название | Содержимое | Требование |
|---|---|---|---|
| `contacts` | Контакты | контакты организации с каналами, кнопка «Добавить контакт», «Сделать основным» для заказов | `У-182` |
| `notes` | Заметки | внутренние заметки: закреплённые сверху, поле ввода с @упоминаниями, редактирование своей, удаление руководителем | `У-183` |
| `dialogs` | Диалоги | диалоги мессенджеров, привязанные к организации или её контактам (этап 3) | `У-210` |

Порядок вкладок в реестре: Обзор · Сотрудники · **Контакты** · Заказы · Заявки на обучение · Документы · Оплаты · Удостоверения · Обращения · Комментарии · **Заметки** · Лиды · Сделки · **Диалоги** · Звонки · Входящие письма · История · Настройки. Плитки-счётчики: добавляется «Контакты» = `_count.contacts` (не архивных).

## 4. Карточка контакта

`/{manager,leader,admin}/contacts/[id]` (`У-179`), общий презентационный компонент по `Р-23`, данные — сервис роли со скоупом.

**Шапка:** имя, должность, организация (ссылка на карточку), значки каналов, кнопки **«Написать»** (→ новый диалог через `Р-М-8`; после `У-205` — и e-mail) и **«Создать лид»**, меню «Изменить · Объединить · В архив».
**Блок «Каналы»:** список с признаком основного, добавление/удаление; нормализация как в `resolveContactByChannel.ts` (телефон → E.164, e-mail → lower-case).
**Вкладки:** Диалоги · Звонки · Входящие письма · Сделки · Заказы (где `primaryContactId`) · Задачи (`listLinkedTasks` + `linkedContactId`, этап 4) · История (аудит по контакту).
**Пустые состояния:** «Диалогов пока нет — напишите первым» с кнопкой; «Заказов, где этот человек указан контактом, нет».

## 5. Карточка заявки

Без изменений: обращение (`/…/requests/[id]`), заявка на обучение (`/…/enrollments/[id]`), входящее (`/manager/inbox`), лид (`/manager/leads/[id]`) — есть во всех кабинетах ЦО (`У-116`). Программа добавляет в карточку лида и обращения блок «Контакт» (найден по телефону/e-mail через `resolveContactByChannel.ts`; кнопка «Создать контакт из данных лида»).

## 6. Карточка сделки / заказа / проекта

Без изменений структуры. Добавления: в карточке сделки — «Контакт» из `Deal.contactId` с переходом; в карточке заказа — «Контакт заказа» (`Order.primaryContactId`, выбор из контактов организации).

## 7. История действий

`У-184`: вкладка «История» карточки организации становится единой лентой: события аудита (как сейчас) + заметки + диалоги (создан, ответ) + звонки + входящие письма + смены статусов заказов. Спека этапа сверяет текущий состав по `organizationCard.ts` и добавляет недостающие типы; каждый элемент — время, автор, тип, ссылка на объект. Фильтр по типу, постраничность (правило хотфиксов №25–№32: `total` + «Показаны N из M»).

## 8. Внутренние комментарии

`У-183`:
- **Кто видит:** только сотрудники ЦО компании организации; клиент и партнёр — никогда (страж IDOR).
- **Кто пишет:** менеджер, руководитель, админ. Редактирует автор в течение 24 ч, руководитель/админ — всегда; удаление — руководитель/админ с аудитом.
- **Упоминания:** `@Имя` → уведомление `note_mention` (обобщение `deal_note_mention`: одно событие с полем `entity: deal | organization`); реестр `notifications/registry.ts` и правила `У-127` обновляются.
- **Закрепление:** до 3 закреплённых заметок сверху вкладки и в «Обзоре» карточки (блок «Важное»).
- **Откуда ещё:** кнопка «Заметка» на карточке контакта пишет заметку в его организацию с префиксом «О контакте Иванов И.И.:» (не заводим третью модель).

## 9. Поиск, фильтры, статусы

- Список контактов (`У-178`): поиск по имени, телефону (любое написание), e-mail, организации; фильтры «с организацией / без организации / архив», сортировка по имени и дате; постраничность 50 с `total`.
- Глобальный поиск и командная палитра (`У-185`) находят контакт по имени/телефону/e-mail и ведут в карточку.
- Объединение дублей (`У-181`): при добавлении канала, который уже есть у другого контакта компании, форма показывает «Этот телефон уже у контакта Петров П.П.» с кнопками «Открыть» и «Объединить». Объединение: выбор главного, перенос каналов/диалогов/звонков/входящих/сделок/заказов (`primaryContactId`)/задач, второй — `isArchived = true`, `mergedIntoId`; аудит `contact_merged`; переход по старому id — редирект на главного.
- Статусов у контакта нет (только «в архиве»); не заводим.

## 12. Критерии приемки

- [ ] `/manager/contacts`, `/leader/contacts`, `/admin/contacts` — одинаковые (страж зеркала), с поиском и фильтрами; флаг `contacts` включается из «Функций платформы» и снят с env-only.
- [ ] Карточка контакта показывает диалоги, звонки, письма, сделки, заказы; кнопка «Написать» открывает новый диалог; «Создать лид» предзаполняет лид.
- [ ] Добавление занятого канала даёт русскую подсказку и кнопку «Объединить»; объединение переносит все связи, старый id редиректит.
- [ ] Вкладки «Контакты» и «Заметки» есть в карточке организации у трёх ролей ЦО и отсутствуют у партнёра/заказчика (исключение записано); заметка с @упоминанием шлёт уведомление.
- [ ] «История» показывает заметки и диалоги; постраничность с `total`.
- [ ] Глобальный поиск находит контакт по номеру в любом формате.
- [ ] Просмотр карточки контакта регистрируется в журнале ПДн (`У-186`); тест `pii.capture-coverage` зелёный.
- [ ] Стражи (`У-187`): IDOR (партнёр/заказчик/чужая компания → 404), `teamMode`-мутация, 100 % покрытие, мутационная проверка каждого стража.

## 13. Ошибки и edge cases

- Контакт без организации (лид «с улицы») — допустим; список и карточка показывают «Без организации», кнопка «Привязать к организации».
- Контакт с `userId` (пользователь кабинета) — каналы синхронизируются с `User.email/telegramChatId` при бэкфилле; правку канала, принадлежащего пользователю, запрещаем с подсказкой.
- Архивный контакт не предлагается в «написать первым», но остаётся в истории.
- Заметка длиннее 4 000 символов → ошибка до сохранения; упоминание несуществующего пользователя — игнорируется без ошибки.

## 14. Риски

- `Contact` создаётся из входящих автоматически (`createContactFromInbound.ts`) — при включении экрана всплывут дубли; объединение (`У-181`) идёт в том же этапе, а не позже.
- Обобщение `deal_note_mention` → `note_mention` меняет ключ события: правила `NotificationRule` бэкфиллятся миграцией (старый ключ → новый), страж полноты реестра.
