# Дорожная карта реализации

**Программа:** «CRM для отдела продаж — замена Битрикс24» · **База:** `main` = `a35d2d22` (12.09.2026, v0.11.0) · **Нумерация:** требования `У-177`…`У-269` (продолжают сквозную линию `У-1`…`У-176`), решения `Р-Б-1`…`Р-Б-12`, дефекты `Д-41`…`Д-49`.
**Как читать:** §2 — этапы с оценками; §3 — полный реестр требований (единственный источник номеров); §4 — решения; §5 — что отложено; §7 — вопросы заказчику. Задачи для Claude Code — [15_claude_code_tasks.md](15_claude_code_tasks.md).

## 1. Принцип приоритизации

1. **Критический путь — выключить Битрикс.** Всё, без чего отдел продаж не переедет, — MVP: контакты и заметки → миграция → коммуникации v2 → автоматизация → уведомления → доборы кабинетов → KPI.
2. **Сначала то, во что переносим, потом перенос.** Контакты и заметки раньше миграции (`Р-Б-4`).
3. **Один этап = одна спека = один close-out**, как в программах 21.08 и 12.09 (CLAUDE.md §8, §14). Внутри этапа — PR по 1–2 требования, аддитивные миграции.
4. **Очистка — в конце**, после утверждения списка заказчиком (`Р-Б-3`).
5. **Оценки — с учётом 100 % покрытия и стражей** (×1,5–2 к «просто коду»). Дни — рабочие дни одного агента с ревью заказчика между PR.

## 4. Решения

| № | Решение | Основание |
|---|---|---|
| Р-Б-1 | Источник Битрикс24: REST-вебхук основной, CSV/XLSX — запасной; два адаптера одного интерфейса | ответ заказчика 12.09.2026 («а и б») |
| Р-Б-2 | Выигранные сделки: `Deal won` **и** заказ; заказ создаётся только если не найден заказ 1С той же организации (сумма ±1 %, дата ±30 дней), иначе связь | ответ заказчика («а и б»); защита от дублей — исполнитель |
| Р-Б-3 | Очистка: мёртвые таблицы — отдельным PR при 0 строк (dry-run); «вечные» флаги — по списку, который заказчик утверждает при спеке этапа 9 | «реши сам» |
| Р-Б-4 | Контакты и заметки (этап 1) раньше миграции (этап 2) | нужно, куда переносить |
| Р-Б-5 | Кабинет — канал `cabinet` в тех же диалогах; «Задать вопрос» продолжает диалог | один экран у менеджера |
| Р-Б-6 | Правила автоматизации слушают реестр событий уведомлений; действия правил не порождают триггеры | один источник событий, нет зацикливания |
| Р-Б-7 | KPI — `SalesTarget.metric`, не вторая модель; метрики — реестр в коде, не формулы пользователя | без дублей сущностей |
| Р-Б-8 | Внутренние заметки — `OrganizationNote`; `DealNote` остаётся; `Comment` не трогаем | `Comment` виден клиенту |
| Р-Б-9 | Новых top-level ролей нет; «сотрудник» = профиль доступа; отделы — вне программы | конструктор профилей есть |
| Р-Б-10 | Пакет ТЗ живёт в `docs/specs/`; действующее ТЗ для стража — тонкий индекс в `docs/tz/` | просьба заказчика + страж репозитория |
| Р-Б-11 | `bitrixId` — отдельные колонки; `externalId` остаётся за 1С | у организации могут быть оба ключа |
| Р-Б-12 | Публичная форма сайта: токен + Origin + rate-limit + honeypot; капча — Позже | достаточно для лендинга |
