# Роли и доступы

**Цель доработки.** Зафиксировать ролевую модель, которая уже есть в коде, назвать её словами из промпта заказчика и закрыть три пробела: контакты (ПДн) в модели доступа, диалоги под профилями доступа, настраиваемая видимость заказов для рядового пользователя организации.

**Текущая ситуация.** Роли, суб-роли и профили доступа реализованы и защищены стражами (`security.role-access-matrix.guardrail`, `security.idor-*`, «серверное действие само спрашивает права» — хотфиксы №15/№16). Новых top-level ролей программа **не заводит** (решение `Р-Б-9`).

## 1. Роли

Маппинг названий из промпта на то, что есть в коде (`prisma/schema.prisma:15` `enum Role`, `src/lib/auth/jwt.ts:28-40`):

| В промпте | В проекте | Как задаётся | Что означает |
|---|---|---|---|
| **admin** | `role = admin` | `User.role` | Model A: управляет всем через зеркало `/admin/*`, в чужие кабинеты не входит (`access.ts:21-28`) |
| **head / supervisor** | `role = leader` | `User.role` | руководитель компании-продавца; свой кабинет `/leader/*` **и** кабинет менеджера («играющий тренер»); видит всё в своей `companyId` |
| **manager** | `role = manager` | `User.role` | менеджер; видимость по `Company.managerTeamVisibility` (`teamMode`) и `managedOrgIds` |
| **employee** | `role = manager` + профиль доступа | `AccessProfile` (`ScopeLevel: own/assigned/all`, capability-коды) | отдельной роли нет и не нужно: «сотрудник с узкими правами» = профиль с `own` и без разделов настроек. Отделы — вне программы |
| **client_admin** | `role = organization`, `roleInOrg = admin` | `OrganizationUser.roleInOrg` | управляет «Доступом в кабинет» своей организации (`server-actions/organization/team.ts`) |
| (нет аналога) | `roleInOrg = leader` | там же | «старший»: то же, что `admin`, но без приглашения администраторов (`requireOrganizationAdminOrLeader`) |
| **client_user** | `roleInOrg = member` | там же | рядовой пользователь организации; сегодня видит **все** заказы организации (ограничения не найдено — `У-236`) |
| **partner_admin** | `role = partner`, `partnerRole = admin` | `PartnerUser.roleInPartner` | команда партнёра, комиссионные отчёты, ставка (чтение), настройки организации портфеля, приглашение администратора организации |
| **partner_user** | `partnerRole = manager` + `assignedOrgIds` | там же | видит только назначенные организации портфеля. **Ловушка:** строка `'manager'` здесь не связана с ролью `manager` |
| — | `role = student` | `User.role` | слушатель: мост в СДО |

**Ловушка данных (`Д-47`):** `src/lib/services/admin/users/mutations.ts:75,193` пишут `roleInPartner: 'member'` — значения нет в контракте `'admin' | 'manager'`; сессия маппит его в `manager`. Чинится `У-261`.

## 3. Правила видимости

1. **Три места защиты** (CLAUDE.md §4): middleware по префиксу, `requireRole`/`requireSettingsSection` на странице и действии, скоуп в сервисе. Скрытая кнопка — не защита.
2. **`teamMode` обязателен** в менеджерских резолверах (`canSeeOrder`, `canSeeDocument`); новые сервисы контактов и диалогов принимают его так же и получают страж-мутацию.
3. **Профили доступа** расширяются двумя capability-кодами: `crm.contacts` и `communications.dialogs` (область `own/assigned/all`), плюс `settings.automation`, `settings.replyTemplates`, `settings.partnerMaterials`, `settings.kpi` в `SETTINGS_CAPABILITIES`. Правило наслоения (`accessProfileId = null` → прежнее поведение) не меняется.
4. **Кросс-компанийная изоляция** держится во всех режимах: чужая компания → `not_found`, не `forbidden` (не раскрываем существование).
5. **Клиентский контур не видит внутреннего**: заметки, лиды, сделки, задачи, KPI, комиссию, коды ошибок, источники данных («из Битрикса»).

## 4. Правила доступа к данным

| Данные | Правило |
|---|---|
| Контакт | принадлежит `companyId`; читается по `crm.contacts` со скоупом; просмотр карточки пишет `recordPiiAccess` (контекст `contact_card`, `У-186`) |
| Диалог мессенджера | компания диалога + очередь непривязанных (`Р-М-3`); с `У-214` — дополнительно ответственный/скоуп профиля |
| Заметка организации | только сотрудники компании организации; автор редактирует свою, руководитель — любую |
| Пакет миграции | только `admin`; в отчёте ПДн контактов — контекст `bitrix_report` в журнале ПДн (`У-199`) |
| Правило автоматизации | компания правила; выполняется только для событий той же компании (`У-227`) |
| KPI-цель | компания; менеджер видит только свою строку (`У-249`) |
| Материал партнёра | компания-издатель; партнёр видит материалы компаний, с которыми у него есть организации в портфеле |

## 5. Клиентские ограничения

- Заказчик видит только свою организацию; `member` при включённой настройке «участники видят только свои заказы» (`У-236`) — только заказы, где он `submittedBy` заявки/обращения или указан контактом заказа.
- Заказчик никогда не видит: комиссию, лиды, сделки, задачи, заметки, входящие письма, чужие организации, внутренних пользователей кроме «Ваш менеджер».
- Переписка (`У-234`): только диалоги, где `MessengerDialog.userId` = текущий пользователь; ответы сотрудников — без внутренних заметок (`direction = 'note'` не отдаётся).

## 6. Партнерские ограничения

- `partnerRole = manager` — только `assignedOrgIds`; пустой список → пустой портфель с подсказкой «попросите администратора партнёра назначить организации» (пустое состояние с действием).
- Партнёр никогда не видит: оплаты клиента, лиды, сделки, задачи, заметки, контакты как справочник, чужие организации, ставки других партнёров; ставку — только на чтение (`У-1`…`У-4`).
- Материалы (`У-237`) — только чтение и скачивание.

## 7. Админские возможности

- Всё из хаба настроек + новые разделы: «Миграция из Битрикс24», «Автоматизация», «Шаблоны ответов», «KPI», «Материалы для партнёров», «Сайт» (токен формы).
- Секреты (вебхук Битрикса, токен сайта) — только admin (`Р-22`); руководитель получает разделы своей компании без секретов.
- Admin переписку не ведёт и правила от лица компании не запускает вручную — исключение зеркала записывается с причиной, как для «Входящих писем».
