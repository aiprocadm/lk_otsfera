# Клиентский кабинет

**Этап дорожной карты:** 6 «Кабинеты заказчика и партнёра — добор» (часть требований приходит из этапов 3 и 5) · **Требования:** `У-234`, `У-235`, `У-236`, `У-238`, `У-239`, `У-240`, `У-241` (+ `У-228` из этапа 5, `У-212` из этапа 3) · **Приоритет:** MVP, кроме `У-234`/`У-236` (Важно) · **Оценка:** 3–4 дня.
**Зависимости:** `У-212` (канал `cabinet`) для `У-234`; `У-228` для страницы уведомлений; `У-238` требует правки `ClientRequest`.

## 1. Цель

Кабинет заказчика уже покрывает ядро (заказы, обращения, заявки, удостоверения, документы с принятием, финансы, «Моя организация», сообщения, настройки — `src/app/organization/*`, 18 страниц). Программа закрывает то, ради чего клиент всё ещё звонит менеджеру: **ответ на обращение**, **счета со статусом оплаты**, **переписка в кабинете**, **кто мой менеджер**, **с чего начать**.

**Что найдено в коде.** `ClientRequest` без текста ответа (`schema.prisma:461-495`: только `status`, `rejectedReason`). Финансы организации — `services/organization/finance.ts` (платежи и задолженность; блока счетов со статусом `unpaid/partially_paid/paid` из `У-148` спека этапа сверяет по коду). Диалоги мессенджеров у клиента в кабинете не показываются (спека мессенджеров §5.4: клиент пишет в бот). `roleInOrg = member` не ограничивает выборки (`organizationPolicy.ts` проверяет только `admin`/`leader`). Дашборд — `services/organization/dashboard.ts`; блок «Ваш менеджер» — спека этапа сверяет наличие и приводит к требованию `У-240`.

## 2. Главные сценарии клиента

1. Открыть кабинет впервые и понять, что делать (`У-239`).
2. Узнать, оплачен ли счёт и сколько должны (`У-235`).
3. Написать менеджеру и получить ответ там же (`У-234`), либо в боте (есть).
4. Подать обращение и увидеть ответ сотрудника, а не только «отклонено» (`У-238`).
5. Найти акт/договор, скачать, подтвердить (есть).
6. Отправить сотрудников на обучение, следить за удостоверениями (есть).
7. Дать доступ коллеге (есть, «Моя организация → Настройки»).

## 3. Дашборд клиента

- **«Первые шаги»** (`У-239`): чек-лист для новых пользователей организации, исчезает, когда всё выполнено или закрыт вручную: реквизиты заполнены → сотрудники добавлены → бот привязан (Telegram/MAX) → первое обращение/заявка. Каждый пункт — ссылка на нужный экран. Состояние — на `OrganizationUser` (`onboardingDismissedAt`), выполненность считается по данным, не хранится.
- **«Ваш менеджер»** (`У-240`): имя, телефон, e-mail ответственного менеджера (`OrganizationManager`, активный; если несколько — первый по `assignedAt`), кнопка «Написать» → «Сообщения → Переписка с менеджером» (`У-234`), либо «Задать вопрос» (есть), если `У-234` ещё не отгружен. При отсутствии менеджера — «Менеджер назначается; напишите нам» с той же кнопкой.
- Остальные блоки (заказы в работе, задолженность, ближайшие обучения, истекающие удостоверения, «Частые задачи`У-71`») — без изменений.

## 4. Заявки клиента

Обращения (`ClientRequest`) — `У-238`:
- поле `staffReply String?` + `staffRepliedAt`, `staffRepliedById`; сотрудник пишет ответ в деталке обращения (`/…/requests/[id]` у ЦО, `У-116`) одновременно со сменой статуса или отдельно;
- клиент видит ответ в карточке обращения блоком «Ответ менеджера» с датой и именем; уведомление `client_request_status_changed` расширяется текстом ответа (шаблон письма `У-128`);
- при `rejected` `rejectedReason` показывается как сейчас; `staffReply` — дополнительно;
- партнёр видит ответ по своим обращениям так же (зеркало).

Заявки на обучение — без изменений (матрица статусов есть).

## 5. Проекты / заказы клиента

Без изменений структуры. `У-236` (Важно): настройка организации «Участники видят только свои заказы» (`Organization.membersSeeOwnOrdersOnly`, по умолчанию выкл.) в «Моя организация → Настройки» (правит `roleInOrg = admin`); при включении `member` видит заказы, где он `submittedBy` заявки/обращения, породившей заказ, или указан `Order.primaryContactId` через свой контакт; `admin`/`leader` — всё. Скоуп — в `organizationPolicy`/`services/organization/orders.ts`, тест IDOR.

## 6. Документы

Без изменений в этом этапе (принятие, отклонение, скачивание с человеческим именем — есть). Из этапа 8: ZIP выбранных документов (`У-252`), последняя версия загруженного файла (`У-251`).

## 7. Счета и оплаты

`У-235`: раздел «Финансы» заказчика получает блок **«Счета»**: номер, дата, сумма, заказ, статус документа, признак оплаты `не оплачен / частично / оплачен` (вычисляется по платежам заказа с привязкой «платёж → счёт», `У-148`), кнопка «Скачать». Фильтр по периоду и статусу оплаты; итог «к оплате» = сумма неоплаченных. Задолженность по заказам и список платежей — как сейчас. Оплата вручную не отмечается (только 1С/выписка — ADR-0004).

## 8. Чат и коммуникации

`У-234` (Важно; серверная часть — `У-212`): «Сообщения» заказчика = две вкладки:
- **«Переписка с менеджером»** — диалоги, где `MessengerDialog.userId` = текущий пользователь (каналы Telegram/MAX/WhatsApp/email/`cabinet`), единой лентой; ответ из кабинета создаёт `MessengerMessage` с каналом `cabinet`, попадает менеджеру в тот же диалог; входящие сообщения от сотрудника дублируются в кабинет всегда, в бот — если привязан. Внутренние заметки (`direction = 'note'`) не отдаются.
- **«По заказам»** — комментарии и переписка по заказу (как сейчас).
Пункт меню не меняется; глоссарий: «Переписка с менеджером → `MessengerDialog` канала `cabinet`».

Обращение «Задать вопрос» (`cabinet_questions`) остаётся как быстрый вход в тот же диалог: вопрос из кабинета создаёт/продолжает диалог канала `cabinet` (после `У-212`), а не отдельную строку инбокса.

## 9. Уведомления

`У-228`: страница «Уведомления» (общий компонент для шести кабинетов), фильтры «непрочитанные / все / по типу», «отметить все прочитанными», переход к объекту. `У-229`: личные настройки «событие × канал» в пределах правил компании. Подробно — [09_notifications.md](09_notifications.md).

## 10. Профиль компании клиента

«Моя организация» (`У-100`) — без изменений. Добавляется настройка `У-236` на вкладке «Настройки».

## 11. Пользователи клиента

«Доступ в кабинет» — без изменений (роли `admin`/`leader`/`member`, приглашения, лимит 10). Добавляется подсказка у роли `member`: «видит все заказы организации» / «видит только свои заказы» в зависимости от `У-236`.

## 12. Что клиент не должен видеть

Комиссию и ставки; лиды, сделки, воронку; задачи и заметки сотрудников; входящие письма и звонки; данные других организаций; внутренние коды ошибок и термины (страж стоп-слов `У-266`); источник записи («из Битрикса», «из 1С» — кроме подписи «Акт из 1С», которая уже принята); внутренние заметки в диалоге; e-mail/телефон менеджера — только через блок «Ваш менеджер».

## 13. Критерии приемки

- [ ] Новый пользователь организации видит «Первые шаги» с рабочими ссылками; после выполнения всех пунктов блок исчезает; «Закрыть» скрывает навсегда.
- [ ] Блок «Ваш менеджер» показывает активного менеджера организации; «Написать» открывает переписку.
- [ ] Обращение с ответом сотрудника показывает текст ответа клиенту и партнёру; письмо-уведомление содержит ответ.
- [ ] «Финансы → Счета» показывает счета с признаком оплаты, совпадающим с карточкой заказа; «к оплате» = сумма неоплаченных; экспорт финансов включает счета.
- [ ] (`У-234`) Сообщение, отправленное из кабинета, видно менеджеру в диалоге; ответ менеджера виден в кабинете и в боте; заметки сотрудников не видны.
- [ ] (`У-236`) При включённой настройке `member` не видит чужой заказ (404), `admin` видит все; тест IDOR.
- [ ] Все экраны проходят три вопроса и 390×844; зеркало с партнёром соблюдено или исключение записано (`У-241`).

## 14. Риски и edge cases

- У организации несколько менеджеров → показываем первого активного и «и ещё N» без контактов остальных.
- Пользователь состоит в двух организациях → «Первые шаги» и «Ваш менеджер» по текущей организации контекста (`orgPageContext.ts`).
- Ответ на обращение после `converted` — допустим (не меняет статус).
- Диалог канала `cabinet` у пользователя без организации — невозможен: пользователь заказчика всегда в организации.
