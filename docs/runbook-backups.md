# Runbook — резервное копирование и восстановление (R0.5)

**Owner**: ops / тех.лид Промтехносфера
**Scope**: что бэкапится, кем, как часто; как проверяется восстановление; RPO/RTO.
**Контекст**: хранение данных — бессрочное (ТЗ §16), потеря невосполнима. PostgreSQL — managed (бэкапы делает провайдер, но это **обязан проверить оператор**), S3 — внешний бакет `documents`, VM держит только Redis (очереди) и сертификаты Caddy.

---

## 1. Матрица «что бэкапим»

| Данные | Где живут | Механизм | Частота | Retention | RPO | Восстановление (RTO) |
|---|---|---|---|---|---|---|
| **PostgreSQL `cabinet`** (вся доменная БД) | Managed-PG провайдера | **Автобэкапы провайдера** (включить при провижне!) + PITR, если тариф даёт | daily (минимум) | ≥ 7 дней (рекоменд. 14) | ≤ 24 ч (с PITR — минуты) | restore в новую managed-БД + переключить `DATABASE_URL` (≈ 1–2 ч) |
| PostgreSQL — **логический дамп** (belt-and-suspenders: защита от аккаунт-/провайдер-инцидента) | Снимается с VM | [`scripts/backup/pg-dump.sh`](../scripts/backup/pg-dump.sh) (pg_dump через docker + gzip + опц. шифрование + ротация) | daily (cron на VM) | 14 дней локально; ≥ 4 недельных — во **второй** независимый бакет | ≤ 24 ч | `scripts/backup/restore-check.sh` тем же дампом (≈ 30–60 мин) |
| **S3 `documents`** (сканы, удостоверения, вложения) | Бакет провайдера | **Versioning на бакете** (защита от удаления/перезаписи) + lifecycle на noncurrent (30–90 дн). Против потери бакета/аккаунта — периодический `rclone sync` во второй бакет (другой аккаунт/провайдер) | versioning — постоянно; rclone — weekly | noncurrent 30–90 дн | ≤ 7 дн (rclone) / ~0 (versioning) | откат версии — минуты; rclone-копия — часы |
| Redis (очереди BullMQ) | VM, том `redisdata` (AOF) | НЕ бэкапится — **принятый риск**: джобы восстановимы (reconcile 1С догоняет, уведомления пере-генерятся), потеря тома переживаема | — | — | — | пересоздание тома, очереди наполнятся сами |
| Caddy-сертификаты | VM, том `caddy_data` | Снапшот VM-диска у провайдера (если включён) или принятый риск: потеря ⇒ повторный выпуск LE (лимит 5 серт/нед — окно риска до недели) | — | — | — | повторный ACME-выпуск |
| Конфигурация (`.env.production`) | VM | Копия в менеджере секретов владельца (НЕ в git) | при каждом изменении | — | 0 | восстановить из менеджера секретов |

## 2. Обязательные действия при провижне (дополняет runbook-prod-infra-rf §1)

- [ ] Managed-PG: **включить автобэкапы** (daily, retention ≥ 7 дней, PITR если доступен) и **убедиться в консоли, что первый бэкап реально создан**.
- [ ] S3: включить **versioning** на бакете `documents` + lifecycle-правило на noncurrent versions (30–90 дней); включить **шифрование бакета по умолчанию** (SSE провайдера), бакет — **приватный** (анонимный GET по прямому URL объекта → 403).
- [ ] VM: добавить в crontab запуск `scripts/backup/pg-dump.sh` (пример в §3).

## 3. Логический дамп: установка на VM

```bash
# /etc/cron.d/lk-otsfera-backup (пример; пути подставить свои)
# daily 02:30 — дамп + ротация 14 дней; лог в journald через systemd-cat
30 2 * * * root cd /opt/lk-otsfera && ./scripts/backup/pg-dump.sh 2>&1 | systemd-cat -t lk-backup
```

Скрипт читает `DATABASE_URL` из `.env.production`, снимает `pg_dump -Fc` через контейнер `postgres:16-alpine` (на VM не нужен установленный PostgreSQL), жмёт gzip'ом, опционально шифрует (`BACKUP_ENCRYPT_PASSPHRASE`) и ротирует старше `BACKUP_KEEP_DAYS` (default 14). Выгрузка недельной копии во второй бакет — `rclone` (настройка remote — вне scope, см. комментарий в скрипте).

## 4. Проверка восстановления (restore-check) — ежеквартально и перед мажорным релизом

```bash
./scripts/backup/restore-check.sh /var/backups/lk-otsfera/<файл>.dump.gz
```

Скрипт: поднимает одноразовый Postgres-контейнер → `pg_restore` дампа → smoke:
1) `prisma migrate status`-эквивалент: таблица `_prisma_migrations` непуста и без failed-строк;
2) ключевые таблицы непусты (`User`, `Company`, `Order`, `Document`, `Payment`);
3) контрольная сумма: количество строк `Order`/`Payment` печатается для сверки с прод-числами.
Успех = вывод `RESTORE CHECK: OK`. Контейнер удаляется автоматически.

Результат проверки фиксируется (дата, кто проводил, номер дампа) — в журнале владельца.

## 5. RPO / RTO (целевые)

- **RPO**: ≤ 24 ч штатно (daily); при включённом PITR у провайдера — минуты.
- **RTO**: БД ≤ 2 ч (restore у провайдера + переключение `DATABASE_URL` + `docker compose up -d`); файлы — от минут (versioning) до часов (rclone-копия).
- Ответственный: владелец/тех.лид; проверка восстановления — ежеквартально (§4).

## 6. Явно принятые риски

- Redis/BullMQ — не бэкапится (см. §1, обоснование там же).
- `caddy_data` — при отсутствии VM-снапшотов потеря ведёт к окну до недели на повторный выпуск сертификата (LE rate-limit).
- Логический дамп на самой VM гибнет вместе с VM — поэтому обязательна недельная копия во второй бакет (§3).
