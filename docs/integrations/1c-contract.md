## Цель

Документ фиксирует требования к API/интерфейсу 1С со стороны кабинета. Без согласования и реализации со стороны IT 1С Фаза 3 (включение реального 1С) невозможна.

## Запрашиваемые операции

### 1. GET Organizations (Контрагенты)

`GET /api/organizations?since=ISO_TS`

Возвращает контрагентов, у которых дата последнего изменения > `since`.

Response (JSON массив):
```json
[{
  "externalId": "string (GUID или внутр. ID 1С)",
  "name": "ООО Завод",
  "legalName": "Общество с ограниченной ответственностью «Завод»",
  "inn": "770000",
  "kpp": "770001",
  "ogrn": "1027700123456",
  "legalAddress": "101000, г. Москва, ул. Промышленная, д. 12",
  "bankName": "ПАО «Сбербанк»",
  "bankAccount": "40702810400000012345",
  "corrAccount": "30101810400000000225",
  "bic": "044525225",
  "signerName": "Смирнов Алексей Петрович",
  "signerPosition": "Генеральный директор",
  "signerBasis": "Устава",
  "partnerExternalId": "string (= slug партнёра в кабинете, см. «Ключ партнёра»)",
  "updatedAt": "2026-05-01T10:00:00Z"
}]
```

> **Примечания (сверено с кодом):**
> - `partnerExternalId` матчится по `Partner.slug` ([sync-organizations.ts:18](../../src/worker/processors/sync-organizations.ts)) — см. раздел [«Ключ партнёра»](#ключ-партнёра-q5). Не совпало → орг сохраняется, но без привязки к партнёру (skip `partner_not_found` в `SyncLog`).
> - **Реквизиты контрагента (этап 8, `У-171`, `Д-23`).** `legalName`, `kpp`,
>   `ogrn`, `legalAddress`, банковские `bankName` / `bankAccount` /
>   `corrAccount` / `bic` и подписант `signerName` / `signerPosition` /
>   `signerBasis` — необязательные строки; они ложатся в карточку
>   организации, откуда кабинет берёт реквизиты для счёта, акта и договора
>   (§6). Правило одно на все поля, включая `inn` и `kpp`: **пустое из 1С
>   (`""`, пробелы, поле отсутствует) не перезаписывает заполненное в
>   кабинете** — иначе первый же обмен стёр бы адрес, вписанный менеджером
>   руками. Непустое значение заменяет. При первом появлении контрагента
>   реквизиты записываются как есть. Ранее `legalName` принимался, но не
>   сохранялся — это и был дефект `Д-23`.

  "organizationExternalId": "...",
  "totalAmount": 250000,

> **Статусы (Q10) — РЕШЕНО (T2, контракт наш).** `executionStatus ∈ {pending, in_progress, completed, cancelled, on_hold}`; `financialStatus ∈ {not_billed, billed, partially_paid, paid, refunded}`. **Кабинет применяет маппинг сам:** 1С может слать родные русские стадии («Оплачено», «Выполнен») — REST-адаптер переводит их в эти коды через `translate.ts` (`normalizeOrderRecord` в [rest-wire.ts](../../src/lib/services/oneCSync/rest-wire.ts)), на паритете с Excel-адаптером. Уже-внутренние коды проходят как есть; нераспознанное значение → карантин (`invalid`) с видимым отчётом.

### 4. GET Documents (Файлы по сделкам)

`GET /api/documents?since=ISO_TS`

```json
[{
  "externalId": "...",
  "orderExternalId": "...",
  "type": "contract|extra_agreement|invoice|act|waybill|certificate|report|other",
  "direction": "incoming|outgoing",
  "number": "245",
  "name": "Договор 245.pdf",
  "mimeType": "application/pdf",
  "size": 248000,
  "signedAt": "2026-04-12T10:00:00Z",
  "downloadUrl": "https://1c.example.com/files/abc123",
  "updatedAt": "2026-04-12T10:00:00Z"
}]
```

> **`direction` и `number` (этап 8, `У-170`, `Д-24`/`Д-25`).** `direction` —
> кто выпустил бумагу: `incoming` — 1С (умолчание, если поле не пришло),
> `outgoing` — кабинет выгрузил её в 1С (§8), и 1С вернула, например,
> подписанной. `number` — номер документа в 1С; необязателен. Кабинет ищет
> уже известный документ по **трём ключам по порядку**: `externalId` →
> `oneCExternalId` (id, под которым 1С приняла нашу выгрузку) → `type` +
> `number` в пределах заказа; найденный **обновляется** (подпись, файл,
> статус «принят» при `signedAt`), а не создаётся заново.

`downloadUrl` должен:
- Быть подписанным (signed URL с TTL ≥ 5 мин), либо
- Использовать Bearer-токен в Authorization header.

> **`type` (сверено).** Inbound-набор: `contract, extra_agreement, invoice, act, waybill, certificate, report, other` (8 значений). Prisma-enum `DocumentType` содержит ещё `commission_statement`, но это **внутренний** документ кабинета (генерится сам, 1С его не присылает) — намеренно вне inbound-схемы. Неизвестный `type` → карантин записи.

### 6. POST Documents (выгрузка документов кабинета в 1С)

`POST /api/documents` — **тот же путь, что у входящего `GET` (секция 4), другой метод.** В коде кабинета это отдельный ключ `documentPush` в `ENDPOINTS` ([rest-wire.ts](../../src/lib/services/oneCSync/rest-wire.ts)): маршрут один, а операции разные, и путать их в настройках нельзя.

Кабинет отдаёт в 1С **только четыре типа**: `invoice` (счёт), `act` (акт), `contract` (договор), `extra_agreement` (дополнительное соглашение). **Коммерческое предложение (`commercial_proposal`) не выгружается никогда** — это предпродажный документ, в бухгалтерии ему делать нечего (решение заказчика `Р-14`). Прочие типы (`waybill`, `certificate`, `report`, `commission_statement`, `other`) контрактом не описаны и не отправляются.

```json
{
  "externalId": "cuid-первой-версии-документа",
  "type": "invoice|act|contract|extra_agreement",
  "number": "С-2026-17",
  "date": "2026-09-03T09:15:00Z",
  "version": 1,
  "counterparty": {
    "inn": "7701234567",
    "kpp": "770101001",
    "name": "ООО Ромашка",
    "legalName": "Общество с ограниченной ответственностью «Ромашка»"
  },
  "order": { "externalId": "1c-order-guid", "orderNumber": "З-245" },
  "parentDocument": { "externalId": "cuid-счёта", "number": "С-2026-17" },
  "lines": [{
    "title": "Обучение по охране труда, 40 ч",
    "quantity": 3,
    "unit": "чел",
    "price": 5000.00,
    "vatRate": 0.2,
    "vatAmount": 3000.00,
    "amount": 18000.00
  }],
  "totals": { "net": 15000.00, "vat": 3000.00, "gross": 18000.00 },
  "fileUrl": "https://s3.example.com/documents/...?X-Amz-Signature=..."
}
```

Response (`200`/`201`):
```json
{ "externalId": "1c-doc-guid" }
```

Поля и правила:

- **`externalId` — идентификатор документа в кабинете, и это `id` ПЕРВОЙ версии.** Перевыпуск документа (`У-151`) создаёт в кабинете новую строку с тем же номером и `version + 1`; в 1С она уезжает под **тем же `externalId`** с большей `version`. Так перевыпуск для 1С — обновление существующего документа, а не второй экземпляр. 1С хранит `externalId` и по нему же отвечает на сверку (секция 7).
- **`version`** — номер перевыпуска, начиная с `1`. Растёт монотонно; одна и та же версия никогда не меняется по содержанию.
- **`date`** — дата выпуска документа в кабинете, ISO-8601 с зоной (правило Q7).
- **`counterparty`** — реквизиты клиента на момент выгрузки: `inn`, `kpp`, `name` (короткое), `legalName` (полное). `kpp` и `legalName` могут быть `null`, если в кабинете не заполнены.
- **`order`** — заказ, по которому выпущен документ: `externalId` заказа в 1С (тот, что 1С сама отдаёт в секции 2) и номер заказа в кабинете. **`null`** — у документа без заказа (выпуск «без заказа», `У-145`). **`order.externalId: null`** при заполненном `orderNumber` — заказ заведён в кабинете и в 1С ещё не бывал (`Order.externalId` в кабинете пуст): 1С сопоставляет такой заказ по номеру или заводит новый на своей стороне.
- **`parentDocument`** — родитель по связи «акт → счёт», «ДС → договор» (`У-147`): `externalId` первой версии родителя и его номер. **`null`**, если родителя нет.
- **`lines`** — табличная часть (`У-146`): наименование, количество, единица, цена без НДС, ставка НДС (доля: `0.2` = 20 %, `null` — не облагается), сумма НДС, сумма с НДС. **`null` — у документов, выпущенных до этапа 6:** у них состава нет, и выдумывать его задним числом кабинет не будет. 1С принимает такой документ без строк.
- **`totals`** — итоги `net` (без НДС), `vat`, `gross` (с НДС). **`null` вместе с `lines`** у тех же legacy-документов.
- **`fileUrl`** — подписанная ссылка на PDF в хранилище кабинета. **Живёт 1 час** (у обычной ссылки на скачивание — 10 минут: человек нажимает «Скачать» сразу, а 1С забирает файл своим расписанием). При каждой повторной отправке ссылка выписывается заново. Вечных ссылок нет: внутри файла цены и реквизиты.
- **Ответ** — `externalId` документа в 1С. Кабинет сохраняет его в `Document.oneCExternalId` и дальше сверяется по нему.

Ошибки 1С (`4xx`/`5xx`, таймаут) кабинет считает неуспехом попытки: документ получает состояние `failed` с текстом ошибки, задача повторяется по расписанию очереди (BullMQ, 5 попыток с экспоненциальной паузой), человек видит ошибку на карточке документа и может нажать «Повторить» (`У-169`, `У-174`).

Повтор на уровне HTTP-клиента (внутри одной попытки задачи) делается только для `429`/`502`/`503`/`504` и сетевых ошибок; `400` (тело не по контракту) и `409` (версия ниже принятой, см. «Идемпотентность») возвращаются сразу — повторять их бессмысленно, тело от повтора не изменится.

### 7. GET Documents по `externalId` (сверка)

`GET /api/documents?externalId=<externalId кабинета>`

Ответ — **массив в формате секции 4**: пустой `[]`, если документа с таким `externalId` в 1С нет, иначе ровно один элемент. Кабинет использует это раз в сутки (`У-172`): каждый документ в состоянии `pushed` спрашивается по одному; отсутствующий переводится в `failed` с причиной `missing_in_1c` и попадает в алерты. Запросов немного (только действующие версии выгруженных документов), поэтому пакетного метода в контракте нет — по умолчанию §6 спеки этапа 8; если объём вырастет, пакетный метод — отдельный разговор с IT 1С.

Уточнения по реализации (PR-8):

- `externalId` в запросе — тот же, что был в `POST` секции 6: **id первой версии цепочки перевыпусков**. Перевыпущенный документ 1С хранит под исходным `externalId` (см. «Идемпотентность»), поэтому кабинет спрашивает именно его; заменённые версии (`supersededAt` заполнен) не спрашиваются.
- **Пустой массив значит «в 1С нет»** и только он. Сетевая ошибка, таймаут, `5xx` — не ответ «нет»: кабинет прерывает сверку на этом документе, ничего не помечает и пишет одну строку ошибки в «Историю» обмена. Если 1С хочет сказать «документа нет» — она обязана ответить `200 []`, а не `404`.
- В найденном элементе 1С отдаёт `direction: "outgoing"` и свой `externalId` (тот, что вернула при выгрузке); кабинету из ответа нужен только факт наличия.

## Ключ партнёра (Q5)

**Текущее состояние кода (сверено 2026-06-06):** общий ключ партнёра между 1С и кабинетом — это **`Partner.slug`** кабинета. Колонки `Partner.externalId` в схеме нет.

| Направление | Поле в JSON | Как используется в коде |
|---|---|---|
| inbound (Organizations/Orders) | `partnerExternalId` | `findUnique({ where: { slug: partnerExternalId } })` — трактуется как slug |
| outbound (POST Lead) | `partnerSlug` | `lead.partner.slug` |

**РЕШЕНО (T2, контракт наш) — вариант (A): `Partner.slug` остаётся общим ключом.** Миграции нет. 1С хранит slug каждого партнёра и эхо-ит его (inbound `partnerExternalId`, outbound `partnerSlug` — оба = slug). Операционно: slug'и заводятся в 1С и держатся стабильными. Вариант (B) (GUID `Partner.externalId` + миграция) — только если 1С физически не сможет слать slug; откладываем до фактической необходимости.

## Форматы и конвенции (Q1/Q6/Q7)

- **Конверт ответа (Q1).** Кабинет принимает либо голый JSON-массив, либо `{ "items": [...] }` (`unwrapEnvelope`). Иной конверт → ошибка job'а → BullMQ retry.
- **Datetime (Q7).** Все timestamp'ы — **с явным offset/`Z`** (UTC ISO-8601 `2026-05-29T10:00:00Z` или `+03:00`). ⚠️ Строка без зоны (`2026-05-29 10:00:00`) парсится `Date.parse` как **локальное время сервера** → молчаливый сдвиг. Если 1С отдаёт МСК без суффикса — зафиксировать, A2 нормализует.
- **Полнота / пагинация (Q6) — РЕШЕНО (T2).** Контракт наш: ответ — голый массив (одна полная страница) ИЛИ `{ items, nextCursor }`. Когда `nextCursor` присутствует, есть ещё страницы, и кабинет запрашивает следующую через `?cursor=<nextCursor>` (курсор непрозрачный, кабинет лишь эхо-ит его). Адаптер исчерпывает страницы за один pull ([adapter-rest.ts](../../src/lib/services/oneCSync/adapter-rest.ts) `getArray`); 1С-сторона ДОЛЖНА следовать этому формату при пагинации. Mock умеет (`MOCK1C_PAGE_SIZE>0`).

## Идемпотентность

**Pull (inbound).** Кабинет может повторно запрашивать тот же `since` (например, после рестарта или в пределах safety-overlap инкрементального курсора). 1С должна возвращать стабильные `externalId` — повторные запросы не должны порождать «дубли с другим ID».

**Push (outbound documents, секция 6).** Ключ идемпотентности — пара **`externalId` + `version`**. Повторный `POST /api/documents` с той же парой — **no-op**: 1С ничего не меняет и возвращает тот же `externalId` документа 1С, что и в первый раз. Та же `externalId` с **большей** `version` — **обновление** существующего документа (новый файл, строки, итоги), а не второй экземпляр. Меньшая `version`, чем уже принятая, — ошибка `409`. Кабинет со своей стороны тоже не шлёт одну версию дважды (сравнивает `oneCPushedVersion` с текущей версией перед каждой отправкой, в том числе в самом обработчике очереди — очередь умеет доставить задачу дважды), но окончательная защита от дубля — на стороне 1С, как и у заявок.

**Push (outbound leads).** 1С **обязана дедуплицировать заявки по `cabinetLeadId`**: повторный `POST /api/leads` с тем же `cabinetLeadId` не должен создавать второй объект — возвращается результат исходного приёма (тот же `oneCRequestId`). Это контрактная гарантия: кабинет ретраит push при сбоях сети/таймаутах (BullMQ + request-level retry), поэтому один и тот же `cabinetLeadId` может прийти более одного раза. На стороне кабинета есть быстрый guard (`Lead.pushedToOneCAt`), но он не покрывает гонку «push прошёл — запись в БД упала», поэтому окончательная защита от дубля — на стороне 1С.

## Расписание запросов

Кабинет будет опрашивать с частотой:
- Orders: каждые 15 мин
- Payments: каждые 15 мин
- Documents: каждый час
- Organizations: каждые 6 часов
- Reconcile (полный с last 30 дней): раз в сутки в 03:00
- Сверка выгруженных документов (секция 7, `GET ?externalId=` по одному): раз в сутки, вместе с reconcile
- Выгрузка документов (секция 6, `POST`): по событию — при выпуске документа (если у компании включено «автоматически») или по кнопке сотрудника; не по расписанию

Если 1С может **push-ить webhook** — фиксируем endpoint:
`POST {cabinet_url}/api/integrations/1c/webhook`
- Auth: HMAC-signature header `X-1C-Signature` (SHA-256 от body с shared secret)
