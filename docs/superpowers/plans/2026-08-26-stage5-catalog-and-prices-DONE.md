## Ключевые решения

- **Снимок цены (`Р-13`)**: цена в строке заказа фиксируется при добавлении;
  правка каталога уже выставленные строки не трогает. Инвариант
  `invariants.price-snapshot` переписан под это — как велит само ТЗ.
- **`vatIncluded` меняет направление расчёта**, а не подпись: налог либо
  выделяется из суммы, либо начисляется сверху. Итоги складывают построчные
  округления — таблица и итог сходятся до копейки.
- **Порядок PR соблюдён**: колонка `OrderItem.amount` удалена последней и
  только после того, как PR-4 снял последнее чтение (мёртвая ветка
  попозиционного счёта в генераторе документов — её нашло ревью).
- Изображения оформления: PNG по канонической сигнатуре, SVG с фильтром
  содержимого, антивирус новой целью `company_branding`, presigned с
  `attachment`.

## Уроки (полные версии — в плане, по PR)

1. **Ревью находит то, чего не видят зелёные тесты.** Четыре PR из пяти
   прошли адверсариальное ревью; в каждом нашлись настоящие дефекты, включая
   два обхода фильтра SVG (второй — уже в моей первой починке) и тупик
   «ручная сумма без строк».
2. **Тест может закрепить дефект как фичу.** В PR-4 тест агента утверждал,
   что удаление последней строки НЕ обнуляет сумму, — переписан под
   требование. Зелёный прогон не отвечает на вопрос «то ли закреплено».
3. **Агент, упавший посреди мутации, оставляет дыру.** В PR-3 из боевого
   роута исчез гард права раздела при зелёных тестах. Правило: мутация и
   откат — один неделимый шаг.
4. **API-роуты раздела хаба не защищены `requireSettingsSection`** — право
   там проверяется руками, иначе `default-deny` профиль обходится (найдено
   трижды за этап).
5. **Комментарий, обещающий защиту, — не защита.** В PR-3 обещанный
   `Content-Disposition: attachment` в коде отсутствовал.
