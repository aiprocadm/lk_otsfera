## Решения, закреплённые в коде

1. **Скрипт — `.ts`, а не `.mjs`** (отклонение от буквы ТЗ, подтверждено
   заказчиком). Причина в самом файле: из `.mjs` нельзя импортировать боевую
   `column-map.ts`, а её копия в скрипте разъехалась бы с оригиналом — то есть
   инструмент врал бы ровно там, ради чего написан.
2. **Диагностика возвращается и в ветке ошибки.** Тип результата стал
   `{ ok: false; error; diagnostics? }`. Без этого блок «что увидела система» не
   показывался бы в главном сценарии — когда не распозналось ничего.
3. **`diagnostics()` — только у файлового адаптера**, в интерфейс `OneCAdapter`
   не добавлен: у сетевого адаптера листов книги нет, требовать от него заглушку
   значит врать в типах.
4. **Сравнение заголовков осталось точным.** Нормализация («ё/е», неразрывный
   пробел, регистр) — это Т-8 этапа 3; здесь она была бы преждевременной, и
   тест `import.diagnostics.unit` фиксирует текущее поведение явно, чтобы
   переход было видно по диффу.
5. **Форма терпит ответ без диагностики** (`?? null`) — страховка на время
   раскатки, когда новый интерфейс уже у пользователя, а сервер ещё старый.

## Проверки

- `npm run typecheck` (два проекта), `npm run lint` (0 предупреждений),
  `npx prettier --check .` — зелёные.
- Полный `npm run test:unit` — зелёный (см. журнал STATUS.md).
- Адресное покрытие изменённых файлов (`diagnostics.ts`, `parse-workbook.ts`,
  `import/index.ts`, `adapter-file.ts`, `import-form.tsx`): **100% по всем
  четырём метрикам** (469/469 строк, 158/158 ветвей, 26/26 функций).
- Скрипт проверен вручную на двух собранных книгах: «правильной» (все три листа
  по карте — распознаёт, показывает лишний заголовок «КПП» и недостающие
  колонки) и «кривой» (лист «Реализация товаров и услуг» — честно говорит, что
  ни один ожидаемый лист не найден, и подсказывает, что это чинит этап 3).
  Временные файлы в репозиторий не клались.

## Что этап НЕ делает (следующие этапы)

Организации из файла по-прежнему не создаются (этап 5), формы по-прежнему молчат
при сетевом сбое (Т-4, этап 2), лимит размера всё ещё рассинхронизирован
(Т-5, этап 2), имена листов сверяются точно (этап 3). Этап давал **видимую
причину**, а не починку — как и записано в ТЗ.

## Для заказчика

Прогоните свой файл: `npm run inspect:1c -- <путь к файлу>` — и пришлите вывод.
По нему этап 3 правит карту листов и колонок; без реального файла делать его
нельзя (§6 ТЗ).
