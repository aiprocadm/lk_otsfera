## Проверка перед удалением (главное)

Колонку `Order.status` удаляем только после того, как убедились, что её никто
не читает:

| Кандидат | Факт |
|---|---|
| Обмен с 1С | **не читает** — в `oneCSync/*` поле `status` относится к журналу синхронизации, а не к заявке |
| Уведомления | шлёт `manager/status.ts` по `executionStatus` |
| Выгрузки xlsx | печатают `executionStatus` |
| Интерфейс | с PR-3 работает со справочником (`statusId`) |
| `transitionOrderLifecycle` | единственный настоящий читатель — **удалён в этом же PR** |

## Найдено по ходу

- **Проверка «кто читает» окупилась.** По названию казалось, что на
  `Order.status` завязан обмен с 1С; на деле совпадало только имя поля в
  журнале синхронизации. Без этой проверки удаление выглядело бы опасным и
  откладывалось бы дальше.
- **Удаление тестов легко уносит с собой чужое покрытие.** Файл
  `services.manager.orderLifecycle.unit.test.ts` покрывал и переходы, и отметку
  бухгалтерии; удалив его целиком, я оставил живую функцию без тестов — поймано
  адресным прогоном покрытия, а не гейтом.
