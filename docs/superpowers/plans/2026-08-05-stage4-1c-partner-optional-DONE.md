## Отгружено

| Требование | Состояние |
|---|---|
| **Т-19** партнёр необязателен | ✅ пусто → прямой клиент (`partnerId: null`); найден → привязка; не найден → `partner_not_found`. Код `no_partner_external_id` удалён полностью |
| **Т-19а** партнёр ↔ много организаций | ✅ закреплено integration-тестом (две строки с одним ИНН → две организации, один `partnerId`) |
| **Т-20** поиск по ИНН | ✅ `findFirst({ OR: [{ inn: normalizeInn(raw) }, { slug: raw }] })` |

Изменений схемы БД нет, миграций нет; правка одна — ветка партнёра в
`upsertOrgRecord` + новая `normalizeInn` (`oneCSync/inn.ts`).

## Решения, закреплённые в коде

1. **OR с прежним `slug` обязателен**: сетевой `adapter-rest` присылает в
   `partnerExternalId` настоящий slug — поиск только по ИНН сломал бы работающую
   сетевую синхронизацию. `Partner.inn @unique` — коллизий OR не даёт.
2. **`normalizeInn` — минимум этапа 4** (все пробельные символы, включая
   неразрывные). Этап 5 (Т-22) расширит эту же функцию (число→строка, ведущие
   нули) — Т-20 требует «тот же код», точка правды одна.
3. **Ветка обновления существующей организации партнёра не трогает** — импорт
   не перевешивает клиента между партнёрами молча (как и раньше).
4. **Честная оговорка §0.2**: до этапа 6 создание организации по сети
   продолжает минтить `Company`; этап 4 расширяет это на бес-партнёрные
   организации сетевого обмена. Порядок утверждён ТЗ; на проде `ONE_C_ADAPTER`
   по умолчанию `fake`. Отражено в CHANGELOG (требование сноски Т-19).
