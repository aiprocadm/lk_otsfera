## Задачи

### 1. Схема (аддитивная миграция)

- [x] `Order.resultDeliveredAt` + `resultDeliveredById` — момент и автор передачи.
- [x] `Order.deliverablesApprovedAt` + `deliverablesApprovedById` — отметка
      «работа согласована» (решение заказчика §6-2).

### 2. Готовность (ФТ-5.1)

- [x] `lib/orders/readiness.ts` — чистая функция `evaluateOrderReadiness`:
      обучение → попозиционно (обучение завершено · удостоверение создано ·
      скан загружен); разработка документов → исходящие документы **и** отметка
      согласования. RU-подписи для UI рядом.
- [x] Существующий `evaluateOrderCompletion` не тронут: новая проверка
      дополняет, а не заменяет (ТЗ называет её основой).

### 3. Передача (ФТ-5.2)

- [x] `services/manager/orderDelivery.ts`: `getOrderReadiness`,
      `approveDeliverables`, `deliverOrderResult`.
- [x] Скоуп — обычный `canSeeOrder` (C8): любой менеджер в скоупе (решение §6-1).
- [x] Идемпотентность (решение §6-3): повтор — no-op, второго уведомления нет.
- [x] Уведомление `order_result_delivered` организации (in-app + письмо на
      универсальном шаблоне), аудит `order_result_delivered`.
- [x] Fan-out best-effort: сбой доставки не откатывает передачу (§3).

### 4. UI

- [x] `OrderReadinessPanel`: показывает ЧЕГО не хватает и по какому слушателю;
      кнопка активна только при готовности; после передачи — дата и пояснение.
- [x] Кнопка «Отметить работу согласованной» — только для `document_development`.
- [x] Встроена в деталку заказа менеджера тем же приёмом, что панель генерации
      документов (страница собирает панель, view её рендерит).

### 5. Клиентский статус (ФТ-5.4)

- [x] `orderStage` получил финальную точку «Результат передан»; отменённый
      заказ по-прежнему важнее (передавать там нечего).
