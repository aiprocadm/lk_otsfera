## Требования §10 — построчная сверка

| Требование | Как закрыто |
|---|---|
| Семь рабочих статусов | сид миграции; названия ровно из ТЗ |
| «Отменена» — терминальный, с любой стадии | флаг `isTerminal`, в порядок не входит |
| Добавление, переименование, порядок, деактивация | экран настройки (PR-2) |
| Настраивают администратор и руководитель | `requireFieldsAdmin` + зеркало `/leader/settings/order-statuses` |
| Использованный статус нельзя удалить физически | удаление только для неиспользованной несистемной строки |
| Хранить прежний/новый статус, дату, пользователя, причину | таблица `OrderStatusChange` + показ истории на карточке |
| Права: менеджер — обычный процесс, admin/leader — возврат и любой статус | сервис переходов + серверный расчёт кнопок |
| Финансовый статус отдельно | не тронут |
| Индивидуальный статус слушателя | не тронут |

## Решения заказчика и их следствия

1. **Q1 = вариант A.** Справочник заменил главный статус. Три пункта семёрки
   (оплата, документы, подпись) остались производными фактами и привязаны
   якорями: переименовать можно, оторвать от события — нет.
2. **Q2 = общий справочник.** `companyId` в модели остался заделом, всегда `null`.
3. **Q3 = `executionStatus` остаётся в базе.** Из интерфейса его пока не
   убирали — это отдельная правка (см. «Не вошло»).
4. **Q4 = менеджер отменяет с причиной**, поднимает из отмены только
   администратор или руководитель.
5. **Q5 = 4 PR** — выдержано.

## Отклонения от спеки

- **Уведомления и выгрузки переводить не понадобилось.** Спека относила их к
  PR-3; разведка показала, что письма `order_status_changed` и xlsx работают на
  оси `executionStatus`, а не на рабочем статусе §10.
- **Удаление старого кода уехало из PR-3 в PR-4.** За `transitionOrderLifecycle`
  тянулось ~800 строк чужих тестов; смешивать это с переездом карточки в одном
  ревью было бы неправильно.

## Что НЕ вошло (осознанно)

- **`executionStatus` остался видимым** на карточке (форма смены операционного
  статуса). Решение Q3 говорит «скрыть из интерфейса» — это отдельная правка UI,
  не входившая ни в один из четырёх PR. **Хвост, требующий решения заказчика:**
  скрывать сейчас или оставить до отдельной задачи.
- Пер-компанийные наборы статусов (задел `companyId`).
- Перевод старых аудит-записей `order_lifecycle_changed` в новый журнал —
  история до этапа 2 остаётся в аудите.

## Грабли этапа (для следующих программ)

1. **Составной unique с NULL не ловит дубли.** `(companyId, key)` при
   `companyId IS NULL` пропускал второй статус с тем же ключом — в Postgres два
   NULL не равны. Лечится частичным индексом; Prisma такие в схеме не выражает.
2. **Заглушки транзакций отстают от кода.** Добавили поле в `order.create` —
   восемь чужих тестов упали на `$transaction`-стабах.
3. **Удаление тестового файла уносит чужое покрытие.** Вместе с тестами
   переходов исчезли тесты отметки бухгалтерии; поймано адресным прогоном
   покрытия, а не гейтом.
4. **Жёсткие счётчики пунктов меню** ломаются от любого нового пункта — за
   программу правились трижды.
