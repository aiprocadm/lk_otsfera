## PR-1 «Тип и модель» — `У-161` (модель)

- [x] `commercial_proposal` в `enum DocumentType` — **отдельной** миграцией
      `20260901090000_stage7_proposal_type`. Вместе с остальным не получается:
      Postgres не разрешает использовать новое значение перечисления в той же
      транзакции, где оно заведено («unsafe use of new value of enum type»).
- [x] Контрагент документа становится **необязательным**, но с тремя
      ограничениями целостности в базе: заполнен «оба или никак»; пустой
      допустим **только у КП**; у КП без контрагента обязателен `leadId`.
- [x] `Document.leadId` и `Document.dealId` — новые необязательные связи.
- [x] `Document.validUntil` — срок действия КП (`У-162`).
- [x] `Document.rejectedAt` и `rejectReason` — отказ клиента отдельно от
      аннулирования сотрудником (`У-164`).
- [x] `DocumentLine.vatIncluded` — иначе перенос строк в заказ (`У-164`)
      разошёлся бы с суммой КП ровно на ставку налога.
- [x] `Company.proposalValidDays` со значением 14 (`У-162`).
- [x] Чинится унаследованная опечатка: ключ `commercial_offer` в справочнике
      имён файлов заменяется на существующий тип.
- [x] Три страницы с исчерпывающей картой типов документа получают «КП»;
      фильтры типов в кабинетах дописываются руками — они не типизированы
      исчерпывающе и промолчали бы.
- [x] Мутации: пустой контрагент у счёта · контрагент заполнен наполовину ·
      КП без контрагента и без лида · строка документа без признака НДС.

### Появилось по ходу PR-1 (плана не было, но без этого он неверен)

- [x] **Связь с лидом переставлена на `RESTRICT`** третьей миграцией
      `20260901110000_stage7_proposal_lead_restrict`. Задуманный `SET NULL`
      противоречит собственной третьей проверке: обнулив `leadId` у КП без
      контрагента, база тут же нарушает `Document_proposal_needs_lead`, и
      удаление лида падает с сообщением, по которому непонятно ничего.
      Обнаружено пробой на живой базе. Правка уже накаченной миграции
      запрещена (§2 CLAUDE.md) — исправление ушло отдельным файлом.
- [x] **Доступ к документу без контрагента описан явно** в
      [policy.ts](../../../src/lib/auth/policy.ts) и
      [customFields/access.ts](../../../src/lib/services/customFields/access.ts).
      Прежнее «нет контрагента — нет доступа» было безобидным, пока таких
      строк не существовало; теперь оно означало бы, что сотрудник не может
      скачать собственное предложение. Читают свои сотрудники своей компании.
      Проверка роли в этой ветке **несущая**: клиентские сессии тоже несут
      `companyId`.
- [x] Термин «Коммерческое предложение» заведён в
      [глоссарии](../../glossary.md) (§15 CLAUDE.md: новое слово интерфейса
      попадает в глоссарий тем же PR).
- [x] Мутации доведены до девяти: шесть на ограничения базы (включая
      `RESTRICT`, умолчание НДС и умолчание срока) и три на политику доступа.
      Умолчания колонок мутируются **в схеме**, а не в базе: Prisma
      подставляет их сама, и правка `DEFAULT` в Postgres страж не тревожит.


## PR-2 «Статусы КП» — `У-164` (статусы)

- [x] `PROPOSAL_FLOW` — **отдельный** поток, а не ссылка на `ISSUED_FLOW`:
      `draft → sent`, `sent → accepted | rejected | expired | cancelled`,
      конечные пустые. У КП три отличия от общего потока (рождается
      черновиком; отклонить и дать истечь можно только отправленное; отказ и
      истечение необратимы), и общий поток пришлось бы обвешать оговоркой
      «кроме КП» в каждой строке — а разъезжаются именно оговорки.
- [x] `issued` у КП недостижим с ОБЕИХ сторон: попасть в него неоткуда и уйти
      некуда. Состояние, куда нельзя попасть, но откуда можно уйти, — ловушка
      для будущей правки.
- [x] `commercial_proposal` в `LIFECYCLE_TYPES` — вместе с ним КП получает
      право уходить письмом и панель статуса.
- [x] **Правило «откуда можно отправить» выведено из матрицы**, а не записано
      вторым списком, и переехало в `statusMatrix.ts`: его спрашивают и сервис
      (пускать ли), и экран (рисовать ли кнопку). Прежний литерал
      `['issued','sent','accepted']` жил в двух местах и прятал бы кнопку у
      КП-черновика, хотя сервис отправку разрешает.
- [x] **«Первая отправка» определяется матрицей**, а не сравнением с `issued`.
      Прежнее условие сочло бы первую отправку КП повторной: документ остался
      бы черновиком навсегда, а заказчик — с бумагой, которой по системе не
      отправляли.
- [x] Страж статусов расширен на `updateMany`. Проверено сравнением: тот же
      обход старый страж пропускал, новый ловит.
- [x] Мутации: КП пускают в `issued` · черновик КП можно отклонить · отказ КП
      обратим · КП убран из `LIFECYCLE_TYPES` · отправка разрешена из любого
      статуса · «первая отправка» снова по `issued` · обход через `updateMany`.

## PR-3a «Тексты и печать КП» — `У-162`, `У-163`

- [x] Реестр слотов переименован: `contractTemplate.ts` → `documentTemplate.ts`
      вместе с типами и `resolveDocumentClauses`. Он перестал быть договорным
      ещё до КП — просто это не было видно по имени.
- [x] Два слота КП: «Вводный текст» и «Условия», со своими группами экрана.
      Номера пункта у них ПУСТЫЕ: у предложения нет нумерованных разделов, и
      выдуманный «1.1» делал бы вид, что это договор.
- [x] Своя подстановка `proposal.validUntil` — **дата**, а не кусок фразы, как
      `contract.term` у договора. Одна вместо другой напечатала бы «до
      15.09.2026» там, где ждут «один год», и наоборот.
- [x] Срок в «Условиях» **обязателен**: предложение без даты «до когда» — это
      прайс-лист. Сохранить текст без него нельзя.
- [x] `proposalDocumentPdf.ts` — отдельный печатный шаблон. Без банковских
      реквизитов (по КП не платят), без подписи заказчика (он ещё ничего не
      подписывает) и без печати (она создаёт видимость обязательства).
- [x] Абзацы КП печатаются **по ключу**, а не по номеру пункта: фильтр по
      префиксу номера не нашёл бы ничего и оставил бы письмо без единого
      слова — молча.
- [x] Срок печатается вёрсткой ОТДЕЛЬНОЙ строкой помимо текста «Условий»:
      менеджер вправе переписать условия своими словами и выкинуть дату.
      Формулировка строки нарочно не совпадает с текстом слота — иначе страж
      чистоты вёрстки не отличил бы подпись к значению от вернувшегося в код
      готового текста.
- [x] **Страж вёрстки стал двусторонним.** Он проверял ровно один файл печати
      и для нового типа молчал бы, оставаясь зелёным. Теперь слот проверяется
      в ТОМ файле, где печатается, есть проверка «текст не просочился в чужой
      файл» и смок «каждый тип знает свой файл печати».
- [x] Экран настроек и карточка раздела перестали говорить только про договор;
      у абзаца без номера подпись «Пункт  · …» с дырой заменена на название
      места печати.
- [x] Мутации: срок КП не обязателен · условия КП печатают срок договора ·
      абзац КП уехал в договор · вводный текст не печатается · срок пропал из
      вёрстки · текст слота вернулся в вёрстку.

## PR-3b «Выпуск КП» — `У-161`, `У-162`, `У-163`

- [x] `commercial_proposal` в `GenerateDocType`; свой префикс номера `КП` и
      **своя последовательность** `kind='proposal'`. Общий счётчик с договором
      разогнал бы номера договоров до сотен за квартал: предложений выставляют
      кратно больше. Исторических КП с номерами из общей последовательности
      нет — столкнуться не с чем, в отличие от акта (`У-151`).
- [x] **Начальный статус — `draft`**, а не `issued`. Отдельного пути выпуска не
      завели: номер, версия, снимок строк, компенсирующее удаление файла и
      аудит остаются общими, различается одно поле.
- [x] **Третья цель выпуска — лид** (`leadId`), взаимоисключимая с заказом и
      организацией. Лид разрешён ТОЛЬКО коммерческому предложению: иначе счёт
      можно было бы выставить клиенту без организации и без реквизитов, и он
      ушёл бы в никуда.
- [x] **Компания КП лида берётся из СЕССИИ** — первый и единственный такой
      случай в проекте (у лида компании-исполнителя в модели нет). Записано
      комментарием как исключение, потому что `issueScope.ts` гарантирует
      обратное для всех прочих путей. Сотруднику без компании отвечаем
      нехваткой реквизитов, а не «нет прав»: искать у себя недостающий доступ
      он будет напрасно.
- [x] **Лид, у которого уже есть организация, выпускает КАК ОРГАНИЗАЦИИ.**
      Иначе у одного клиента появились бы две нити бумаг: одна в карточке
      организации, вторая невидимая — на лиде.
- [x] Заказчик для проверок и печати у КП лида — **синтетический** блок с одним
      названием. Это вместо `PartyBlock | null`: почти весь код ниже хочет от
      заказчика ровно название, а необязательное поле обросло бы веткой «а если
      пусто» в каждом месте — причём молча, пропущенная давала бы не падение, а
      пустое место в бумаге.
- [x] Пятый набор проверки реквизитов: исполнителю — без банка, заказчику —
      только название. Именно набор, а не отключение проверки.
- [x] Контрагент пишется «оба поля или ни одного»; у КП лида проставляются
      `leadId` и `dealId`, а срок действия ложится **в поле** `validUntil`:
      считать «истекло» по напечатанным словам невозможно.
- [x] Файл КП лида кладётся под `leads/<id>/…`: `organizations/null/…` сделал
      бы разбор хранилища по префиксу бессмысленным.
- [x] Поиск «соседних» документов у КП лида идёт **по лиду**: `counterpartyId:
      null` в Prisma означает «IS NULL» и собрал бы предложения ВСЕХ лидов
      компании.
- [x] Черновик клиенту **не анонсируется письмом**: уведомление уезжает в
      момент отправки (`У-164`).
- [x] Тексты компании читаются и для КП — без этой строки компания правила бы
      их в настройках впустую.
- [x] **Страж «абзацы собираются одним вызовом» переформулирован.** Он считал
      вызовы `resolveDocumentClauses` и держался на том, что тип с текстами
      один; с приходом КП веток стало две, и счётчик покраснел, хотя инвариант
      цел. Инвариант на самом деле: сборка живёт в общем `renderDocument`, а
      предпросмотр и выпуск оба зовут ЕГО. Проверено обеими мутациями.
- [x] Мутации: КП выпускается выставленным · КП делит счётчик с договором ·
      черновик анонсируется письмом · счёт лиду разрешён · лид с организацией
      заводит вторую нить · контрагент заполняется наполовину · срок действия
      не пишется в поле · КП требует банк исполнителя · КП требует реквизиты
      заказчика.

## PR-4a «Дверь для КП» — `У-161`, `У-162`, `У-164`

**Почему PR-4 разделён.** Точек входа пять, и они лежат в разных частях кода.
Но главное — до этого PR выпуск КП был НЕДОСТИЖИМ из интерфейса вовсе: схема
входа не принимала ни тип `commercial_proposal`, ни цель-лид. Сначала дверь,
потом остальные входы в неё.

- [x] Схема входа: тип КП, поле `leadId`, правило «ровно одна цель из трёх».
      Прежнее `!!orderId !== !!organizationId` на трёх полях молча пропускало
      бы «все три сразу»: два `true` дают `false`, и третье поле не смотрят.
- [x] **Гейт лида переехал в `issueScope.ts`** — туда же, где гейт организации,
      и по той же причине: форма выпуска и сам выпуск обязаны спрашивать ОДНО
      правило. Заодно закрыта дыра: `loadLeadTarget` из PR-3b не звал
      `canSeeLead`, и менеджер с профилем «только свои» мог выпустить КП на
      чужого лида, зная лишь его идентификатор — имя и контакт чужого клиента
      напечатались бы в его бумаге.
- [x] То же и на карточке лида: `getManagerLead` охват профиля не проверял
      вовсе — чужой лид открывался прямым адресом вместе с телефоном и почтой.
- [x] Лид с закрытой судьбой (`rejected`, `promoted_to_order`) адресатом быть
      не может; лид, ставший сделкой, — может: сделка и есть место, где
      выставляют КП.
- [x] Панель формы для лида (`getLeadDocumentIssuePanel`) и её серверный экшен
      со своим гейтом. Тип панели тот же, что у организации: форма одна, и
      второй почти-такой-же тип заставил бы её ветвиться в каждом поле.
- [x] У лида с уже заведённой организацией форма целится в ОРГАНИЗАЦИЮ и
      говорит об этом: сервис подменяет цель молча, и форма обязана называть
      настоящего адресата.
- [x] Поля предложения в форме: «О чём предложение» и «Действительно до» с
      умолчанием `сегодня + Company.proposalValidDays`. Сервер отдаёт ЧИСЛО
      ДНЕЙ, дату собирает браузер: сервер живёт в UTC, и готовая дата
      разошлась бы на сутки у части страны.
- [x] **Умолчание срока продублировано в СЕРВИСЕ**: форма — удобство, а вход
      открыт и напрямую (тот же разбор у предпросмотра). Без этого по API
      выпускалось бы предложение с «действительно до —».
- [x] Свой текст успеха для КП: «Черновик предложения № … готов». Общий
      «Коммерческое предложение № … выпущен» неверен дважды — и род, и смысл:
      КП создаётся черновиком, а «выпущено» обещает, что клиент его уже видит.
- [x] `revalidatePath` разложен на три ветки по цели. Тернарник на две давал
      бы `/manager/organizations/undefined`.
- [x] Кнопка «Выставить КП» и блок «Коммерческие предложения» на карточке
      лида. Без списка кнопка вела бы в никуда: у лида нет ни организации, ни
      заказа, и выпущенную бумагу можно было бы найти только поиском по номеру.
- [x] `missingByType` собирается ЛИТЕРАЛОМ, а не циклом по списку видов:
      массив с `satisfies` гарантирует «каждый элемент валиден», но не «каждый
      вид на месте» — проверено, пропуск вида собирался без единой ошибки.
- [x] **КП по заказу запрещено в сервисе** (`proposal_needs_no_order`).
      Предложение делают ДО заказа; иначе у него появился бы контрагент заказа,
      и оно уехало бы в портфель партнёра вместе с ценами и скидками.

### Найдено критиком полноты и починено здесь же

- [x] **Черновик КП утекал бы клиенту.** Канальные выборки статус не смотрели
      вовсе — и не должны были: до КП черновиков не существовало. Первая же
      кнопка «Выставить КП» организации показала бы клиенту неотправленную
      бумагу с ценой, которую ему ещё не предлагали. Фильтр добавлен во все
      три канальных строителя и в гейт чтения (прямая ссылка и скачивание).
      План ставил это в PR-7 — на три PR позже, чем появлялась дыра.
- [x] Фильтр написан ТОЛЬКО про КП, а не «спрятать все черновики»: общий
      запрет молча прятал бы любой будущий тип со стадией черновика.
- [x] **Тип и состояние обязан присылать вызывающий гейта** — иначе каждый
      вызов ходил бы в базу второй раз. Обязанность вынесена в страж
      `security.document-read-fields.guardrail`, который сразу нашёл вызов,
      про который забыли (`server-actions/documents/reissue.ts`).
- [x] Заведён ПДн-контекст `proposal_issue_lead` (§12): в бумагу печатается
      имя контактного лица лида — персональные данные физлица, и карточку
      лида человек мог не открывать вовсе.

## PR-4b «Вход из сделки» — `У-161`, `У-164`, `У-166`

- [x] `Deal.leadId` доезжает до карточки доски: без него экран не мог решить,
      кому выставлять предложение у сделки без организации.
- [x] Блок «Документы» карточки сделки говорит РАЗНОЕ в трёх случаях: есть
      организация — весь набор; есть только лид — одно предложение (счёт
      клиенту без реквизитов выставлять не на что); нет ни того, ни другого —
      кнопки нет, но сказано, что сделать. Пустой блок без объяснения был бы
      дефектом приёмки (§15).
- [x] У сделки без организации открывается форма ЛИДА, а не «та же с пустой
      организацией»: у лида нет ни реквизитов, ни договоров-оснований.
- [x] **`Document.dealId` ставится и у КП организации.** Раньше связь
      появлялась только на пути через лид, а самый частый случай — клиент уже
      заведён, переговоры идут по сделке — оставлял её пустой, и блок
      предложений в карточке сделки (`У-166`, PR-8) оказался бы пустым.
- [x] Связь со сделкой приходит из формы, поэтому **сверяется на сервере**:
      сделка обязана быть своей компании и про того же клиента, что цель
      выпуска. Без проверки документ появился бы в карточке ЧУЖОЙ сделки —
      не утечка наружу, но чужая бумага с ценами в чужих переговорах.
- [x] Дефолтная стадия «Предложение» переименована в **«КП отправлено»**
      (`У-164`): стадия называется тем, что на ней произошло, а «Предложение»
      не отвечало на вопрос «в каком мы состоянии» — его могли ещё готовить.
- [x] Мутации: сделка не сверяется с компанией · сделка не сверяется с
      клиентом · связь со сделкой не пишется · кнопка КП у сделки с лидом
      убрана · объяснение «чего не хватает» убрано · форма лида не
      открывается с доски · стадия снова «Предложение» · `leadId` не доезжает
      до карточки.
