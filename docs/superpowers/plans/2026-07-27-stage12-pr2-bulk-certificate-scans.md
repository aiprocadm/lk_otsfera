# Этап 12 PR-2 — массовая загрузка сканов удостоверений (ФТ-5.3)

Дата: 2026-07-27 · Спека: [2026-07-27-stage12-order-readiness-delivery-design.md](../specs/2026-07-27-stage12-order-readiness-delivery-design.md)
(✅ подтверждена 27.07.2026, §3 «ФТ-5.3») · Ветка от `main` (§14 CLAUDE.md).

## Зачем

PR-1 ввёл чек-лист готовности: по каждой позиции обучения требуется
«скан удостоверения загружен» (`Certificate.documentId`). **Закрыть этот пункт
через UI сегодня нечем**: `documentId` проставляется только при создании
удостоверения через API, а диалог «Выдать удостоверение» его не передаёт.
PR-2 даёт менеджеру рабочий путь — загрузить пачку сканов на заказ и разложить
их по слушателям.

## Задачи

### 1. Сопоставление «файл → слушатель» (чистая функция)

- [x] `lib/orders/certificateScanMatch.ts`: нормализация имени файла (регистр,
      `ё→е`, разделители) и подбор позиции по ФИО слушателя.
- [x] Совпадение — **подсказка**, а не автопривязка (ТЗ: «с обязательным ручным
      подтверждением»): функция возвращает `suggestedItemId` + признак
      `ambiguous`, решение остаётся за менеджером в форме.
- [x] Без БД, юнит-тестируема.

### 2. Сервис `services/manager/certificateScans.ts`

- [x] `listCertificateScanTargets` — позиции заказа с ФИО, номером
      удостоверения и признаком «скан уже есть».
- [x] `uploadCertificateScans` — пачка `{ orderItemId, file }`:
      скоуп `canSeeOrder` (C8, как в `manager/uploads.ts`), позиция обязана
      принадлежать заказу и иметь удостоверение, файл проходит
      `persistUploadedDocument` (docType `certificate`, direction `outgoing`,
      контрагент — организация заказа), затем `Certificate.documentId`.
- [x] **Пофайловый результат**: сбой одного файла не отменяет остальные;
      ответ несёт список `{ fileName, ok } | { fileName, error }`.
- [x] Замена скана существующего удостоверения разрешена (перезагрузка
      испорченного файла) — старый `Document` остаётся в истории заказа.
- [x] Аудит `certificate_scan_attached` на каждое привязанное удостоверение
      (загрузка самого файла уже пишет `document_uploaded` в upload-core).

### 3. API-роут

- [x] `POST /api/manager/orders/[id]/certificate-scans` — multipart, тонкий
      (эталон `documents/[id]/upload`), маппинг кодов в статусы.

### 4. UI

- [x] `certificate-scans-panel.tsx`: выбор нескольких файлов, таблица
      «файл → слушатель» с предзаполненной подсказкой и явной пометкой
      «подсказка — проверьте», отправка, пофайловый итог.
- [x] Панель рендерится только для заказов `training` и встраивается в деталку
      тем же приёмом, что панели PR-1/этапа 8 (страница собирает — view рендерит).

### 5. Заражённый скан не закрывает чек-лист

- [x] Скан ClamAV асинхронный, поэтому «заражённый файл не привязывается»
      реализуется на стороне готовности: `evaluateOrderReadiness` получает
      `scanStatus` скана и при `infected` даёт новый пробел
      `certificate_scan_infected` («скан заражён — загрузите другой файл»).
- [x] `getOrderReadiness` дочитывает статусы сканов одним запросом
      (`Certificate.documentId` — не relation, отдельная выборка `Document`).
- [x] `pending` пробелом не считается: скан в полёте, скачивание клиенту всё
      равно закрыто 410 до вердикта.
