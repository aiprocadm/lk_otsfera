# Кабинет руководителя (шестой кабинет)

**Дата:** 2026-06-11
**Статус:** дизайн утверждён пользователем (brainstorming, выбран вариант А из двух макетов), ждёт plan
**Зависимость:** строится **после** [2026-06-11-ui-repair-design.md](2026-06-11-ui-repair-design.md) (нужен единый канон навигации и `homeFor()`).

## Контекст

Руководитель отдела продаж («начальник менеджеров») сегодня — невидимая надстройка над кабинетом менеджера: `User.managerRole='leader'` (C8) даёт ему страницу `/manager/team` и блок комиссии в `/manager/finance`, но обоих пунктов нет в реальном меню менеджера, своей главной у него нет, и после входа он неотличим от рядового менеджера. Пользователь видит руководителя как **полноценный шестой кабинет** (наряду с админом, менеджером, партнёром, организацией, студентом).

Рассматривались два варианта (макеты в visual companion): **А** — отдельный кабинет со своей главной; **Б** — усиленная надстройка внутри кабинета менеджера. Выбран **А**.

## Решения пользователя

- Отдельный кабинет с маршрутами `/leader/*` и своей главной «Сводка по команде».
- **«Играющий тренер»**: руководитель сохраняет доступ в обычный кабинет менеджера; в меню кабинета руководителя — переключатель «Мои заказы» → `/manager/dashboard`, в меню менеджера-руководителя — обратный пункт «Кабинет руководителя».
- Комиссия: видят **только партнёр (свою), руководитель, админ** — кабинет руководителя показывает комиссию, рядовой менеджер не видит её нигде.

## Доступ и безопасность (defense-in-depth, §4 CLAUDE.md)

1. **Middleware**: `protectedPrefixes` += `/leader` → пускает только `role=manager` (sub-роль в middleware не видна — это нормально, как с другими sub-ролями).
2. **Page/route**: каждый `/leader/*` page вызывает `requireManagerLeader()` (уже существует); рядовой менеджер → `/forbidden`.
3. **Service**: выборки — **company-wide всегда** (`{ companyId: session.companyId }`, `companyId=null` → deny-all sentinel), независимо от `managerTeamVisibility`. Инвариант C8 cross-company изоляции сохраняется и закрепляется тестом.

Admin в `/leader` **не входит** (Model A: админ смотрит всё через зеркало `/admin/*`, у него уже есть `/admin/finance`). Не добавлять admin в префикс — мёртвая дверь.

**Feature flag**: новый opt-in `leader_cabinet` со всеми тремя точками гейтинга (middleware → 404, navigation, `notFoundIfDisabled` на страницах). До включения флага руководитель живёт по-старому (в кабинете менеджера, «Команда» в меню из ui-repair §1).

**Логин-редирект**: `homeFor()` учитывает `managerRole='leader'` + включённый флаг → `/leader/dashboard` (JWT-продьюсер в `login/route.ts` уже несёт `managerRole` — проверить, по уроку C1 о narrowing).

## Меню кабинета (ключ `leader` в каноне)

Важно: `leader` — **не новая JWT-роль** (роль остаётся `manager`, sub-роль `managerRole='leader'`). Канон навигации расширяется ключом `'leader'` поверх `Role` (`Record<Role | 'leader', NavItem[]>`); выбор набора пунктов делает серверный shell по sub-роли.

| Пункт | Маршрут | Содержимое |
|---|---|---|
| Сводка | `/leader/dashboard` | главная (ниже) |
| Команда | `/leader/team` | переезд `/manager/team` (roster, toggle видимости, выдача ролей — как сейчас) |
| Финансы | `/leader/finance` | витрина `getManagerFinanceOverview` company-wide **с комиссией** |
| Заказы | `/leader/orders` | все заказы компании (manager-orders view в company-scope) |
| Организации | `/leader/organizations` | все организации компании |
| Сообщения | `/leader/messages` | как у менеджера (комментарии к заказам + чат при флаге `chat`) |
| Мои заказы | `/manager/dashboard` | переключатель в кабинет менеджера |

Старый `/manager/team` → redirect на `/leader/team` (при включённом флаге), чтобы у контента не было двух домов. Пункт «Команда» из меню менеджера при включённом флаге убирается (его заменяет пункт «Кабинет руководителя»).

## Главная «Сводка по команде»

- **KPI-ряд** (кликабельные, `StatCard href`): менеджеров в команде · заказов в работе · долг клиентов · комиссия за месяц.
- **Таблица по менеджерам**: менеджер → активных заказов → сумма/оплачено → просроченные дедлайны. Строка ведёт в `/leader/orders?manager=…`.
- **Последние события команды** (документы/оплаты/комментарии по заказам компании) — реиспользовать events-feed менеджерского дашборда в company-scope.

## Компоненты и переиспользование

- По sibling-правилу §4 CLAUDE.md компоненты — `leader-*` (`LeaderSidebar`, `LeaderDashboard*`); презентационные доменно-нейтральные (`StatCard`, `EmptyState`, table-примитивы) переиспользуются как есть.
- Сервисы: тонкие обёртки/реиспользование `manager/finance` (overview уже умеет leader-режим), `manager/team`, manager-orders queries с company-scope. Никакой новой бизнес-логики в роутах.

## Seed и демо

- Seed: `leader@demo.local` (`role=manager`, `managerRole='leader'`, та же компания, что `manager@demo.local`).
- Демо-блок логина: кнопка «Руководитель».

## Тестовая стратегия

- **Unit**: `homeFor()` для leader (флаг on/off); nav-канон leader; гейт `requireManagerLeader` на каждой странице (рядовой менеджер → forbidden); redirect `/manager/team`→`/leader/team`.
- **Integration**: cross-company инвариант для `/leader`-выборок (руководитель компании A не видит данных компании B) — расширение существующих C8-тестов; комиссия в `/leader/finance` присутствует, в manager-view отсутствует.
- **E2E visual**: решить на этапе плана, нужен ли отдельный Playwright-проект `leader-*` со своим storageState; минимум — ручной smoke-чеклист по образцу manager staging-smoke (C7).

## Вне scope

- Push/email-уведомления руководителю о просрочках команды.
- Какие-либо новые права записи: кабинет руководителя — read + существующие team-операции из `/manager/team`; новых мутаций нет.

Нет — состав меню, scope и правило комиссии зафиксированы.
