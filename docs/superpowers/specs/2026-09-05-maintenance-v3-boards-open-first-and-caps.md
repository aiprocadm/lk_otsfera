# Сопровождение, вопрос `В-3` → решение `Р-27`: «доски не теряют открытое, селекты не теряют привязку» — микро-спека

[MAINTENANCE.md](../../tz/MAINTENANCE.md) (находка `С-6` прогона №2, вопрос
`В-3` в [STATUS.md](../../tz/STATUS.md)) · **Статус:** решение принято
исполнителем по поручению заказчика («прими решение самостоятельно наиболее

## 1. Что было

**Доски.** Сделки (`services/deals/board.ts`), воронка (`services/funnel/board.ts`)
и задачи (`services/tasks/board.ts`) берут 500 карточек по `createdAt desc`
**включая закрытые** (`won`/`lost`, `promoted_*`/`rejected`, `done`) и молчат.
Пока карточек меньше 500 — всё видно. Когда станет больше, первыми за предел
уйдут самые старые карточки **независимо от статуса**: открытая сделка
полугодовой давности исчезнет с доски раньше, чем вчерашняя проигранная.

**Диалог задачи.** Селекты «Организация» (200 по алфавиту) и «Заявка»
(100 новейших) без поиска и без подписи. Хуже того: при **редактировании**
задачи, чья организация или заявка не попала в список, `defaultValue` селекта
не находит свой `<option>`, браузер показывает «— не привязана —», и
сохранение стирает привязку (`tasks.ts:230`, `linkedOrderId: data.linkedOrderId ?? null`).
Заявок у компании больше 100 — обычное дело, так что это не гипотеза, а
дефект потери данных при правке старой задачи.

## 2. Решение (`Р-27`)

Сочетание вариантов (а) и (б) из `В-3` без нового экрана и без комбобокса:

1. **Открытые — первыми.** Доски сортируют `orderBy: [{ status: 'asc' }, { createdAt: 'desc' }]`.
   Postgres сортирует enum по порядку объявления, а в `schema.prisma`
   терминальные статусы стоят последними: `DealStatus { open, won, lost }`,
   `LeadStatus { new, in_review, qualified, promoted_to_order, promoted_to_deal, rejected }`,
   `TaskStatus { todo, in_progress, review, done }`. Значит, в 500 сначала
   попадают все открытые карточки, а за предел уходят самые старые закрытые.
   Внутри колонки порядок прежний (колонка — один статус; при явной стадии
   с другим статусом открытые идут выше).
   Стражи порядка: юнит по тексту `schema.prisma` (терминальные значения —
   в конце enum) и integration по `pg_enum` живой базы (миграция
   `ADD VALUE` без `BEFORE` дописывает значение в конец — схема и база могут
   разойтись, база важнее).
2. **Честная подпись.** Сервисы досок отдают `shown` (сколько получено) и
   `total` (`count` по тому же `where`); шесть страниц
   (`{manager,leader}/{deals,funnel,tasks}`) рисуют `ListCapNotice` под
   доской с подсказкой, где искать остальное (карточка организации —
   вкладки «Сделки»/«Лиды»; для задач — фильтры и список). Примитив молчит,
   пока скрывать нечего.
3. **Селекты диалога задачи.** Организации — по последней активности
   (`updatedAt desc`) вместо алфавита: у 200 «живых» организаций больше шансов
   быть нужными, чем у 200 на «А…». Сервис отдаёт `organizationsTotal` и
   `ordersTotal`; диалог показывает подпись «Показаны N из M» под селектом,
   когда список усечён. **Текущая привязка редактируемой задачи всегда есть
   в списке**: если `target.linkedOrganizationId`/`linkedOrderId` не среди
   опций, диалог добавляет `<option>` с её именем — сохранение больше не
   стирает связь.

Отклонено: комбобокс с поиском (новый примитив UI — за границей §9.4),
скрытие закрытых карточек с доски (меняет привычный экран: «Проиграна» —
такая же колонка, как остальные).

## 3. Границы (§9.4 ТЗ)

Экраны, сущности, миграции не добавляются; тексты — только подписи
`ListCapNotice` и подпись под селектами. Предел 500/200/100 не меняется.

## 4. Проверка

- Юнит: сервисы досок (`orderBy`, `count` по тому же `where`, `shown`/`total`),
  `getTaskFormOptions` (`updatedAt desc`, счётчики), диалог (текущая привязка
  в списке, подпись при усечении), шесть страниц (`ListCapNotice`), страж
  `prisma.enum-terminal-last.guardrail` по `schema.prisma`.
- Integration: `boards.status-order.integration` — порядок `pg_enum` в базе
  и живая проверка «открытая старая сделка попадает в выборку раньше
  закрытой новой».
- Мутации — таблица в `MAINTENANCE.md`. Гейты `С-1`.
