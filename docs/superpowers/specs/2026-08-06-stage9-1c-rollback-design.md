## 1. Зачем

Ошибочный импорт (не тот файл, не та компания) сегодня разгребается руками по
одной записи. Этап 8 дал историю: какой батч что создал/обновил и снимки «до».
Этап 9 строит на ней кнопку «Откатить» — с жёсткой защитой: откат никогда не
должен снести данные, на которые уже что-то завязано (согласованная комиссия
партнёра, заведённые пользователи, документы).

## 3. Разведка по коду (факт на `main` a831ecfa)

- История готова (этап 8): `OneCImportBatch` (status/`rolledBackAt`/`rolledBackById`
  уже в схеме — **миграция этапу 9 не нужна**), `OneCImportRow`
  (entity/entityId/action/before/reverted).
- Конфликтные связи по схеме: `CommissionStatementItem.paymentId`,
  `CommissionCorrection.paymentId @unique`; `OrderStatusChange.orderId`,
  `Document.orderId`, `Payment.orderId`; у `Organization` — **19 обратных
  связей** (users, organizationUsers, students, certificates, deals,
  clientRequests, enrollmentRequests, leads, tasks, звонки, контакты…).
- Реестр аудита: новое действие обязано попасть в `AUDIT_ACTIONS`
  (`lib/auth/audit.ts`) и получить русское название в `lib/audit/labels.ts` —
  иначе не соберётся / падает тест полноты (правило §2b CLAUDE.md).
- Страницы «Загрузка Excel» — две (admin и leader, этап 7); модалки — только
  через примитив `Dialog` (§9 CLAUDE.md); мутации — server action (§2).
- `before` хранит `Decimal` строкой и `DateTime` ISO-строкой (этап 8) — Prisma
  принимает их в `update` как есть (Date парсится из ISO).

## 4. Решения

### 4.1. Сервис `src/lib/services/import/rollback.ts` (Т-35, Т-38)

Result-контракт §3 CLAUDE.md, права — `mayImportOneC`; руководитель видит и
откатывает **только батчи своей компании** (`batch.companyId`), admin — все.

- `listImportBatches(prisma, session)` → последние 20 батчей с производным
  `rollback: 'available' | 'expired' | 'already_rolled_back'` (Т-39/Т-40).
- `planImportRollback(prisma, session, { batchId })` → счётчики «будет
  удалено/восстановлено» + список конфликтов (для диалога, без записи).
- `rollbackImport(prisma, session, { batchId, partial: boolean })` → сам откат.

### 4.2. Конфликты (Т-36) — список ТЗ + страховка «любая другая связь»

Проверяются только `created`-строки (восстановление полей `updated`-строк
разрушительным не бывает). Блокировки:

- **платёж**: строка в `CommissionStatementItem` или `CommissionCorrection`;
- **заказ**: `OrderStatusChange`, документы, зачисления (`EnrollmentRequest`),
  комментарии/файлы, платежи **не из этого батча**;
- **организация**: пользователи, заявки (`ClientRequest`/`EnrollmentRequest`),
  сделки, сертификаты, студенты, лиды, задачи и прочие обратные связи, заказы
  **не из этого батча**.

Буква ТЗ даёт минимум — спека расширяет его до «**любая** обратная связь вне
батча = конфликт»: дух Т-36 («запись обросла связями») + иначе `DELETE` упрётся
в FK и уронит транзакцию невнятной ошибкой. В UI конфликт печатается по-русски
(«платёж уже в акте комиссии», «у организации 2 пользователя»), редкие связи —
обобщённо («другие связи: N»).

**Распространение блокировки вверх:** заблокированный платёж блокирует свой
созданный в этом же батче заказ, заблокированный заказ — свою созданную
организацию (иначе их удаление упало бы по FK). Вниз — нет: платёж
заблокированного заказа удалить безопасно.

### 4.3. Транзакция (Т-35, Т-37, Т-38)

Весь откат — **одна интерактивная `prisma.$transaction`**; конфликты
пересчитываются **внутри** неё (план из диалога мог устареть — гонка):

1. батч перечитывается под замком: `status: 'committed'`, возраст ≤ 30 дней,
   компания в скоупе — иначе отказ;
2. пересчёт конфликтов; `partial: false` и конфликты есть → вся транзакция
   отменяется, наружу — список (`error: 'conflicts'`);
3. безопасные строки в обратном порядке: `created`-платежи удаляются, затем
   заказы, затем организации; `updated`-строки восстанавливают поля из
   `before` (если запись уже удалена вручную — это тоже конфликт «запись не
   найдена», проверяется до записи, а не ловится по P2025);
4. откаченные строки → `reverted: true`; батч → `rolled_back` (все строки)
   или `rollback_partial` + `rolledBackAt`/`rolledBackById`;
5. `recordAudit('one_c_import.rollback', after: { batchId, deleted, restored,
   skippedConflicts })` — **внутри той же транзакции** (Т-38 требует запись
   обязательно: не записался аудит — не выполнен и откат).

Повторный откат `rollback_partial`-батча разрешён (добить хвост, когда
оператор руками разобрал конфликты); `rolled_back` — отказ.

### 4.4. UI (Т-39, Т-40) — блок «История импортов» на обеих Excel-страницах

Серверная часть страницы отдаёт список батчей; клиентский компонент
`import-history.tsx` (общий admin/leader — презентационный, как `ImportForm`):

- таблица: дата, файл, кто импортировал, «создано/обновлено» по сущностям,
  статус по-русски;
- «Откатить» активна при `rollback: 'available'`; для батчей старше 30 дней —
  disabled + подсказка (Т-40), для откаченных — статус вместо кнопки;
- клик → **диалог 1** (примитив `Dialog`): «Будет удалено: N организаций,
  N заказов, N платежей; восстановлено: M записей» → «Продолжить»;
- «Продолжить» зовёт план; конфликтов нет → выполняется полный откат;
  конфликты есть → **диалог 2**: русский список конфликтов, кнопки
  «Отменить» (default, primary) и «Откатить только безопасные» (secondary,
  Т-37);
- итог — `toast` + обновление таблицы.

Server actions: `planImportRollbackAction`, `rollbackImportAction`
(`src/server-actions/import.ts`), тонкие адаптеры над сервисом.

### 4.5. Аудит (Т-38)

`AUDIT_ACTIONS` += `one_c_import.rollback`; `lib/audit/labels.ts` += «Откат
импорта 1С». В `after` — перечень затронутых id (по сущностям), счётчики и
режим (full/partial).

## 7. Риски

**Высокий** (единственный в программе) — откат удаляет боевые данные. Гасится:
одна транзакция (частично применённого отката не бывает), пересчёт конфликтов
внутри транзакции (гонка план/выполнение), расширенный список блокировок
(§4.2 — любая связь вне батча), дефолт «отменить целиком» (Т-37), 30 дней
(Т-40), права Т-25, обязательный аудит в той же транзакции, «запись не
найдена» проверяется до записи (не ловля P2025 в мёртвой транзакции).

## 8. Решения, требующие «ок» заказчика

Встроены в спеку, отдельного ответа не требуют — «ок» подтверждает:

1. **§4.2** — список блокировок расширен с минимума ТЗ до «любая обратная
   связь вне батча» (дух Т-36; иначе FK-ошибка вместо внятного конфликта).
2. **§4.3** — повторный откат разрешён для `rollback_partial` (добить хвост
   после ручного разбора), запрещён для `rolled_back`.
3. **§4.3** — аудит отката пишется в той же транзакции: не записался аудит —
   не выполнен и откат (буква Т-38 «обязательная запись»).
