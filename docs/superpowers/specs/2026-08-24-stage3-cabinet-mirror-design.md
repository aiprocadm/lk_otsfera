# Этап 3 — зеркальная логика кабинетов

**ТЗ:** [единая логика кабинетов, документы для заказчика и управление интеграциями из интерфейса](../../tz/2026-08-21-tz-cabinets-documents-integrations.md), требования `У-106`…`У-121`, решение `Р-21` (правило зеркала).
**Дата:** 24.08.2026. **Статус:** ждёт подтверждения заказчика.

## 0. Коротко

Этап 2 сделал зеркальной **одну карточку**. Этап 3 делает зеркальными **сами
кабинеты**: меню, названия разделов, порядок групп, шапку, шаблон страницы.

Сегодня название раздела пишется в каждой роли отдельной строкой, поэтому один
и тот же экран называется «Комиссии» у админа и «Комиссионные отчёты» в
разговоре, «Импорт оплат» у менеджера и «Выписка (сч. 51)» у админа. Порядок
пунктов у трёх кабинетов сотрудников разный, у руководителя нет «Документов» и
«Сообщений», у админа нет списка заказов, а переключение между кабинетами
руководителя размазано по двум пунктам-мостам в разных меню.

Этап заканчивается **стражем зеркальности** (`У-121`): он сравнивает реестры
пар кабинетов и падает на любом расхождении, которого нет в явном списке
исключений. Список исключений — часть приёмки: вы видите его целиком.

## 2. Решения, которые предлагаю

### 2.1. Порядок: шесть PR

Этап помечен в ТЗ **высоким риском**: он трогает меню всех шести кабинетов
сразу. Поэтому режем так, чтобы каждый PR был отдельно проверяем, а страж
зеркальности включался **последним** — иначе он будет красным всё время работы.

| PR | Что | Требования |
|---|---|---|
| **PR-1 «ключ раздела и словарь названий»** | `sectionKey` у пункта меню, словарь `sectionLabels.ts`, переименования, страж названий на ключах + вкладки и плитки | `У-106`, `У-107`, `У-108` |
| **PR-2 «порядок групп и настройки внизу»** | Единые группы меню сотрудников ЦО, «Обмен с 1С» одним пунктом с вкладками, `pinnedBottom` везде | `У-113`, `У-114` (меню) |
| **PR-3 «руководитель»** | «Документы» и «Сообщения» у руководителя, переключатель кабинетов в шапке, снятие двух пунктов-мостов, вкладки «Обмен с 1С» | `У-110`, `У-111`, `У-118` |
| **PR-4 «администратор»** | Список заказов `/admin/orders`, «Поиск» админу, состав карточки заказа, `leader` в `/admin/users` | `У-112`, `У-119` |
| **PR-5 «`PageHeader` и деталки»** | Компонент шаблона страницы, перевод стража подзаголовков на него, деталки заявок и обращений у сотрудников ЦО | `У-120`, `У-116` |
| **PR-6 «зеркало»** | `/partner/deals` → `/partner/orders`, мобильная панель из реестра, зеркальность заказчика и партнёра, страж зеркальности со списком исключений | `У-109`, `У-115`, `У-117`, `У-121` |

**Почему `У-109` в последнем PR.** Порядковое ограничение §5 ТЗ прямое:
переименование `/partner/deals` → `/partner/orders` идёт **отдельным PR и не
раньше `У-117`** — иначе нижняя панель партнёра потеряет вкладку в тот момент,
когда адрес изменится, а `MOBILE_TABS` ещё держит старый.

### 2.2. Ключ раздела вместо строки (`У-106`)

У пункта меню появляется `sectionKey` — тот же приём, что с `iconKey`. Название
и значок выводятся из ключа словарём
`src/lib/navigation/sectionLabels.ts`, а не пишутся в каждой роли:

```ts
export const SECTION_LABELS = {
  orders: { label: 'Заказы', iconKey: 'orders' },
  commissionStatements: { label: 'Комиссионные отчёты', iconKey: 'commissions' },
  // …
} as const;
```

Пункт меню задаёт `href`, `sectionKey`, группу, флаг и права; `label`/`iconKey`
он больше не носит. Разъехаться названиям станет физически негде.

**Почему это лучше нынешней проверки по сегменту адреса.** Сегмент — совпадение
путей, а не смысл: `/leader/team` и `/manager/team` совпали случайно, а
«Комиссионные отчёты» у админа (`/admin/commission-statements`) и у партнёра
(`/partner/finance`) не совпадут никогда, хотя это близкие разделы. Ключ
называет смысл прямо.

### 2.3. Переименования (`У-107`)

Строго по списку ТЗ, одним PR вместе со словарём и глоссарием. H1 страницы
берётся из того же словаря — расхождение «пункт меню одно, заголовок другое»
станет невозможным.

Дохабовые пункты («Здоровье», «Доступ к ПДн», «Синхронизация (авто)») видны
только при выключенном флаге `settings_hub`. ТЗ разрешает **не заводить под них
отдельной работы**: переименовываем вместе с карточками хаба.

### 2.4. Порядок групп (`У-113`)

Группы получают все три кабинета сотрудников ЦО, в одном порядке:
**Главная · Работа · Продажи · Клиенты · Документы · Финансы · Коммуникации ·
Аналитика · Справочники**, внизу закреплены **Настройки** и **Справка**. Состав
внутри группы — фильтр флагов и прав; порядок — общий.

У менеджера два пункта («Загрузка Excel из 1С» и «Выписка по счёту 51»)
схлопываются в один — **«Обмен с 1С»** с вкладками, тем же компонентом вкладок,
что в хабе настроек.

### 2.5. Переключатель кабинетов руководителя (`У-111`)

Вместо двух пунктов-мостов в разных меню — **один переключатель в шапке**,
видимый только роли `leader`. Переход сохраняет текущий раздел, если он есть в
обоих кабинетах (`/leader/orders` ↔ `/manager/orders`), иначе ведёт на главную.
Соответствие разделов берётся из `sectionKey` — то есть из `У-106`, и это
вторая причина делать ключ первым PR.

### 2.6. Мобильная панель из реестра (`У-117`)

`MOBILE_TABS` перестаёт быть списком адресов и становится списком `sectionKey`
**с запасными**: если пункт выключен флагом или правами, панель берёт
следующий по приоритету. Правило — «панель не короче четырёх вкладок, пока в
меню есть четыре доступных пункта» (закрывает `Д-40`).

### 2.7. Страж зеркальности (`У-121`)

Тест сравнивает реестры пар кабинетов — `admin`/`leader`/`manager` между собой и
`organization`/`partner` между собой — по `sectionKey` → название, значок,
группа, порядок внутри группы, наличие раздела. Любое расхождение, которого нет
в `src/lib/navigation/mirrorExceptions.ts`, роняет сборку. Каждое исключение —
строка с причиной.

**Предварительный список исключений** (уточнится в PR-6, предъявляется вам
целиком):

| Расхождение | Причина |
|---|---|
| «Партнёры» — только у админа | Партнёрами управляет учебный центр, у менеджера и руководителя этого раздела нет |
| «Пользователи», «Здоровье системы», «Функции платформы» — только у админа | Платформенные разделы: чужой кабинет ими не управляет (Model A) |
| «Команда» — только у руководителя | Менеджер не управляет составом команды |
| «Портфель» ↔ «Моя организация» | Разные объекты: у партнёра список клиентов, у заказчика — своя организация |
| «Финансы» у партнёра — комиссия, у заказчика — оплаты | Один раздел, разное содержание; название и место общие |
| «Кабинет слушателя» — только у заказчика | Вход в соседний домен, у партнёра его нет |
| «Поиск» — у админа, руководителя, менеджера | После `У-112` расхождения не остаётся; строка снимается в PR-4 |

### 2.8. `PageHeader` (`У-120`)

Один компонент: заголовок (из словаря `У-106`), подзаголовок, главная кнопка,
крошки. Страж подзаголовков переводится с «первого H1 в файле» на «каждый H1» —
сейчас он проверяет только первый, и второй заголовок на экране может остаться
без пояснения.

## 3. Тесты

- **словарь названий**: пункт меню не может нести свой `label`; одинаковый
  `sectionKey` ⇒ одинаковые название и значок; H1 страницы равен названию
  пункта (страж по исходникам, как в `У-72`);
- **переименования**: старых подписей нет ни в реестре, ни в глоссарии;
- **порядок групп**: порядок групп в трёх кабинетах ЦО совпадает; внутри группы
  порядок общий; «Настройки» и «Справка» закреплены внизу во всех шести;
- **переключатель кабинетов**: виден только `leader`; сохраняет раздел, когда он
  есть в обоих кабинетах; ведёт на главную, когда нет; роль `manager` его не
  получает (проба доступа);
- **мобильная панель**: выключенный флагом раздел заменяется запасным; панель
  не короче четырёх вкладок, пока есть четыре доступных пункта;
- **админ**: список заказов виден по всем компаниям, фильтры работают, «Поиск»
  доступен; `/admin/users` фильтрует `leader` и по компании;
- **руководитель**: «Документы» и «Сообщения» открываются со скоупом компании
  (IDOR-проба на живом Postgres); вкладки «Обмен с 1С» не дают 404;
- **зеркальность**: страж пар кабинетов + список исключений с причинами;
  **проверен мутацией** — переименование раздела в одной роли роняет тест;
- **§0**: каждый новый экран проходит правило трёх вопросов; ширина 390 px.

## 4. Риски

| Риск | Что делаем |
|---|---|
| Этап трогает меню всех кабинетов сразу — легко уронить навигацию целиком | Ключ раздела и словарь идут первым PR и **не меняют состав**: только источник названия. Состав меняется потом, по одному кабинету |
| Страж зеркальности будет красным всю работу | Он включается последним PR, когда расхождения уже устранены |
| Переименование `/partner/deals` ломает закладки и мобильную панель | Постоянный редирект со старого адреса + `MOBILE_TABS` переводится на ключи **раньше** (`У-117` перед `У-109`, порядок §5 ТЗ) |
| Список исключений превратится в свалку «чтобы позеленело» | Каждая строка — с причиной; список предъявляется заказчику целиком как часть приёмки |
| `settings.ts` правят два этапа сразу (`У-114` и этап 4) | ТЗ прямо требует последовательности: сначала `У-114`, этап 4 — после. Параллельных веток по этому файлу не открываем |
