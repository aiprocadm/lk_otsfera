## 1. Зачем этот этап

Сегодня при загрузке файла из 1С пользователь видит либо пустой экран, либо
короткое «Файл пуст или нет валидных строк». Что именно система прочитала в
файле — не видно ни ему, ни разработчику: исключения гасятся пустым `catch {}`,
в журнал не попадает ничего.

Этап ничего не чинит по существу. Он делает **видимой причину**: какие листы
нашлись в книге, какие заголовки не распознались, что упало. Без этого правки
карты колонок (этап 3) — гадание, а разбор инцидента на проде невозможен.

Заказчику этап 1 нужен ещё и как инструмент: скрипт Т-1 можно прогнать на файле
Павла **до** любого кода и сразу выписать точные имена листов и заголовков.

## 4. Решения

### 4.1. Скрипт-инспектор — `.ts`, а не `.mjs` (отклонение от буквы ТЗ)

ТЗ называет файл `scripts/inspect-1c-xlsx.mjs`. Предлагаю
**`scripts/inspect-1c-xlsx.ts`** и запуск `npx tsx scripts/inspect-1c-xlsx.ts <файл>`
(плюс ярлык `npm run inspect:1c`).

Причина: скрипт обязан показывать заголовки **по текущей `column-map.ts`**
(требование Т-1). Из `.mjs` импортировать TypeScript-модуль нельзя — пришлось бы
скопировать карту колонок в скрипт, и она немедленно разъехалась бы с боевой.
Копия карты — ровно та ошибка, ради которой этап и делается. В репозитории
`.ts`-скрипты — норма (10 из 11).

Поведение скрипта:

```
$ npx tsx scripts/inspect-1c-xlsx.ts ~/1c.xlsx

Файл: 1c.xlsx, 2.4 МБ, формат по сигнатуре: xlsx
Листов в книге: 3 — «Контрагенты», «Реализация товаров и услуг», «Поступления»

Лист «Контрагенты» (строк: 148)
  ✔ распознано: Наименование → name, ИНН → inn
  ✖ не распознано: «ИНН партнера», «КПП», «Адрес»
  ✖ не найдены колонки карты: ИНН партнёра
  Первые 3 строки: …

Ожидались листы: Контрагенты, Реализации, Поступления
  ✖ не найден лист «Реализации» (похоже, это «Реализация товаров и услуг»)
```

- ничего не пишет в БД и не ходит в сеть — только читает файл;
- код возврата 0 всегда (это инструмент, а не проверка);
- ИНН и наименования печатаются как есть — файл смотрит владелец на своей машине;
  в репозиторий вывод не коммитится.

### 4.2. Диагностика возвращается и при ошибке

Т-3 просит блок «Что увидела система в файле». Он нужнее всего именно тогда,
когда **ничего не распозналось**, — а сейчас в этом случае отчёт не возвращается
вовсе (`{ ok: false, error: 'empty' }`).

Поэтому диагностика прикладывается к результату **в обоих исходах**:

```ts
export type ImportDiagnostics = {
  /** Имена листов, фактически найденные в книге. */
  sheetsFound: string[];
  /** Имена листов, которые ищет текущая карта (SHEET_NAMES). */
  sheetsExpected: string[];
  /** Лист → заголовки его первой строки, которых нет в карте колонок. */
  unmatchedHeaders: Record<string, string[]>;
};

export type ImportReport = {
  orders: BatchSummary;
  payments: BatchSummary;
  diagnostics: ImportDiagnostics;
};

// было: { ok: false; error: Err }
// стало:
type Failure = { ok: false; error: Err; diagnostics?: ImportDiagnostics };
```

`diagnostics` отсутствует только при `parse_failed` — там книгу открыть не
удалось, показывать нечего (сама причина уходит в журнал по Т-2).

Состав полей — дословно из Т-3, ничего не добавляю. Список **недостающих**
колонок карты просится в отчёт, но это Т-12 этапа 3 (`columns_not_recognized`);
здесь он есть только в скрипте (§4.1), где не меняет контракта.

### 4.3. Откуда берётся диагностика

`parseWorkbook()` уже держит книгу в руках — он и собирает `diagnostics`
(имена листов из `wb.worksheets`, нераспознанные заголовки — при построении
`colIndex`). `FileOneCAdapter` получает метод `diagnostics()`.

**Метод НЕ добавляется в интерфейс `OneCAdapter`** — иначе его пришлось бы
реализовывать сетевому `adapter-rest`, где понятия «лист книги» нет. Сервис
импорта конструирует `FileOneCAdapter` напрямую, поэтому вызов доступен без
расширения общего контракта.

### 4.4. Журнал (Т-2)

```ts
} catch (e) {
  log.error('[1c-import] не удалось разобрать файл', e);
  return { ok: false, error: 'parse_failed' };
}
```

Логгер — `@/lib/logging` (в проде pino + `scrub()`; сырой `console` запрещён,
CLAUDE.md §12). Префикс `[1c-import]` — по нему ТЗ §6 предлагает искать в логах.
Возвращаемый код ошибки не меняется: `parse_failed` уже разобран интерфейсом.

### 4.5. Интерфейс

Блок «Что увидела система в файле» под формой, виден и при успехе, и при ошибке:

```
Что увидела система в файле
  Листы в файле:      Контрагенты · Реализация товаров и услуг · Поступления
  Ожидаемые листы:    Контрагенты · Реализации · Поступления
  Не распознаны заголовки:
    Контрагенты — «ИНН партнера», «КПП»
```

Серый информационный блок (не красный — это не ошибка сама по себе), примитивы
из `components/ui`. Локальный дубль типа `ImportReport` в форме расширяется
теми же полями.

## 6. Тесты

| Слой | Что проверяем |
|---|---|
| unit `parse-workbook` | книга со всеми листами → `unmatchedHeaders` пуст; книга с чужими именами листов → они видны в `sheetsFound`, `orders` пуст; лишний заголовок → попал в `unmatchedHeaders` |
| unit `adapter-file` | `diagnostics()` отдаёт то же, что парсер, и не ломает существующие `pullOrders`/`pullPayments` |
| unit `import/index` | диагностика есть в успешном отчёте **и** в ответе `empty`; при `parse_failed` — вызван `log.error` с префиксом `[1c-import]` |
| компонентный `import-form` | блок рендерится при наличии диагностики и скрыт без неё; перечислены имена листов |

Книги для тестов собираются в памяти через ExcelJS — бинарные фикстуры в
репозиторий не кладём (обезличенный реальный файл 1С понадобится этапу 3, ТЗ §5).

Гейты: `typecheck`, `lint`, `boundaries`, `deadcode`, `dup:check`,
`format:check`, `test:unit`; порог покрытия 100% на `src/**` — новый код
приходит со своими тестами. Скрипт лежит вне `src/`, под порог не попадает;
проверяется ручным прогоном на тестовом файле.

## 7. Риски

Риск этапа по ТЗ — «нет», и это подтверждается: единственное изменение
поведения — расширение типа отчёта. Два места, за которыми стоит проследить:

1. **Локальный дубль типа `ImportReport` в форме** — если расширить только
   серверный, интерфейс тихо не покажет блок. Закрывается компонентным тестом.
2. **Ветка `empty` теперь возвращает не только код ошибки.** Форма обязана
   пережить `{ ok: false, error, diagnostics }` без правок в остальных ветках —
   тоже под тестом.
