# Этап 6 ТЗ — сделки и канбан сделок (Модуль 4, ФТ-4.1–4.6)

Дата: 2026-07-25 · Статус: **ждёт подтверждения заказчика** (вопросы §9) ·
ТЗ: [docs/tz/2026-07-23-tz-lk-otsfera-v1.md](../../tz/2026-07-23-tz-lk-otsfera-v1.md) §Модуль 4, §9 этап 6.

**Решение по вопросу 1 §10 ТЗ** (заказчик, 25.07.2026): DealNote —
**параллельная привязка**: `orderId` остаётся, добавляется `dealId?`;
существующие заметки по заказам не мигрируются и не ломаются.

## 1. Цель и критерий приёмки (§9 ТЗ)

«Менеджер ведёт сделку по канбану от лида до выигрыша с созданием заказа;
руководитель настраивает стадии и видит доску команды; клиентские роли
сделок не видят (404 на всех трёх слоях RBAC)».

## 2. Контекст кода (разведка)

Слово «deal» в коде сейчас занято Order-контуром: `/partner/deals` — портфолио
заказов клиента, `DealNote`/`deal-activity` — заметки и лента по заказу.
Новая сущность `Deal` — greenfield, но по готовым лекалам: канбаны
`funnel-board` (G2, словарь `FunnelStage` со `statusAnchor` + native dnd +
`StageConfig` руководителя) и `task-board` (G3, `TaskColumn`). `SalesTarget` и
план/факт (`leader/analytics.ts`) уже существуют. Неймспейсы разводим:
prisma-модели `Deal`/`DealStage` (коллизий в схеме нет), сервисы —
`src/lib/services/deals/`, компоненты — `src/components/deals/`; партнёрское
портфолио (`partner/deals.ts`, `partner/deal-*`) не трогаем.

## 3. Модель данных (ФТ-4.1, 4.2)

**`Deal`**: `id/createdAt/updatedAt`, `companyId` (граница C8, NOT NULL),
`leadId? @unique` (источник), `organizationId?`, `contactId?`, `title`,
`amount Decimal?`, `managerId?` (ответственный), `status DealStatus
@default(open)` (`open | won | lost`), `stageId?` (FK `DealStage`, SetNull;
null → дефолт по якорю), `expectedCloseAt?`, `wonAt?/lostAt?`, `lostReason?`,
`orderId? @unique` (созданный при выигрыше заказ). Индексы: companyId+status,
managerId, stageId.

**`DealStage`** — зеркало `FunnelStage`: `companyId`, `name`, `position`,
`statusAnchor DealStatus`, `color`, `isTerminal`,
`@@unique([companyId, position])`. Дефолтные стадии в коде (как
`DEFAULT_FUNNEL_STAGES`): «Новая → Переговоры → Предложение → Выиграна(терм.,
won) → Проиграна(терм., lost)». CRUD стадий — руководитель/админ
(клон `access/funnelStages.ts` + `stage-config.tsx`).

**`DealNote`**: `+dealId String?` (SetNull) — параллельная привязка (решение
§10-1); `orderId` остаётся как есть.

**`Lead`**: `+promotedDealId String? @unique`; enum `LeadStatus` —
**additive** значение `promoted_to_deal` («Передан в сделку», терминальная
дефолт-стадия воронки добавляется в `DEFAULT_FUNNEL_STAGES`; вопрос §9-1).

Миграция чисто аддитивная, данные не трогаются.

## 4. Канбаны (ФТ-4.3)

- `/manager/deals` — доска «свои сделки» (C8: companyId сессии + `managerId ==
  sub`; уровни accessProfile.deals — по образцу leads: own/assigned/all,
  дефолт own для менеджера).
- `/leader/deals` — доска команды (company-floor) + фильтр по менеджеру
  (образец — план/факт) + `StageConfig` (настройка стадий).
- Механика: native HTML5 dnd из `funnel-board`; `moveDeal(dealId, stageId)`:
  смена стадии; перенос в терминальную стадию с якорем `won` → диалог
  «Выиграна: создать заказ?» (§5), с якорем `lost` → диалог причины
  (`lostReason`, `lostAt`). Обратный перенос из терминальной — запрещён
  (lifecycle_violation), как в воронке.
- Карточка сделки: диалог (title, amount, организация, ответственный,
  expectedCloseAt, лента §6) — по образцу `task-dialog`.
- Клиентские роли: 404 на трёх слоях (middleware-префиксы + nav + page/route
  гейты) — флаг `deals_pipeline` (ФТ-4.6, opt-in route-флаг).

## 5. Конверсии (ФТ-4.4)

- **Лид → сделка**: кнопка «Создать сделку» на карточке лида и в воронке
  (рядом с существующим «Создать заказ»): транзакция — `Deal` из полей лида
  (title=subject, amount=estimatedAmount, организация/менеджер наследуются),
  `Lead.promotedDealId`, статус лида `promoted_to_deal`; аудит.
- **Сделка → заказ (выигрыш)**: перенос в won-стадию → диалог подтверждения:
  транзакция — Order по паттерну `promoteLead` (обязательна организация —
  без неё валидация с русским сообщением), `Deal.orderId`, `status=won`,
  `wonAt`; лид-источник (если есть) остаётся `promoted_to_deal`. Заказ
  локальный (`externalId=null` — 1С-синк его не трогает, как у promoteLead).
- Существующий путь «лид → заказ напрямую» (`promoteLead`) сохраняется —
  сделка не обязательна.

## 6. Лента активности сделки (ФТ-4.4)

- `addDealNote` расширяется параллельной привязкой: заметка к сделке
  (`dealId`) или к заказу (`orderId`) — существующие вызовы не меняются.
- Лента на карточке сделки: заметки по `dealId` + (при связанном `orderId`)
  полная существующая лента заказа (`getDealActivity`); до выигрыша — заметки
  сделки и события стадий (аудит `deal_stage_changed`).

## 7. Аналитика (ФТ-4.5)

По ТЗ — «отдельным подэтапом после стабилизации модели»: в план/факт
(`getPlanFact`) добавляется колонка «Выиграно сделок / сумма won за месяц»
(по `wonAt`). Предлагаю третьим маленьким PR в этом же этапе (вопрос §9-2).

## 8. Тестовая стратегия (порог 100%)

- Модель/миграция: аддитивность, дефолт стадий, резолвер по якорю (integration).
- Сервисы: скоупы C8 (менеджер свои/лидер команда/чужая компания невидима),
  moveDeal (обычная/терминальные/из терминальной → violation), конверсии
  (лид→сделка: поля/статус/unique; won→заказ: транзакция, без организации →
  validation), CRUD стадий (роль-гейт, position_taken), DealNote.dealId
  (параллельность: старые по orderId живы).
- Клиентские роли → 404/forbidden на всех поверхностях (guard критерия).
- UI: доски (dnd move, терминальные диалоги), StageConfig, карточка сделки,
  лента; страницы renderServerComponent; nav.
- Integration на живом Postgres: полный путь лид → сделка → won → заказ.

   переиспользовать «Преобразована в заказ», но это врёт в отчётах.)
2. **Аналитика ФТ-4.5** (сумма выигранных сделок в план/факт): делаем третьим

   стабилизации»)?

   подтверждения; сделке для выигрыша обязательна организация — ок?
4. **Разбивка**: PR-1 «модель + стадии + канбаны + move» → PR-2 «конверсии +
   лента + won/lost диалоги» (+ PR-3 аналитика, если да в §9-2) — ок?
