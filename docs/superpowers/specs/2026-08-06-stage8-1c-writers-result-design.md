# Этап 8 «Writer'ы возвращают результат + модели батча» — дизайн

**Дата:** 2026-08-06

**Этап в STATUS.md:** 8 из 10 · риск «средний» · строго **до** этапа 9 (откат, высокий риск)
**Статус:** 📝 ждёт подтверждения заказчика (кода нет)

## 1. Зачем

Откат импорта (этап 9) нельзя построить без двух вещей: **истории** (какой файл,
кто, когда, какие записи создал/обновил) и **снимков «до»** для обновлённых
записей. Сегодня writer'ы возвращают `void` — они инкрементят счётчики, и после
импорта невозможно узнать, какие именно строки БД он затронул. Этап 8 — чисто
техническая подготовка: модели истории + возврат результата из writer'ов +
запись истории в `commitImport`. Поведение импорта для пользователя не меняется.

## 2. Что в объёме (Т-32…Т-34)

| Требование | Суть |
|---|---|
| **Т-32** | Миграция: модели `OneCImportBatch` / `OneCImportRow` по образцу `PaymentImportBatch` — ровно по эскизу из ТЗ (батч: кто/когда/файл/счётчики/статус; строка: entity, entityId, action, `before`, `reverted`) |
| **Т-33** | `commitImport` пишет батч и строку на каждую созданную/обновлённую запись; `before` — только для `updated` и только поля, которые импорт трогает (per-entity список из ТЗ) |
| **Т-34** | `upsertOrgRecord` / `upsertOrderRecord` / `upsertPaymentRecord` возвращают `{ entityId, action, before }` вместо `void` |

**Вне объёма:** сама логика отката, блокирующие связи, срок 30 дней, UI
«История импортов» (Т-35…Т-40, этап 9); документы (`upsertDocumentRecord`) —
Т-34 его не называет, файловый импорт документы не пишет; сетевая
синхронизация батчи **не** пишет (Т-33 говорит про `commitImport`) — воркер
просто игнорирует возвращаемое значение.

## 3. Разведка по коду (факт на `main` 04642ee6)

- `runRecordBatch(handler: (r, summary) => Promise<void>)` — тип менять не
  нужно: TS допускает обработчик, возвращающий `Promise<что-угодно>`;
  результат собирает замыкание в `commitImport`, воркеры ничего не замечают.
- Writer'ы уже делают `SELECT` существующей записи перед update — для снимка
  «до» достаточно расширить `select` нужными полями (лишнего запроса нет).
- `Order.totalAmount`/`paidAmount`, `Payment.amount` — `Decimal`; `paidAt` —
  `DateTime`. В `before` (Json) кладутся строками (`String(x)` / ISO) — этап 9
  их распарсит.
- `PaymentImportBatch` (образец) уже в схеме — та же форма: `importedBy`
  relation `"PaymentImportBatchBy"`, `companyId String?` без relation,
  `counts Json`, `status String`. У `User` появится обратная связь
  `@relation("OneCImportBatchBy")` — миграция чисто аддитивная.
- Моки призмы в тестах `commitImport` (contract/unified) не знают про новые
  делегаты — запись истории обязана деградировать мягко (§4.4), иначе волна
  ложных падений.

## 4. Решения

### 4.1. Контракт writer'а (Т-34)

```ts
// writers.ts
export type WriteOutcome = {
  entityId: string;
  action: 'created' | 'updated';
  /** Только для updated: значения затронутых полей ДО записи. */
  before?: Record<string, unknown>;
};
// upsertOrgRecord / upsertOrderRecord / upsertPaymentRecord:
//   Promise<void> → Promise<WriteOutcome | undefined>
```

`undefined` — во всех случаях, когда запись НЕ менялась: skip, invalid-строка
до writer'а, **shadow-режим** (записи нет — откатывать нечего, и id не
существует). `created` в live возвращает id созданной записи (у
`order.create`/`payment.create`/`organization.create` он и так есть в ответе).

### 4.2. Снимок `before` — буквально по списку Т-33

| Сущность | Поля в `before` (updated) |
|---|---|
| организация | `name`, `inn`, `kpp`, `externalId`, `partnerId` |
| заказ | `totalAmount`, `paidAmount`, `financialStatus`, `executionStatus` |
| платёж | `amount`, `paidAt`, `purpose` |

Список — из ТЗ дословно. Честная оговорка для этапа 9: update заказа трогает и
`orderNumber`/`title`/даты, update платежа — и `method`/`vatAmount`; ТЗ
осознанно ограничил снимок «финансовым ядром» (полный снимок — ПДн и объём).
Если на этапе 9 захочется откатывать больше полей — это правка списка здесь,
отдельным решением заказчика.

### 4.3. Сбор истории — замыкание в `commitImport` (Т-33)

`run()` дополнительно к отчёту отдаёт наружу собранные строки: обработчик
каждого батча оборачивается `(d, s) => upsertXxx(...).then(r => { if (r)
rows.push({ entity, ...r }) })`. В `previewImport` writer'ы в shadow вернут
`undefined` — строк нет по построению.

После успешного прогона `commitImport` пишет:

```ts
const batch = oneCImportBatch.create({
  importedById: session.sub,
  companyId,            // company-скоуп → компания руководителя; global → выбранная в форме
  fileName: args.fileName ?? '—',
  counts: { orgs, orders, payments },   // шесть счётчиков каждой сущности
  status: 'committed',
});
oneCImportRow.createMany({ rows });     // entity, entityId, action, before
```

`fileKey` остаётся `null` — файл пока никуда не сохраняется (модель поле
предусматривает, наполнение — вопрос этапа 9, если понадобится).

### 4.4. Отказ записи истории — мягкая деградация (§3 CLAUDE.md)

Импорт к моменту записи батча уже применён; уронить ответ — значит показать
оператору «ошибка» на фактически выполненный импорт. Поэтому запись истории —
`try/catch` + `log.error('[1c-import] история батча не записана — откат этого
импорта будет недоступен', e)`, ответ остаётся `ok`. Тот же контракт, что у
аудита. Побочный бонус: моки призмы в старых тестах без новых делегатов не
падают, а честно логируют.

### 4.5. Миграция (Т-32)

Модели — ровно по эскизу ТЗ (имена полей/индексы не менялись), плюс обратная
связь `User.oneCImportBatches @relation("OneCImportBatchBy")`. Миграция
аддитивная, существующие таблицы не трогаются. `rolledBackById` — просто
строка, как в эскизе (relation не нужен до этапа 9).

## 6. Тесты

| Слой | Что проверяем |
|---|---|

| **integration** (живой Postgres) | полный файл: батч со строками `created` для org/order/payment; повторный прогон → строки `updated` со снимками `before`; предпросмотр батча не создаёт; каскад: удаление батча удаляет строки |

Гейты: typecheck, lint, prettier, `prisma:generate`, покрытие изменённых 100%,
**полный** `test:integration` на свежей seed-базе (урок этапа 7), полный
`test:unit`. Грабли учтены: ИНН-сиды с разными двузначными префиксами; моки
призмы без новых делегатов живут за счёт §4.4.

## 7. Риски

Средний. Главные: (1) смена сигнатуры трёх writer'ов — все вызовы в одном PR,
воркеры игнорируют результат по типовой совместимости; (2) миграция —
аддитивная, `prisma migrate status` в CI подтвердит; (3) объём `before`
ограничен списком ТЗ — сознательно (§4.2).

## 8. Решения, требующие «ок» заказчика

Встроены в спеку, отдельного ответа не требуют — «ок» подтверждает:

1. **§4.4** — отказ записи истории не роняет уже применённый импорт
   (лог + недоступный откат конкретного батча), по контракту аудита.
2. **§4.2** — снимок `before` строго по списку Т-33; расширение списка (если
   этап 9 захочет откатывать больше полей) — отдельным решением.
3. **§4.1** — shadow/skip возвращают `undefined`; батчи пишет только файловый
   `commitImport`, сетевая синхронизация историю не ведёт (буква Т-33).
