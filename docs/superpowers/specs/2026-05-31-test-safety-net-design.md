# Автоматическая страховочная сетка: гейт интеграционного слоя + покрытие воркера + guardrail — design

**Дата:** 2026-05-31
**Автор:** Claude (session-driven, brainstorming)
**Статус:** Approved (design step), pending implementation
**Related:** Трек 1 (production-readiness) из whole-project improvement survey 2026-05-30. Паттерн «структурный guardrail» наследуется из [2026-05-30-modal-dialog-primitive-design.md](2026-05-30-modal-dialog-primitive-design.md) (ESLint `forbid hand-rolled modals`). Контракт тестовой дисциплины — CLAUDE.md §6; запрет на возврат CI — §11.

## Проблема

Проект feature-complete (4 кабинета), но у тестовой пирамиды две дыры, обе бьют по production-readiness:

1. **Интеграционный слой негейтится.** По CLAUDE.md §6 тесты разложены на три слоя: L1 (pre-commit, изменённые unit), L2 (pre-push, весь unit), L3 (интеграция — **только вручную**). L3 — это ~33 интеграционных файла (среди них 6 worker-тестов), все с `new PrismaClient(` → требуют живой Postgres. **Ничто не заставляет L3 прогоняться перед мержем** — регрессия в сервис/воркер-слое может молча уехать в `main`.

2. **3 процессора без покрытия вовсе.** Из 10 процессоров в [src/worker/index.ts](../../../src/worker/index.ts) покрыты 7 (`syncOrganizations/Orders/Payments/Documents` через `worker.oneCSync.upsert.test.ts`, `syncReconcile`, `scanDocument`, `calculateMonthlyCommissions`). **Не покрыты:** `pushLeadProcessor` (+ inline-хук финального провала `notifyPushLeadFinalFailure`, живущий прямо в [worker/index.ts:47-58](../../../src/worker/index.ts)), `generateCommissionPdfProcessor`, `generateCommissionXlsxProcessor`.

3. **Дыра покрытия самовоспроизводится.** Слой интеграционных тестов в [vitest.config.ts:43-50](../../../vitest.config.ts) определяется «по построению»: файл интеграционный ⟺ содержит `new PrismaClient(`. Значит любой новый DB-тест автоматически уезжает в негейтящийся L3. Залатать 3 дыры сегодня недостаточно — четвёртый процессор завтра молча окажется непокрытым/негейтящимся.

**Ограничение:** GH Actions выключены намеренно (§11: «не возвращай CI без обсуждения»). Решение должно жить в локальной хук-архитектуре §6, а не реанимировать серверный CI.

## Цель

Сделать так, чтобы интеграционный слой **надёжно прогонялся перед тем, как код покидает машину** — оставаясь в локальной Husky-архитектуре §6 и на уже существующей Docker-инфраструктуре. Закрыть 3 дыры покрытия и **структурно** не дать им открыться снова.

Инфраструктура для этого уже есть: [docker-compose.yml](../../../docker-compose.yml) поднимает `db` (postgres:16, healthcheck) и `redis`; интеграционные тесты подключаются через окружение (`new PrismaClient()` без аргументов → читает `DATABASE_URL`); ClamAV в [.env.example:59-60](../../../.env.example) опционален («safe for dev/CI»). То есть тестовое окружение уже спроектировано CI-безопасным — нужен оркестратор, а не новая инфраструктура.

## Не-цели / Out of scope (явно)

- **Реальный адаптер 1С** (Трек 1А) — отдельная фича. Сетка тестирует против `FakeOneCAdapter`, как и весь текущий L3.
- **Возврат GH Actions / любой серверный CI** (§11) — явно вне scope. Серверный гейт (Вариант 3 при обсуждении) — потенциальная будущая эскалация отдельным решением, не здесь.
- **Мониторинг / readiness-пробы** (Трек 1В) — отдельная фича.
- **Переписывание 33 существующих интеграционных тестов** — не трогаем, только гейтим их прогон. *(Update 2026-05-31: гейт выявил, что слой НЕ зелёный на свежей БД — предсуществующая хрупкость изоляции. По согласованию с пользователем scope расширен: 3 теста стабилизированы — полный FK-каскад очистки + скоуп глобальных ассертов. См. план, Task 0; commit `f470141`.)*
- **jsdom / DOM-тесты** — наследуем решение из 2026-05-27 (не добавляем).
- **Параллелизация интеграционных тестов** — `fileParallelism: false` остаётся (§6: тесты делят живой Postgres и 1С-fixture externalId).
- **Гейтинг Playwright e2e** — отдельная история (`npm run e2e:visual`, нужен seed+dev), не входит.

## Дизайн

Четыре компонента: запускаемый гейт (1) → принуждение (2) → покрытие (3) → структурная защита покрытия (4).

### Компонент 1 — запускаемый гейт (`npm run gate`)

Кроссплатформенный оркестратор `scripts/gate.ts` (на `tsx`). **Почему tsx, а не bash:** dev-машина на Windows/PowerShell, Husky-хуки на `sh`; единый Node-скрипт убирает грабли «работает в одном шелле, падает в другом»; `tsx` уже в зависимостях (используется `prisma:seed`, `worker`).

Шаги:
1. `docker compose up -d db` → дождаться `healthy` (compose-healthcheck уже определён; поллить `docker compose ps`/`pg_isready` exec'ом). Redis по умолчанию **не** поднимается — worker-процессоры в тестах вызываются как обычные функции с фейковым `job()`, минуя BullMQ/Redis (см. паттерн в `worker.oneCSync.upsert.test.ts`). Флаг `--redis` поднимет и его, если понадобится.
2. **Host-facing `DATABASE_URL`.** Корневой `.env` указывает на хост `db` (имя сервиса внутри Docker-сети, резолвится только в контейнерах). Тест-раннер на хосте должен идти на `localhost:5432`. Гейт **инжектит** `DATABASE_URL`/`DIRECT_URL` прямо в env дочерних процессов (`postgresql://postgres:postgres@localhost:5432/cabinet`, переопределяемо через `GATE_DATABASE_URL`). Инжекция в дочерний env важна: Prisma авто-грузит `.env` через dotenv, но dotenv **не перетирает** уже выставленные переменные → наш localhost-URL выигрывает у `db`-URL из `.env`. Отдельный `.env.test` не нужен.
3. `npm run prisma:migrate:deploy` (НЕ `migrate dev` — без интерактива) + `npm run prisma:seed` (идемпотентный upsert, безопасно повторять).
4. `npm run test:integration` (`vitest run --mode=integration`; `fileParallelism:false` уже в конфиге).
5. **Teardown:** по умолчанию контейнер остаётся поднятым (быстрые повторные прогоны); `npm run gate:down` (или `gate -- --down`) останавливает. Шаг 1 идемпотентно переживает «уже поднят».
6. **Exit code** ненулевой при падении любого шага — чтобы и хук, и человек видели провал.

### Компонент 2 — условное принуждение (pre-push «L2.5»)

Расширить [.husky/pre-push](../../../.husky/pre-push): после `npm run test:unit` решить, нужен ли гейт для **этого** пуша, и запустить его только если да.

- **Триггер по путям.** Гейт запускается, если в диапазоне пуша затронут хоть один файл под `prisma/`, `src/worker/` или `src/lib/services/`, либо любой `*.test.ts` с `new PrismaClient(`. Иначе — пропуск (нулевой оверхед, как сейчас).
- **Вычисление диапазона.** pre-push получает на stdin строки `<local ref> <local sha> <remote ref> <remote sha>`. Сравниваем `remote_sha..local_sha`; для новой ветки (`remote_sha` = нули) — против `merge-base origin/main`. Логику выносим в `scripts/gate-precheck.ts` (тоже `tsx`, кроссплатформенно), хук лишь зовёт его и по exit-коду решает, звать ли `npm run gate`.
- **Docker недоступен + релевантные изменения** → exit≠0 с понятным сообщением: «Изменения затрагивают интеграционный слой, но Docker не запущен. Запусти Docker и повтори, либо осознанно `git push --no-verify`.» (Молчаливый пропуск сделал бы гейт бессмысленным.)
- **Аварийный выход** — `--no-verify`, как и для L1/L2 (§6).

### Компонент 3 — закрыть 3 дыры покрытия

Новые интеграционные тесты по существующему паттерну (`worker.oneCSync.upsert.test.ts`: прямой вызов процессора с фейковым `job()`, фикстуры с уникальным `stamp`, cleanup по `externalId`). Все три процессора принимают инжектируемый `db: PrismaClient = prisma` вторым параметром — тест передаёт свой `PrismaClient` (чистый шов, как в существующих worker-тестах):

- **`worker.push-lead.test.ts`** — `pushLeadProcessor` зовёт `pushLeadToOneC(db, leadId)` и возвращает `{ leadId, externalIdInOneC }`; тест проверяет успешный путь (проставлен `externalIdInOneC`) и проброс ошибки при `!res.ok`. Отдельно — **`notifyPushLeadFinalFailure`** (уже экспортируется из `processors/push-lead`): тест зовёт её напрямую и проверяет, что **админам партнёра** (`roleInPartner='admin'`, `isActive`) создаются `Notification` типа `sync_error` (обвязку BullMQ из `worker/index.ts` не воспроизводим).
- **`worker.generate-commission-pdf.test.ts`** и **`worker.generate-commission-xlsx.test.ts`** — застабить Supabase Storage (`getServerClient`/`documentBucket` из `@/lib/storage/supabase`, паттерн `vi.hoisted` + `vi.mock` из §6), прогнать процессор на засеянном `CommissionStatement`, проверить: генератор произвёл непустой буфер; `storage.upload` вызван с корректными `path` (`partners/<id>/commission/<id>.pdf|xlsx`) и `contentType`; запись statement обновлена (`pdfPath` / `xlsxPath` соответственно). Покрыть и ветки ошибок `NOT_FOUND` (нет statement) и `STORAGE_FAILURE` (upload вернул error). Тесты остаются **интеграционными** (читают/пишут `CommissionStatement` в Postgres), но внешний Supabase замокан — гибрид, уже принятый в проекте для upload-роутов.

Новые тесты содержат `new PrismaClient(` → самообнаруживающийся детектор автоматически отнесёт их к `--mode=integration`. Настраивать ничего не нужно.

### Компонент 4 — структурный guardrail (не дать дыре открыться)

Unit-тест `src/__tests__/worker.processor-coverage.guardrail.test.ts`. **Не** содержит `new PrismaClient(` → это unit/L2-тест, гейтится `pre-push` **всегда**, без Docker.

- **Логика:** прочитать зарегистрированные процессоры (источник истины — файлы `src/worker/processors/*.ts`, экспортирующие `*Processor`). Для каждого убедиться, что существует `*.test.ts`, импортирующий `@/worker/processors/<name>`. Падать со списком непокрытых процессоров. Явный `ALLOWLIST` для сознательных исключений — с комментарием-обоснованием.
- **Реализация:** `readdirSync` по `src/worker/processors` и `src/__tests__` + греп импортов. Без DOM, без Postgres — та же «проверка по построению», что и mode-partitioning в `vitest.config.ts`.
- **Почему Vitest-скан, а не ESLint** (в отличие от модального guardrail): ESLint смотрит на один файл за раз и не выражает кросс-файловую инвариантность «для процессора X где-то существует тест». Это естественно ложится на файловый скан в unit-слое.

## Tests

- **Гейт-скрипт (К1):** ручная верификация — `npm run gate` на машине с Docker; ожидаем migrate+seed+зелёный интеграционный прогон; повторный запуск (контейнер поднят) тоже зелёный (идемпотентность шага 1).
- **Триггер (К2):** три кейса, ручная проверка (хуки трудно юнит-тестировать кроссплатформенно): (а) пуш, трогающий `src/worker/**` → гейт запускается; (б) пуш, трогающий только доки/README → гейт пропущен; (в) Docker остановлен + релевантные изменения → exit≠0 с сообщением.
- **3 новых процессорных теста (К3):** зелёные под `npm run gate`.
- **Guardrail (К4):** (а) на дереве после К3 — зелёный; (б) **негативный кейс**: временно добавить пустой `src/worker/processors/_probe.ts` без теста → guardrail обязан упасть со списком; убрать probe. Разовая ручная проверка при добавлении.

## Принятые решения (зафиксировано по делегированию пользователя)

1. **Механизм принуждения — Вариант 2 (локальный условный pre-push), НЕ серверный CI.** Эффективность = достижение цели в рамках задокументированных ограничений; №3 (CI) строго надёжнее, но разворачивает §11 без известной причины отключения Actions — риск перевешивает выигрыш. №2 реально принуждает и остаётся в архитектуре §6. №3 — потолок для отдельного решения с обсуждением.
2. **Триггер хука — по путям** (`prisma/`, `worker/`, `services/` + DB-тесты), не «всегда» (медленно на каждом push) и не «только push в main» (пуши идут в feature-ветки → почти не срабатывал бы).
3. **Оркестрация — `tsx`-скрипт, не bash** (кроссплатформенность Windows/sh).
4. **Teardown — контейнер остаётся поднятым** по умолчанию (скорость повторов); `gate:down` опционально.
5. **Docker-недоступность при релевантных изменениях — падение хука**, не молчаливый пропуск.
6. **Guardrail — Vitest-скан (unit/L2), не ESLint:** кросс-файловая инвариантность «у процессора есть тест» не выражается одним ESLint-правилом.
7. **Redis в гейте по умолчанию не поднимается** (процессоры в тестах вызываются как функции, минуя BullMQ); флаг `--redis` при необходимости.

## Риск

Низкий.

- **Docker-зависимость:** гейт требует Docker на машине. Митигировано: compose уже есть и используется; релевантные пуши редки; `--no-verify` как аварийный выход (§6).
- **Кроссплатформенность хука:** pre-push парсит git-stdin-протокол; вынесено в `tsx`-скрипт ради независимости от sh/PowerShell. Разовая проверка на Windows-машине разработчика.
- **Нестандартный локальный Postgres:** если у разработчика БД на другом порту/хосте — переопределяется через `GATE_DATABASE_URL`. Документируется в §6.
- **Самый правдоподобный сбой:** guardrail ложно-зелёный (процессор есть, теста нет, а скан не заметил) — покрыто негативным probe-кейсом; ложно-красный — `ALLOWLIST`.
- **Время pre-push** на релевантных пушах вырастает на единицы минут — осознанный компромисс ради гейтинга; триггер по путям сужает частоту.
