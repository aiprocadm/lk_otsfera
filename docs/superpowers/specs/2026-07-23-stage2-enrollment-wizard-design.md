# Этап 2 ТЗ — мастер заявки на обучение (Модуль 2, ФТ-2.1–2.6)

Дата: 2026-07-23 · Статус: **draft — ждёт подтверждения заказчика** ·
ТЗ: [docs/tz/2026-07-23-tz-lk-otsfera-v1.md](../../tz/2026-07-23-tz-lk-otsfera-v1.md) §Модуль 2, §9 этап 2.

## 1. Цель и критерий приёмки (§9 ТЗ)

«Организация подаёт заявку на 20 слушателей одной заявкой ≤ 3 минут;
направление — только из справочника; податель получает уведомления о смене
статуса».

Сейчас: `EnrollmentRequest` — однострочная (один слушатель, `courseTitle`
свободным текстом), форма без шагов, уведомлений подателю нет.

## 2. Модель данных (ФТ-2.2 + ответ на вопрос 5)

**`EnrollmentRequest` (шапка)** — остаётся, меняется состав:

- `directionId` FK → `TrainingDirection` (обязательное; свободный текст запрещён).
- `courseTitle` → переименовывается в `legacyCourseTitle String?` (данные
  сохраняются; для старых заявок направление показывается из legacy-текста).
- `studentName`/`studentEmail` уходят в позиции (см. миграцию).
- Остальное (податель, роль, partner/org, статус, ревью-поля) — без изменений.

**`EnrollmentRequestItem` (позиция, новая модель)**:

```
id, createdAt, updatedAt
requestId FK → EnrollmentRequest (Cascade)
studentId String?        — существующий сотрудник (Student) ИЛИ:
fullName  String         — ФИО (для существующего — копия на момент подачи)
email     String
position  String?        — должность (вопрос 5)
snils     String?        — СНИЛС (вопрос 5)
birthDate DateTime?      — дата рождения (вопрос 5)
extra     String?        — свободное редактируемое поле (вопрос 5), подпись в UI «Дополнительно»
status    EnrollmentStatus @default(pending) — индивидуальный статус позиции
externalStudentId String? — при ручном зачислении (переезжает с шапки)
@@index([requestId])
```

Доп. поля (`position/snils/birthDate/extra`) — **необязательные** и редактируемые
для обеих разновидностей позиций (у выбранного из справочника сотрудника их в
`Student` нет — вводятся в мастере при желании). Модель `Student` не трогаем —
данные слушателя для конкретного обучения живут в позиции заявки (в §10 вопрос
о будущей синхронизации).

**Статусы (ФТ-2.3).** Enum `EnrollmentStatus` расширяется добавлением значений
(безопасная additive-миграция): `pending → approved → provisioned →
in_training → certificates_ready` (+ `rejected`). Русские подписи ленты:
«подана → принята → зачислены → идёт обучение → удостоверения готовы».
Шапка агрегирует: статус шапки = минимальный по конвейеру статус её позиций
(отклонённые позиции не учитываются; все отклонены → шапка rejected).

**Миграция данных**: каждая существующая заявка получает одну позицию
(`fullName = studentName`, `email = studentEmail`, `status` = статус шапки,
`externalStudentId` переносится); `courseTitle` → `legacyCourseTitle`;
`directionId` у legacy-заявок NULL (в UI показываем legacy-текст) — поэтому
`directionId` в схеме nullable, но **обязателен при создании** (валидация сервиса).

## 3. Мастер подачи (ФТ-2.1) — 3 шага

Одна страница-мастер (client component, shared для organization/partner/manager —
текущая форма уже сознательно shared presentational; пропсы: список направлений,
организации, сотрудники выбранной организации):

1. **Направление** — select активных `TrainingDirection` (сортировка `sortOrder`).
   Партнёр/менеджер дополнительно выбирают организацию (как сейчас) — выбор
   организации подгружает её сотрудников для шага 2.
2. **Слушатели** — таблица позиций:
   - блок «Из сотрудников организации»: чекбоксы (`listOrgStudents`, поиск по ФИО);
   - «Добавить слушателя» — строка с полями ФИО*, email*, должность, СНИЛС,
     дата рождения, «Дополнительно»;
   - «Импорт из Excel»: кнопка «Скачать шаблон» (xlsx с колонками ФИО*, Email*,
     Должность, СНИЛС, Дата рождения, Дополнительно) + загрузка файла,
     построчная валидация с русскими сообщениями («Строка 3: не указан email»),
     валидные строки добавляются в таблицу, невалидные показываются списком ошибок;
   - у любой позиции до отправки поля редактируемы, позицию можно удалить.
3. **Проверка** — направление, итоговый список (N слушателей), примечание
   (`note` шапки), кнопка «Отправить заявку».

Валидация: ≥ 1 позиции; email обязателен и валиден; дубликаты email внутри
заявки склеиваются с предупреждением. СНИЛС (если заполнен) — 11 цифр
(маска `XXX-XXX-XXX XX`, без проверки контрольной суммы — см. вопрос §10).

Excel: чтение — существующая зависимость `xlsx`, шаблон — `exceljs`
(обе уже в package.json; паттерн — admin payments-import).

## 4. Сервисы и API

- `submitEnrollmentRequest` переписывается: вход
  `{ directionId, organizationId?, note?, items: [{studentId?|fullName+email, position?, snils?, birthDate?, extra?}] }`;
  скоуп-проверки организаций/партнёра — как сейчас; `studentId` обязан
  принадлежать выбранной организации (иначе `forbidden`); создание шапки+позиций
  в транзакции; аудит.
- `POST /api/enrollments` — тот же роут, новый контракт тела (тонкий, мапит коды).
- Шаблон: `GET /api/enrollments/import-template` (xlsx, публичных данных нет —
  под сессией). Парсинг Excel — **на клиенте** (библиотека `xlsx` уже клиентская
  в admin-импорте) → на сервер уходит уже разобранный JSON позиции.
- `lifecycle.ts`: `approve`/`reject` остаются на шапке (принята/отклонена целиком);
  новые переходы `markProvisioned`/`markInTraining`/`markCertificatesReady` —
  **по позициям** (bulk: выбранные позиции или все) из очереди менеджера/админа;
  агрегация статуса шапки после каждого перехода. Ручной режим (LMS-автоматизации
  нет — как сейчас), защита lifecycle_violation по конвейеру.
- `list.ts`/`enrollment-list`/`enrollment-queue`: списки показывают направление
  (или legacy-текст), число слушателей; деталка — позиции с индивидуальными
  статусами.

## 5. Деталка подателя (ФТ-2.3) + дашборды (ФТ-2.4)

- Страница деталки заявки у подателя (organization/partner):
  статусная лента 5 точек по русским подписям §2; таблица позиций со
  статус-бейджами; на `certificates_ready` — ссылка «Скачать удостоверение»,
  если у слушателя есть `Certificate.documentId` по этому направлению
  (скачивание — существующий presigned-роут документов). Полноценный реестр
  удостоверений — Модуль 6 (этап 3), здесь только прямые ссылки при наличии.
- Дашборды организации и партнёра: кнопка «Подать заявку на обучение» +
  блок «Последние заявки» (5 шт., статус-бейдж, ссылка на деталку).
- Пустые состояния и инлайн-подсказки (ФТ-2.6) — в мастере и списках.

## 6. Уведомления (ФТ-2.5)

Тип `enrollment_status_changed` **подателю** (submittedByUserId) на каждый
переход статуса шапки (approve/reject/provisioned/in_training/certificates_ready):
мультиканально через существующий диспетчер (email + связанные каналы), текст
русский («Заявка на обучение: N слушателей, направление X — статус „зачислены“»).
Существующее `enrollment_submitted`-уведомление менеджерам при подаче — сохраняется.
Fan-out best-effort (§3) — сбой уведомления не блокирует переход.

## 7. RBAC и флаги

- Роли подачи — как сейчас (`canSubmitEnrollments`: partner/organization/manager/admin).
- Скоупы чтения — как сейчас (податель видит свои; org — своей организации;
  partner — своих организаций; staff — очередь).
- Feature-флаг: существующий `enrollment_requests` (opt-in) — мастер живёт под
  ним же, новый флаг не нужен.

## 8. Тестовая стратегия (порог 100%)

- Модель/миграция: integration — legacy-заявка получает позицию, `legacyCourseTitle`
  сохранён; enum-расширение применяется.
- `submitEnrollmentRequest`: скоупы (org/partner/manager), чужой `studentId` →
  forbidden, ≥1 позиции, дубликаты email, транзакционность (unit + integration).
- lifecycle по позициям: конвейер, bulk, агрегация шапки, lifecycle_violation.
- Валидатор Excel-строк (чистая функция): каждая ошибка → русское сообщение;
  СНИЛС-маска; дата рождения.
- Уведомления: enrollment_status_changed на каждый переход, best-effort.
- UI: мастер (шаги, добавление/удаление/редактирование позиций, импорт-ошибки),
  лента статусов, дашборд-блоки, пустые состояния; страницы — renderServerComponent.
