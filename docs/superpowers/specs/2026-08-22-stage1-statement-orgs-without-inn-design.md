# Этап 1 — выписка по счёту 51: организации без ИНН

**ТЗ:** [единая логика кабинетов, документы для заказчика и управление интеграциями из интерфейса](../../tz/2026-08-21-tz-cabinets-documents-integrations.md), требования `У-83`…`У-93` (блок J), решение заказчика `Р-11`.
**Дата:** 22.08.2026. **Статус:** ждёт подтверждения заказчика.

## 0. Коротко

Вы загрузили выписку, где контрагентов десятки, а организаций создалось три.
Причина доказана (§3.1 ТЗ): 1С печатает в карточке счёта 51 только название
контрагента, без ИНН, а весь путь создания — автоматический, пакетный и даже
ручной из строки очереди — требует валидный ИНН. Этап учит импорт создавать
организации по названию: ИНН подтягивается из справочника ЕГРЮЛ (DaData),
когда там нашлась ровно одна действующая организация с таким названием; дубли
ловятся по нормализованному «ключу контрагента» (без кавычек, регистра и формы
собственности); предпросмотр показывает три группы и даёт вписать ИНН руками;
очередь разбора перестаёт молча обрезаться на 200 строках; откат покрывает и
новые организации.

Делегированные решения `Р-15`…`Р-24` этап не задействует. Действует `Р-11`
(ваше решение 21.08.2026) и два решения прошлой программы, которые сохраняю:
`Р-9` (автосоздание работает сразу, без отдельного флага) и `Р-10` (создание —
только после показа списка; применение «вслепую» запрещено).

## 2. Решения, которые предлагаю

### 2.1. Порядок: три PR

| PR | Что | Требования |
|---|---|---|
| **PR-1 «ключ контрагента»** | Модуль нормализации, две колонки с индексами и SQL-бэкфиллом (единственная миграция этапа), расширение разбора ИНН и названия | `У-83`, `У-84`, `У-91` |
| **PR-2 «матчер и очередь»** | Ступень точного совпадения по ключу; очередь: страницы по 50 со счётчиком, фильтры, сортировка, группировка | `У-88`, `У-90` |
| **PR-3 «создание без ИНН»** | DaData-обогащение, автосоздание по названию с дедупом, предпросмотр в три группы с ручным ИНН, пакетное и ручное создание без ИНН, диагностика «Контрагенты», интеграционный регресс с откатом, переписанные стражи | `У-85`, `У-86`, `У-87`, `У-89`, `У-92`, `У-93` |

**Почему так.** §5 ТЗ требует накатить бэкфилл `nameKey` (`У-84`) миграцией
**до** включения ступени матчера (`У-88`) — это ровно граница PR-1/PR-2. Все
изменения схемы живут в PR-1; PR-2 и PR-3 схему не трогают, поэтому откат
любого из них — обычный revert без обратной миграции (колонки безвредны, как
и записано в ТЗ). Опасное действие — создание организаций без ИНН — едет
последним, когда ключи уже посчитаны, дубли уже ловятся матчером, а очередь
уже видна целиком, с фильтрами и счётчиком.

### 2.2. Ключ контрагента (`У-83`, `У-84`) — PR-1

Новый модуль `services/import/oneCAccountCard/counterparty-key.ts`:

```ts
counterpartyKey(raw: string): { key: string; orgForm: string | null }
```

верхний регистр · `ё → е` · кавычки и пунктуация → пробел · пробелы схлопнуты ·
организационно-правовая форма (ООО, АО, ПАО, ЗАО, ОАО, ИП, НКО, АНО, ГБУ, МБУ,
ФГУП, МУП и т. п.) вырезана из ключа и возвращена отдельным полем.

Сегодняшняя `normalizeName` — основа, но её приходится чинить, а не просто
переносить (см. таблицу §1: `ё`, короткий список форм, неработающий `\b`).
Матчер (fuzzy-ступень) переводится на новый модуль тем же PR — поведение
fuzzy от этого только выравнивается.

Миграция (единственная в этапе):

- `PaymentImportRow.counterpartyKey String?` + индекс — заполняется при записи
  строки в очередь; у уже лежащих строк — SQL-бэкфиллом той же миграции;
- `PaymentImportRow.counterpartyInnSource String?` (`'file' | 'dadata' |
  'manual'`) — колонка появляется здесь, заполнять её начнёт PR-3;
- `Organization.nameKey String?` + индекс `[companyId, nameKey]` — бэкфилл
  всех организаций той же миграцией; дальше ключ пишут все точки создания и
  переименования.

Опасность бэкфилла: SQL может молча разойтись с TS-функцией. Страж:
интеграционный тест берёт SQL-выражение **из файла миграции** (приём стража
`У-36`), прогоняет его через `$queryRaw` на наборе имён («ООО «Ромашка»»,
«РОМАШКА, ООО», «Ёлки-Палки АО», «ИП Иванов И.И.», …) и сравнивает с
`counterpartyKey()`. Расхождение — красный тест.

Чтобы `nameKey` не протухал, его пишут **все** точки записи `Organization.name`
(автосоздание импорта, ручное создание из очереди, админский диалог, формы
реквизитов, writer 1С-синка — точный список даст план по grep). Держит
текстовый страж по образцу `import.no-second-writer`: файл, создающий или
переименовывающий организацию без записи `nameKey`, — красная сборка
(исключения — списком с причиной; страж проверяется мутацией).

### 2.3. ИНН из ЕГРЮЛ по названию (`У-85`) — PR-3

`suggestParty` расширяется полями `status` и `opf` (сегодня нормализатор их
выбрасывает). Правило приёмки ИНН — строже не бывает:

> ИНН принимается, только если DaData вернула **ровно одну действующую**
> (`ACTIVE`) организацию, чей ключ контрагента совпал с ключом из выписки
> (форма собственности может отличаться — вопрос 1). Ноль подсказок, две и
> больше, ликвидированная, несовпавший ключ — ИНН не подставляется,
> организация создаётся без ИНН.

Механика: обогащение бежит по **уникальным контрагентам** (не по строкам)
до транзакции; ответ кладётся в модульный кэш с TTL 15 минут по ключу
контрагента — применение переиспользует ответы предпросмотра, DaData видит
один запрос на контрагента. Сервис зовётся напрямую (`suggestParty`); лимит
роута `/api/suggest/party` (30/мин на пользователя) серверного пути не
касается. DaData выключена, не настроена или упала → шаг молча пропускается,
импорт работает, в диагностике строка «DaData не использовалась: …».

Источник ИНН пишется в `counterpartyInnSource` и в аудит создания
(`organization_created_auto` получает `innSource`).

### 2.4. Автосоздание по названию и дедупликация (`У-86`) — PR-3

`collectNewCounterparties` группирует кандидатов по **ключу контрагента**, а
не по ИНН; ИНН — атрибут кандидата (из файла, из DaData, введён руками) и
может быть пуст. Строки без названия и без ИНН кандидатами не становятся
(«без названия — создать нечего», причина в очереди). Перед созданием дедуп:

- **(а) по ИНН** — организация с таким ИНН уже есть (`Organization.inn` —
  глобальный `@unique`): своя компания → платежи привязываются к ней, дубль
  не создаётся; чужая компания → строка в очередь с причиной «ИНН совпал с
  другой компанией»;
- **(б) по `nameKey`** среди организаций компании импорта → привязка к
  существующей, дубль не создаётся.

Ре-матч после создания расширяется картой «ключ → организация» (сегодня —
только «ИНН → организация»), привязку делает ступень матчера из 2.5. Правило
компании `У-50` — без изменений: руководитель — своя; админ — выбранная в
форме; рядовой менеджер организации не заводит, его строки идут в очередь.
Плашка «ИНН не указан» и кнопка «Найти в ЕГРЮЛ» в карточке организации — это
этап 2 (`У-94`), сюда не тянем.

### 2.5. Ступень матчера «ключ → организация» (`У-88`) — PR-2

Между ступенями «ИНН» и «fuzzy»: точное совпадение `nameKey` в скоупе
**компании импорта** → `route: 'exact'`, платёж привязан. Скоуп: руководитель —
своя компания; админ — компания, выбранная в форме; компания не определена →
ступень пропускается, строка идёт по прежним правилам (чужие компании по
названию не матчим — изоляция C8). Fuzzy остаётся только кандидатом очереди.

### 2.6. Предпросмотр в три группы (`У-87`) — PR-3

«Будет создано организаций: N» разбивается на группы: **с ИНН из файла** ·
**ИНН найден через DaData** (рядом с названием из файла — название из ЕГРЮЛ) ·
**без ИНН**. У каждой строки — галочка «создавать» (включена по умолчанию) и
поле ИНН: вписанный руками валидируется `isValidInn`; «такой ИНН уже есть» →
строка превращается из создания в привязку, с подсказкой.

Как выбор доезжает до применения: предпросмотр и применение по-прежнему
пересчитывают файл заново (осознанное решение прошлой программы — состояние
на сервере не храним), а форма передаёт применению **правки по ключу
контрагента**: `{key, create: false}` и `{key, inn: '…', innSource:
'manual'}`. Сервер валидирует правки заново: неизвестный ключ игнорируется,
кривой ИНН — ошибка до записи. Применение без показа списка остаётся
запрещённым (`Р-10`).

### 2.7. Очередь разбора (`У-90` — PR-2, `У-89` — PR-3)

Список (`У-90`): `listQueue` возвращает `{rows, total}`, страницы по 50
(`Paginator`, эталон — заказы заказчика), счётчик «всего в очереди N»,
фильтры «без ИНН / с ИНН / есть кандидат / есть кандидат-заказ», сортировка
по дате, сумме и контрагенту, группировка «по контрагенту» — свёрнутые строки
одного ключа (при сортировке по контрагенту группа целиком лежит на одной
странице). `take: 200` удаляется.

Создание (`У-89`): пакетное «Создать организации» группирует строки и по ИНН,
и по ключу; колонка ИНН в диалоге редактируема; пустой ИНН разрешён с
предупреждением «организация будет создана без ИНН». `createOrgFromQueueRow`
принимает пустой ИНН (`bad_inn` — только для **непустого** невалидного).
После создания привязываются все строки очереди с тем же ключом или ИНН.

### 2.8. Разбор файла (`У-91`) — PR-1

`extractInn` дополнительно распознаёт «ИНН/КПП 7701234567/770101001» и
«ИНН: 7701234567»; уже работающие формы закрепляются регрессами.
`extractCounterparty` чистит название от всех этих хвостов и от скобок с
ИНН/КПП. Регресс — на фикстуре реального файла
(`import.card51.real-layout.test.ts`).

### 2.9. Диагностика «а остальные почему нет» (`У-92`) — PR-3

Блок «Контрагенты» в предпросмотре и в итоге импорта: «в файле N · с ИНН из
файла a · ИНН найден через DaData b · без ИНН c · уже есть в системе d ·
будет создано e». Причины очереди пополняются («без названия — создать
нечего», «ИНН совпал с другой компанией»), а словарь причин переезжает из
компонента в `errors/messages.ts` — единый источник русских строк.

### 2.10. Стражи и откат (`У-93`, переписывание по `Р-11`) — PR-3

Тесты, закреплявшие «только валидный ИНН», **переписываются** под новое
правило, а не «чинятся» откатом кода (ловушка 4 CLAUDE.md §14):
`import.card51.new-counterparties`, `import.card51.queue-bulk`,
`import.card51.create-org.unit` (пустой ИНН), `import.card51.batch.unit`,
`import.card51.matcher`. Вердикты `У-49`/`У-51` в AUDIT.md получают пометку
«уточнено Р-11» тем же PR.

Откат уже удаляет автосозданные организации по следу батча — организации,
созданные по названию, попадают в тот же след без нового кода. Интеграционный
регресс на живом Postgres (это и есть регресс жалобы «3 из многих»): фикстура
реальной раскладки, **пять контрагентов, ИНН только у одного, DaData замокана
на двух** → организаций **пять**, платежей привязано пять, очередь пуста;
откат батча возвращает исходное состояние.

## 3. Тесты

- **ключ**: таблица пар «сырое имя → ключ + форма» (кавычки всех видов, `ё`,
  каждая орг-форма, форма без пунктуации вокруг, дефисы, ИП с ФИО); страж
  «SQL-бэкфилл ≡ TS-функция» через `$queryRaw` по тексту миграции;
- **nameKey**: создание и переименование из каждой точки записи обновляют
  ключ; текстовый страж точек записи (мутация: убрать запись `nameKey` из
  одной точки → тест падает);
- **матчер**: «то же название, другая орг-форма» → exact; «в кавычках и без» →
  exact; «похожее, но другое название» → очередь; организация **другой**
  компании по ключу не матчится; прежние ступени не сломаны;
- **DaData**: ИНН принят (ровно одна ACTIVE + ключ совпал); отвергнут (0
  подсказок / 2+ / ликвидирована / ключ не совпал); выключена → пропуск со
  строкой диагностики; кэш: повторный вызов по тому же ключу в сеть не ходит;
- **предпросмотр/применение**: три группы с правильными составами; снятая
  галочка — не создаём; ручной ИНН валидируется, существующий ИНН превращает
  создание в привязку; правка с неизвестным ключом игнорируется;
- **очередь**: 250 строк → счётчик «всего 250» и страницы по 50; фильтры и
  сортировка; пакетное создание без ИНН — с предупреждением; после создания
  привязаны все строки того же ключа;
- **интеграционный регресс** «пять из пяти» + откат (см. 2.10) — живой
  Postgres, обязателен (`npm run gate`);
- **права**: рядовой менеджер организации не заводит (строки — в очередь);
  руководитель не видит чужие батчи и не создаёт в чужой компании.

## 4. Риски

| Риск | Что делаем |
|---|---|
| DaData подставит чужой ИНН | Правило «ровно одна действующая + совпавший ключ»; в предпросмотре видно название из ЕГРЮЛ рядом с названием из файла; галочку можно снять; откат удаляет созданное |
| Дубли организаций по названию | Дедуп по `nameKey` в скоупе компании + глобальный `@unique` на `inn`; бэкфилл `nameKey` едет миграцией **до** включения ступени (граница PR-1/PR-2 — порядковое ограничение §5 ТЗ) |
| SQL-бэкфилл молча разойдётся с TS-нормализацией | Страж-сравнение через `$queryRaw`, SQL берётся из файла миграции |
| Большая выписка съест квоту DaData | Один запрос на уникального контрагента + кэш 15 минут; потолок — вопрос 3 |
| Мусорное название станет организацией | Кандидат строится из субконто «Контрагент» (колонка «Аналитика»), строки без названия не создаются, показ списка с галочками обязателен (`Р-10`) |
