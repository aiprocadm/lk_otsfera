## 1. Что требует ТЗ (§10 дословно)

**Рабочий статус (основной пайплайн заявки), семь значений:**

1. Черновик заявки
2. Принято в работу
3. Оплата поступила
4. Документы выданы
5. Бухгалтерия подписана
6. Заявка закрыта
7. Отменена — терминальный, доступен на любой стадии

Плюс: **финансовый статус хранится отдельно** (счёт не выставлен · выставлен ·
не оплачен · частично оплачен · оплачен · частичный возврат · полный возврат ·
отменён), а у каждого слушателя внутри заявки — **свой статус обучения**.

**Права:** партнёр/организация — только черновик и отправка; менеджер — обычный
процесс; администратор и руководитель — любой статус, возврат на предыдущую
стадию, отмена. При каждом изменении хранится: прежний статус, новый, дата и
время, пользователь, комментарий/причина.

**Настройка:** администратор и руководитель добавляют, переименовывают,
меняют порядок и деактивируют статусы. **Использованный статус нельзя удалить
физически — только деактивировать.**

## 2. Что в коде (разведка, сверено 29.07.2026)

Главное открытие: **«статус заявки» в системе не один, а три независимые оси**,
и ни одна не совпадает с семёркой из §10.

| Ось | Поле | Значения | Кто двигает |
|---|---|---|---|
| **Жизненный цикл** | `Order.status` (`OrderStatus`) | `new`, `in_progress`, `waiting_client`, `completed` | [orderLifecycle.ts](../../../src/lib/services/manager/orderLifecycle.ts) — **матрица переходов** + причина при «ждём клиента» + условия завершения |
| **Операционный** | `Order.executionStatus` (`ExecutionStatus`) | `pending`, `in_progress`, `completed`, `cancelled`, `on_hold` | [manager/status.ts](../../../src/lib/services/manager/status.ts) — намеренно **плоский** список, любой переход разрешён |
| **Финансовый** | `Order.financialStatus` | `not_billed`, `billed`, `partially_paid`, `paid`, `refunded` | считается по платежам |

Плюс отдельные факты-даты, которые в §10 выглядят статусами:
`accountingSignedAt` («бухгалтерия подписана» — галочка менеджера),
`resultDeliveredAt` / `deliverablesApprovedAt` («документы выданы» — этап 12),
`paidAt` («оплата поступила»). И статус обучения по каждому слушателю —
`OrderItem.trainingStatus` (`pending`, `in_progress`, `certificate_issued`, `cancelled`).

**Что это значит.** Пункты 3, 4, 5 семёрки §10 сегодня — **не статусы, а
производные факты**: оплата приходит из платежей, «документы выданы» ставится
кнопкой передачи результата, «бухгалтерия подписана» — галочкой. Сделать их
строками настраиваемого справочника — значит либо дублировать источник правды,
либо переносить эти факты в справочник целиком.

**Где ещё завязано на статусы** (это придётся трогать):

- уведомления: `order_status_changed`, шаблоны писем менеджеру и организации;
- панель жизненного цикла на деталке заказа (кнопки переходов, причина возврата);
- выгрузки: [`services/orders/xlsx.ts`](../../../src/lib/services/orders/xlsx.ts) переводит статусы в русские подписи;
- задачи: `lib/tasks/columns.ts` держит `statusAnchor`;
- фильтры списков заказов у всех ролей.

## 3. Развилка, которую должен решить заказчик (Q1)

Есть три честных пути. Они различаются не «как красивее», а **сколько боевых
механизмов придётся переписать**.

### Вариант A — справочник поверх жизненного цикла (рекомендую)

`Order.status` перестаёт быть enum'ом и становится ссылкой на строку
справочника `OrderStatusDefinition` (id, название, порядок, активность,
системный флаг, «терминальный»). Семь значений §10 заводятся сидом.

- Оплата, выдача документов и подпись бухгалтерии **остаются производными
  фактами**, но получают в справочнике «якорь»: строка статуса помечается
  `anchor: 'paid' | 'documents_issued' | 'accounting_signed'`, и система
  **сама** переводит заявку в этот статус, когда факт наступил. Заказчик может
  переименовать статус и подвинуть его в порядке, но не может оторвать от факта.
- Матрица переходов заменяется на порядок: вперёд — на любой следующий активный,
  назад — только администратору и руководителю (§10 «возврат на предыдущую стадию»).
- «Отменена» — строка с флагом `isTerminal`, доступна с любой стадии.
- Миграция: `new → Черновик`, `in_progress → Принято в работу`,
  `waiting_client → Принято в работу` (+ причина сохраняется как раньше),
  `completed → Заявка закрыта`. Старые значения не теряются — их видно в журнале.

**Цена:** трогаем `Order.status`, панель, уведомления, выгрузки, фильтры.
**Выгода:** ровно то, что просит §10, и один источник правды.

### Вариант B — справочник как «витрина» поверх существующих осей

Добавляем справочник только для отображения: каждая строка описывает, при каком
сочетании `status`/`financialStatus`/дат заявка «считается» в этом статусе.
Заказчик правит названия и порядок, но **добавить свой статус не может** —
только переименовать существующий.

**Цена:** минимальная, ничего боевого не ломается.
**Проблема:** §10 прямо требует «добавление», а этот вариант его не даёт.

### Вариант C — новая ось «рабочий статус» рядом с существующими

Заводим `Order.workflowStatusId` как четвёртую ось и не трогаем три старые.

**Цена:** ничего не ломается сегодня.
**Проблема:** у заявки станет четыре статуса, и никто (включая менеджера) не
будет понимать, какой из них настоящий. Через полгода это станет источником
расхождений в отчётах. **Не рекомендую.**

## 4. Дизайн (по варианту A)

### 4.1 Модель

```prisma
model OrderStatusDefinition {
  id         String   @id @default(cuid())
  companyId  String?  // null = общесистемный набор
  key        String   // машинный ключ, неизменяем
  label      String   // название — переименовывается
  sortOrder  Int
  isActive   Boolean  @default(true)
  isSystem   Boolean  @default(false) // из семёрки §10 — не удалить
  isTerminal Boolean  @default(false) // «Отменена»
  anchor     String?  // 'paid' | 'documents_issued' | 'accounting_signed' | 'closed'
  @@unique([companyId, key])
}
```

`Order.statusId` → ссылка. Старый `Order.status` **остаётся в схеме на время
перехода** (заполняется по якорю) — чтобы отчёты и 1С-обмен не сломались в день
релиза; удаляется отдельным PR после проверки на стенде.

### 4.2 Журнал переходов

§10 требует хранить прежний/новый статус, дату, пользователя и причину.
Сегодня это лежит в аудите. Предлагаю **отдельную таблицу
`OrderStatusChange`** (orderId, fromId, toId, userId, reason, createdAt) —
аудит остаётся общим журналом, а история статусов должна быть быстрым запросом
для карточки и выгрузок, а не поиском по логу.

### 4.3 Права

| Действие | Админ | Руководитель | Менеджер | Партнёр / организация |
|---|:---:|:---:|:---:|:---:|
| Настраивать справочник | ✓ | ✓ | ✗ | ✗ |
| Двигать вперёд | ✓ | ✓ | ✓ | ✗ |
| Возврат назад | ✓ | ✓ | ✗ | ✗ |
| Отмена | ✓ | ✓ | ✓ (с причиной) | ✗ |
| Черновик → отправка | ✓ | ✓ | ✓ | ✓ (свои) |

### 4.4 Экран настройки

`/admin/order-statuses` + зеркало `/leader/settings/order-statuses` — ровно тот
же приём, что сработал в §11 (Model A: руководителя в `/admin/*` не пускаем).
Список с порядком (стрелки вверх/вниз), переименование, деактивация;
системные строки — с бейджем и без кнопки удаления.

### 4.5 Что НЕ делаем

- Не трогаем `financialStatus` — §10 явно оставляет его отдельной осью.
- Не трогаем `trainingStatus` слушателей.
- Не делаем настраиваемым `executionStatus` — он останется внутренним
  операционным полем (или будет упразднён отдельным решением, см. Q3).

## 6. Тестовая стратегия

- **Миграционный регресс (главный):** заявка в каждом старом статусе после
  миграции оказывается в ожидаемом новом; ни одна заявка не теряет статус.
- Переходы: вперёд можно всем, назад — только админу и руководителю, отмена —
  с любой стадии, деактивированный статус нельзя выбрать, но уже стоящий —
  показывается.
- Якоря: оплата пришла → статус переехал сам; статус, привязанный к якорю,
  нельзя удалить и нельзя оторвать от факта.
- Журнал: каждая смена пишет строку с причиной; возврат назад без причины
  отклоняется.
- Изоляция: справочник компании A не виден компании B (если Q2 = «по компаниям»).

## 7. Риски

| Риск | Митигация |
|---|---|
| В день релиза ломаются отчёты и 1С-обмен | `Order.status` остаётся заполненным до PR-4 |
| Заказчик переименует статус, и сломаются уведомления | тексты писем берут название из справочника, а не хардкод |
| Настроят порядок так, что «Отменена» окажется в середине | терминальные строки в порядок не входят |
| Менеджер потеряет право двигать статус | матрица §4.3 закрыта тестами |
