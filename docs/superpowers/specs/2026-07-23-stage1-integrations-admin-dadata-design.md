## 1. Цель и критерий приёмки

ТЗ §9: «Все интеграции настраиваются и проверяются из админки без правки env;
смена настройки применяется без рестарта; секреты не отображаются».

Волна 2 уже перенесла в `/admin/integrations` почту, Telegram, Max, WhatsApp,
Mango, IMAP (реестр `SETTING_SPECS` + синхронный кэш + аудит + env-fallback).
Осталось закрыть по этапу 1 **дельту**:

| # | Работа | ФТ | Состояние сейчас |
|---|---|---|---|
| A | Настройки **1С** в UI (adapter, base url, токен) | 14.1, 14.2 | 1С читается из сырого env, в реестре нет |

## 2. A. Настройки 1С

Сейчас `getOneCAdapter()` ([oneCSync/index.ts](../../../src/lib/services/oneCSync/index.ts))
читает сырой `ONE_C_ADAPTER` / `ONE_C_API_URL` / `ONE_C_API_TOKEN` и кэширует
синглтон; `assertEnvOnBoot` требует url+token при `adapter=rest`.

Решение:
- Добавить в `SETTING_SPECS`: `onec.adapter` (`ONE_C_ADAPTER`), `onec.apiUrl`
  (`ONE_C_API_URL`), `onec.apiToken` (`ONE_C_API_TOKEN`, **secret**) и
  `onec.healthPath` (путь для проверки связи, задаётся админом; env
  `ONE_C_HEALTH_PATH`, по умолчанию пусто). Env — fallback, как у всех.
  **Универсальность (решение заказчика):** конфиг 1С может меняться, поэтому
  адрес проверки не зашивается в код — админ задаёт `apiUrl` + опционально
  `healthPath` в профиле и сам подключает интеграцию без разработчика.
- `getOneCAdapter()` переводится на `cachedIntegrationSetting` и перестаёт быть
  «вечным» синглтоном: пересборка по kind+url+token (паттерн `cachedForKey`, как
  IMAP-адаптер). Server-action 1С после сохранения зовёт сброс кэша адаптера.
- Воркер уже праймит кэш в sync-процессорах (волна 2) — 1С-джобы подхватят новые
  креды без рестарта (≤ TTL + интервал очереди).
- `assertEnvOnBoot`: убрать **жёсткое** требование url+token на бут (теперь их
  можно задать в UI после старта). Оставить мягкое предупреждение в лог, если
  `adapter=rest` и креды не заданы ни в env, ни (на момент бута) в БД. Это
  снимает риск «нельзя стартовать без env».
- Форма «1С» на `/admin/integrations`: select adapter (`fake|rest`), text apiUrl,
  secret apiToken. Плашка: тюнинг-переменные (`ONE_C_MODE`, таймауты, курсор)
  остаются в env — это деплой-константы, не операционные настройки.

## 3. B. whatsapp.baseUrl

ТЗ §5 ФТ-14.1 явно требует `baseUrl` в реестр (волна 2 оставляла его в env как
деплой-константу). Следуем ТЗ: добавляем `whatsapp.baseUrl` (`WHATSAPP_AGGREGATOR_BASE_URL`,
не secret) в `SETTING_SPECS`, `whatsappAggregatorBaseUrl()` переводим на
`cachedIntegrationSetting`, добавляем поле в форму WhatsApp. (`max.baseUrl`
аналогично — по симметрии, чтобы обе формы были полными.)

## 4. C. DaData — настройки и прокси (ФТ-13.1, 13.2)

**Только инфраструктура.** Подсказки в клиентских формах и антидубли
(ФТ-13.3–13.4) — этап 5, здесь их НЕ делаем.

- Реестр: `dadata.enabled` (`DADATA_ENABLED`), `dadata.apiKey`
  (`DADATA_API_KEY`, **secret**). Карточка-форма на `/admin/integrations`.
- Прокси `GET /api/suggest/party?query=` ([новый роут]):
  - **Только авторизованные** (любая роль с валидной сессией — формы-потребители
    появятся на этапах 5/8/9). Неавторизованный → 401.
  - Rate-limit через `@/lib/rateLimit` `isRateLimited` (ключ `suggest:party:<userId>`,
    окно/лимит — напр. 30/мин; превышение → 429).
  - Читает `dadata.enabled` + `dadata.apiKey` через `getSettingValue` (async-роут).
    Выключено / нет ключа / DaData недоступна → **200 с пустым списком**
    `{ suggestions: [] }` (форма деградирует до ручного ввода без ошибок).
  - Ключ **не покидает сервер**: запрос уходит на
    `https://suggestions.dadata.ru/suggestions/api/4_1/rs/suggest/party` с
    заголовком `Authorization: Token <ключ>`; клиенту отдаётся только
    нормализованный результат (название, ИНН, КПП, ОГРН, адрес).
  - Таймаут ~3 с, fail-soft (ошибка сети → пустой список + `log.warn`).

## 5. D. «Проверить подключение» (ФТ-14.3) — универсальный механизм

**Решение заказчика:** механизм должен быть **универсальным и config-driven** —
админ вводит настройки в своём профиле и сам подключает/проверяет любую
интеграцию, без правки кода под конкретный сервер. Никаких зашитых в код
эндпоинтов конкретной 1С/Mango.

Общий server-action `testIntegrationAction(key)` (requireAdmin) → проба по
данным, которые **ввёл админ** → запись результата → `{ ok, message }` в форму;
строка «последняя проверка: <дата>, <статус>» под каждой карточкой.

**Хранение результата** — переиспользуем существующую модель `SyncState`
(entity `integration.<name>`: `lastRunAt`, `lastSuccessAt`, `lastError`). Новой
таблицы и миграции не требуется.

Пробы — по единому принципу «взять то, что задал админ, и дёрнуть сервис»:

| Интеграция | Проба (по админ-конфигу) |
|---|---|
| Почта | тестовое письмо на email админа (Resend) |
| Telegram | `getMe` по введённому botToken |
| Max | `getMe`-эквивалент по введённому токену |
| WhatsApp | GET канала по введённым apiKey + channelId + baseUrl |
| IMAP | коннект + logout (`ImapFlow`) по введённым host/port/user/password/tls |
| DaData | тестовый suggest по введённому ключу |
| 1С | HTTP-проба по введённым `apiUrl` (+ опц. `healthPath`) с `apiToken`: успех = 2xx/понятный ответ, иначе — текст ошибки связи |
| Mango | HTTP-проба доступности `vpbxBaseUrl` с подписью по введённым `apiKey`/`apiSalt` |

Для 1С и Mango это **generic-проба доступности** (достучались до адреса,
авторизация принята), а не завязка на внутренний протокол — этого достаточно,
чтобы админ убедился «связь есть / связи нет», и работает с любым сервером.
Живой обмен данными (реальные звонки Mango, полноценный протокол 1С) — отдельные
модули позже; здесь только проверка связи по админ-конфигу.

## 6. E. Диагностика вебхуков (ФТ-14.4)

Каналы TG/Max/WhatsApp/Mango имеют вебхук-роуты, но не пишут «последнее событие».

- В каждый вебхук-роут добавить **неблокирующую** запись `SyncState`
  (entity `webhook.<name>`, `lastSuccessAt = now`) при успешном приёме события.
  Ошибка записи глотается (`log.warn`) — вебхук обязан вернуть 200 быстро
  (НФ-4 degrade gracefully).
- На карточке интеграции — строка «последнее входящее: <дата|—>» + подсказка
  регистрации вебхука: готовый URL (`<APP_URL>/api/integrations/<name>/webhook`)
  и имя заголовка-секрета. Сам секрет не показываем — только «задан/не задан».

## 7. F. Матрица feature-флагов на /admin/settings (ФТ-14.6)

Read-only компонент: перечисляет `FEATURE_FLAGS` из
[featureFlags.ts](../../../src/lib/featureFlags.ts) с текущим состоянием
(`isFeatureEnabled(flag)` → «включён/выключен») и типом (opt-out/opt-in).
Источник истины по описанию — [docs/feature-flags-matrix.md](../../../docs/feature-flags-matrix.md).
Инфраструктурные переменные (`DATABASE_URL`, `JWT_SECRET`, S3, `REDIS_URL`)
перечисляются рядом как «управляются в env сервера» — без значений. Правки нет,
только отображение.

## 8. Тестовая стратегия (НФ-6, порог 100%)

- **A (1С):** `getOneCAdapter` — DB-значение побеждает env после prime, пересборка
  по смене url/token; server-action (маппинг FormData, сброс кэша); `assertEnvOnBoot`
  больше не бросает без env (мягкое предупреждение).
- **B:** `whatsappAggregatorBaseUrl`/`maxApiBaseUrl` из БД после prime; формы.
- **C (DaData):** прокси — 401 без сессии, 429 при rate-limit, пустой список при
  выключено/нет ключа/ошибка сети, happy-path (мок fetch → нормализация), ключ не
  уходит клиенту; настройки-форма.
- **D:** `testIntegrationAction` по каждому ключу (мок клиента → `SyncState`
  обновлён; стабы → статус «недоступно»); рендер строки «последняя проверка».
- **E:** вебхук-роуты пишут `SyncState.lastSuccessAt`; ошибка записи не роняет 200;
  рендер строки «последнее входящее» + подсказки.
- **F:** матрица флагов рендерит состояние из `isFeatureEnabled`.
- Существующие тесты каналов/доставки не праймят кэш → env-путь, зелёные без правок
  (контракт волны 2 сохраняется).

## 9. Решения заказчика (2026-07-23)

1. **Размер этапа.** Разбиваем на 2 PR (см. §11).
2. **Проверка 1С.** Health-адрес не зашиваем — конфиг 1С меняется, нужен
   универсальный формат: админ задаёт `apiUrl` (+ опц. `healthPath`), проба —
   generic-доступность (§5). Полноценный протокол — позже.
3. **Проверка Mango.** Делаем универсальной generic-пробой доступности по
   админ-конфигу, чтобы админ подключал из профиля без разработчика (§5). Живой
   обмен звонками — отдельным модулем позже.
