# Этап 7 «Коммерческое предложение» — спека

**Дата:** 31.08.2026 · **Требования:** `У-161`…`У-166` действующего
[ТЗ кабинетов, документов и интеграций](../../tz/2026-08-21-tz-cabinets-documents-integrations.md)
(блок N2, решение `Р-14`) · **Статус:** предъявлена заказчику.

Этап опирается на только что закрытый этап 6: выпуск документов, статусы,
нумерация с версиями, снимок строк, печать таблицы и реестр текстов уже есть.
Главная работа здесь — не «сделать ещё один документ», а **вписать в готовый
механизм бумагу, у которой почти всё иначе**: она рождается черновиком, живёт
до срока, адресована клиенту, которого может не быть в системе, и при
согласии превращается в заказ.

---

## 1. Что есть сейчас (разведка, факты с якорями)

**Готово и подходит без правок:**

- **Статусы КП уже заведены.** `enum DocumentStatus` содержит
  `draft/issued/sent/accepted/rejected/expired/cancelled`
  ([schema.prisma:146-157](../../../prisma/schema.prisma)), и комментарий прямо
  говорит: «`draft` — только у КП». Новых значений заводить не нужно.
- **Нумерация под `kind = 'proposal'` работает без миграции.**
  `DocumentCounter.kind` — обычная строка, ключ `(companyId, year, kind)`.
- **Уникальность номера КП обеспечена автоматически:** частичный индекс
  `(companyId, type, number, version) WHERE number IS NOT NULL` включает `type`,
  поэтому «КП-2026-1» и «С-2026-1» не сталкиваются.
- **Версии и перевыпуск (`У-165` → `У-151`)**: `supersededAt`,
  `replacesDocumentId` с настоящим FK, общий фильтр `ACTIVE_VERSION_WHERE`.
- **Печать строк и итогов**: `buildPrintTable` даёт таблицу, НДС, «Всего
  наименований», сумму прописью. Оформление (логотип, подпись, печать) —
  `loadDocumentBranding`, сбой ничего не блокирует.
- **Документ без заказа (`У-145`)**: две двери выпуска, `issueScope`,
  составной FK «документ → заказ» не проверяется при `orderId IS NULL`.

**Есть, но придётся расширять:**

- **Матрица переходов знает четыре типа**
  ([statusMatrix.ts:19-24](../../../src/lib/documents/statusMatrix.ts)), и все
  четыре делят один `ISSUED_FLOW`. **Поток КП не является его подмножеством:**
  `draft → sent` там нет (из `draft` ведёт только `issued`), а `rejected` и
  `expired` — конечные состояния, в которые никто не входит. Сегодня эти три
  статуса недостижимы ни для одного типа — этап 7 будет их первым потребителем.
- **`LIFECYCLE_TYPES` решает сразу три вопроса**: есть ли жизненный цикл, можно
  ли слать письмом ([send.ts:93](../../../src/lib/services/documents/send.ts)) и
  показывать ли кнопку (список продублирован литералом в
  [document-detail-view.tsx:193-197](../../../src/components/documents/document-detail-view.tsx)).
- **Реестр текстов `У-160` сам ждёт КП** — так и написано в его шапке. Но тип
  `ContractTemplateDocType` = `'contract' | 'extra_agreement'`, и обе ветки
  `generate.ts` включают шаблон только для них.
- **Отправка переводит в `sent` только из `issued`**
  ([send.ts:174-181](../../../src/lib/services/documents/send.ts)); для КП
  переход идёт из `draft`.

**Чего нет вовсе:**

- `commercial_proposal` в `enum DocumentType`. Добавление значения **сломает
  сборку** в трёх страницах, где лежит исчерпывающая карта
  `Record<DocumentType, string>` (кабинеты заказчика и партнёра).
- Поля `Document.validUntil` в базе нет: `validUntil` формы выпуска — это
  только кусок печатной фразы договора.
- Связи документа с лидом или сделкой.
- Телефона у сотрудника (`User.phone`) — для подписи менеджера.
- Места, где лид получает организацию: `lead.organizationId` ставится только
  при создании лида, дальше его не трогает ни один `update`.
- **Опечатка-ловушка**: в справочнике имён файлов заведён ключ
  `commercial_offer` ([fileName.ts:21](../../../src/lib/documents/fileName.ts)),
  которого в системе нет. После заведения типа КП скачается как «Документ …».

## 2. Модели

```prisma
enum DocumentType { … commercial_proposal }        // новое значение

model Document {
  // `У-161`: КП можно выставить клиенту, которого нет в системе.
  counterpartyType CounterpartyType?               // было обязательным
  counterpartyId   String?                         // было обязательным
  leadId           String?                         // новое: КП «повисло» на лиде
  dealId           String?                         // новое: КП выставлено по сделке
  validUntil       DateTime?                       // `У-162`: срок действия КП
  rejectedAt       DateTime?                       // `У-164`: отказ клиента
  rejectReason     String?                         //          с комментарием
}

model Company {
  proposalValidDays Int @default(14)               // `У-162`: срок по умолчанию
}
```

**Три ограничения целостности** (миграцией, Prisma их не моделирует):

1. `counterpartyType` и `counterpartyId` заполнены **вместе или никак**;
2. пустой контрагент допустим **только у КП** — остальным типам он обязателен,
   как и раньше;
3. у КП без контрагента обязателен `leadId`: бумага не может висеть в воздухе.

**Почему контрагент стал необязательным, а не появился третий вид контрагента.**
Соблазн — добавить `'lead'` в `CounterpartyType`. Но это поле — ось изоляции
клиентов: по нему построены все канальные выборки и проверки доступа
(`documentChannelPolicy.ts`, `policy.ts`). Третье значение пришлось бы
обработать в каждой из них, и любая пропущенная ветка означала бы, что чужой
клиент увидел чужую бумагу. Пустой контрагент, наоборот, **не совпадает ни с
чем**: в Postgres `NULL` не равен ничему, поэтому КП лида не попадёт ни в один
кабинет само собой, без единой правки кода изоляции.

## 3. Ключевые решения

### 3.1. Кому принадлежит КП лида (`У-161`)

Лид не несёт компании-исполнителя (в модели её нет), поэтому **`companyId` КП
берётся из сессии выпускающего сотрудника**. Это первый случай в проекте, когда
компания документа приходит не из данных, — и это записано здесь явно, потому
что комментарий `issueScope.ts` сегодня гарантирует обратное. Гарантия
сохраняется для всех остальных путей: у КП организации и у любого документа
заказа компания по-прежнему берётся из данных.

**Перенос КП на организацию** делается **отдельным действием «Создать
организацию из лида»**: сегодня в системе нет ни одного места, где лид получает
организацию, поэтому «навесить перенос на существующий переход» не на что.
Переносим только внутри одной компании-исполнителя; если организация оказалась
в другой компании — КП остаётся у лида, и экран объясняет почему. Номер при
переносе не меняется: бумага уже у клиента.

### 3.2. Черновик и отправка (`У-164`)

КП рождается в `draft` — это единственный тип, который не выпускается сразу.
Значит:

- у `generateOrderDocument` появляется **начальный статус** параметром, а не
  вторая копия выпуска: номер, версия, снимок строк, компенсирующее удаление
  файла и аудит — общие;
- письмо `document_published` при создании КП **не уходит**: черновик клиенту
  не показывают. Уведомление переезжает в момент отправки;
- в `STATUS_TRANSITIONS` заводится **отдельный `PROPOSAL_FLOW`**, а не ещё одна
  ссылка на `ISSUED_FLOW`: `draft → sent`, `sent → accepted | rejected |
  expired | cancelled`, конечные — пустые.

`LIFECYCLE_TYPES` расширяется, и вместе с ним КП автоматически получает право
уходить письмом. Дублирующий литерал в карточке документа заменяется на импорт
того же списка — два списка разъехались бы при первой правке.

### 3.3. Истечение срока: один источник правды (`У-164`)

Требование просит и «проверку при чтении», и ежедневную задачу. Разъехаться им
нельзя, поэтому:

- **чистая функция** «истекло ли» и **парный where-строитель** — один и тот же
  расчёт для карточки и для списка (приём уже применён к удостоверениям);
- **в базу статус пишет только задача** `docs.expireProposals`, через ту же
  дверь `setDocumentStatus`;
- на экране показывается расчёт на лету, поэтому «истекло вчера, а задача ещё
  не отработала» не выглядит ошибкой.

Актором фоновой смены статуса выступает **пользователь, инициировавший
отправку** (он записан в `sentById`): заводить системного пользователя ради
одной задачи — отдельная работа, а `AuditLog.userId` обязателен.
**Страж статусов расширяется на `updateMany`**: сегодня он ловит только
`document.update(` и на фоновой задаче стал бы декорацией.

### 3.4. Принятие КП (`У-164`)

Четыре возможных состояния, главный — первый:

| Откуда КП | Что делает принятие |
|---|---|
| организация без сделки | создаётся заказ, строки КП переносятся в `OrderLine` |
| сделка без заказа | то же + заказ связывается со сделкой |
| сделка с заказом **без строк** | строки переносятся в существующий заказ |
| сделка с заказом **со строками** | состав **не перезаписывается**, показывается предупреждение |

**Принятие КП не означает «сделка выиграна».** Кнопка «Выиграна» остаётся
ручной: `winDeal` сегодня одной транзакцией создаёт заказ, ставит `won` и пишет
аудит — позвать его из принятия значило бы поменять смысл существующей кнопки.

**Перенос строк.** `DocumentLine` не хранит признак «цена включает НДС», а
`OrderLine` его требует. Восстановить его из суммы налога нельзя (при ставке 0 и
при «не облагается» результат неразличим). Поэтому **`DocumentLine` получает
колонку `vatIncluded`** — иначе сумма заказа разошлась бы с суммой в КП ровно на
ставку налога.

### 3.5. Реквизиты для КП (`У-161`)

Заводится **пятый набор** проверки, а не отключение проверки: у исполнителя
обязательны юр. название, ИНН, юр. адрес, ФИО и должность подписанта — без них
нечего печатать в шапке и подписи; банковские реквизиты **не требуются**. У
заказчика — только название. «Отключить проверку» и «проверять меньше» — разные
вещи: первое молча пропустило бы КП без исполнителя.

**Подпись менеджера**: имя и e-mail сотрудника + телефон компании. Личного
телефона у сотрудников в системе нет; заводить новое поле профиля ради подписи —
отдельная работа (вынесено заказчику).

### 3.6. Тексты КП (`У-162` → `У-160`)

Реестр слотов расширяется двумя записями — «Вводный текст» (обращение) и
«Условия» — со своими группами экрана и `docTypes: ['commercial_proposal']`.
Экран настроек рисует поля по реестру, поэтому сам он не меняется; меняются его
заголовок и подзаголовок, которые сегодня говорят только про договор. Файл
`contractTemplate.ts` переименовывается в `documentTemplate.ts`: он перестал
быть договорным.

**Страж чистоты вёрстки односторонний** — он проверяет, что текстов слотов нет
в файле печати договора. Слоты КП печатаются из другого файла, поэтому страж
дополняется симметричной проверкой для КП, иначе он молча перестанет что-либо
охранять для нового типа.

### 3.7. Стадия «КП отправлено» (`У-164`)

Дефолтные стадии живут **в коде, а не в базе** (`stageId = null` означает
«стадия по умолчанию для текущего якоря»). Поэтому автоперевод технически
возможен только у компаний, заведших **свой** словарь стадий. Решение:

- дефолтная стадия «Предложение» переименовывается в **«КП отправлено»**;
- у компании со своим словарём отправка КП переводит сделку на стадию с этим
  назначением;
- у компании с дефолтными стадиями сделка **не двигается**, и форма честно об
  этом сообщает, а не делает вид, что сработало.

### 3.8. Конверсия (`У-166`)

Считается **по самим КП** — сколько отправлено за период и сколько из них
принято, — а не по колонкам доски. По стадиям посчитать нельзя: дефолтные
стадии в базе не хранятся, и цифры врали бы. У документа есть компания, поэтому
граница компании здесь чище, чем у лидов.

### 3.9. Что видит заказчик и партнёр (`У-165`)

Заказчик видит КП своей организации, **кроме черновиков**. Отклонённое и
истёкшее остаются видны с подписью состояния — человек должен понимать, что
произошло. Фильтр черновиков ставится **только для КП**, а не внутри общего
канального строителя: там он изменил бы поведение и для остальных типов.

Отказ требует комментария и кладётся в **новые поля** `rejectedAt`/`rejectReason`,
а не в `cancelReason`: «аннулировал сотрудник» и «отклонил клиент» — разные
события, и в журнале они должны различаться.

**Партнёру КП в списке не показывается** (сохраняется сегодняшнее поведение),
хотя право на чтение у него формально есть. Цены и скидки в предложении — не то,
что показывают посреднику без отдельного решения.

### 3.10. Границы этапа

- **КП не выгружается в 1С** (решение `Р-14`): поля обмена этап не заводит,
  белые списки типов не трогает. Записано явно, иначе «добавили тип везде»
  привело бы КП в 1С.
- **Приёмка (`У-175`) остаётся этапу 9**, но новый термин «Коммерческое
  предложение» добавляется в глоссарий **этим** этапом: правило §15 требует,
  чтобы слово интерфейса было в глоссарии в том же PR, что его вводит.
- Настройка «префиксы номеров» **не оживляется**: она сохраняется, но
  генератором не читается — это отдельный дефект, и чинить его посреди КП
  значит рисковать номерами уже выпущенных бумаг.

## 5. Тестовая стратегия

- **Юнит**: матрица `PROPOSAL_FLOW` (включая недостижимость `issued` для КП),
  расчёт «истекло» на границе суток, пятый набор реквизитов, перенос строк
  `DocumentLine → OrderLine` с НДС и скидкой.
- **Сервисы** (mock-prisma): четыре сценария принятия, отказ с комментарием,
  скоуп КП лида (не виден ни одному кабинету), companyId из сессии.
- **Integration**: три ограничения целостности на живой базе (пустой контрагент
  только у КП; контрагент «оба или никак»; КП без контрагента требует лида);
  перенос КП с лида на организацию; ежедневная задача.
- **Стражи**: черновик не виден заказчику · КП не попадает в выгрузку 1С ·
  статус меняется только через `setDocumentStatus` (включая `updateMany`) ·
  тексты КП не живут в вёрстке · имя файла КП. Каждый — проверен мутацией.

## 6. Вопросы заказчику (умолчания действуют, если не отменены)

1. **КП лида не отправляется системой**: у такого клиента нет кабинета, менеджер
   скачивает PDF и отправляет сам. **Умолчание: да.** Автописьмо на адрес из
   лида — отдельная работа.
2. **Принятие КП не закрывает сделку выигрышем** — кнопка «Выиграна» остаётся
   ручной. **Умолчание: да.**
3. **Заказ со строками при принятии не перезаписывается** — предупреждение,
   как у «собрать строки из позиций». **Умолчание: да.**
4. **Автоперевод сделки на «КП отправлено» работает только у компаний со своим
   словарём стадий.** **Умолчание: да**, при дефолтных стадиях сделка не
   двигается и на экране написано почему.
5. **Телефон менеджера в подписи КП не печатается** — личного телефона в
   системе нет, печатается телефон компании. **Умолчание: да.**
6. **Партнёр КП в списке не видит.** **Умолчание: да** (цены и скидки —
   не для посредника без отдельного решения).
7. **Срок действия по умолчанию — 14 дней**, настраивается в «Реквизитах
   исполнителя», нового раздела настроек не заводим. **Умолчание: да.**
8. **Восемь PR.** Этап меньше шестого, но трогает четыре точки входа, воронку
   и кабинет заказчика. **Умолчание: да**, порядок — в §4.
