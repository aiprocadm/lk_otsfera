# Этап 2 программы ПМ — кабинет слушателя (спека)

**ТЗ:** [2026-10-13-tz-pm-review-student-manager.md](../../tz/2026-10-13-tz-pm-review-student-manager.md), §4 блок 2 (`У-284`…`У-287`) и `У-273` (перенесён из этапа 1 по порядковому ограничению 2).
**Решения:** `Р-ПМ-5` (схема только аддитивно), `Р-ПМ-7` (поручение владельца: стоп на подтверждение снят, решения — исполнителю), `Р-ПМ-2` (тексты ПМ дословно).
**База:** `main` = `ad9cc174` (14.10.2026, этап 1 закрыт по коду).

## 1. Что есть сейчас

- **Кабинет** — [student/page.tsx](../../../src/app/student/page.tsx): заголовок и кнопка «Перейти к обучению». Больше ничего.
- **Учётка слушателя** — `User` с ролью `student`. **Карточка слушателя** — `Student` (справочник организации: ФИО, e-mail, СНИЛС…). Между ними **связи нет**: совпасть они могут только по e-mail.
- **Обучения слушателя** — позиции заявок `EnrollmentRequestItem` (`studentId`, `directionId`, `status`: `pending → approved → provisioned → in_training → certificates_ready`, `rejected`). Подтверждение заявки заводит карточки `Student` (`attachStudentsToApprovedItems`), учёток не создаёт.
- **Удостоверения** — `Certificate` (`studentId`, `directionId`, `number`, `validUntil`).
- **Дат начала и окончания обучения нет нигде** — ни у заявки, ни у позиции, ни у направления.
- **Уведомления** — у роли `student` типов нет (`ROLE_AUDIENCES.student = []`); подзаголовок экрана один на все роли («…по вашим заказам, обращениям и задачам»).
- **Справка** — `/help` — общий словарь терминов CRM для всех шести кабинетов.

## 2. Решения этапа

| № | Решение | Причина |
|---|---|---|
| `Р-2-1` | **Связь учётки и карточки — колонка `Student.userId`** (необязательная, FK на `User`, `onDelete: SetNull`, индекс). Один человек может быть сотрудником нескольких организаций — значит, у учётки может быть несколько карточек | Аддитивно (`Р-ПМ-5`); без связи слушателю нечего показать и некого уведомить |
| `Р-2-2` | **Связь ставится автоматически по e-mail** (без учёта регистра): карточки со свободным `userId` и тем же e-mail, что у учётки `student`, привязываются при подтверждении заявки и при каждом открытии кабинета. Карточку, уже привязанную к другой учётке, не трогаем | E-mail — единственный общий ключ; ручная привязка — лишний шаг для администратора |
| `Р-2-3` | **Сроки обучения — у позиции заявки**: `EnrollmentRequestItem.startsOn` / `endsOn` (дата без времени, необязательные). Задаёт сотрудник в карточке заявки, у каждой позиции | Обучение — это и есть позиция «человек × направление»; у шапки сроков нет (позиции разные) |
| `Р-2-4` | **«Мои обучения» — позиции заявок слушателя, кроме отклонённых**, с направлением, статусом простыми словами, сроками и удостоверением по тому же направлению | Это и есть «назначенные обучения» из `У-284`/`У-285` |
| `Р-2-5` | **Кнопка учебной площадки одна на все обучения** (`/student/redirect`) — площадка у компании одна (`У-274`) | Отдельный адрес на курс в системе не хранится |
| `Р-2-6` | **Уведомления слушателя — новая аудитория `student`**: `training_assigned` (заявка подтверждена), `training_ending_soon` (до окончания обучения 3 дня — раз на позицию), `certificate_expiring` получает и сам слушатель | `У-286`; пороги удостоверений — прежние (`REMINDER_THRESHOLDS`) |
| `Р-2-7` | **Справка слушателя — свой экран на `/help`** для роли `student`: вступление ПМ и три инструкции; словарь CRM ему не показывается, остальным ролям — без изменений | `У-287` |

## 4. Стражи

- Привязка: чужая карточка (другой `userId`) не перехватывается; e-mail без учёта регистра; учётка не-слушателя не привязывается.
- Кабинет: слушатель видит только свои карточки (скоуп — `userId = session.sub`), отклонённые позиции не показываются.
- Сроки: правит только сотрудник (`canReviewEnrollments`), «окончание раньше начала» — отказ.
- Уведомления: подтверждение заявки → `training_assigned` каждому привязанному слушателю; «скоро заканчивается» не повторяется.
- Сквозной тест `У-273` на живой базе: подтверждение → слушатель видит обучение и уведомление.
