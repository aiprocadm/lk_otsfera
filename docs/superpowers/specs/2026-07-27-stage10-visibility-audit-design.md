# Этап 10 ТЗ — зачистка клиентских кабинетов и аудит видимости (раздел 3.2 + раздел 7)

Дата: 2026-07-27 · Статус: **📝 предъявлена заказчику, ждёт подтверждения** ·
ТЗ: [docs/tz/2026-07-23-tz-lk-otsfera-v1.md](../../tz/2026-07-23-tz-lk-otsfera-v1.md)
§3.2 (чистота клиентских кабинетов), §7 (матрица видимости), §9 этап 10.
Открытых вопросов §10 ТЗ по этому этапу нет.

## 1. Цель и критерии приёмки (§9 ТЗ)

> «Таблица "эндпоинт → поля → вердикт" для всех partner/organization API;
> негативные тесты видимости зелёные».

Этап не добавляет функциональности. Он доказывает — таблицей и тестами, — что
клиент физически не может получить внутренние данные компании, и чинит места,
где это не так.

## 2. Контекст кода (разведка 27.07.2026)

**Поверхности, через которые клиент получает данные** (полный периметр аудита):

| Слой | Сколько | Где |
|---|---|---|
| API партнёра | 16 роутов | `src/app/api/partner/**` |
| API организации | 4 роута | `src/app/api/organization/**` |
| Общие API (доступны и клиентам) | 8 роутов | `client-requests`, `comments`, `dashboard`, `documents`, `enrollments`, `messages`, `notifications`, `support/question` |
| Server-actions клиентов | 5 файлов | `server-actions/{organization,partner}/**`, `welcome.ts` |
| Страницы кабинетов с прямым `prisma.*` | 9 `page.tsx` | `src/app/{partner,organization}/**` |

**Найденные на разведке расхождения с §7 ТЗ** (не исчерпывающий список — полный
даст сам аудит):

1. **`assignedManagerName` утекает партнёру.** `getLead`
   ([partner/leads.ts:139](../../../src/lib/services/partner/leads.ts)) отдаёт
   имя назначенного менеджера в деталке лида. §7 ТЗ: «Лид: назначенный
   менеджер… → Партнёр: **нет**». Это прямое нарушение.
2. **Выборки лидов построены пост-фильтрацией.** `listLeads` тянет `include`-ом
   **всю** запись `Lead` (вместе с `assignedManagerId`, `funnelStageId`,
   `source`, `notes`, `promotedDealId`, `externalIdInOneC`, `pushedToOneCAt`) и
   отбрасывает лишнее уже в JS-маппинге. §7 ТЗ прямо требует обратного:
   «обеспечиваются select-ами на уровне сервисов (**не пост-фильтрацией**)».
   Сейчас наружу уходит безопасный `LeadRow`, но одна неосторожная правка
   (вернуть `rowsRaw`, добавить поле в тип) превращает это в утечку без единого
   красного теста.
3. **`Lead.notes` в клиентской деталке — двусмысленное поле.** Для лида,
   созданного партнёром, это его собственный текст (показывать корректно). Но
   тем же полем пользуется `manager/createLead.ts` — ручной лид, заведённый
   сотрудником на этого партнёра, отдаст партнёру заметку сотрудника. Нужен
   вердикт: либо не показывать `notes` клиенту вовсе, либо разделить поля
   (`notes` клиента vs внутренняя заметка).
4. **Соседство чувствительной логики с клиентским неймспейсом.**
   `getOrgIntermediaryCommissionForOrgs` живёт в
   `services/**organization**/finance.ts` с комментарием «Sensitive — callers
   MUST gate this to admin/leader». Сейчас её зовёт только `manager/finance.ts`
   (проверено), но расположение провоцирует ошибку: клиентская страница
   финансов импортирует соседние функции из того же файла.

**Что уже сделано и переиспользуется** (не делать заново): изоляция кабинетов
на трёх слоях RBAC; регрессы `c3.idor-cross-access`, `f.list-cross-tenant`,
`security.idor-{lead,comments,calls,inbox}`, `security.partner-commission-idor`;
запрет партнёрского создания лидов и redirect `/partner/leads → /partner/requests`
(этап 5).

## 3. Метод аудита

Для **каждой** поверхности из §2 фиксируется строка таблицы:

| Эндпоинт / action | Роль | Какие поля реально уходят наружу | Вердикт |
|---|---|---|---|

- «Поля наружу» берутся из типа ответа **и** из фактического `select`/`include`
  (расхождение между ними — само по себе замечание).
- Вердикт — один из: `ok` · `over-fetch` (лишнее из БД, но не наружу) ·
  **`leak`** (внутреннее поле уходит клиенту) · `n/a`.
- Таблица кладётся в `docs/audit/2026-07-27-client-visibility-matrix.md` и
  становится живым артефактом: новая клиентская поверхность обязана в неё
  попасть.

## 4. Что чиним

- **Все `leak`** — безусловно, в первом же PR.
- **`over-fetch`** — переводим на явные `select` с полями ровно под тип ответа.
  Правило §7 ТЗ («select, не пост-фильтрация») становится проверяемым.
- **Guardrail-тест**: клиентские сервисы (`services/partner/**`,
  `services/organization/**`) не используют `include:` без явного `select`
  внутри — по образцу существующих guardrail-тестов (`pii.capture-coverage`,
  `worker.processor-coverage`). Ловит регресс на будущее, а не только сегодня.

## 5. Негативные тесты видимости (§7 ТЗ)

На каждую строку матрицы §7 ТЗ — интеграционный тест «роль X запрашивает Y →
`forbidden`/`404`/поля нет»:

| Строка §7 | Проверка |
|---|---|
| Лид: менеджер, заметки, стадия, источник | партнёр читает свой лид → в ответе нет `assignedManager*`, `funnelStage*`, `source`, внутренних заметок |
| Сделка целиком | партнёр/организация → любой путь к `Deal` даёт 404/forbidden |
| Связь заявки с лидом/сделкой | клиент видит только статус и «создан заказ №X», без `leadId`/`dealId` |
| Существование ИНН (антидубль) | клиент дёргает `/api/duplicates/by-inn` → 403 (регресс этапа 5 — подтвердить) |
| Удостоверения | партнёр — по своим организациям, организация — по своим сотрудникам (есть, дополняем) |
| DealNote / внутренние заметки | клиент не получает ни одной |
| Данные других партнёров/организаций | cross-tenant: есть, дополняем недостающими сущностями этапов 6–9 (сделки, задачи, Intake, обращения, реквизиты) |

## 6. Разбивка на PR

- **PR-1 «Матрица и явные select»**: аудит всех поверхностей → таблица в
  `docs/audit/`; фикс найденных `leak` (начиная с `assignedManagerName`);
  перевод клиентских выборок на явные `select`; guardrail-тест.
- **PR-2 «Негативные тесты видимости»**: интеграционные тесты по всем строкам
  §7 ТЗ, включая сущности этапов 6–9, которых старые регрессы не знают.

Порядок важен: PR-1 чинит, PR-2 закрепляет.

## 7. Вопросы заказчику (до кода)

1. **`Lead.notes` в кабинете партнёра** (расхождение №3): убрать поле из
   клиентской деталки совсем — или оставить, но запретить сотрудникам писать в
   него (завести отдельную внутреннюю заметку)? Предлагаю **убрать из
   клиентской выдачи**: у партнёра уже есть своя переписка по заявке, а поле
   двусмысленно по происхождению.
2. **Статус лида у партнёра.** §7 запрещает «стадию воронки», но `status`
   (`new / in_review / qualified / promoted_to_order / rejected`) — это тоже
   внутренняя кухня продаж. Предлагаю **схлопнуть для клиента** в три
   состояния: «на рассмотрении» / «принята» / «отклонена» — как уже сделано для
   обращений (этап 5). Или оставить как есть?
3. **Глубина аудита общих API** (`comments`, `documents`, `notifications`,
   `dashboard`): включаем в матрицу целиком (они доступны клиентам) — или
   ограничиваемся `partner/**` и `organization/**`, как буквально написано в
   §9 ТЗ? Предлагаю **включить**: утечка через общий роут ничем не лучше.
4. **Разбивка на 2 PR** (§6) — ок?

## 8. Вне скоупа этапа 10

- Изменения UI кабинетов (перекладка меню, бейджи) — это этап 11.
- Ревизия staff-скоупов между собой (менеджер vs менеджер) — C8 закрыт ранее и
  подтверждён регрессами; здесь трогаем только границу «клиент ↔ компания».
