## 1. Цель и критерии приёмки (§9 ТЗ)

«Ни одна входящая единица не остаётся без статуса; эскалация по SLA
срабатывает; из звонка/обращения создаются лид и задача в 1 клик» +
карточка организации получает вкладки Заявки/Лиды/Сделки.

## 2. Контекст кода (разведка)

Уже есть и переиспользуется:
- 4 очереди-источника: ClientRequest (`clientRequests/list.ts`, триаж
  `takeInTriage` пишет `triagedByUserId`), EnrollmentRequest
  (`enrollments/*`, «неразобранная» = `pending`, ответственного нет),
  InboundMessage (`inbound/scope.ts` — паттерн «своя компания ∪ общая
  неразобранная очередь», статусы `unresolved|bound|archived`), Call
  (`telephony/listCalls.ts`, привязка `CallBindForm`, статуса разбора нет).
- Эталон «Взять в работу» — `claimOrder` (`manager/distribution.ts:105`):
  scope-gate до мутации, `already_assigned`, идемпотентность, аудит.
- Дневные джобы: `certificate-expiry` (дедуп через уникальную строку-журнал
  + P2002-skip), `calendar-reminder` (атомарный claim `updateMany`).
- Уведомления: `type` — свободная строка (миграций не нужно), фан-ауты
  `notifyManagers`/`createNotification`+`deliverNotificationToUser`.
- Задачи: `Task`/`TaskAssignee`/`TaskColumn` + канбан; фильтров, списка,
  уведомлений и привязок к лиду/сделке нет.
- Карточка лида не показывает источник; `Lead.sourceCallId/sourceInboundId`
  в схеме отсутствуют; «Создать сделку» уже есть (этап 6).
- Бейджей в меню нет: `NavItem` без счётчиков; образец поллинга —
  `NotificationBell` (30 с) / `UnreadBadge`.
- Карточка организации: `org-card-tabs.tsx` — 8 вкладок, сервис
  `getOrganizationCard` (параллельные select'ы по 20 строк).

## 3. Модель данных (все миграции аддитивные)

- **`Task`**: `+linkedLeadId?` (SetNull), `+linkedDealId?` (SetNull) —
  ФТ-7.1; `+dueSoonNotifiedAt?` (дедуп джоба «скоро срок»).
- **`Lead`**: `+sourceCallId? @unique`, `+sourceInboundId? @unique` (§6 ТЗ);
  enum `LeadSource` — additive значения `call`, `inbound_message`.
- **`EnrollmentRequest`**: `+claimedByUserId?`, `+claimedAt?` — ответственный
  до approve/reject (сейчас есть только пост-фактум `reviewedByUserId`).
- **`InboundMessage`**: `+claimedByUserId?`, `+claimedAt?` (binding-поля
  `boundById/boundAt` не трогаем — это «целевая сущность», не claim).
- **`Call`**: `+claimedByUserId?`, `+claimedAt?`, `+intakeClosedAt?`,
  `+intakeClosedById?` («Закрыть» нецелевой/спам-звонок — вопрос §10-1).
- **`Company`**: `+slaResponseHours Int @default(24)`,
  `+slaWarningHours Int @default(4)` (§4.4: порог эскалации / подсветка).
- **`SlaEscalation`**: журнал эскалаций — `sourceType`, `sourceId`,
  `escalatedAt`, `@@unique([sourceType, sourceId])` (дедуп по образцу
  `CertificateReminder` + P2002-skip).
- ClientRequest не меняется: claim = существующий `takeInTriage`
  (`triagedByUserId`), лок «занято другим» уже даёт lifecycle-гейт.

## 4. Intake «Входящие в работу» (ФТ-8.1–8.4)

- Страницы `/manager/intake` и `/leader/intake` (зеркало админа —
  `/admin/intake`), флаг **`intake_inbox`** (opt-in route-флаг: middleware +
  nav + page-гейт).
- Без новой таблицы: сервис `services/intake/list.ts` — union-ридер 4
  источников с нормализацией в `IntakeItem { type, id, from, essence,
  createdAt, waitingMs, slaLevel(ok|warning|breach), responsible?, href }`.
  Каждый источник — своим существующим scope-резолвером (клиентские роли —
  `forbidden`); сортировка «дольше всех ждёт — сверху», merge в памяти,
  cap + пагинация.
- Критерий «в Intake»: ClientRequest `submitted|in_triage`; EnrollmentRequest
  `pending`; InboundMessage `unresolved`; Call — входящий без привязки
  (`resolvedOrgId`,`contactId` пусты), без лида/задачи-источника и без
  `intakeClosedAt`. Покидает Intake — когда есть ответственный **и** целевая
  сущность (конверсия/привязка/закрытие) — ФТ-8.2.
- Подсветка ожидания: жёлтая > `slaWarningHours` (4 ч), красная >
  `slaResponseHours` (24 ч) — из настроек компании.
- Действия строки (по типу): «Взять в работу» (claim по образцу
  `claimOrder` — 4 сервисных claim'а с `already_assigned`), «Создать лид»,
  «Создать задачу», «Привязать» (переиспользуем существующие bind-формы
  inbound/call), «Отклонить»/«Закрыть» (reject заявки — существующие
  сервисы; звонок — `intakeClosedAt`).
- Руководитель: вся команда (company-floor), фильтр по менеджеру, секция
  «Без ответственного», та же сортировка по ожиданию (ФТ-8.3).
- Бейдж-счётчик в меню (ФТ-8.4): расширение `NavItem` полем `badgeKey`,
  один агрегирующий эндпоинт `GET /api/staff/badges` (один запрос на
  поллинг 30 с, по образцу `NotificationBell`), клиентский бейдж в
  manager/leader-сайдбарах. Ключи v1: `intake`, `tasks_overdue` — каркас
  расширяем для ФТ-15.2 (этап 11).

## 5. Создание лида и задачи из источников (ФТ-1.6, ФТ-7.5, ФТ-3.1)

- «Создать лид» из обращения и звонка (карточка + строка Intake):
  предзаполненная форма (контакт/организация из `resolveCaller`/binding),
  `source='inbound_message'|'call'`, `sourceCallId`/`sourceInboundId`;
  транзакция помечает источник разобранным (inbound → `bound`).
- «Создать задачу» из звонка («Перезвонить …»), обращения, заявки:
  предзаполнение title/description + `linkedOrganizationId` (если
  привязана) — диалог по образцу `task-dialog`.
- Карточка лида: блок «Источник» (тип + ссылка на исходную
  заявку/обращение/звонок — уже есть `sourceRequestId`, добавляются новые)
  и блок «Задачи» (список привязанных + быстрое создание) — ФТ-3.1/3.2.

## 6. Задачи (ФТ-7.1–7.4)

- Привязки к лиду/сделке: поля §3, блоки «Задачи» в карточке лида и в
  `deal-dialog` (валидация `validateRefs` расширяется, scope-чек по C8).
- Уведомления: `task_assigned` — при назначении исполнителя (кроме
  самоназначения), `task_due_soon` — дневной джоб воркера
  (`notifications.taskDueSoon`, cron 07:00 МСК по образцу CertExpiry):
  `dueDate` сегодня/завтра, не `done` → исполнителям в их каналы; дедуп —
  `dueSoonNotifiedAt` (атомарный `updateMany`-claim, повтор при переносе
  срока — сброс поля при изменении `dueDate`).
- Фильтры доски (ФТ-7.3): «мои / все» (уважая `tasksScope`
  AccessProfile/teamMode), по исполнителю (руководитель), «просроченные»;
  счётчик просроченных — бейдж `tasks_overdue` (§4).
- Вид «список» (ФТ-7.4): таблица рядом с канбаном (переключатель),
  сортировка по сроку/приоритету, те же фильтры и диалог задачи.

## 7. SLA-эскалация (§4.4, ФТ-8.5)

- Настройка порогов: карточка «SLA входящих» на `/leader/team` (по образцу
  `TeamVisibilityToggle`; вопрос §10-3): часы реакции (дефолт 24) и часы
  подсветки (дефолт 4); аудит изменения.
- Джоб `monitoring.slaEscalation` (cron каждые 30 мин): выборка единиц
  Intake без ответственного старше `slaResponseHours` → уведомление
  `sla_escalation` (ФТ-15.7) руководителям компании (для единиц общей
  очереди без компании — руководителям всех компаний, они видят её в своём
  Intake); один раз на единицу (журнал `SlaEscalation`), идемпотентно,
  degrade gracefully.
- Email-шаблон — generic `notification` (без отдельного rich-шаблона);
  deep-link — `meta.url` на Intake.

## 8. Карточка организации (§9 этап 7)

- `ORG_CARD_TABS` + три вкладки: «Заявки» (ClientRequest организации),
  «Лиды» (лиды с `organizationId`), «Сделки» (сделки организации) — по 20
  строк со ссылками на деталки/доски; select'ы в `getOrganizationCard`
  тем же паттерном (deals/leads — только staff-scope, C8).
- Видимость вкладок — по существующим флагам `client_requests` /
  `sales_funnel` / `deals_pipeline` (как уже сделано для
  inbound_messages/calls).

## 9. Тестовая стратегия (порог 100%)

- Union-ридер Intake: нормализация, сортировка по ожиданию, slaLevel по
  порогам компании, scope (менеджер/лидер/чужая компания/клиентские роли →
  forbidden), пагинация.
- Claim-сервисы ×4: успех/идемпотентность/`already_assigned`/scope-гейт до
  мутации; выход единицы из Intake по каждому пути (конверсия, привязка,
  reject, close).
- Создание лида из звонка/обращения: транзакция, `source`+source-поля,
  @unique-повтор, пометка источника.
- Задачи: миграция привязок, фильтры/список, уведомления (самоназначение —
  нет; дедуп due_soon, сброс при переносе срока), джоб идемпотентен.
- SLA-джоб: пороги, дедуп-журнал, получатели-руководители, общая очередь.
- Бейджи: агрегирующий эндпоинт (роли/скоупы), рендер в сайдбарах.
- UI: intake-таблица + действия, блоки задач в лиде/сделке, вкладки
  карточки организации, страницы через `renderServerComponent`.
- Integration на живом Postgres: полный путь «обращение → взять в работу →
  создать лид → задача» + SLA-эскалация по просроченной заявке.
