## 2. Ключевые решения

### 2.1. Карточка организации у администратора — по реестру, а не в исключения (`У-95`, `У-96`, §0.2, §7.3)

Сценарная приёмка §7.3 требует дословно: «открыть карточку одной и той же
организации **администратором**, руководителем, менеджером и партнёром →
одинаковые вкладки, одинаковые цифры на плитках». Записать карточку админа в
исключения зеркала значит провалить этот пункт заранее. Поэтому решение —
**перестроить страницу на тот же `OrgCardTabs`**, что у руководителя и
менеджера (`Р-23`: общий презентационный компонент, данные и права — от
сервиса роли):

- `getOrganizationCard` получает ветку Model A: `session.role === 'admin'` →
  организация видима без скоупа (как везде в `policy.ts`). Один `if`, один
  тест.
- Страница админа: крошки → плашка «создано из 1С» → `OrgCardTabs` с
  `orgCardTabsFor('admin')`. Свои секции никуда не пропадают, они переезжают
  во вкладки по реестру: «Сотрудники» → вкладка `employees`; «Документы» →
  вкладка `documents` с кнопкой выпуска без заказа и блоком КП; реквизиты,
  ставка комиссии, менеджеры, доступ в кабинет, доп. поля → вкладка
  `settings` через уже используемый `OrgSettingsTab`. Вкладки «Обзор»,
  «Заказы», «Оплаты», «История» и прочие приходят от `card` — те же данные,
  что видит руководитель, только без границы компании.
- Новый страж `navigation.org-card-registry-usage.guardrail`: **каждый
  кабинет, названный в `ORG_CARD_TABS[*].cabinets`, открывает карточку через
  `orgCardTabsFor('<кабинет>')`** — иначе реестр обещает вкладки, которых
  экран не показывает. Проверяется мутацией (убрать вызов у одного кабинета —
  страж падает).

Находка `⚠` в AUDIT.md переводится в `✅` строкой `У-95`/`У-96` с датой.
Если заказчик скажет «нет» — альтернатива описана в §5, п. 1.

### 2.2. Приёмка §0.1 и §0.2 — правилом по всем, руками по выборке (`У-175`)

«По всем новым и изменённым экранам» и «воспроизводимая выборка, как в
`У-77`» не противоречат друг другу: правило проходит **все** экраны, глаза —
**выборку**.

1. **Правилом — все 162 экрана.** Скрипт приёмки (в `scripts/`, запускается
   руками, в гейты не входит) берёт список `git diff --name-status 92c683e
   main -- 'src/app/**/page.tsx'` и по каждому файлу проверяет цепочку
   «страница + её компоненты» (урок `У-77`: заголовок и кнопки часто живут в
   клиентском компоненте): есть `h1`/`PageHeader` с русским названием ·
   есть подзаголовок либо экран — карточка сущности из списка исключений
   стража · есть главная кнопка либо `EmptyState`. Итог — таблица «кабинет →
   экранов → где я / что здесь / что дальше» в close-out этапа, как у `У-77`.
2. **Вживую — все статические экраны и вкладки карточки.** Обход
   `screen-rules-check.ts` расширяется адресами карточки организации:
   e2e открывает список организаций кабинета, берёт первую строку и
   проходит **все вкладки из `orgCardTabsFor(кабинет)`** (для заказчика —
   «Моя организация», для партнёра — портфель). Проверки те же: ширина,
   один `h1`, подзаголовок, плюс «подпись активной вкладки = `label`
   реестра». Пропущенные (нет данных, нет флага) пишутся в лог строкой
   «ПРОПУЩЕН», а не считаются пройденными.
3. **Глазами — выборка `seed=175`.** Из 42 новых экранов детерминированно
   выбираются **12 (по два на кабинет)**; каждый открывается на стенде на
   390×844 и на десктопе, три вопроса записываются словами в таблицу
   close-out (экран → где я → что здесь → что дальше → что поправлено).
4. **Правило зеркала** держится стражами (см. §1) — приёмка их **не
   переписывает**, а предъявляет: полный список 26 исключений с причинами
   выносится в close-out этапа таблицей (§7.4 ТЗ: «показан заказчику и
   принят»). Новых исключений этап не добавляет; расхождение, найденное
   обходом, чинится, а не записывается.

Всё найденное чинится **в том же PR** (это правило §16 для файлов, которых
касается этап) — как `У-77` нашла и закрыла четыре экрана без подзаголовка.

### 2.5. Полный drift-аудит `У-1`…`У-176` (`У-176`, §16 п. 4)

177 строк — руками за один проход не пройти честно, и прошлый полный проход
(19.08.2026) это уже решил **зоной риска**: сначала считается, у каких строк
якоря менялись с даты их сверки, и они проверяются целиком; у остальных
подтверждается, что якорь не менялся. Здесь тот же приём, с тремя видами
отметки в колонке «Сверено» — по каждой строке ровно один:

| Отметка | Что означает | Как получена |
|---|---|---|
| `страж, прогон 0N.09.2026` | требование держится тестом-стражем, тест зелёный | `npm run test:unit` этого PR |
| `якорь не менялся с DD.MM` | ни один файл-якорь строки не менялся после даты сверки | `git log --since=<дата> -- <якоря>` пуст — считает скрипт аудита |
| `проверено руками 0N.09.2026` | якорь менялся и стража нет — цепочка поведения пройдена по колонке «Что проверять» | руками, по одному |

Скрипт зоны риска — тот же, что в §2.2 п. 1 (один файл в `scripts/`, два
режима). Ожидание по разведке: у `У-1`…`У-77` менялись якоря меню, вкладок,
документов и обмена (этапы 2, 3, 6, 8) — это порядка 30–40 строк руками;
`У-78`…`У-174` сверялись в своих PR за последние две недели, у них зона
риска — соседние этапы (например, `У-141`…`У-143` после этапа 8).

Сводка пересчитывается: ожидаемо ✅ **176** / ⏳ **0** / ❌ 0 / ⚠ 1 (остаётся
только расхождение в тексте ТЗ понятности про «287 маршрутов», чинить в коде
нечего). Любое `❌` чинится по правилу §16: файл этапа — в этом PR, иначе —
хотфикс-PR от `main` со стражем.

### 2.6. Первый полный прогон `С-1`…`С-10` (`У-176`, §9.2 ТЗ)

Все десять проверок выполняются по своим процедурам из `MAINTENANCE.md` и
получают дату, короткий хеш `main` и итог одной строкой. Особенности:

- `С-1` гейты — без `npm run gate` (Docker на сервере нет): integration-слой
  гоняется `npx vitest run --mode=integration` против живого Postgres, это
  записывается в итог честно, а не как «gate зелёный».
- `С-2` drift-аудит — это §2.5, ссылка на него.
- `С-3` живой обход и `С-10` эталоны — это §2.2 п. 2 и §2.3 плюс пересъёмка
  устаревших эталонов этапов 4–8 **с объяснением по каждому экрану**, что
  сдвинулось и почему это ожидаемо (новые плитки, колонка «Выгрузка в 1С»,
  переименования).
- `С-5` мутация стражей — первые десять из 58 файлов `*.guardrail.test.ts`
  по алфавиту; список проверенных пишется в реестр, чтобы
  следующий прогон взял следующие десять.
- `С-9` зависимости — `npm audit` в двух режимах; мажор с уязвимостью — `⚠`.

Каждая находка — строка журнала с вердиктом. `❌` чинятся **не более чем
тремя хотфикс-PR** (§9.4); остальное остаётся в очереди журнала первым
пунктом следующего прогона. `⚠` — вопрос заказчику, не PR.

## 4. Тестовая стратегия

- **Сервис карточки:** админ получает карточку любой организации (Model A);
  партнёр и заказчик — по-прежнему только свою (регрессы существующего
  `services.organizationCard.integration` против живого Postgres).
- **Страница админа:** `renderServerComponent` — вкладка по умолчанию
  «Обзор», `?tab=settings` показывает реквизиты, ставку и доступ в кабинет;
  чужая вкладка из адреса → «Обзор»; `notFound` при пустой карточке.
- **Страж реестра вкладок** (`navigation.org-card-registry-usage.guardrail`):
  текстовый, по одной странице на кабинет; проверен мутацией (убрать вызов —
  падает).
- **Страж словаря:** двенадцать терминов в `GLOSSARY` и в `docs/glossary.md`,
  каждый объяснён, не дублируется; мутация — удалить «Моя организация» из
  `docs/glossary.md`.
- **Скрипт приёмки/зоны риска:** unit-тест на разбор строк `AUDIT.md`
  (дата сверки, список якорей) и на детерминированность выборки
  (`seed=175` дважды → один список).
- **e2e:** `screen-rules` с вкладками карточки — зелёный на стенде;
  новые снапшоты — две сверки подряд без диффов (как при пересъёмке 20.08:
  воспроизводимость доказывается повтором, а не одним прогоном).
- **Документы:** `docs.tz-program` зелёный на каждом PR; сводка AUDIT
  сходится с таблицами.

Coverage-гейт 100 % на `src/lib/**`, `src/components/**`, `src/app/**/*.tsx`
держится: новый код страницы и сервиса покрывается тестами выше.

## 5. Вопросы заказчику (умолчания действуют, если не отменены)

Решения приняты по поручению «если есть вопросы — прими решение сам»; каждое
можно отменить до подтверждения спеки.

1. **Карточка администратора: перестроить на реестр вкладок (умолчание)**
   или записать в исключения зеркала с причиной «служебная карточка Model A»?
   Умолчание выбрано потому, что §7.3 называет администратора среди тех, у
   кого карточка одинаковая. Если «исключение» — PR-1 сжимается до записи в
   `mirrorExceptions`-подобный список вкладок и страж §2.1 учит его читать.
2. **Выборка глазами — 12 экранов (по два на кабинет, `seed=175`)** из 42
   новых. Больше — дольше день на стенде; меньше — формальность.
3. **Мобильные эталоны — десять экранов из §2.3**, по одному на новый раздел,
   а не на каждый файл. Карточки с `[id]` не снимаем (кроме двух названных),
   чтобы эталоны не протухали от seed.
4. **Полный аудит — зоной риска с тремя отметками** (§2.5), как 19.08.2026,
   а не «177 строк руками». Каждая строка получает свежую отметку с датой.
5. **Хотфиксов из прогона `С-1`…`С-10` — не более трёх** (§9.4 ТЗ); остальное
   — очередь журнала, следующий прогон начинает с неё.
6. **Устаревшие эталоны этапов 4–8 пересъёмка в PR-3** с пояснением по
   каждому экрану — а не «обновить всё одной командой».
7. **Находка про «287 маршрутов»** остаётся `⚠` в тексте ТЗ понятности:
   приёмка считалась по фактическим 188 `page.tsx`; ТЗ заказчика не правим.

После «да» — план в `docs/superpowers/plans/2026-09-05-stage9-acceptance-and-closeout.md`
и PR-1.
