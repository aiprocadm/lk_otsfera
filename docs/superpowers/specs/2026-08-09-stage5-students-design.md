# Этап 5 «Справочник сотрудников» — дизайн

- **ТЗ:** [Понятность интерфейса и функциональные пробелы](../../tz/2026-08-08-tz-usability-and-core-gaps.md)
- **Требования:** `У-20`…`У-32` (блок D) + долг `У-63` (кнопка) из этапа 4
- **Статус:** 📝 спека, ждёт «ок» заказчика. Код не начат (CLAUDE.md §8)
- **Факт кода:** ветка `stage5-students` от `main` `d0979c36` (этапы 1–4 влиты)
- **Риск:** **высокий** — единственный этап программы с миграцией схемы

## 1. Зачем

Это не «улучшение интерфейса», а **дыра в функциональности**: сотрудника
(слушателя) в системе **нельзя создать нигде**. Поиск `student.create(` по
`src/lib`, `src/server-actions`, `src/app` даёт **ноль** совпадений — записи
появляются только из сидов и из импорта 1С. Поэтому заявку на обучение нельзя
подать на человека, которого ещё нет в базе, а кнопка «Добавить сотрудника» из
этапа 4 не могла быть сделана.

Плюс модель не подходит для охраны труда: `email` **обязателен**, а рабочих
обучают без корпоративной почты.

## 2. Что в объёме

`У-20` поля модели · `У-21` email необязателен · `У-22` дедупликация ·
`У-23` сервис · `У-24`…`У-26` кнопки в кабинетах · `У-27`/`У-28` импорт списком
с предпросмотром · `У-29` автосоздание при одобрении заявки · `У-30` карточка
сотрудника · `У-31` аудит и журнал ПДн · `У-32` права.
Плюс долг этапа 4: кнопка на вкладке «Сотрудники» партнёра (`У-63`/`У-25`).

**Не в объёме:** перестройка заявки «много слушателей × много обучений» — это
этап 6, он **обязан** идти после этого этапа (§5 ТЗ).

## 3. Разведка по коду (факт на `main` `d0979c36`)

1. **`model Student`** (`prisma/schema.prisma`): `email String` (**обязателен**),
   `name`, `status`, `position String?`, `organizationId`, `externalStudentId`,
   связи `orderItems` / `certificates` / `enrollmentItems`,
   `@@unique([organizationId, email])`. Полей `snils` / `birthDate` / `phone` /
   `note` нет — объект `У-20`, `У-21`.
2. **Модуля `services/students/` не существует** — `У-23` пишется с нуля.
3. **Экраны уже есть, но только на чтение:** `/organization/students` (+`[id]`),
   `/manager/students` (+`[id]`); сервисы `services/organization/students.ts`,
   `services/organization/students-xlsx.ts` (выгрузка), `services/manager/students.ts`.
4. **Журнал ПДн уже знает про сотрудников:** в `lib/pii/contexts.ts` есть
   `manager_students_list`, `manager_student_view`, `enrollment_wizard_students`
   с `subjectType: 'student'`. Для `У-31` заводим контексты на **новые** места
   чтения (карточка, импорт), а механизм не трогаем.
5. **Готовая инфраструктура импорта** от программы 1С: `services/import/load-xlsx.ts`,
   `parse-workbook.ts`, `normalize.ts` (нормализация заголовков, «ё/е», регистр).
   Двухшаговый предпросмотр (`У-28`) — тот же приём, что у импорта 1С.
6. **Шаблон Excel уже отдаётся роутом** `api/enrollments/import-template` —
   образец для шаблона сотрудников (`У-27`).
7. **Точка автосоздания (`У-29`)** — `services/enrollments/lifecycle.ts:62`,
   где статус заявки становится `approved`.

## 4. Решения

### 4.1. Миграция (`У-20`, `У-21`) — самая опасная часть

```prisma
model Student {
  email     String?   // было String
  snils     String?
  birthDate DateTime?
  phone     String?
  note      String?
  @@unique([organizationId, email])   // остаётся
}
```

**Почему это безопасно:** расширение `String` → `String?` не теряет данные, а в
PostgreSQL уникальный индекс допускает **много** `NULL` — значит десятки
сотрудников без почты не конфликтуют между собой, но два одинаковых email в
одной организации по-прежнему запрещены.

**Что проверяем до мержа:** все места, где `student.email` считается
непустым. По ним пройдёмся отдельно — тип станет `string | null`, и `typecheck`
покажет каждое; молчаливых мест не останется.

### 4.2. Сервис (`У-23`, `У-32`)

`src/lib/services/students/` c Result-контрактом (§3):
`createStudent`, `updateStudent`, `deactivateStudent`, `findDuplicates`,
`importStudents`.

**Права — в сервисе, а не в UI** (§4): организация ведёт своих сотрудников
(`admin`/`leader` активного членства), партнёр — сотрудников организаций своего
портфеля (проверка по БД `Organization.partnerId` + `assignedOrgIds`, как в
`partnerAccess` этапа 4), менеджер — по `managerPolicy` с mode-aware `teamMode`,
админ — везде. Отдельный страж на каждую отказную ветку.

### 4.3. Дедупликация (`У-22`)

`findDuplicates` в порядке: СНИЛС → `ФИО + дата рождения` → `ФИО + email`.
Совпадение возвращается **кодом** (`duplicate_found` + список кандидатов), а не
исключением; экран показывает «Такой сотрудник уже есть» с выбором
«Использовать существующего» / «Всё равно добавить».

**Дубли не запрещаются жёстко** — оператор может настоять. Это осознанно:
однофамильцы существуют, а блокировка ввода дороже дубля.

### 4.4. Кнопки (`У-24`…`У-26` + долг `У-63`)

Один диалог `student-dialog.tsx` на все четыре кабинета (строго
презентационный, принимает domain-agnostic пропсы), четыре точки подключения:
`/organization/students`, вкладка «Сотрудники» портфеля партнёра,
`/manager/organizations/[id]`, `/admin/organizations/[id]`.

### 4.5. Импорт списком (`У-27`, `У-28`)

Шаблон: **ФИО** (обязательно) · должность · СНИЛС · дата рождения · email ·
телефон. Разбор — на готовых `load-xlsx` + `normalize`. Два шага: предпросмотр
(«будет создано N, обновлено M, дубликатов K», построчные ошибки по-русски) →
подтверждение. Ничего не пишем до подтверждения.

### 4.6. Автосоздание из заявки (`У-29`)

В `lifecycle.ts` при переходе в `approved`: для каждой позиции со
`studentId = null` — `createStudent` (через ту же дедупликацию `У-22`) и
проставление `studentId`. Всё в одной транзакции с одобрением: одобрили —
значит слушатели заведены.

### 4.7. Карточка сотрудника (`У-30`) и журнал ПДн (`У-31`)

Карточка показывает реквизиты, историю обучений (позиции заявок) и удостоверения
со сроками. Просмотр СНИЛС и даты рождения пишет `PiiAccessEvent` через
существующий `recordPiiAccess`; новые контексты заводятся в `pii/contexts.ts`
(иначе падает страж `pii.capture-coverage`). Все операции — в `AuditLog`,
новые действия регистрируются в `AUDIT_ACTIONS`.

## 5. Разбивка на PR

Этап большой, поэтому предлагаю **два PR** вместо одного:

| PR | Состав | Почему так |
|---|---|---|
| **PR-1 «фундамент»** | `У-20`…`У-26`, `У-31`, `У-32` + долг `У-63`: миграция, сервис, дедупликация, кнопки в четырёх кабинетах, права, аудит | Миграцию и права стоит смотреть отдельно от импорта — их ревью разное по характеру |
| **PR-2 «массовые операции»** | `У-27`…`У-30`: импорт списком с предпросмотром, автосоздание при одобрении, карточка сотрудника | Опирается на сервис из PR-1 |

## 6. Тесты

- миграция: существующие сотрудники с email живы, новый — без email создаётся;
- дедупликация: по СНИЛС, по ФИО+ДР, по ФИО+email; «всё равно добавить» создаёт;
- права: организация не видит чужих сотрудников, партнёр — только свои
  организации, менеджер — по своему скоупу (оба режима `teamMode`); каждая
  отказная ветка проверяет **и** код, **и** отсутствие записи;
- импорт: предпросмотр ничего не пишет; подтверждение пишет ровно то, что
  показал предпросмотр; кривые строки дают русские ошибки;
- одобрение заявки заводит сотрудников и проставляет `studentId`;
- журнал ПДн: просмотр СНИЛС оставляет запись `PiiAccessEvent`.

Integration-тесты на живом Postgres обязательны — этап трогает схему.

## 7. Риски

| Риск | Что делаем |
|---|---|
| `email` становится nullable — молчаливые падения там, где он считался строкой | `typecheck` покажет каждое место; проходим по списку до мержа |
| Автосоздание при одобрении создаёт мусор при повторном одобрении | дедупликация `У-22` + идемпотентность: позиция с уже проставленным `studentId` пропускается |
| Импорт пишет частично при ошибке в середине файла | одна транзакция на подтверждение, как в импорте 1С |
| Права: четыре роли × «свои/чужие» — легко пропустить ветку | таблица прав в тестах, отдельный страж на каждую роль |

## 8. Решения, требующие «ок» заказчика

1. **Делим этап на два PR** (§5 спеки): фундамент и массовые операции.
   Согласны? Если нужен один PR — сделаю одним, но ревью будет тяжелее.
2. **СНИЛС хранится как обычное поле** (без шифрования), а защита — журнал
   доступа `PiiAccessEvent`, как у остальных ПДн в системе. Так?
3. **Дубли разрешены осознанно:** при совпадении показываем предупреждение и
   даём кнопку «Всё равно добавить», но не блокируем. Согласны?
4. **Автосоздание сотрудников при одобрении заявки идёт в одной транзакции с
   одобрением** — если завести слушателя не удалось, заявка не одобрится.
   Альтернатива — одобрять и создавать «как получится». Считаю, что «всё или
   ничего» честнее. Согласны?
