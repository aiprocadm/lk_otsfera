## 0. Коротко

Диалоги мессенджеров отгружены 12.09.2026 (PR #580…#583) и умеют ровно одно:
переписку **текстом** в трёх мессенджерах, видимую всей компании. Этап 3
превращает их в рабочее место отдела продаж: ответить на **письмо**, приложить
**файл**, назначить **ответственного**, ответить **шаблоном**, оставить
**внутреннюю заметку**, принять **заявку с сайта**, увидеть переписку **в
карточке** организации и заказа, а клиенту — писать **из кабинета**.

Ничего из этого сейчас нет. Проверено по цепочкам, не по именам файлов: ни одно
из `У-204`…`У-217` не реализовано даже частично, кроме трёх заделов, которые
этап использует как фундамент (см. §1.3).

Восемь PR, каждый — 1–3 требования, каждый закрывается своим стражем с
мутацией. Схема БД меняется **аддитивно и обратимо** (пять новых колонок, одна
новая модель, одна новая цель антивируса); ни одной колонки не удаляем.

### 1.2. Почта, инбокс, сайт

- **Ответить на письмо нельзя по построению.** `replyToInbound` ([reply.ts:29-46](../../../src/lib/services/inbound/reply.ts)) для канала `email` возвращает `{ok:false}` с комментарием «No raw-send available… Deferred to boarding»; `sendReply.ts:63-66` превращает это в код `email_unsupported`. Кабинет и три мессенджера отвечать умеют.
- **Приём писем работает**: IMAP-адаптер (`adapter-imap.ts`, ImapFlow + mailparser), процессор `inbound.email.poll` каждые 5 минут, курсор `uidValidity:lastSeenUid`, батч 50. Но `InboundEmailDto` — это `{externalId, from, subject, text}`: **вложения писем не парсятся вовсе**, `scanStatus` у писем всегда `'none'`.
- **Отправка писем через Resend есть, вложения умеет** (`EmailAttachment {filename, content}` → Resend `attachments`, образец `sendOrgDocumentSentEmail`). **Заголовков `In-Reply-To`/`References`/`Reply-To` тип `EmailTransport.send` не поддерживает вообще** — их придётся добавлять в транспорт. Адрес отправителя — настройка `email.from` (БД → env `EMAIL_FROM` → `no-reply@otsfera.ru`).
- **`ClientRequestSource.website` объявлен в enum, но пути создания нет.** Единственный создатель обращений — `submitClientRequest`, и он жёстко ставит источник по сессии: `session.role === 'partner' ? 'partner_cabinet' : 'organization_cabinet'`. Публичного роута, формы и сервиса не существует.
- **Связь инбокс ↔ диалог есть в БД, но не в интерфейсе.** `MessengerMessage.inboundMessageId` — реальный уникальный FK, обратная связь `InboundMessage.dialogMessage` тоже объявлена. Но `INBOX_SELECT` эту связь не выбирает, а `inbox-list.tsx` не рисует ссылки «Открыть диалог»; обратной ссылки в карточке диалога тоже нет.
- **Бейджи** (`getStaffBadges`) считают `intake` (4 источника), `tasksOverdue`, `clientRequestsNew`, `messagesUnread`, `messengersUnread` — счётчика «диалоги ждут ответа» среди них нет (и не может быть: статуса `waiting_staff` не существует).

### 1.3. Три задела, на которых стоит этап

1. **Вкладка «Диалоги» в карточке контакта уже есть** — `contactCardTabs.ts` объявляет её первой строкой (флаг `inbound_messaging`). То есть `У-210` наполовину закрыт этапом 1: у **контакта** вкладка есть, у **организации** — нет (в `orgCardTabs.ts` 17 вкладок, `dialogs` среди них отсутствует). Блок «Контакт заказа» (`order-contact-panel.tsx`) и `Order.primaryContactId` тоже готовы — блоку «Переписка с клиентом» есть на чём стоять.
2. **Движок подстановок готов и обкатан** — `src/lib/templates/placeholders.ts` (`extractPlaceholders`, `findUnknownPlaceholders`, `applyPlaceholders`, синтаксис `{{namespace.field}}`), а `NotificationTemplate` — готовый образец архитектуры «переопределение на компанию + отказ сохранить неизвестную подстановку». `ReplyTemplate` пишется по этому лекалу, а не с нуля.
3. **Шкала охвата и capability работают** — `scopeLevelSchema = z.enum(['own','assigned','all'])`, `can(session, capability)` с default-deny при размеченном профиле, образцы `orderWhereForLevel`/`taskWhereForLevel`/`canSeeTask`. В профиле есть шкалы `orders/organizations/threads/documents/finance/leads/tasks` — шкалы `dialogs` нет, capability `communications.dialogs` нет.

Плюс инфраструктура, которую этап переиспользует без изменений: `isRateLimited(key,{windowMs,max})`; `SETTING_SPECS` + `IntegrationSetting` с шифрованием секретов и правилом «наружу отдаём только `isSet`»; реестр `SETTINGS_SECTIONS` (добавление раздела = одна строка реестра + страница с `requireSettingsSection`); реестр уведомлений с уже заведёнными `note_mention`, `client_request_submitted`, `sla_escalation`; процессор `monitoring.slaEscalation` и часы `Company.slaResponseHours`/`slaWarningHours`; антивирус `scan-document` с восемью видами целей.

### 1.4. Одно расхождение требования с кодом — записать сейчас, а не обнаружить в PR

`У-217` требует «публичный роут в allow-list middleware с причиной». **В этом
проекте у middleware нет и не может быть такого списка для API:** его matcher
исключает `/api/*` целиком (`'/((?!api|_next/static|_next/image|favicon.ico|.*\\..*).*)'`),
то есть middleware API-роутов не видит. Публичные роуты защищают себя сами —
так уже сделаны три вебхука мессенджеров (секрет из `IntegrationSetting` +
`secretEquals`). Решение — `Р-3-8` ниже: вместо правки matcher заводим явный
**реестр публичных API-роутов** со страж-тестом. Требование выполняется по
смыслу («публичность объявлена явно и с причиной»), а не буквально по
несуществующему механизму.

## 3. Ключевые решения

### 3.1. `Р-3-1`. Диалог шире мессенджера: `DIALOG_CHANNELS` рядом с `MESSENGER_CHANNELS`

`MESSENGER_CHANNELS = ['telegram','max','whatsapp']` — это список **транспортов
с исходящей отправкой в тот же адрес**, и комментарий в `channels.ts` прямо
объясняет, почему диалог заводится только для них. Этап 3 снимает это
ограничение для двух каналов: у `email` появляется исходящая отправка (`У-205`),
у `cabinet` — тоже (`У-212`). Поэтому:

```ts
export const DIALOG_CHANNELS = [...MESSENGER_CHANNELS, 'email', 'cabinet'] as const;
```

`MESSENGER_CHANNELS` **остаётся неизменным** — его читают 12 файлов, и все они
про мессенджеры (вебхуки, доступность бота, «написать первым» в бот). Новый
список — только там, где речь о диалоге как таковом (скоуп, фильтры, карточка,
бейджи). Модуль остаётся чистым (без серверных импортов): страж
`components.client-server-boundary` ловит обратное, и на этом уже падала сборка.

### 3.2. `Р-3-2`. Статусный автомат — один модуль, два вызывающих

Значения и переходы живут в `src/lib/services/messengers/dialogStatus.ts`
(чистые функции `nextStatusOnInbound`, `nextStatusOnOutbound`, `canCloseManually`),
а вызываются ровно из двух мест: `appendInbound.ts` (входящее) и `send.ts`
(ответ сотрудника). Правила:

| Событие | Было | Стало | `waitingSince` |
|---|---|---|---|
| входящее от клиента | любой, включая `closed` | `waiting_staff` | ставится, если не стоял |
| ответ сотрудника (`out`) | любой | `waiting_client` | сбрасывается в `null` |
| внутренняя заметка (`note`) | — | **не меняет статус** | не трогает |
| «Закрыть» руками | любой | `closed` | сбрасывается |
| «Открыть снова» руками | `closed` | `open` | не ставится |

`open` остаётся начальным значением для только что созданного диалога, у
которого ещё нет ни одного сообщения (кнопка «Новый диалог» до отправки). Это
осознанно: иначе первый же созданный диалог повис бы в `waiting_staff` и попал
в SLA-эскалацию, хотя клиент ничего не спрашивал.

**Заметка не двигает статус** — иначе внутреннее обсуждение снимало бы диалог с
SLA-контроля, ничего не ответив клиенту. Это тот же класс ошибки, что
«пометка без строки журнала» из этапа 2: действие выглядит как ответ, но
клиент его не видел.

### 3.3. `Р-3-3`. Вложения диалогов — свой путь, не `upload-core`

`persistUploadedDocument` не подходит: он создаёт `Document` (документ **заказа
или контрагента**), рассылает уведомления, требует заказ/контрагента и кладёт
ключ в `orders/…`. Вложение диалога — не документ заказа. Ближайший работающий
образец — вложения чата (`src/lib/chat/upload-attachment.ts` + `Message.attachmentPath`),
которые тоже живут своим путём и своей целью антивируса `chat_attachment`.

Поэтому: свой модуль `src/lib/services/messengers/attachment.ts`, ключ
`messengers/<dialogId>/<uuid>-<safeName>`, **та же** проверка MIME и размера
(`validateUploadFile` из `upload-core` переиспользуется — это чистая функция без
БД), та же очередь `docs.scanDocument` с новым `kind: 'messenger_attachment'`.

Скачивание — отдельный роут по образцу `/api/documents/[id]/download`:
`infected` → **410** (не 404 — это разные сигналы, CLAUDE.md §10), ссылка
подписывается на 600 с. Пока `scanStatus` не `clean`, в ленте показывается
«файл проверяется» без ссылки; `error` — «проверить не удалось», ссылки тоже
нет (расходимся с документами, где admin может скачать заражённое для
расследования: в диалоге такой нужды нет, а дыра была бы).

**Исходящее вложение уходит в транспорт только после `clean`.** Иначе мы
отправим клиенту заражённый файл раньше, чем узнаем об этом. Практически это
значит: сообщение с вложением создаётся сразу (видно менеджеру со статусом
«проверяется»), а отправка ставится задачей, которую запускает завершение
скана. Для `error` — сообщение остаётся неотправленным с кнопкой «Повторить».

### 3.4. `Р-3-4`. Почта: один диалог на нормализованный адрес

Ответ на письмо (`У-205`) — это `EmailTransport.send` с новыми заголовками
`In-Reply-To`, `References` (из `Message-ID` исходного письма) и `Reply-To`
(адрес входящего IMAP-ящика, чтобы ответ клиента вернулся в тот же ящик).
Значит, у входящего письма нужно **хранить `Message-ID`**, которого сейчас нет:
`InboundEmailDto` расширяется полем `messageId`, оно кладётся в существующее
`InboundMessage.externalId`? — **нет**, `externalId` уже занят под `email:<uid>`
и уникален. `Message-ID` едет в новое поле `MessengerMessage.externalId`
(оно уже есть и свободно для писем) при сворачивании письма в диалог.

Диалог для письма — `channel: 'email'`, `peerRef` = **нормализованный адрес**
(нижний регистр, обрезка пробелов). Правило нормализации — то же, что уже
используется для поиска контакта по каналу (урок этапа 2: «ключи поиска должны
быть нормализованы так же, как в правиле сравнения» — на этом там сломались
телефон и ИНН).

`email_unsupported` исчезает: `replyToInbound` для `email` начинает работать, а
`sendReply.ts` перестаёт различать каналы. Страж — grep по исходникам: кода
`email_unsupported` не должно остаться нигде.

### 3.5. `Р-3-5`. Внутренняя заметка — `direction = 'note'`, и **два** запрета, а не один

Заметка не уходит клиенту — это требование надо доказать в двух местах, потому
что у сообщения два пути наружу:

1. **Транспорт**: `send.ts` для `note` не зовёт `sendToMessenger` вовсе.
2. **Клиентские API** (`У-212`, `У-234`): выборка сообщений для клиента
   фильтрует `direction: { in: ['in','out'] }`.

Два стража, оба с мутацией. Именно этот класс — «одна дверь закрыта, вторая
осталась» — дал в этапе 2 дефект «роуты отчёта проверяли только роль».

Упоминание `@коллега` в заметке шлёт `note_mention` через **существующий**
общий отправитель `noteMention.ts` (страж реестра уведомлений требует один
продьюсер на тип — свой дубль не заводим).

### 3.6. `Р-3-6`. Ответственный: правило первого ответившего уже есть — расширяем, а не дублируем

В `send.ts` уже работает «первый ответивший забирает диалог в свою компанию»
(`Р-М-2`). Туда же добавляется «…и становится ответственным, если ответственного
нет». Уведомление `messenger_message` меняет таргетинг: **ответственному**, а
при его отсутствии — менеджерам организации (как сейчас). Диалог без
организации и без ответственного по-прежнему виден только во «Входящих в
работу» — и это правильно, но теперь он ещё и считается бейджем (`У-215`).

Смена ответственного — аудит (`dialog_assignee_changed` в `AUDIT_ACTIONS` +
русское название в `audit/labels.ts`, иначе не соберётся) и уведомление новому.

### 3.7. `Р-3-7`. Права: шкала `dialogs` в профиле + capability `communications.dialogs`

Строго по образцу задач: `dialogs: ScopeLevel` в `SessionAccessProfile`,
`dialogWhereForLevel(session, level)`:

- `all` — вся компания + непривязанная очередь (нынешнее поведение);
- `assigned` — свои (`assigneeId = я`) + диалоги организаций из `managedOrgIds` + непривязанная очередь;
- `own` — только `assigneeId = я` **плюс непривязанная очередь**.

Очередь непривязанных видна на всех уровнях осознанно: иначе новое обращение от
неизвестного человека не увидит никто, кроме админа, и оно провисит до SLA. Это
записывается в спеку как решение, а не «случайно так вышло».

`teamMode` уважается там же, где и в задачах: при выключенной командной
видимости `assigned` не расширяется до чужих организаций.

Профиль без размеченных `settings.*`/capability-кодов работает по-старому
(legacy, CLAUDE.md §2b) — включение новой шкалы не должно молча отнять доступ у
ранее заведённых профилей.

### 3.8. `Р-3-8`. Публичный роут: реестр вместо несуществующего allow-list middleware

Заводится `src/lib/api/publicRoutes.ts` — список путей, объявленных публичными,
с **причиной строкой** для каждого:

```ts
export const PUBLIC_API_ROUTES = [
  { path: '/api/public/requests', reason: 'Форма заявки на сайте otsfera.ru (У-211): токен X-Site-Token + Origin + rate-limit' },
  { path: '/api/integrations/telegram/webhook', reason: 'Вебхук бота Telegram: секрет в заголовке (Р-М-6)' },
  // ...max, whatsapp
] as const;
```

Страж `security.public-api-routes.guardrail`: каждый роут в `src/app/api/**`,
не вызывающий ни одного `require*`/`getSession`, обязан быть в реестре с
непустой причиной — и наоборот, реестр не должен содержать путей, у которых
гард на самом деле есть. Это даёт ровно то, ради чего `У-217` просил
allow-list: список публичных дверей нельзя пополнить молча.

Защита самого роута `У-211`: токен `X-Site-Token` (сравнение `secretEquals`,
как у вебхуков), `Origin` из списка разрешённых доменов, `isRateLimited('site-form:'+ip, {windowMs: 60_000, max: 10})`,
honeypot-поле → **200 без записи** (бот не должен узнать, что его отсекли),
Zod-форма, тело ≤ 16 КБ, вложений нет.

### 3.9. `Р-3-9`. Токен формы сайта — «показывается один раз» поверх механизма, который не показывает секреты никогда

`getSettingsView` для `isSecret: true` отдаёт только `isSet: boolean` — значение
наружу не уходит **никогда**, и ломать это нельзя. Поэтому «показывается один
раз» реализуется так: токен генерируется **действием** «Выпустить токен»,
и открытое значение возвращается **в результате этого действия** (показывается
в модалке с кнопкой «Скопировать» и предупреждением «больше он не покажется»).
В хранилище едет шифрованным, в форме потом — только «задан». Перевыпуск
отзывает прежний.

### 3.10. `Р-3-10`. Флаг раскатки — `comm_center` (opt-in, поведенческий)

Как в этапах 1 и 2 (`contacts`, `bitrix_migration`): новые элементы закрыты до
приёмки заказчиком. Флаг **поведенческий** (страницы `notFound`, действия
`forbidden`, блоки не рендерятся) — env не заводим, переключается из «Функций
платформы». Строка в `docs/feature-flags-matrix.md` обязательна: страж
`docs.feature-flags-matrix` не пропустит флаг без неё.

Что **не** гейтится флагом: существующие диалоги, статусы и ответственный
(они улучшают то, что уже работает под `inbound_messaging`, и прятать их
вредно). Гейтятся: шаблоны ответов, раздел «Сайт» и публичный роут, канал
`cabinet`. Приём заявок с сайта дополнительно имеет **свой** переключатель в
разделе «Сайт» — флаг раскатки и рабочий выключатель это разные вещи.

### 3.11. Границы этапа

**Не входит** (и не «заодно»): чат-виджет сайта, VK/Avito/Viber, зеркалирование
`OrderThread`, «не беспокоить», капча, бот на компанию — всё это §6 ТЗ
«Позже». Вкладка «Задачи» в диалоге и триггер `dialog_waiting_staff_overdue` —
**этап 4** (порядковое ограничение: этап 3 до этапа 4). Экран «Переписка с
менеджером» в кабинете заказчика — **этап 6** (`У-234`); этап 3 делает только
серверную часть (`У-212`, порядковое ограничение 4 из §5 ТЗ).

## 5. Тестовая стратегия

Помимо обычного «unit + integration + 100 % покрытия затронутых файлов»:

- **Стражи этапа (каждый проверяется мутацией — сломать и убедиться, что падает):**
  1. `messengers.note-not-leaked` — заметка не уходит ни в транспорт, ни в клиентский API (**два** сценария, `Р-3-5`);
  2. `security.dialogs-scope-own` — профиль `own` не видит чужой диалог, `assigned` не видит чужую организацию при `teamMode=off`;
  3. `security.public-api-routes` — реестр публичных роутов полон и честен (`Р-3-8`);
  4. `messengers.attachment-idor` — чужой `messageId` в роуте скачивания → 404/403, заражённый → 410;
  5. `messengers.dialog-status-machine` — таблица переходов из `Р-3-2` целиком, включая «заметка не двигает статус»;
  6. `messengers.email-unsupported-gone` — grep по исходникам (через `readSource`, иначе страж сам себя обманет комментарием);
  7. `navigation.org-card-tabs` / `org-card-tiles` — обновляются под новую вкладку (они держат точный список подписей).
- **Повторный прогон и нормализация** — урок этапа 2: письмо, пришедшее дважды, не должно создать два диалога; адрес `Ivan@Mail.RU` и `ivan@mail.ru` — один диалог.
- **Что попадёт в снимок** — урок этапа 2 (PR-4): у аудита смены ответственного отдельно проверяем содержимое `after`.
- **Интеграционные на живой базе:** автопереходы статусов под нагрузкой параллельных сообщений; SLA-эскалация диалога; загрузка и скан вложения; приём формы с сайта (401/403/429/honeypot/успех).
- **Мобильные эталоны** — карточка диалога и раздел «Шаблоны ответов» на 390×844 (§15 CLAUDE.md).

## 6. Риски

| Риск | Чем гасим |
|---|---|
| **Вложение уходит клиенту до антивируса** | Отправка только после `clean` (`Р-3-3`), страж на путь «pending → транспорт не зван» |
| **Заметка утекает клиенту** | Два независимых запрета и два стража (`Р-3-5`) — один запрет исторически всегда оказывался обойдён вторым путём |
| **Ответ на письмо уходит не в ту переписку** | `In-Reply-To` + `References` + нормализованный адрес; тест «ответ клиента вернулся в тот же диалог» |

| **`own` не видит новых обращений** | Непривязанная очередь видна на всех уровнях (`Р-3-7`), закреплено тестом |

| **`status` — строка, опечатка не ловится типами** | Все значения только через `dialogStatus.ts`; страж на литералы статуса вне этого модуля |
