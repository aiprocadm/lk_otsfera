## PR-1 — что сделано

### `У-341` — страж миграций

`src/__tests__/prisma.migrations-compat.guardrail.test.ts`: новая `migration.sql` без пометки
`-- contract: <ссылка>` не может содержать `DROP TABLE`, `DROP COLUMN`, `RENAME`,
`ALTER COLUMN … TYPE`, `SET NOT NULL`, `FOREIGN KEY`/`CHECK` на существующую таблицу без
`NOT VALID`. **Решение:** ограничение на таблицу, созданную в той же миграции, не считается
нарушением — таблица пуста, проверять нечего, а Prisma пишет такие ключи для каждой новой модели
(иначе страж заставлял бы руками править каждую миграцию с новой таблицей). Комментарии SQL не
читаются (слово `DROP COLUMN` в пояснении — не нарушение).

**Разведка:** из 144 применённых миграций правило нарушили бы 49 (43 — внешние ключи на
существующие таблицы, 5 `DROP COLUMN`, 5 `SET NOT NULL`, 2 `RENAME`, 1 `DROP TABLE`, 1 смена
типа). Применённые миграции не правятся (CLAUDE.md §2) — они в замороженном списке
`APPLIED_BEFORE_GUARD`; страж проверяет, что список не пополняется (самая поздняя запись — до
31.10.2026) и не содержит несуществующих имён.

**Мутации:** временная миграция с `DROP COLUMN` → красный; с пометкой `contract` → зелёный;
внешний ключ на существующую таблицу без `NOT VALID` → красный; после удаления — зелёный.
Самопроверка распознавания — 13 случаев (8 нарушений, 5 разрешённых форм).

## PR-2 — что сделано

### `У-338` — образ по тегу

`docker-compose.prod.yml`: `migrate`/`web`/`worker` — `${IMAGE_REPO:-lk-otsfera}:${IMAGE_TAG:?…}`.
Без тега compose не стартует. **Находка:** обязательный тег ломал бы и служебные команды
(`docker compose ps/logs/restart` тоже подставляют переменные) — поэтому `deploy.sh` после удачной
выкладки пишет работающий тег (и `COMPOSE_FILE`) в `.env` стека, который compose читает сам; при
осечке там остаётся прежний тег. Страж `infra.compose-prod` (мутация — старый compose → красный).

### `У-339` — `scripts/deploy/deploy.sh <тег>`

Один скрипт на обе среды (ДП §7): проверка тега (только `[A-Za-z0-9._-]`), образ локальный или из
реестра, `up -d --wait` (миграции — сервисом `migrate` до приложения), `/api/health/live`, тег в
`deploy.log`. При осечке печатает команду отката на прежний тег, но **сам не откатывает** — решение за
человеком (ДП §7 п. 6). Среда задаётся `.deploy.env` стека (`COMPOSE_FILE`, `IMAGE_REPO`).
Тест `scripts.deploy-sh` запускает скрипт с двойниками `docker`/`curl` (12 случаев); мутации —
без проверки тега и запись журнала до проверки здоровья — красные.

**Сверка с `npm run deploy:stand` (ДП §7):** `update-stand.sh` обновляет тестовый стенд из
исходников (systemd, без Docker) — другая топология; он остаётся для стенда, стейджинг и прод
выкладываются только `deploy.sh`. Это записано в шапке скрипта.

### `У-340` — конфигурация сред

- `.env.production.example` — один шаблон на прод и стейджинг с пометками «прод: … / стейджинг: …»
  по таблице ДП §5; добавлены `TRUSTED_PROXY_HOPS=1`, `FEATURE_STAFF_2FA=1`, `SENTRY_RELEASE`.
- **Расхождение с ДП:** для стейджинга ДП пишет `ONE_C_ADAPTER=mock`, а код знает только `fake` и
  `rest` (`getOneCAdapter` бросает на неизвестном) — в шаблоне `fake`.
- **`NEXT_PUBLIC_SENTRY_DSN` не нужен:** клиентской части Sentry в проекте нет (ДП просил сверить).
  Добавлять её — новая функция с вопросом ПДн, не входит в этап. `SENTRY_RELEASE` читают
  `instrumentation.ts` и воркер; compose подставляет его из `IMAGE_TAG`.
- `env.ts`: заглушка (`replace_with…`/`replace_me`/`changeme`) в **любой** переменной — не только в
  обязательных — не даёт стартовать (раньше пропускались токен 1С, пароль IMAP, ключи Mango, общий
  секрет моста). Перед этим проверено, что в настройках стенда заглушек нет. Мутация — красная.
- `Caddyfile.staging` + `docker-compose.staging.yml`: всё за паролем, кроме `/api/integrations/*` и
  `/api/public/*`; `X-Robots-Tag: noindex`. Хеш пароля не в репозитории — `import` файла
  `caddy-staging-users` с сервера (нет файла — Caddy не стартует, стейджинг не открывается без
  пароля). Страж `infra.staging` (мутации: открыт весь `/api/*`, пароль закомментирован — красные).
- Ранбуки `RUNBOOK.md` §3.1, `runbook-prod-infra-rf.md`, `runbook-launch-deploy.md` переведены с

## PR-3 — что сделано

### `У-343` — ранбук выкладки

`docs/runbook-release.md` — главный документ: разведение сред (таблица ДП §2, `mock` → `fake`), фаза A с
привязкой к действиям владельца `Н-1`…`Н-7`, фаза B (свежий клон: `verify`, `gate`, `build`, `audit:prod`,
`schema:drift`, тег и образ), фаза C (`.env.production`, `.deploy.env`, пароль стейджинга), фаза D (первый
запуск через `deploy.sh`, первый администратор, смоук-чек-лист go/no-go ДП §6 плюс проверка пароля
стейджинга), фаза E (стейджинг → тест отката → тег → прод → 24 часа → откат), хотфикс прода. Клон стека на
сервере переключается на тег/коммит образа — иначе новый образ поехал бы со старыми compose-файлами.
`RUNBOOK.md`, `runbook-prod-infra-rf.md`, `runbook-launch-deploy.md` и README «Финальный release checklist»
ссылаются на него (сверка ДП §11: фаза B заменяет шаги 1–5 и 7 README, шаг 6 — запуск dev — оставлен).

**Находка — дефект первого запуска.** Команда `docker compose run --rm web npm run db:create-admin` (ДП §6,
`runbook-prod-infra-rf` §5) падала бы: папка `scripts/` в рабочий образ не копировалась. `Dockerfile` теперь
кладёт в образ только `scripts/create-admin.ts` (его импорты — `src/`, уже в образе). Страж проверяет строку в
стадии `runtime` (мутация — строка удалена → красный).

**Живой первый запуск (Docker, образ `lk-otsfera:pr3-check`).** В образе из `scripts/` — только
`create-admin.ts`; на пустом `postgres:16-alpine` из образа `prisma migrate deploy` применил все 144
миграции; `npm run db:create-admin` без переменных — понятный отказ, с ними — «admin создан», в базе
пользователь `admin` и запись аудита `admin_bootstrapped`. **Вторая находка:** без `DIRECT_URL` миграции
падают (`schema.prisma` читает `directUrl`), а web/worker ждут `migrate` — прод не поднимается, а в таблице
ДП §5 этой переменной нет. `env.ts` теперь требует её в production (на стенде задана — проверено); ранбук
говорит об этом в фазе C. Сборка внутри Docker на агентском сервере идёт только через прокси хоста
(`--network host` + `HTTPS_PROXY`): без него CDN SheetJS (`xlsx`) недоступен — свойство сервера, не кода.

### `У-344` — заготовки `staging → main`

`.github/staging-switch/`: `CODEOWNERS.template` (чувствительные пути ДП §7), `ci-source-branch.job.yml`,
`deploy-staging.yml`, `README.md` (условия `Н-9`/`Н-11`/`Н-5`, таблица «что переключить»: CODEOWNERS, триггеры
и джоб `ci.yml`, автодеплой, `renovate.json` `baseBranches`, CLAUDE.md §11/§14 и порядок вливания, rulesets).
**Решение:** заготовки не кладутся в `.github/workflows/` и не вставляются в `ci.yml` — GitHub исполнил бы
их сразу: `source-branch` валил бы каждый нынешний PR в `main`, а новый workflow требует решения владельца
(CLAUDE.md §11). Из этой папки GitHub ничего не читает.

Страж `infra.staging-switch`: заготовки на месте и выключены (в `workflows` только `ci.yml`, джоба нет,
`CODEOWNERS` прежний); шаг `source-branch` **исполняется** bash-ем — пропускает `staging` и `hotfix/*`,
отклоняет `feat/…`, `claude/…`, `staging-old`, `main`; автодеплой — только push в `staging`, тот же
`deploy.sh`, клон на коммит образа. Мутации: проверка пропускает любую ветку (4 красных), автодеплой перенесён
в `workflows` (красный), образ без скрипта администратора (красный).
