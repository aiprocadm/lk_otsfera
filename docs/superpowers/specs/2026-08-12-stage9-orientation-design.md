# Этап 9 — ориентирование и приёмка §0 (финальный этап программы)

**ТЗ:** [понятность интерфейса и закрытие функциональных пробелов](../../tz/2026-08-08-tz-usability-and-core-gaps.md), требования `У-71`…`У-77`.
**Дата:** 12.08.2026. **Статус:** ждёт подтверждения заказчика.

## 0. Коротко

Последний этап программы: система умеет всё, что требовало ТЗ, — осталось,
чтобы в ней было легко ориентироваться. Пять видимых вещей (частые задачи,
крошки, подзаголовки, пустые экраны, палитра), словарь терминов и финальная
приёмка по правилу трёх вопросов «где я / что здесь / что дальше».

## 2. Решения, которые предлагаю

### 2.1. Порядок: три PR

| PR | Что | Требования |
|---|---|---|
| **PR-1 «опоры»** | `/help` со словарём + ссылка в подвале меню; `EmptyState` дорастает до требования (заголовок + кнопка) и вычищаются сырые места; блок «Частые задачи» на шести стартовых экранах | `У-76`, `У-74`, `У-71` |
| **PR-2 «где я»** | Хлебные крошки на все вложенные экраны; подзаголовок на 51 экран | `У-72`, `У-73` |
| **PR-3 «палитра и приёмка»** | Командная палитра Ctrl/Cmd+K; чек-лист приёмки §0 по шести кабинетам; **финальный полный drift-аудит всех `У-1`…`У-77`** перед закрытием программы (§16) | `У-75`, `У-77` |

Почему так: PR-1 — независимые опоры, на которые ссылаются остальные (пустой
экран с кнопкой нужен крошкам и палитре как целевое состояние); PR-3 последний,
потому что приёмка имеет смысл, когда экраны перестали меняться, — ровно как
сказано в §5 ТЗ.

### 2.2. «Частые задачи» (`У-71`)

Один презентационный компонент плиток (по образцу навигатора 1С: вопрос +
подсказка + стрелка) и **реестр задач по ролям в lib** — рядом с
`welcomeActionsFor`, форма данных та же `{href, title, hint}`. Блок постоянный,
стоит первым на стартовом экране. Одноразовый `WelcomeCard` после этого
удаляется: два блока плиток на одном экране — шум, а его список задач
переезжает в реестр.

Предлагаемый состав (4–6 плиток на роль, приму правки):

- **Партнёр:** Подать заявку на обучение · Добавить сотрудника · Посмотреть удостоверения · Проверить начисления · Задать вопрос
- **Организация:** Подать заявку на обучение · Добавить сотрудника · Посмотреть удостоверения · Документы · Задать вопрос
- **Менеджер:** Входящие в работу · Создать сделку · Загрузка из 1С · Импорт оплат · Найти клиента
- **Руководитель:** Команда · Сверка с 1С · Акты комиссии · Аналитика · Настройки
- **Администратор:** Пользователи · Организации · Обмен с 1С · Функции платформы · Журнал аудита
- **Слушатель:** экран и так одно действие («Перейти к обучению») — блок не нужен, требование к нему неприменимо; зафиксирую в реестре сверки

Плитки, ведущие в разделы под флагами, показываются только при включённом
флаге (реестр это уже умеет через `navItemsFor`-подход).

### 2.3. Крошки (`У-72`) — два механизма, потому что задачи две

- **Статические вложенные страницы** (например «Портфель → Настройки
  организации») получают крошки **из пути по реестру меню**: родитель — пункт
  первого уровня из `navByRole`, как это уже сделано в хабе настроек.
- **Деталки `[id]`** так не могут: имя сущности лежит в базе, а не в URL.
  Для них — лёгкий помощник «крошки из пары (раздел, имя сущности)», по
  образцу уже существующих построителей лида и заказа. Страница и так
  загружает сущность — отдаёт готовый заголовок в крошку.

Рендер — существующий компонент `Breadcrumbs`; отдельного «умного» слоя в
layout не завожу: деталкам всё равно нужны данные, а два способа монтирования
(layout + страница) хуже одного явного.

### 2.4. Подзаголовки (`У-73`)

51 экран получает одну строку «что здесь делают» — простыми словами, термины
из глоссария. Карточкам сущностей (заказ, сотрудник, организация) подзаголовок
не выдумываю: там после имени уже стоят метаданные (ИНН, email, номер) — это
и есть ответ «что здесь»; такие экраны фиксирую в реестре как соответствующие
по смыслу, а не по букве. Спорные формулировки соберу таблицей в PR — быстрее
поправить пачкой, чем переписывать по одной.

### 2.5. Пустые состояния (`У-74`)

`EmptyState` дорастает до требования: заголовок «Здесь пока пусто» (с
возможностью переопределить), строка объяснения, **слот кнопки становится
ожидаемым** — и линтер-страж на сырые русские «пока нет/пусто» в JSX вне
компонента, чтобы список не отрастал заново.

Границу провожу так: **пустой экран или пустая вкладка** — обязателен
компонент с кнопкой (или явной причиной, почему кнопки нет — например, данные
приходят только из 1С); **мелкие инлайновые пустоты внутри карточек** («оплат
по заказу пока нет», «комментариев пока нет») компонентом не оборачиваю — там
карточка-родитель уже отвечает на три вопроса, а дюжина серых плиток на одном
экране хуже строки текста. Ручную копию разметки и «Нет данных» без объяснения
чиню в любом случае.

### 2.6. Палитра (`У-75`)

Клиентский оверлей на существующем примитиве `Dialog` (focus-trap и Escape уже
есть), горячая клавиша Ctrl/Cmd+K, смонтирован в общем шелле — доступен во
всех шести кабинетах.

- **Переходы по разделам — все роли.** Источник — реестр меню `navByRole`
  своей роли с его же фильтрами флагов: палитра не покажет раздел, которого
  нет в меню, и не станет второй картой доступа.
- **Поиск по данным — только роли, у которых он уже есть** (менеджер,
  руководитель): палитра при вводе длиннее двух символов зовёт существующий
  сервис с его скоупами. Клиентским ролям поиск по данным не открываю — их
  сервис никогда не скоупил, это отдельный большой объём безопасности, а ТЗ
  требует «поиск по разделам меню и быстрый переход» (см. вопрос 2).
- Существующие страницы поиска не трогаю: палитра — быстрый вход, страница —
  полные результаты; из палитры есть переход «показать все результаты».

### 2.7. Словарь (`У-76`)

Страница `/help` — серверная, контент переносится из `docs/glossary.md` в
типизированный реестр терминов в lib (страница из него рендерит, глоссарий-md
остаётся источником для разработчиков; тест-страж сверяет, что шесть терминов
из ТЗ есть в обоих). Ссылка «Справка» — в подвале меню всех шести кабинетов
(`pinnedBottom`), новый значок в семантическом реестре. Доступ — все вошедшие
роли, без правок middleware.

### 2.8. Приёмка (`У-77`) и закрытие программы

Чек-лист §0 по шести кабинетам × 10 случайных экранов — таблицей в close-out
этапа (экран → три вопроса → да/нет → что поправлено). Вместе с ним — **полный
drift-аудит `У-1`…`У-77`** (§16: обязательный проход при закрытии программы) и
обновление всех четырёх указателей на ТЗ, если программа объявляется закрытой.

## 3. Тесты

- реестр «частых задач»: у каждой роли 4–6 плиток, все `href` существуют в
  реестре меню или в списке известных маршрутов; плитки под флагом исчезают
  при выключенном флаге;
- крошки: статический построитель отдаёт «раздел → страница» по реестру;
  деталка отдаёт «раздел → имя сущности»; последняя крошка без ссылки;
- подзаголовки: страж «новый/переписанный экран без подзаголовка» остаётся
  ревью-правилом (§15), а не тестом — автоматическая проверка по маршрутам
  ломается о карточки сущностей;
- `EmptyState`: заголовок/объяснение/кнопка; линтер-страж на сырые пустоты;
- палитра: открывается по Ctrl/Cmd+K, ищет по своим разделам (чужая роль не
  видит чужие пункты — прогон по всем шести реестрам), Enter ведёт по ссылке,
  Escape закрывает; поиск по данным зовётся только у менеджера/руководителя;
- `/help`: страж полноты — шесть терминов ТЗ присутствуют; ссылка в подвале
  каждого кабинета; страница отвечает каждой роли.
