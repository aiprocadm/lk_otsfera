## 1. Зачем

Дефект §0.2: ветка создания организации в `upsertOrgRecord` на каждого нового
контрагента минтит **новую `Company`** — то есть новую компанию-**продавца** с
названием клиента. Компания в системе — граница тенанта (инвариант C8): на ней
держатся видимость менеджеров, скоупы, отчёты. Организация-клиент, живущая в
собственной пустой «компании», не видна никому, кроме админа. Дефект действует
и в сетевой синхронизации, поэтому осиротевшие `Company` в базе, возможно,
уже есть — их чинит бэкфилл (Т-42).

Без этого этапа нельзя делать этап 7: право импорта руководителю выдать можно,
но каждая созданная им организация попадала бы в чужую свежеминтованную
компанию — `mayCreateOrg` сегодня честно запрещает это (`out_of_scope`).

## 2. Что в объёме (Т-41…Т-44)

| Требование | Суть |
|---|---|
| **Т-41** | Убрать `tx.company.create`. Новая организация получает `companyId`: скоуп `company` (руководитель) → его компания; скоуп `global` (admin) → компания, выбранная в форме импорта (единственная в системе — по умолчанию, без вопроса); воркер без скоупа → компания из конфигурации синхронизации, не задана → явная ошибка в журнале, а не молчаливый тенант |
| **Т-42** | Скрипт-бэкфилл осиротевших `Company` (без пользователей, ровно одна организация с совпадающим названием): перепривязать организации к целевой компании, пустые `Company` удалить. Dry-run по умолчанию, отчёт списком, применение только с явным флагом, перед продом — бэкап |
| **Т-43** | `mayCreateOrg` расширяется на скоуп `company` (создание теперь ВНУТРИ компании актора — C8 не нарушается); комментарий-обоснование и тест инварианта обновляются |
| **Т-44** | Guardrail: импорт любого файла не создаёт **ни одной** `Company` — `company.count()` до/после в integration-тесте |

**Вне объёма:** право импорта руководителю и зеркальные страницы (этап 7,
Т-25…Т-29); возврат результата writer'ами (этап 8); откат (этап 9).

## 3. Разведка по коду (факт на `main` 4b800586)

- `writers.ts` — ветка создания: `db.$transaction` → `tx.company.create({ name:
  input.name })` + `tx.organization.create`. После правки транзакция не нужна —
  остаётся один `organization.create`.
- `mayCreateOrg` (`writers.ts:45`) — `!scope || scope.kind === 'global'`;
  комментарий над ней прямо объясняет запрет тем, что «создание минтит новую
  Company» — после Т-41 обоснование устаревает (Т-43 требует обновить).
- `import/index.ts` — `WriteCtx` собирается как `{ mode, notify, scope }`;
  у `Args` компании нет. Сессия admin — Model A, своей компании не имеет →
  выбор в форме обязателен.
- Воркер `sync-organizations.ts` — ctx `{ mode, notify, bump }` **без скоупа**;
  в `oneCSync/config.ts` настройки компании нет (только mode/timeout/cursor).
- `Company` имеет **16 обратных связей** (users, orders, organizations,
  documents, accessProfiles, funnelStages, deals, … calendarEvents) — удалять
  осиротевшую компанию можно только после явной проверки пустоты по всем.
  Минтованные сироты несут organizations (1) и orders (writer заказов ставит
  `companyId: org.companyId`).
- Тесты, живущие на минте: stage5-integration (уборка минтованной Company),
  stage4-partner (прямые вызовы writer'а), unit-моки с `company: { create` и
  `$transaction` — все перечислены в §6.

## 4. Решения

### 4.1. Откуда берётся компания — одна точка в create-ветке (Т-41)

`WriteCtx` получает поле `createCompanyId?: string` — «компания для НОВЫХ
организаций». Ветка создания решает так:

```ts
const companyId =
  ctx.scope?.kind === 'company' ? ctx.scope.companyId : ctx.createCompanyId;
if (!companyId) {
  sum.failed += 1;
  sum.failures.push({ externalId: input.externalId, error: 'company_not_configured' });
  return;
}
// organization.create({ ..., companyId }) — company.create больше НЕТ
```

Скоуп `company` (руководитель) всегда побеждает — подсунуть чужую компанию
через параметр нельзя. Скоуп `orgs` (обычный менеджер) в создание по-прежнему
не попадает (`mayCreateOrg`, §4.4).

### 4.2. Admin: выбор компании в форме (Т-41)

- `Args` импорта получает `companyId?: string`; server action передаёт его из
  `FormData`.
- Сервис для скоупа `global` до батчей: `companyId` передан → проверить, что
  такая `Company` существует; не передан → если компания в системе **ровно
  одна** — она по умолчанию (буква Т-41), иначе отказ новым кодом
  **`company_required`** («выберите компанию для новых организаций») ещё до
  записей. Проверка одинакова для предпросмотра и применения — план честный.
- UI: страница `/admin/settings/integrations/1c/excel` читает список компаний
  (id + название) и передаёт в `ImportForm`. В форме — селект «Компания для
  новых организаций» (обязателен при нескольких компаниях; при единственной —
  скрытое поле и строка «Новые организации попадут в компанию „X“»). Значение
  уходит и с предпросмотром, и с применением. Страница менеджера/руководителя
  селект не показывает — там компанию даёт скоуп.

### 4.3. Воркер: компания из конфигурации (Т-41)

`oneCSync/config.ts` + `oneCDefaultCompanyId(): string | null` — env
`ONE_C_COMPANY_ID` (трим, пусто → null). `sync-organizations.ts` кладёт её в
`ctx.createCompanyId`; если не задана — `log.error` один раз перед батчем
(«ONE_C_COMPANY_ID не задан — новые организации создаваться не будут»), а
каждая строка, требующая создания, честно падает `company_not_configured` в
отчёт синхронизации.

**Осознанное толкование буквы ТЗ** («импорт организаций не выполняется с явной
ошибкой в журнале»): полная остановка батча молча заморозила бы и **обновления
существующих** организаций — это новый молчаливый отказ вместо старого.
Запрещённое по смыслу — молчаливое создание тенанта; построчная явная ошибка
это исключает, обновления продолжают идти, ошибка видна и в pino-журнале, и в
отчёте прогона. Если заказчик хочет именно полную остановку — скажите, это
одна строка.

### 4.4. `mayCreateOrg` расширяется (Т-43)

`!scope || scope.kind === 'global' || scope.kind === 'company'` (то есть
запрещён только скоуп `orgs`). Комментарий переписывается: создание больше не
минтит Company; company-скоуп создаёт СТРОГО в своей компании (§4.1), поэтому
C8 держится; обычному менеджеру создание расширило бы его скоуп — остаётся
запрет. Тест инварианта (`security.import-org-doc-scope.test.ts`) обновляется.

### 4.5. Бэкфилл (Т-42)

Логика — в **`src/lib/services/oneCSync/backfill-orphans.ts`** (слой services:
покрытие 100%, боевые импорты, честные integration-тесты), CLI-обёртка —
`scripts/backfill-orphan-companies.ts` + `npm run backfill:orphan-companies`.
`.ts` + `tsx` вместо `.mjs` из буквы ТЗ — конвенция этапа 1, согласована.

- **Кандидат-сирота:** `Company` без пользователей, у которой ровно одна
  `Organization`, и её название совпадает с названием компании (сигнатура
  минта: writer копировал `name` клиента).
- **Dry-run (по умолчанию):** таблица кандидатов (компания, организация, ИНН,
  число заказов) + напоминание о бэкапе (`docs/runbook-backups.md`). Ничего
  не пишет.
- **Применение:** только `--apply --company <id целевой компании>`; целевая
  обязана существовать и не быть сама кандидатом. На каждого кандидата — одна
  транзакция: организация и её заказы перевешиваются на целевую компанию,
  затем компания-сирота удаляется **только если все 16 обратных связей пусты**
  (явные счётчики); не пуста → остаётся, в отчёте строка «оставлена: не пуста».

### 4.6. Guardrail (Т-44) и волна по тестам

Integration-тест этапа 6: файл с новой организацией → `company.count()` до и
после `commitImport` **равны**, организация привязана к выбранной компании.
Дополнительно: путь руководителя (скоуп company → своя компания), путь без
компании (`company_not_configured` в failures, батч жив).

Существующие тесты, живущие на минте, переводятся: stage5-integration заводит
целевую `Company` сам и передаёт `companyId` (иначе на общей базе с многими
компаниями сработает `company_required`), уборка минтованной компании
удаляется; stage4-partner получает `createCompanyId` в ctx; unit-моки с
`company: { create` / `$transaction` перерабатываются. Новый экспорт
`oneCDefaultCompanyId` добавляется **во все** `vi.mock`-фабрики конфига
(грабля этапа 5). Новый код ошибки `company_required` — в словарь
`XLSX_IMPORT_ERRORS` с русским текстом (exhaustive-тип + тест полноты);
причина `company_not_configured` показывается в таблице причин как есть,
наравне с `partner_not_found`.

## 7. Риски

Средний (по ТЗ). Главные: (1) смена источника `companyId` затрагивает сетевую
синхронизацию — закрыто конфигом + CHANGELOG + построчной ошибкой вместо
молчания; (2) бэкфилл трогает боевые данные — dry-run по умолчанию, явные
флаги, транзакция на кандидата, удаление только после проверки пустоты по всем
16 связям, напоминание о бэкапе; (3) волна по тестам, живущим на минте, —
перечень известен из разведки (§6).

## 8. Решения, требующие «ок» заказчика

Оба встроены в спеку, отдельного ответа не требуют — «ок» по спеке подтверждает:

1. **§4.3** — воркер без `ONE_C_COMPANY_ID`: построчная явная ошибка
   (обновления продолжаются), а не полная остановка батча организаций.
2. **§4.5** — целевая компания бэкфилла задаётся флагом `--company <id>`
   (в системе может быть больше одной компании — угадывать нельзя).
