# Импорт данных 1С из Excel-выгрузки — дизайн (под-проект 1)

**Дата:** 2026-06-09
**Статус:** согласовано (брейнсторм) → spec self-review → ревью пользователя → план
**Связано:** [completion-roadmap](2026-06-02-completion-roadmap.md) (Трек A, альтернатива встрече с 1С) · [1c-contract.md](../../integrations/1c-contract.md) · [organization-finance-hub-design](2026-06-04-organization-finance-hub-design.md) · [c8-manager-company-wide-design](2026-06-05-c8-manager-company-wide-design.md)

## Цель

Дать кабинету **реальные данные об оплатах** без зависимости от боевого REST-интерфейса 1С и встречи с IT-1С (Трек A заблокирован внешне). Источник данных — ручная **Excel-выгрузка** из 1С (контрагенты / реализации / поступления), которую бухгалтер/менеджер/руководитель формирует сам. После импорта партнёр и организация видят свои оплаты в **уже построенных** витринах `organization/finance` и `partner/finance`.

Это **под-проект 1** из декомпозиции. Под-проект 2 (витрина оплат в кабинете менеджера с гейтом процентов посредника, открытый пункт C-a roadmap) — **отдельная спека следом**; здесь не реализуется.

## Контекст: что уже есть, чего не хватает

- **Витрины готовы.** `organization/finance.ts` и `partner/finance.ts` рендерят KPI + payment ledger. Не трогаем их UI.
- **Sync-инфраструктура готова.** `src/lib/services/oneCSync/*` содержит DTO, zod-схемы, мапперы (`mapOrgDto`/`mapOrderDto`/`mapPaymentDto`) и upsert-логику с резолвом связей. Файл-импорт переиспользует эту логику как новый **источник**, а не переписывает её.
- **Не хватает только источника данных.** Сейчас данные течь могут лишь через `FakeOneCAdapter` (выдуманные) или боевой REST (заблокирован).

## Реальность данных (определяет всю модель)

Простая Excel-выгрузка 1С использует **натуральные ключи** (ИНН, номер заказа, номер документа), а не GUID 1С. Ключевой факт по листу «Поступления»: колонки `Дата, Наименование организации, ИНН, назначение платежа, сумма` — **оплата привязана к организации (по ИНН), а не к заказу**. Свободный текст «назначение платежа» не является структурированным ключом заказа.

Текущая схема требует `Payment.orderId` (NOT NULL) и `Organization.partnerId` (NOT NULL). Обе константы расходятся с реальностью (org-level оплаты; самостоятельные обращения без партнёра) и требуют аддитивных миграций.

## Решения брейнсторма

1. **Scope = B (полный конвейер):** импорт организаций → заказов → оплат (порядок диктует FK-зависимость).
2. **Привязка орг→партнёр по ИНН** (вариант A): партнёрские аккаунты заводятся вручную; в листе «Контрагенты» есть колонка с ИНН партнёра. Пустая → standalone-орг (самостоятельное обращение).
3. **Подход 1 (оплата org-level):** оплата привязывается напрямую к организации по ИНН; `Payment.orderId` опционален (nullable, обычно не заполняется). KPI/комиссия остаются заказо-центричными (из «Реализации»).
4. **Дедуп оплат (A):** колонка **«Номер документа»** (номер платёжного поручения) → `Payment.externalId`. Стабильная идемпотентность при повторной загрузке.
5. **RBAC scoped:** менеджер импортирует только свои закреплённые орги; руководитель + админ — все. Привязку менеджер↔орг импорт не пишет.

## Модель данных и миграции (аддитивные, безопасные)

| # | Миграция | Назначение |
|---|---|---|
| M1 | `Partner.inn String? @unique` | Ключ привязки орг→партнёр по ИНН партнёра. |
| M2 | `Organization.partnerId String?` (nullable) | Самостоятельные обращения без партнёра. |
| M3 | `Payment.organizationId String` + relation `Organization`; `Payment.orderId String?` (nullable) | Оплата org-level (Подход 1). |
| M4 (data) | Backfill `Payment.organizationId` из `order.organizationId` **до** установки NOT NULL | Двухшаговая миграция: existing/seed-оплаты не должны падать по NOT NULL. |

**Правка чтения:** [`listOrgPayments`](../../src/lib/services/organization/finance.ts) `where: { order: { organizationId } }` → `where: { organizationId }`. Аналогичный путь у partner-витрины, если он читает оплаты через заказ. KPI (`getOrgFinanceKpis`) и комиссия (`getOrgIntermediaryCommission`) остаются на заказах — **не меняются**.

> Изменение `Payment.orderId` на nullable требует ревизии всех чтений `payment.order` (TypeScript поймает обязательные доступы; убедиться, что ledger-рендер допускает `orderNumber = null`).

## Архитектура и поток

```
[вход] /manager/import (менеджер/руководитель)  ·  /admin/import (админ, зеркало Model A §4)
        │  загрузка .xlsx (один воркбук, листы: Контрагенты / Реализации / Поступления)
        ▼
[1] parse-workbook.ts  ──exceljs──▶  сырые строки по листам
        │   Рус-заголовки → поля через COLUMN_MAP (единственный «спекулятивный» модуль, лочится по образцу)
        ▼
[2] validate.ts (zod)  ──▶  валидные DTO  +  карантин { row, sheet, reason }
        ▼
[3] plan-import.ts (DRY-RUN, без записи)
        │   резолв ключей (орг по ИНН, заказ→орг, оплата→орг) + scope-решение по actor
        │   сводка: орг (новые/обновл./standalone/skip-scope), заказы (matched/skip),
        │           оплаты (matched/skip), карантин
        ▼
   Admin/менеджер подтверждает  ──▶  [4] commit-import.ts
        │   prisma.$transaction: upsert орг → заказ → оплата (порядок зависимости)
        │   skip-строки не пишутся; AuditLog (actor, имя файла, счётчики, skip-причины)
        ▼
   данные в Payment/Order/Organization → витрины organization/partner finance
```

### Компоненты (новый каталог `src/lib/services/import/`)

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `column-map.ts` | Рус-заголовки листов → имена полей DTO + upsert-ключи. **Единственный модуль, зависящий от образца.** | — |
| `parse-workbook.ts` | exceljs: воркбук → `{ orgs[], orders[], payments[] }` сырых строк. | exceljs, column-map |
| `validate.ts` | zod-валидация строк → DTO + карантин. Переиспользует/расширяет `oneCSync/schemas.ts`. | oneCSync/schemas |
| `plan-import.ts` | Dry-run: резолв связей + scope-фильтр по actor → `ImportPlan` (счётчики + per-row решения). Без записи. | managerPolicy, prisma (read) |
| `commit-import.ts` | Транзакционный upsert по плану + audit. Переиспользует `oneCSync` мапперы + новый `mapPaymentRow`. | oneCSync/mappers, prisma |
| `index.ts` | barrel: `previewImport()` / `commitImport()` — публичный контракт сервиса. | все выше |

### Контракт сервиса (§3 Result-тип)

```ts
type ImportError = 'invalid_file' | 'forbidden' | 'empty' | 'parse_failed';

function previewImport(
  prisma, session, args: { fileBuffer: Buffer }
): Promise<{ ok: true; plan: ImportPlan } | { ok: false; error: ImportError }>;

function commitImport(
  prisma, session, args: { fileBuffer: Buffer }
): Promise<{ ok: true; applied: ImportCounts; skipped: SkipReport } | { ok: false; error: ImportError }>;
```

`ImportPlan` несёт счётчики и per-row решения (apply / skip+reason / quarantine+reason). Превью и commit парсят один и тот же буфер (детерминированно) — commit не доверяет клиентскому плану, а пересчитывает (защита от подмены).

## Ключи привязки и upsert

| Сущность | Upsert-ключ | Привязка | Если ключ привязки не найден |
|---|---|---|---|
| Организация | ИНН (`Organization.inn`) | партнёр по `Partner.inn`; пустой ИНН партнёра → `partnerId = null` (standalone) | партнёр не найден → орг сохраняется **без** партнёра + warn в отчёт (не skip) |
| Заказ | `externalId` / номер заказа (по образцу) | орг по ИНН | орг не найдена/skip → заказ skip + в отчёт |
| Оплата | «Номер документа» → `externalId` | орг по ИНН (`orderId = null`) | орг не найдена/skip → оплата skip + в отчёт |

> `Organization.inn` сейчас не `@unique`. Для надёжного upsert по ИНН добавить `@unique` **отдельной аддитивной миграцией (M5)** — но только после проверки, что в существующих данных нет дублей ИНН (иначе миграция упадёт) **или** upsert-ить через `externalId`, если выгрузка его содержит. Решается по образцу; дефолт — `Organization.inn @unique` (M5).

## RBAC + scope (§4 defense-in-depth)

| Actor | Новые орги | Обновление орг | Зона записи |
|---|---|---|---|
| админ | ✅ | ✅ | все |
| руководитель (`managerRole='leader'`) | ✅ | ✅ | все (company-wide) |
| менеджер | ❌ | ✅ | только `managedOrgIds` |

- **Три точки** §4: middleware (`/manager/import` под `manager_cabinet`, `/admin/import` под admin-гардом) + page-гард (`requireManager` / `requireRole('admin')`) + сервис (`previewImport`/`commitImport` фильтруют строки по actor-scope).
- **Менеджер:** строка применяется ⟺ орг ∈ `managedOrgIds(session)`. Новая орг или чужая → skip + причина («новая организация — нужен руководитель/админ» / «вне вашей зоны»). Заказы/оплаты skip-нутой орги тоже skip.
- **Руководитель/админ:** все строки, включая создание новых орг.
- **Импорт никогда не пишет `OrganizationManager`** — привязка менеджер↔орг ставится отдельным существующим UI кабинета (вариант B брейнсторма).

> **Тонкость C8 (write-scope ≠ read-visibility).** Write-scope импорта = per-manager `managedOrgIds` (фактическое закрепление), а **НЕ** company-wide read-режим `Company.managerTeamVisibility`. Импорт — мутация; скоупим по закреплению, иначе при `teamMode=ON` рядовой менеджер перезаписал бы данные всей компании. Видимость ≠ право записи (тот же принцип, что у уведомлений §4). Руководитель — отдельная ветка (unscoped), детектируется по `managerRole='leader'`.

## Обработка ошибок (§3, degrade gracefully)

- Невалидная строка → **карантин с причиной** (row, sheet, reason), не молчаливый дроп. Видна в превью и итоговом отчёте.
- Несматченный FK (орг заказа/оплаты не найдена) → skip + счётчик (по образцу sync `partner_not_found`).
- Out-of-scope строка (менеджер) → skip + причина.
- Парс-ошибка/битый файл/нет нужных листов → `parse_failed`/`invalid_file`, транзакция не стартует.
- Пустой файл / нет валидных строк → `empty`.
- **Идемпотентность:** повторная загрузка того же файла безопасна (upsert по `externalId`/ИНН; «Номер документа» гарантирует стабильный ключ оплаты).
- **Атомарность:** commit в одной `$transaction` — частичный сбой откатывает весь импорт (всё-или-ничего), кроме явно skip-нутых строк.

## Тест-стратегия (§6)

- **Unit** (без Postgres): парсер на fixture-воркбуке (валидные + битые строки); валидация → карантин; резолв ключей; scope-фильтр (менеджер видит только `managedOrgIds`; руководитель/админ — все); standalone-орг (пустой ИНН партнёра); дедуп-идемпотентность плана.
- **Integration** (живой PG, см. §6 L2.5/L3): полный commit орг→заказ→оплата; повторная загрузка = без дублей (upsert по externalId/ИНН); unmatched-skip не пишется; backfill-миграция M4 (existing-оплаты получают `organizationId`); cross-scope инвариант (менеджер не пишет чужую орг даже при `teamMode=ON`).
- **Manual** перед merge: реальный образец → превью → commit на staging, сверка витрин.

## Не входит (YAGNI / отдельно)

- Витрина оплат менеджера/руководителя + гейт процентов посредника → **под-проект 2** (C-a).
- Парсинг «назначения платежа» для привязки оплаты к заказу → отвергнут (Подход 2 брейнсторма).
- Авто-расписание / подхват папки / webhook → ручная загрузка.
- Импорт партнёров и привязок `OrganizationManager` файлом → заводятся вручную в кабинете.
- Боевой REST-адаптер 1С (Трек A/A2) → остаётся отдельным треком; этот импорт — параллельная разблокировка.

2. `Organization.inn @unique` vs upsert по externalId — решается образцом (дефолт: сделать `inn` уникальным).
