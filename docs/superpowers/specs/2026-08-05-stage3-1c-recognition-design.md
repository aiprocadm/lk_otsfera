## 1. Главный вопрос этапа: можно ли его делать без файла

В трекере записано «этап 3 без реального файла 1С делать нельзя». Разбор
требований показывает, что это **верно только для одного из семи**:

| Требование | Нужен файл? |
|---|---|
| Т-8 нормализация заголовка (`ё/е`, неразрывный пробел, регистр, двойные пробелы) | нет |
| Т-9 алиасы вместо одной строки — **механизм** | нет |
| Т-9 алиасы — **точные названия из вашей выгрузки** | **да** |
| Т-10 лист ищется по вхождению, а не по точному имени | нет |
| Т-11 `sheets_not_recognized` вместо «Файл пуст» | нет |
| Т-12 `columns_not_recognized` с перечнем фактических заголовков | нет |
| Т-13 поддержка `.xls` | нет |
| Т-14 проверка по сигнатуре файла, а не по расширению | нет |

**Предложение: сделать механизм сейчас, точные названия добавить, когда придёт
файл.** Добавление алиаса — одна строка в списке; после этапа 1 у вас уже есть
инструмент, который показывает, какую именно строку добавить (`npm run
inspect:1c` и блок «Что увидела система в файле»).

Так этап перестаёт блокировать программу: этапы 4–5 (то самое «организации не
создаются») ждут только его.

Стартовый набор алиасов берётся из вариантов, которые называет **само ТЗ**
(§1 П-7): «Контрагент», «Реализация товаров и услуг», «Поступление на расчётный
счёт», «ИНН партнера» (через «е»), а также из внутреннего расхождения карты
(`ORDER_COLS.orgInn = 'ИНН организации'` против `PAYMENT_COLS.orgInn = 'ИНН'`).

## 3. Разведка по коду (факт на `main` 1b14d849)

- `column-map.ts` — три листа и три карты колонок, значения **строки**; помечена
  `SAMPLE-LOCKED`.
- `parse-workbook.ts` (после этапа 1) — `readSheet()` берёт лист **точным
  именем** (`wb.getWorksheet(name)`), заголовки сверяет точным равенством
  (`colIndex.get(label)`), плюс собирает диагностику.
- `diagnostics.ts` — `unmatchedHeadersOf()` тоже сравнивает точно.
- `oneCAccountCard/read-spreadsheet.ts` — умеет **и** `.xls`, **и** `.xlsx`, но:
  читает **только первый лист** и отдаёт «сетку строк» (`string[][]`), потому что
  писался под одностраничную банковскую выписку. Формат определяет по
  **расширению** (`sniffFormat(fileName)`).
- `import/index.ts` — коды ошибок `forbidden | parse_failed | empty`.
- `server-actions/import.ts` — принимает только `.xlsx` (по имени файла),
  `import-form.tsx` — `accept=".xlsx"`.

## 4. Решения

### 4.1. Нормализация — одна функция на весь импорт (Т-8)

```ts
// src/lib/services/import/normalize.ts
export function normalizeLabel(raw: string): string; // trim →   и переносы → пробел
                                                     // → схлопнуть пробелы → lowercase → ё→е
```

Её используют: сопоставление листов, сопоставление колонок и диагностика
нераспознанных заголовков. Иначе диагностика показывала бы не то, на что смотрит
рабочий код (в этапе 1 это специально зафиксировано тестом — его придётся
переписать, и это ожидаемо).

### 4.2. Алиасы (Т-9, Т-10)

`column-map.ts` переходит со строк на массивы; первый совпавший — победитель:

```ts
export const ORG_COLS = {
  name: ['Наименование', 'Наименование контрагента', 'Контрагент'],
  inn: ['ИНН', 'ИНН контрагента', 'ИНН организации'],
  partnerInn: ['ИНН партнёра', 'ИНН партнера'],
} as const;
```

Лист ищется **по вхождению нормализованных имён в обе стороны**: алиас
«реализация» находит лист «Реализация товаров и услуг», а алиас «контрагенты» —
лист «Контрагент». Если под один вид подошло несколько листов, берётся первый в
порядке книги, а остальные попадают в диагностику — молча «съесть» второй лист
нельзя.

### 4.3. `.xls` — не переиспользование `readSpreadsheet`, а общий загрузчик (Т-13)

ТЗ предлагает «вынести `readSpreadsheet()` в общий модуль и использовать в
`parse-workbook`». **Буквально это не сработает**: `readSpreadsheet` читает
только первый лист и отдаёт строки, а импорту нужны листы по имени и значения
(суммы — числами, даты — датами). Подмена сломала бы разбор сумм.

Вместо этого — общий загрузчик, отдающий обоим модулям одинаковую форму:

```ts
// src/lib/services/import/workbook.ts
export type SheetGrid = { name: string; rows: unknown[][] }; // rows[0] — шапка
export async function loadWorkbookSheets(buffer: Buffer): Promise<SheetGrid[]>;
```

- сигнатура `PK` → ExcelJS (текущий путь для `.xlsx`, поведение значений не
  меняется — риск регресса нулевой);
- сигнатура `D0 CF 11 E0` → SheetJS (`xlsx`), уже есть в зависимостях;
- `parse-workbook` переписывается поверх `loadWorkbookSheets`.

`readSpreadsheet` банковской выписки **не трогаем** — у него свой контракт и свои
тесты; сливать два разных чтения в одно ради буквы требования значит взять на
себя лишний риск в чужом модуле.

`accept` в форме → `.xls,.xlsx`, серверная проверка имени — тоже.

### 4.4. Формат по сигнатуре (Т-14) — с уточнением

ТЗ: несовпадение расширения и содержимого → `format_mismatch` с подсказкой
«пересохраните из 1С в xlsx». Эта формулировка написана, когда `.xls` **не
поддерживался**. В этом же этапе он поддерживается — и отказывать в файле,
который мы умеем прочитать, только из-за неправильного расширения, было бы
вредно.

**Предлагаю:** формат определять **по содержимому** и читать файл, даже если
расширение врёт (переименованный `.xls` — самый частый случай). Отказ
`format_mismatch` остаётся для случая, когда содержимое **не является** ни
`.xlsx`, ни `.xls`:

> Это не похоже на файл Excel. Проверьте, что выгружали из 1С именно в Excel
> («Лист Excel 2007-…(xlsx)»), а не в `.mxl` или PDF.

Расхождение имени и содержимого при этом попадает в блок «Что увидела система»
как замечание — видно, но не мешает работать. **Это отклонение от буквы Т-14 —
вынесено вопросом (§8).**

### 4.5. Внятные коды вместо «Файл пуст» (Т-11, Т-12)

- ни один лист не распознан → `sheets_not_recognized` (фактические имена листов
  уже едут в диагностике этапа 1);
- лист найден, но нет обязательной колонки → `columns_not_recognized`; в
  диагностику добавляется, **каких колонок не хватает** по каждому листу.

Обязательные колонки: контрагенты — ИНН; реализации — номер и ИНН; поступления —
номер, ИНН, сумма, дата. Остальные необязательны (их отсутствие не мешает
импорту, а только обедняет запись).

Диагностика этапа 1 расширяется полем `missingColumns: Record<string, string[]>`
— это ровно то, чего в ней не хватало (в этапе 1 оно осознанно не делалось: там
не было кода `columns_not_recognized`, к которому его прицепить).

### 4.6. `empty` остаётся

Файл прочитан, листы и колонки распознаны, но строк нет — это по-прежнему
`empty`. Теперь это честный ответ, а не маскировка нераспознанного файла.

## 7. Риски

1. **Переписывание `parse-workbook` на новый загрузчик** — единственное
   рискованное место: там разбираются суммы и даты. Митигация: для `.xlsx`
   остаётся ExcelJS с теми же значениями ячеек, а существующие тесты разбора
   специально не переписываются — они и есть страховка.
2. **Слишком широкие алиасы.** «ИНН» как алиас и для организации, и для
   контрагента внутри одного листа может поймать не ту колонку. Митигация:
   порядок алиасов значим (точный вариант раньше общего), и в диагностике видно,
   какая колонка чем стала.
