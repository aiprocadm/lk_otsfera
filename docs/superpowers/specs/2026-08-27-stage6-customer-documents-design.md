# Этап 6 «Документы для заказчика: счёт, акт, договор, ДС» — спека

**Дата:** 27.08.2026 · **Требования:** `У-141`…`У-160` действующего
[ТЗ кабинетов, документов и интеграций](../../tz/2026-08-21-tz-cabinets-documents-integrations.md)
(блок N, решения `Р-15`, `Р-16`, `Р-18`) · **Статус:** предъявлена заказчику.

Самый крупный этап программы: 20 требований, закрывающих 22 дефекта реестра
(`Д-1`…`Д-22`). Опирается на этап 5: строки `OrderLine` и расчётное ядро
`lineMath` уже есть — печать берёт их, а не считает заново.

---

## 1. Что есть сейчас (разведка, факты с якорями)

- **Генерация** — [generate.ts](../../../src/lib/services/documents/generate.ts)
  (368 строк): счёт, акт, договор, ДС по заказу в один клик.
  **PDF рендерится ВНУТРИ транзакции** (строки 217–290) — это `Д-1`/`Д-2`:
  долгая транзакция держит счётчик номеров, а сбой загрузки в S3 оставляет
  запись без файла.
- **Номер**: `DocumentCounter(companyId, year, kind)`; ведомые типы (акт, ДС)
  наследуют номер ведущего разбором `/(\d+)$/`. `companyId` счётчика — **не
  FK** (`Д-21`), уникальности `(companyId, type, number, version)` нет
  (`Д-4`).
- **Табличная часть** — [orderDocumentPdf.ts](../../../src/lib/services/documents/orderDocumentPdf.ts):
  печатает **три колонки** (№ · Наименование · Сумма, строки 152–170). Нет ни
  количества, ни цены, ни построчного НДС, ни суммы прописью (`Д-6`, `Д-7`).
  Функции «сумма прописью» в проекте нет вовсе.
- **Статусов документа нет**: `enum DocumentStatus` в схеме отсутствует, есть
  только `signedAt`. Признака оплаты счёта нет.
- **Панель генерации смонтирована только у менеджера**
  (`manager/orders/[id]/page.tsx`) — `Д-13`; у руководителя и админа её нет.
  Флаг `document_generation` — opt-in (`Д-20`).
- **Скачивание**: все три роута зовут `createSignedUrl(path, ttl)` без
  третьего аргумента — файл сохраняется под UUID-именем (`Д-17`), хотя
  механизм `contentDisposition` в `s3.ts` уже есть.
- **`ManagerDocUploadForm` существует, но нигде не смонтирован** (`Д-14`);
  `adminUpload.ts` — отдельная ветка мимо `upload-core` (`Д-18`).
- **Строки заказа готовы** (этап 5): `OrderLine` + `lineMath` (`vatIncluded`
  меняет направление расчёта, итоги складывают построчные округления).
  Реквизиты исполнителя, логотип, подпись, печать и шаблон нумерации — тоже
  (`У-138`).

## 2. Модели

```prisma
enum DocumentStatus { draft issued sent accepted rejected expired cancelled }

model DocumentLine {                 // `У-146`: снимок строк на момент выпуска
  documentId      String   // FK Document, onDelete: Cascade
  title           String
  quantity        Decimal  @db.Decimal(12, 3)
  unit            CatalogUnit
  unitPrice       Decimal  @db.Decimal(14, 2)
  discountPercent Decimal? @db.Decimal(5, 2)
  vatRate         Decimal? @db.Decimal(5, 4)
  vatAmount       Decimal  @db.Decimal(14, 2)
  amount          Decimal  @db.Decimal(14, 2)
  sortOrder       Int
  @@index([documentId, sortOrder])
}
```

`Document` дополняется: `status DocumentStatus @default(issued)`,
`amountNet` / `amountVat` / `amountGross Decimal(14,2)?`, `currency String?`
(«RUB»), `parentDocumentId String?` (FK: акт → счёт, ДС → договор),
`sentAt` / `sentById`, `acceptedAt` / `acceptedByUserId`, `cancelledAt` /
`cancelReason`, `templateVersion Int?`. `replacesDocumentId` становится
**FK**; `DocumentCounter.companyId` — тоже FK (`Д-21`).

**Документы, выпущенные до этапа 6, строк и итогов не получают** (`У-146`
дословно): списки показывают «—», бэкфилл из `totalAmount` не делается — он
выдумал бы суммы задним числом. Статус при миграции: `issued`, а при
заполненном `signedAt` — `accepted`.

## 3. Ключевые решения

### 3.1. Печать (`У-141`, `У-142`, `У-153`)

Табличная часть: **№ · Наименование · Кол-во · Ед. · Цена · Сумма**; строки
«Итого», «В том числе НДС (ставка) — сумма» либо «НДС не облагается»,
«Всего наименований N на сумму …» и **сумма прописью**. Суммы берутся из
`DocumentLine` (снимок), разложение по НДС — из `lineMath` этапа 5: одна
арифметика на экране, в счёте и в будущей выгрузке.

Сумма прописью — своя функция `lib/format/amountInWords.ts` с тестами: рубли
и копейки, склонения («один рубль», «две тысячи рублей», «пять копеек»),
ноль, миллионы. Библиотеку не тянем: правило склонения простое, а чужая
зависимость в PDF-контуре — лишний риск.

Заказ без строк (`У-142`): одна строка «Услуги по заказу №…» на
`totalAmount` со ставкой НДС **по умолчанию компании** (`У-138`); в форме
выпуска её можно поправить до выпуска.

Логотип, подпись и печать (`У-153`) — из `CompanyBrandingAsset`, только
файлы со статусом `clean`; без них печать как сейчас.

### 3.2. Форма выпуска (`У-147`, `У-143`, `У-152`, `У-156`)

Диалог: тип · контрагент (предзаполнен) · строки (из заказа, правятся) ·
дата · для договора — предмет, срок действия, порядок оплаты (шаблон
`У-160`) · для акта — период оказания услуг и **ссылка на счёт выбором из
счетов заказа**, а не «последний по типу» · для ДС — ссылка на договор и
текст изменения · **предпросмотр PDF до выпуска**.

**Сверка сумм (`У-143`)**: расхождение строк и `totalAmount` — не молчаливый
выбор одной из цифр, а вопрос с тремя ответами: «обновить сумму заказа по
строкам» / «выпустить по строкам, сумму заказа не трогать» / «отмена».

**Транзакция (`У-152`)**: короткая транзакция резервирует номер; PDF
рендерится и грузится в S3 **вне** транзакции; ключ содержит UUID; при сбое
записи документа — компенсирующее удаление объекта. Коды ошибок
расшифрованы в `errors/messages.ts`.

**Реквизиты (`У-156`)**: проверка зависит от типа — договору нужен подписант
и основание с обеих сторон, счёту и акту — банковские реквизиты исполнителя
и ИНН/КПП/юр. название заказчика. ИНН — `isValidInn`, ОГРН и расчётный счёт
— контрольными суммами (счёт — по БИК).

### 3.3. Статусы (`У-148`)

Матрица допустимых переходов по типу — **одним объектом в коде**; страж
падает на переходе вне матрицы (`invalid_transition`). Для счёта
дополнительно вычисляемый признак оплаты (`unpaid` / `partially_paid` /
`paid`) по платежам заказа: привязка «платёж → счёт» по номеру счёта из
назначения платежа — `accountCandidates` уже извлекаются импортом выписки.

### 3.4. Доступ и видимость (`У-144`, `У-150`, `У-155`, `У-158`)

Панель генерации — **одним компонентом во всех трёх кабинетах ЦО**; флаг
`document_generation` переводится в opt-out и переключается из UI (`Д-13`,
`Д-20`). Заказчик видит список с номером, типом, датой, суммой, статусом и
версией; у акта и договора — «Принять»/«Подписать»; у счёта «Оплачено»
руками **не ставится** — только по платежам. Партнёр видит документы
организаций своего портфеля на чтение (`Р-18`), страж изоляции: организация
вне портфеля не видна. Загрузка документа в заказ менеджером и
руководителем — общий компонент; `adminUpload` переводится на `upload-core`.

### 3.5. Нумерация и версии (`У-151`, решение `Р-16`) — отдельным PR последним

Перевыпуск **сохраняет номер** и создаёт версию +1; прежняя версия помечена
«заменён» и скрыта из списков по умолчанию. Уникальность
`@@unique([companyId, type, number, version])`, причём «две цепочки с одним
номером» проверяется **сервисом при выпуске**, а не только индексом. Год
номера — по `Europe/Moscow`. Ведущий документ из 1С без номера не активирует
кнопку «Акт», а предлагает указать номер.

**Миграция данных — отдельным PR, последним:** сначала dry-run
`npm run report:document-numbers` (дубли номеров `Д-4`, осиротевшие
`replacesDocumentId`, счётчики без компании), затем миграция, падающая
внятным текстом, если отчёт не пуст. Порядок тот же, что доказал себя в
этапе 5: сначала снять чтения, потом менять данные.

## 5. Тестовая стратегия

- **Юнит**: сумма прописью (рубли, копейки, склонения, ноль, миллионы),
  матрица переходов статусов, разложение НДС в печати (берётся `lineMath` —
  проверяем стыковку, а не арифметику заново), проверка реквизитов по типам,
  контрольные суммы ОГРН и расчётного счёта.
- **Сервисы** (mock-prisma): выпуск (номер, версия, снимок строк,
  компенсирующее удаление объекта при сбое записи), сверка сумм (три ветки),
  статусы, признак оплаты, скоупы (партнёр вне портфеля не видит; заказчик
  видит свои).
- **Integration**: конкурентный выпуск двух документов (номера не
  дублируются); миграция данных PR-8 на живой базе — обе ветки (есть
  расхождения / пусто), как в этапе 5.
- **Стражи**: матрица переходов, изоляция партнёра, `Content-Disposition` во
  всех трёх роутах, панель во всех трёх кабинетах. Каждый — проверен
  мутацией (§16).

## 6. Вопросы заказчику (умолчания действуют, если не отменены)

1. **Сумма прописью — своя функция**, без внешней библиотеки?
   **Умолчание: да** (правило склонения простое, зависимость в PDF-контуре —
   лишний риск).
2. **Признак оплаты счёта** считается по платежам заказа с привязкой по
   номеру счёта из назначения платежа; при неоднозначности — `unpaid` и
   пометка «не удалось сопоставить»? **Умолчание: да.**
3. **Документы, выпущенные до этапа 6**, печатаются как прежде (строк у них
   нет) и автоматически не перевыпускаются? **Умолчание: да** — `У-146`
   прямо запрещает бэкфилл сумм задним числом.
4. **Восемь PR** вместо привычных пяти-шести: этап крупный (20 требований,
   22 дефекта). **Умолчание: да**, порядок — в §4.
