# Этап 4 «Всё настраивается из интерфейса» — дизайн

**Требования:** `У-122`…`У-135` действующего
[ТЗ кабинетов, документов и интеграций](../../tz/2026-08-21-tz-cabinets-documents-integrations.md)
(§4, блок L). Дефекты, которые этап закрывает: `Д-35`, `Д-36`, `Д-37`, `Д-38`,
`Д-39`.

**Приёмочный критерий этапа — §0.3 ТЗ:** «Любая настройка, которая нужна
администратору или руководителю в работе, доступна из интерфейса. Переменные
окружения остаются только для инфраструктуры». Формулировка «ключ ввести
можно, а включить нельзя, пока программист не зайдёт на сервер» — дефект
приёмки.

## 1. Что не так сейчас (разведка по коду, `ef0ecf39`)

### 1.1. Переменных окружения втрое больше, чем документации

| Что мерили | Сколько |
|---|---|
| Различных `process.env.X` в `src/**` (без тестов) | **123** |
| Всего чтений | **822** |
| Строк в `.env.example` | **28** |

То есть **95 переменных из 123 не описаны нигде** — человек, поднимающий
стенд, узнаёт о них только когда что-то не работает. Это `Д-39`, требование
`У-134`.

Кроме буквальных чтений есть **семь динамических** (`process.env[...]`) — в
`featureFlags.ts`, `admin/featureFlags.ts`, `storage/s3.ts`,
`integrationSettingsCache.ts` и `integrationSettings.ts`. Страж `У-122` обязан
их учитывать: они читают ключ, вычисленный из реестра, а не литерал, и
регулярка по литералам их не увидит.

### 1.2. Механизм «настройка из UI» есть, но накрывает четверть нужного

`IntegrationSetting` (ключ → значение, `isSecret`) + `SETTING_SPECS` +
приоритет «база → env → умолчание» уже работают — это `У-66` прошлой
программы. В реестре **26 ключей**: почта, IMAP, Mango (частично), Telegram,
Max, WhatsApp, 1С (частично), DaData.

Не покрыто ничего из того, что просит этап 4: пороги алертов, расписания
обмена, параметры обмена, политики входа, правила уведомлений, шаблоны писем,
SLA.

## 2. Как делаем

### 2.1. Общий приём — «настройка живёт в реестре, а не в коде»

Этап не изобретает нового механизма: он **расширяет** `SETTING_SPECS`
(платформенное) и добавляет второй, компанийский слой на `Company` —
ровно как требует `Р-22` («настройки компании хранятся на `Company`, а не в
глобальной `IntegrationSetting`; у неё нет `companyId`, иначе руководитель
одной компании менял бы обмен всей платформы»).

Правило разнесения:

| Что настраивается | Где хранится | Кто правит |
|---|---|---|
| Подключения к внешним системам, секреты платформы, расписания обмена, флаги платформы, пороги алертов, политики входа | `IntegrationSetting` | только администратор |
| Правила уведомлений компании, SLA компании, шаблоны текстов компании, реквизиты | поля/строки, привязанные к `companyId` | руководитель своей компании, администратор — любой |

Приоритет чтения везде один и тот же и уже реализован: **база → env →
умолчание в коде**. Новых механизмов приоритета не вводим.

### 2.2. Типы настроек в реестре

Сейчас `SettingSpec` — это `{ key, envVar, isSecret }`. Для форм этого мало:
поле «таймаут» надо проверять как число в границах, «режим» — как выбор из
двух значений, а cron — как cron. Расширяем спецификацию **необязательными**
полями, чтобы 26 существующих ключей не пришлось переписывать:

```ts
type SettingSpec = {
  key: string;
  envVar: string;
  isSecret: boolean;
  // новое, всё необязательное:
  kind?: 'string' | 'number' | 'boolean' | 'enum' | 'cron';
  options?: readonly string[];   // для enum
  min?: number; max?: number;    // для number — безопасные границы (`У-129`)
  label?: string;                // русское название поля
  hint?: string;                 // одна строка «зачем это»
};
```

Валидация значения — одна функция на весь хаб, а не по форме на раздел.
Значение вне границ не сохраняется: ответ `invalid_value` и русская строка.

### 2.3. Расписания обмена (`У-125`)

Сегодня `SYNC_SCHEDULES` — литералы, и та же строка продублирована в
`syncControl.ts` как `cronLabel`. Делаем так:

1. `SYNC_SCHEDULES` остаётся в коде как **значение по умолчанию**.
2. Фактический паттерн читается из `IntegrationSetting` по ключу
   `sync.cron.<schedulerId>`; пусто → умолчание из кода.
3. `cronLabel` в `syncControl.ts` **удаляется** — экран берёт паттерн из того
   же места, что и воркер. Два источника правды схлопываются в один.
4. Воркер перечитывает расписания при регистрации и по сигналу — рестарт не
   нужен (`registerSyncSchedules` уже вызывается при старте; добавляем
   перечитывание по изменению настройки).
5. В форме — пресеты «каждые 15 минут / час / 6 часов / сутки / выключено» и
   поле cron с валидацией; рядом показываются **ближайшие три запуска**,
   чтобы человек видел, что он задал, а не гадал по звёздочкам.

«Выключено» — это существующий `SyncSchedulePause`, а не пустой cron: механизм
паузы уже есть и пишет в аудит, дублировать его строкой в cron нельзя.

### 2.4. Телефония (`У-124`, решение `Р-24`)

`telephony_mango` снимается с `FEATURE_PREFIXES` и становится поведенческим.
Это **осознанное отступление от «трёх точек чтения флага»** (§5 `CLAUDE.md`)
для одного флага — так прямо записано в `Р-24`. Взамен раздел закрывают три
серверные точки:

- страница `/manager/calls` — `notFoundIfDisabled` (уже есть, остаётся);
- пункт меню — флаг в реестре навигации (уже есть);
- **все** роуты `/api/manager/calls*` — `requireFeature`; сейчас гард стоит
  только на `recording`.

`integrations.ts` и `integrationsHealth.ts` обязаны читать флаг **одним**
способом — сейчас один смотрит env, другой зовёт `isFeatureEnabled`.

### 2.5. Правила уведомлений и шаблоны (`У-127`, `У-128`)

Самая крупная пара требований. Модель:

- **Правило** = (событие, роль-получатель, канал) → включён/выключен. Реестр
  в коде (`NOTIFICATION_TYPES`, 30 событий) — значение по умолчанию; строки в
  БД — переопределения. Приоритет: **компания → платформа → код**.
- **Шаблон** = (событие, канал) → тема + тело с подстановками. Подстановки
  объявляются рядом с событием; **неизвестная подстановка — ошибка
  сохранения**, а не пустое место в письме (это прямо в `У-128`).
- Кнопка «вернуть стандартное» удаляет строку переопределения, а не пишет в
  неё копию кода: иначе шаблон замерзает и перестаёт получать правки.

Существующие TSX-шаблоны **не выбрасываем**: они остаются рендерером и
значением по умолчанию. Переопределение из БД подменяет тему и тело, а вёрстку
письма (шапку, подвал, кнопку) по-прежнему даёт `layout.tsx` — иначе первый же
отредактированный шаблон потеряет фирменный вид.

### 2.6. Списки env и два стража (`У-122`, `У-134`)

Оба стража включаются **последним PR этапа** — тем, который увозит последнюю
переменную. Иначе они красные всё время работы, и их придётся или отключать,
или «позеленить» подгонкой; оба пути мы уже проходили на этапе 3 со стражем
зеркальности.

- **Страж `У-122`:** собирает `process.env.X` по `src/**` (кроме тестов) и
  падает на переменной вне списка. Список — файл-реестр с причиной у каждой
  строки: `инфраструктура` или `edge-флаг (пока не переведён на серверный
  гард)`.
- **Страж `У-134`:** переменная, которую читает код, обязана иметь строку в
  `.env.example` с назначением и пометкой. Устаревшие строки («задаётся в
  интерфейсе») помечаются, а не удаляются молча — человек со старым `.env`
  должен понять, почему его значение больше ни на что не влияет.

Оба стража обязаны быть **проверены мутацией** (§16): добавить лишнюю
переменную и убедиться, что сборка краснеет.

## 4. Тесты

- **Приоритет источников** для каждой новой настройки: база перекрывает env,
  env перекрывает умолчание, пустая строка в базе — это «не задано», а не
  «пустое значение». Отдельным тестом, а не по одному примеру на раздел.
- **Границы значений** (`У-129`): TTL кода вне разумных границ не
  сохраняется; ответ — стабильный код и русская строка.
- **Телефония без рестарта** (`У-124`): при выключенном флаге страница и все
  роуты `/api/manager/calls*` отвечают 404; после включения из БД — 200 в том
  же процессе.
- **Холодный процесс** (`У-133`): флаг включён только в БД, `getSession()` ещё
  не звался — `api/auth/login` обязан увидеть включённый флаг.
- **Баннер до попытки** (`У-132`): без ключа шифрования страница интеграций
  показывает предупреждение **до** нажатия «Сохранить»; `/api/health` это
  отражает.
- **Сброс секрета** (`У-131`): после сброса читается значение сервера, а не
  пустая строка.
- **Расписание из БД** (`У-125`): воркер регистрирует паттерн из базы;
  `cronLabel` в коде отсутствует (страж по исходнику).
- **Неизвестная подстановка** (`У-128`): сохранение шаблона с `{{нет.такого}}`
  отклоняется.
- **Изоляция руководителя** (`У-135`): `GET` секретов платформы и параметров
  подключения 1С под сессией `leader` → `403`. Проба доступа, а не проверка
  того, что кнопка скрыта (§16: скрытая кнопка — это внешний вид).
- **Два стража** `У-122` и `У-134`, каждый проверен мутацией.

## 5. Риски

| Риск | Что делаем |
|---|---|
| Переезд переменной ломает прод: значение осталось в env, а код уже читает базу | Приоритет «база → env» означает, что **старый env продолжает работать**. Ни одна переменная не удаляется из чтения — она перестаёт быть единственным источником |
| Стражи `У-122`/`У-134` красные всю работу | Включаются последним PR — это записано и в ТЗ, и в разбивку |
| Снятие `telephony_mango` с edge открывает раздел | Взамен ставятся три серверные точки, включая **все** роуты `/api/manager/calls*` (сейчас гард только на одном). Тест на 404 при выключенном флаге — обязателен |
| Редактируемые шаблоны теряют фирменный вид | Из БД подменяются только тема и тело; вёрстка остаётся за `layout.tsx` |
| «Вернуть стандартное» замораживает шаблон | Кнопка **удаляет** переопределение, а не копирует в него текущий код |
| Этап трогает `settings.ts`, который правил `У-114` | Порядок соблюдён: `У-114` отгружен этапом 3 (PR #420). Параллельных веток по этому файлу не открываем |
| Девять PR — долго | Каждый самостоятелен и вливается отдельно; порядок внутри этапа менять можно, кроме PR-9 |

## 6. Вопросы заказчику

1. **Канал ops-оповещений** (`У-126`): ТЗ называет Telegram-бота и список
   e-mail. Нужен ли третий канал (Max/WhatsApp) сразу или достаточно двух?
   **Умолчание: два** — Telegram и e-mail.
2. **Правила уведомлений на уровне компании** (`У-127`): руководитель правит
   правила своей компании. Должен ли он видеть, что именно перекрывает
   платформенное правило (пометка «изменено вами»)?
   **Умолчание: да**, пометка показывается — иначе непонятно, почему у соседней
   компании иначе.
3. **Шаблоны на уровне компании** (`У-128`): правит ли руководитель тексты
   писем своей компании, или тексты общие для платформы?
   **Умолчание: правит**, тем же приоритетом «компания → платформа → код».
4. **Разбивка на девять PR** — согласны? Порядок внутри этапа можно менять,
   кроме последнего (стражи `У-122`/`У-134`).

Умолчания действуют по решению `Р-15`…`Р-24` (делегированы исполнителю);
заказчик может отменить любое до подтверждения спеки.
