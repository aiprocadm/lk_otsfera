# Этап 4 «Задачи и автоматизация» — дизайн

**Программа:** «CRM для отдела продаж — замена Битрикс24» (ТЗ 12.09.2026), этап 4 из 11.
**Требования:** `У-218`…`У-227` (10 шт.), приоритет MVP, кроме `У-221` — «Важно».
**Файл пакета:** [11_tasks_and_workflows.md](../../specs/11_tasks_and_workflows.md). **Оценка ТЗ:** 6–7 дней.
**База:** этап 1 (контакты, `linkedContactId`) и этап 3 (диалоги, статус `waiting_staff`, шаблоны ответов) — оба закрыты.
**Сверка кода (§16):** 15.09.2026 против `main` `c2c5cce1`.

## 0. Коротко

Задачи в проекте уже есть: доска с колонками, исполнители, срок, приоритет,
привязка к заказу, организации, лиду и сделке, уведомление «вам назначили» и
напоминание «скоро срок». Этого хватает, чтобы **записать** задачу, и не
хватает, чтобы **вести** её.

Этап 4 добавляет три вещи, которых нет ни в каком виде:

1. **Место для работы внутри задачи** — своя страница, обсуждение и чек-лист
   (`У-218`, `У-219`). Сейчас задача живёт в модальном окне: открыть её по
   ссылке нельзя, обсудить негде, разбить на шаги негде.
2. **Задача откуда угодно** (`У-220`) — из карточки контакта, диалога,
   документа и КП; сейчас привязок четыре, нужно семь.
3. **Роботов** (`У-222`…`У-224`) — правила «если случилось событие, то создай
   задачу или пошли уведомление». Этого в коде **нет вообще**: поиск по
   `automation|автоматизац` в `src/` и `prisma/` даёт ноль совпадений.

Плюс два довеска: просроченная задача должна о себе напоминать (`У-225`) и
«Мой день» должен показывать всё, что ждёт сегодня (`У-226`).

Семь PR, каждый — 1–3 требования, каждый закрывается своим стражем с мутацией.
Схема БД меняется **аддитивно и обратимо**: четыре новые модели, восемь новых
колонок у `Task`, одна у `Company`. Ни одной колонки не удаляем, ни одного
существующего экрана не переписываем.

Главный риск этапа — не объём, а **зацикливание роботов**: правило создаёт
задачу, задача порождает событие, событие снова запускает правило. Решение
`Р-Б-6` ТЗ («действия правил не порождают триггеры») закрывается не
осторожностью, а конструкцией: каталог действий и каталог триггеров физически
не пересекаются, и это проверяется стражем **до** первого правила из коробки
(§3.2).

### 1.2. Автоматизации нет — ноль

`grep -riE "automation|автоматизац" src prisma` → **0 совпадений**. Нет моделей,
нет `src/lib/automation/`, нет очереди, нет раздела хаба. Строим с нуля.

**Единой точки «событие произошло» в коде тоже нет.** Реестр уведомлений
[registry.ts](../../../src/lib/notifications/registry.ts) — это **пассивный
каталог метаданных** (35 типов, у каждого `label`, `audience`, `producer` —
строка-путь к файлу). К нему нельзя «подписаться»: продюсеры пишут в
`Notification` двумя независимыми путями — 13 файлов зовут `createNotification`
напрямую, ещё шесть веерных функций (`notifyOrgUsers`, `notifyManagers` и
соседи) создают строки сами, внутри цикла по получателям.

Это и есть главное расхождение пакета с кодом: формулировка `Р-Б-6`

событий», а шины нет. Как это решается — §3.1.

## 2. Модели

Всё аддитивно. Четыре новые таблицы, восемь новых колонок у `Task`, одна у
`Company`. Ни одного удаления, ни одного `NOT NULL` на существующей колонке.

### 2.1. Задачи

```prisma
model TaskComment {
  id             String   @id @default(cuid())
  createdAt      DateTime @default(now())
  taskId         String
  task           Task     @relation(fields: [taskId], references: [id], onDelete: Cascade)
  authorId       String
  author         User     @relation("TaskCommentAuthor", fields: [authorId], references: [id])
  body           String

}

model TaskChecklistItem {

  taskId    String
  task      Task      @relation(fields: [taskId], references: [id], onDelete: Cascade)

  sortOrder Int       @default(0)

```

Новые колонки `Task`:

| Колонка | Тип | Зачем |
|---|---|---|
| `linkedContactId` | `String?` → `Contact`, `SetNull` | `У-220` |
| `linkedDialogId` | `String?` → `MessengerDialog`, `SetNull` | `У-220` |
| `linkedDocumentId` | `String?` → `Document`, `SetNull` | `У-220` (документ и КП — одна модель) |
| `createdByRuleId` | `String?` → `AutomationRule`, `SetNull` | `У-223`, «Создана правилом X» |
| `overdueNotifiedAt` | `DateTime?` | `У-225`, claim первого уведомления исполнителю |
| `overdueEscalatedAt` | `DateTime?` | `У-225`, claim эскалации руководителю |
| `recurrence` | `Json?` | `У-221` |
| `recurrenceParentId` | `String?` → `Task`, `SetNull` | `У-221`, серия |

Индексы: по каждой новой связи (как у существующих четырёх) и составной
`@@index([companyId, status, dueDate])` под выборку просроченных.

**Два отдельных поля-claim для просрочки, а не одно.** `dueSoonNotifiedAt`
показал, зачем: одно поле умеет сказать «уже уведомляли» ровно один раз, а
`У-225` требует двух разных уведомлений в разные дни (исполнителю — в день
просрочки, руководителю — на N-й). Одним полем это не выражается, а «посчитать
по датам на каждом прогоне» — это то самое чтение всей таблицы, от которого
уходили в прогоне сопровождения №26.

### 2.2. Автоматизация

```prisma
model AutomationRule {
  id          String   @id @default(cuid())
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  companyId   String   // правила всегда компанейские: платформенных роботов нет
  company     Company  @relation(fields: [companyId], references: [id], onDelete: Cascade)
  name        String
  isActive    Boolean  @default(false)
  isBuiltin   Boolean  @default(false)
  trigger     String   // ключ из AUTOMATION_TRIGGERS
  conditions  Json     @default("{}")
  actions     Json     // массив действий, ключи из AUTOMATION_ACTIONS
  createdById String?  // null у встроенных до первого включения
  updatedBy   String?
  @@index([companyId, trigger, isActive])
}

model AutomationRun {
  id              String   @id @default(cuid())
  createdAt       DateTime @default(now())
  ruleId          String
  rule            AutomationRule @relation(fields: [ruleId], references: [id], onDelete: Cascade)
  eventId         String
  companyId       String
  status          String   // ok | failed | skipped
  error           String?  // человеческая причина; секретов и ПДн здесь нет (§12)
  createdTaskIds  String[]
  notifiedUserIds String[]
  @@unique([ruleId, eventId])
  @@index([ruleId, createdAt])
}
```

**`companyId` у правила обязателен — в отличие от `NotificationRule`.** Там
`null` означает «правило платформы», и ради него в миграции живёт частичный
уникальный индекс, которого Prisma не описывает. Робот, который создаёт задачи
сразу во всех компаниях, — не функция, а происшествие; обязательный
`companyId` снимает и этот риск, и всю возню с NULL-ами в уникальном ключе.

**`actions` — `Json`, а не отдельная таблица.** Действий у правила 1–3, они
редактируются целиком одной формой и никогда не запрашиваются отдельно от
правила. Таблица дала бы порядок сортировки, миграцию и join ради нуля выгоды.
Форма действия проверяется Zod-схемой при сохранении (неизвестное действие или
неизвестная подстановка — отказ сохранить, §9 пакета).

### 2.3. Порог SLA задач

`Company.taskOverdueEscalationDays Int @default(3)` — на какой день просрочки
уведомить руководителя. `0` = не эскалировать. Значение по умолчанию взято из
текста `У-225` («на 3-й день»), то есть появление поля ничего не меняет по
сравнению с требованием.

## 3. Ключевые решения

### 3.1. `Р-Э4-1` — события испускаются явно, а каталог триггеров привязан к реестру уведомлений

Шины событий нет и в этом этапе не появится: строить её значит переписать 19
мест отправки уведомлений, а это не объём этапа 4.

Вместо этого — **явный вызов** `emitAutomationEvent(prisma, { trigger,
companyId, payload })` в тех же сервисах, где уже происходит бизнес-операция.
Каталог триггеров — константа по образцу `NOTIFICATION_TYPES`:

```ts
export const AUTOMATION_TRIGGERS = {
  order_status_changed: {
    labelRu: 'Заказ сменил статус',
    notificationType: 'order_status_changed', // якорь в реестре уведомлений
    callSite: 'src/lib/services/manager/orderStatus.ts',
    params: { toStatusId: 'orderStatus' },
  },
  // …
} as const satisfies Record<string, AutomationTriggerSpec>;
```

- `notificationType` — ссылка на реестр уведомлений там, где событие **уже**
  порождает уведомление (4 из 8 триггеров). Это и есть исполнение `Р-Б-6`:
  каталог триггеров не заводит вторую параллельную систему событий, а
  ссылается на существующую. Для четырёх триггеров, у которых уведомления нет
  (`lead_stage_changed`, `deal_stage_changed`, `proposal_no_answer`,
  `dialog_waiting_staff_overdue`), поле `null` — и тогда единственный якорь
  `callSite`.
- `callSite` — файл, обязанный звать `emitAutomationEvent`. Проверяется
  стражем по образцу `notifications.rules.guardrail` (файл содержит вызов, и
  вызов не закомментирован — исходник читается через `readSource()`).

`emitAutomationEvent` присваивает событию `eventId` (uuid), находит активные
правила компании по `trigger`, отсеивает по `conditions` и ставит в очередь
`automation.run` задачу `{ ruleId, eventId, payload }` с детерминированным
`jobId = auto_<ruleId>_<eventId>`. Сам вызов — **fail-open**: обёрнут в
`try/catch` с `log.error`, ошибка не поднимается в бизнес-операцию (§3 CLAUDE.md).

### 3.2. `Р-Э4-2` — зацикливание исключено конструкцией, а не осторожностью

Три независимых заслона, каждый со своим стражем:

1. **Каталоги не пересекаются.** Действия MVP — `create_task` и `notify`
   (и `send_message`, см. `Р-Э4-13`). Ни одно из них не меняет статус заказа,
   стадию лида или сделки, не выставляет документ и не принимает платёж — то
   есть не может породить ни один из восьми триггеров. Страж: пересечение
   множества «что делают действия» и множества «на что подписаны триггеры»
   пусто, проверяется по каталогам, а не по тексту файлов.
2. **Действия физически не могут испустить событие.** `src/lib/automation/actions.ts`
   не импортирует `emitAutomationEvent`; правило добавляется в
   `.dependency-cruiser.cjs` (`npm run boundaries`), так что нарушение = красная
   сборка, а не замеченная на ревью строчка.
3. **Диспетчер отбрасывает событие, помеченное как порождённое правилом.**
   `emitAutomationEvent` принимает `source?: 'automation'` и при нём выходит
   сразу. Это страховка на будущее: когда каталог действий когда-нибудь
   расширят, первые два заслона придётся пересматривать сознательно, а этот
   сработает сам.

Страж пишется **до** первого правила из коробки — так требует §5 ТЗ
(«закрепляется тестом до первого правила»), и это правильный порядок: тест,
написанный после, проверяет то, что уже сделано, а не то, что требуется.

### 3.3. `Р-Э4-3` — идемпотентность двухслойная

`AutomationRun @@unique([ruleId, eventId])` + пропуск по `P2002` (канон
`SlaEscalation`) — это истина в базе. Детерминированный `jobId` — дешёвый отсев
до базы. Первый слой обязателен, второй экономит работу: BullMQ и так может
доставить задачу дважды (ретраи, перезапуск воркера), а «повторная доставка
события не создаёт вторую задачу» — прямой пункт `У-227`.

### 3.4. `Р-Э4-4` — системную сессию не подделываем

`createTask` требует `SessionPayload` и зовёт `staffGate`. Подсунуть процессору
фальшивую сессию «от имени админа» — самый быстрый способ обойти проверку прав
в месте, где её никто не ищет.

Вместо этого `tasks.ts` расщепляется на два уровня (обычный приём этого
репозитория — так же устроены тонкие роуты над сервисами, §3 CLAUDE.md):

- `createTaskCore(tx, { companyId, createdById, … })` — без гарда, знает только
  данные;
- `createTask(prisma, session, input)` — `staffGate` + `validateRefs` +
  `createTaskCore`.

Процессор правил зовёт `createTaskCore` с явными `companyId` (из правила) и
`createdById`. **Автор задачи-робота — человек, включивший правило**
(`AutomationRule.createdById`; у встроенных заполняется при первом включении
галочкой). Правило нельзя включить, не записав включившего, поэтому
`Task.createdById` остаётся обязательным и ни одна миграция не делает
существующую колонку nullable.

### 3.5. `Р-Э4-5` — если ответственного нет, задача не теряется

Порядок выбора исполнителя для действия `create_task` с
`assignee: responsible_manager`:

1. ответственный менеджер объекта события;
2. если его нет — **все руководители компании**, в описание задачи добавляется
   строка «У объекта нет ответственного менеджера»;
3. если руководителей нет — задача создаётся **без исполнителей** (она видна на
   доске в «Без исполнителя», а не исчезает), прогон записывается со статусом
   `ok` и пометкой, и уходит уведомление `automation_failed` администратору.

Молча ронять задачу нельзя: робот, который иногда ничего не делает и не говорит
об этом, хуже отсутствующего робота.

### 3.6. `Р-Э4-6` — SLA задач живёт в существующем разделе хаба

Раздел `catalogs.slaIntake` переименовывается из «SLA входящих в работу» в
**«SLA»** и получает второй блок — «SLA задач» (порог эскалации в днях).
Новый раздел не заводим: пользователь ищет пороги в одном месте, а не в двух с
похожими названиями. Раздел уже открыт обоим кабинетам сотрудников
(`cabinets: ['admin','leader']`), так что правило зеркала соблюдено само собой.

Переименование задевает подпись в меню, хлебные крошки и глоссарий — всё в том
же PR (`У-76`).

### 3.7. `Р-Э4-7` — страница задачи есть у менеджера и руководителя, у админа нет

`/{manager,leader}/tasks/[id]`. У админа задач нет вовсе — это **существующее**
исключение правила зеркала, а не новое; этап 4 лишь дописывает его в реестр
исключений (`У-121`) с причиной, раз уж трогает домен.

С доски карточка теперь открывает страницу. Диалог быстрого создания
(`task-dialog.tsx`) **остаётся** — он нужен там, где задачу заводят «на бегу»
из чужой карточки, и убирать его значит менять привычный путь без требования.

### 3.8. `Р-Э4-8` — комментарии задачи это своя модель, а не `Comment`

`Comment` в этом проекте — разговор клиента с менеджером по заказу, он виден
заказчику (§5 CLAUDE.md, отдельно оговорено, что это **не** внутренняя
заметка). Задачи клиенту не видны вообще. Смешивать эти две вещи в одной
таблице — прямой путь к тому, что однажды внутреннее обсуждение задачи окажется
в кабинете клиента.

Упоминания через `@` переиспользуют существующий тип `note_mention` (этап 1,
продюсер `noteMention.ts`); новый тип для этого не заводим.

### 3.9. `Р-Э4-9` — чек-лист не запрещает завершить задачу, а переспрашивает

Сервер принимает перевод в `done` с невыполненными пунктами **только** при явном
`force: true`; без него возвращает код `checklist_incomplete`, а интерфейс
показывает подтверждение «завершить всё равно». Жёсткий запрет здесь был бы
вредительством: чек-лист — помощник, а не замок, и пункт «позвонить» иногда
становится неактуальным.

### 3.10. `Р-Э4-10` — флаг `automation`, поведенческий

Новый флаг, **выключен по умолчанию** (opt-in, как `contacts` и
`bitrix_migration` в этой программе), снимается после приёмки заказчиком.
Три точки чтения не применимы буквально — диспетчер это не маршрут, — поэтому
флаг поведенческий, и его точки перечисляются комментарием в
`featureFlags.ts` (правило §5 CLAUDE.md):

1. раздел хаба — поле `flag` в реестре `settings.ts` (карточка и пункт меню исчезают);
2. страницы раздела — `notFoundIfDisabled('automation')`;
3. `emitAutomationEvent` — выходит сразу, не трогая базу.

Задачи остаются под существующим `internal_tasks`; страница задачи, комментарии
и чек-лист наследуют его.

### 3.11. `Р-Э4-11` — «Мой день» дополняется у менеджера, руководителю добавляется только «Просроченные»

`У-226` дополняет существующий экран, а у руководителя «Моего дня» нет вовсе.
Собрать его руководителю — это новый экран, то есть новый объём (§14 CLAUDE.md).
`У-225` при этом прямо требует блок «Просроченные» на дашборде руководителя —
его и делаем. Полноценный «Мой день» руководителя вынесен в вопрос `В-4-1`.

### 3.12. `Р-Э4-12` — повторы (`У-221`) идут последним PR

Единственное требование этапа с приоритетом «Важно» и единственное, где
рождается своя очередь и понятие серии («эта / все будущие»). Если этап придётся
сузить по времени, отрезается ровно этот PR, и все остальные требования MVP
остаются целыми.

### 3.13. `Р-Э4-13` — действие «отправить сообщение» включаем, но правила из коробки его не используют

Пакет помечает `send_message` как «Важно, после `У-208`»; `У-208` (шаблоны
ответов) отгружен этапом 3, так что техническая причина откладывать отпала.
Но робот, который сам пишет клиенту, — это то, что заказчик должен включить
осознанно. Поэтому действие доступно в форме правила, **ни одно из пяти правил
из коробки его не использует**, и в форме рядом с ним стоит предупреждение
«сообщение уйдёт клиенту без участия менеджера».

### 3.14. `Р-Э4-14` — право доступа

Новый код `settings.automation.manage` в `SETTINGS_CAPABILITIES`. Следствие,
которое надо понимать заранее: профиль, где коды `settings.*` уже размечены,
нового кода не получит и в раздел не попадёт — это и есть задуманный
default-deny для нового раздела (§2b CLAUDE.md). Профили без единого
`settings.*`-кода и `accessProfileId = null` работают как раньше.

Ни один из них не блокирует начало работ: у каждого есть умолчание, по которому

реестр исключений зеркала.

**`В-4-2`. Раздел «SLA входящих в работу» переименовывается в «SLA»** и получает

одном месте, но подпись в меню у сотрудников изменится. **Умолчание:
переименовываем.**

**`В-4-3`. Повторяющиеся задачи (`У-221`) — в этом этапе или отдельно?**
Единственное требование с приоритетом «Важно». **Умолчание: делаем, последним
PR** — так его можно отрезать без ущерба остальным, если время кончится.

**`В-4-4`. Действие «отправить сообщение клиенту» (`send_message`).**
**Умолчание: добавляем в форму правил, но ни одно правило из коробки его не
использует** (`Р-Э4-13`). Если заказчик считает, что робот не должен писать
клиентам вообще — действие убирается из каталога одной строкой.

**`В-4-5`. Правила — только компанейские.** Платформенных роботов «на все
компании сразу» не будет (`Р-Э4-2`, §2.2): admin заводит правило, выбрав
компанию. **Умолчание: так и делаем.**
