## 1. Зачем этот этап и почему он строго ДО этапа 5

Сегодня писатель организаций (`upsertOrgRecord`) устроен так: нет колонки «ИНН
партнёра» → строка пропущена (`no_partner_external_id`); колонка есть, но
партнёр ищется по полю `slug` — а в колонке лежит **ИНН** → пропущена
(`partner_not_found`). То есть даже когда этап 5 включит чтение контрагентов из
файла, **каждая строка будет отброшена**. ТЗ прямо фиксирует порядок: снять
обязательность партнёра надо до включения импорта, иначе первый прогон даст
100% пропусков и работу придётся переделывать.

Решение владельца №1 (§0.1 ТЗ): **организация без партнёра допустима как прямой
клиент**; у одного партнёра может быть несколько организаций.

## 2. Что в объёме (строго Т-19, Т-19а, Т-20)

| Требование | Суть |
|---|---|
| **Т-19** | Партнёр в строке контрагента необязателен: пусто → прямой клиент (`partnerId: null`); найден → привязка; указан, но не найден → `skip: partner_not_found`. Код `no_partner_external_id` удаляется полностью |
| **Т-19а** | Никакого 1:1 партнёр↔организация: тест «две строки с одним ИНН партнёра → две организации с одним `partnerId`» |
| **Т-20** | Партнёр ищется по **ИНН** (плюс прежний `slug` как запасной путь): `findFirst({ where: { OR: [{ inn }, { slug }] } })` |

**Вне объёма:** включение `pullOrganizations` и синтетический ключ (этап 5);
валидация и полная нормализация ИНН с ведущими нулями (Т-21/Т-22, этап 5);
привязка к компании — `tx.company.create` в ветке создания пока остаётся
(этап 6, Т-41).

## 3. Разведка по коду (факт на `main` 6c360239)

- [`writers.ts:281`](../../../src/lib/services/oneCSync/writers.ts) —
  `upsertOrgRecord`: партнёр ищется `findUnique({ where: { slug } })`; `!partnerId`
  → skip с одним из двух кодов. Всё ровно как описывает П-2 ТЗ.
- `Partner.inn String? @unique` — уже в схеме (`prisma/schema.prisma:646`),
  **миграция не нужна**; `Organization.partnerId` уже nullable.
- `Partner.organizations Organization[]` — связь «один ко многим» уже есть,
  Т-19а закрывается тестом, не кодом.
- Через `upsertOrgRecord` идёт **и сетевая синхронизация** (`adapter-rest`) —
  файловый путь до этапа 5 организации не поставляет (`pullOrganizations()`
  возвращает `[]`), поэтому видимый эффект этапа 4 сегодня — именно на сетевом
  обмене и на unit/integration-тестах.

## 4. Решения

### 4.1. Новая логика ветки партнёра (Т-19 + Т-20)

```ts
const rawPartnerRef = input.partnerExternalId?.trim();
let partnerId: string | null = null;
if (rawPartnerRef) {
  const partner = await db.partner.findFirst({
    where: { OR: [{ inn: normalizeInn(rawPartnerRef) }, { slug: rawPartnerRef }] },
    select: { id: true },
  });
  if (!partner) {
    sum.skips.push({ externalId: input.externalId, reason: 'partner_not_found' });
    return; // указан, но не найден — не угадываем и не создаём партнёра молча
  }
  partnerId = partner.id;
}
// дальше partnerId (string | null) уходит в create; ветка update партнёра не трогает — как и сейчас
```

- Запасной путь по `slug` обязателен: **сетевой** `adapter-rest` присылает в
  `partnerExternalId` настоящий slug — без OR этап 4 сломал бы работающий
  сетевой обмен.
- Код `no_partner_external_id` исчезает из writer'а; в отчётах он больше
  никогда не появится.

### 4.2. `normalizeInn` — общая функция, растущая в этап 5

Новый модуль `src/lib/services/oneCSync/inn.ts`:

```ts
/** Этап 4: убрать пробелы (включая неразрывные). Этап 5 (Т-22) добавит сюда
 *  приведение числа из Excel к строке и ведущие нули — та же функция,
 *  как того требует Т-20 («тем же кодом, что и ИНН организации»). */
export function normalizeInn(raw: string): string;
```

Т-20 требует нормализовать ИНН партнёра «тем же кодом», что ИНН организации, —
но этот код (Т-22: ведущие нули, число→строка) принадлежит этапу 5. Чтобы не
тащить пол-этапа-5 сюда, функция появляется сейчас в минимальном виде (пробелы)
и расширяется в этапе 5 в одном месте. Единственная точка правды сохраняется.

### 4.3. Что НЕ меняется

- Ветка **обновления** существующей организации партнёра не трогает — как и
  сейчас (импорт не перевешивает клиента между партнёрами молча).
- `mayCreateOrg` и `tx.company.create` в ветке создания — без изменений
  (этап 6). До него новый контрагент по сети продолжает минтить `Company`;
  **этап 4 расширяет этот известный дефект §0.2 на бес-партнёрные организации
  сетевого обмена** — осознанно, порядок этапов утверждён ТЗ, а боевой адаптер
  на проде (`ONE_C_ADAPTER`) по умолчанию `fake`.
- Excel-импорт видимого поведения не меняет до этапа 5.
