# Spec: мессенджеры как полноценный канал общения с клиентами

**Дата:** 2026-09-12
**Источник:** просьба заказчика 12.09.2026 — «не только ботов добавить у
пользователей в Telegram и MAX, но и полноценная возможность добавить
мессенджер Telegram и другие».
**Статус:** design → реализация срезами (план —
[2026-09-12-messengers-dialogs.md](../plans/2026-09-12-messengers-dialogs.md)).
Указатель «действующее ТЗ» в `STATUS.md` не переключается — прецедент
[ТЗ роли руководителя](../../tz/2026-08-17-tz-leader-role.md): точечная
программа со своей спекой, а не новая линейка `У-N`.

## 0. Как понята просьба

Сегодня мессенджеры в системе — это **боты для уведомлений**: администратор
вводит токены, пользователь привязывает бота и получает в него уведомления.
Написать боту клиент может, но дальше «Входящих писем» сообщение не уходит.

«Полноценный мессенджер» в терминах любой CRM — это **канал переписки**:

1. мессенджер **подключают** как канал (Telegram, MAX, WhatsApp — и далее по
   одному адаптеру на каждый новый), из интерфейса, без сервера;
2. у сотрудника есть **диалоги** с клиентами: вся история в обе стороны,
   ответ из диалога, привязка к организации, возможность **написать первым**;
3. клиент, привязавший бота, просто **пишет в него** — и попадает к своему
   менеджеру, а ответ менеджера приходит туда же.

Три части — три группы срезов ниже.

## 1. Как есть (сверено по коду 12.09.2026)

| Что | Где | Вывод |

## 2. Решения (Р-М-1 … Р-М-10)

- **Р-М-1. Диалог — новая сущность.** `MessengerDialog` (кто, в каком канале,
  чей) + `MessengerMessage` (все сообщения в обе стороны). `InboundMessage`
  **остаётся** источником для «Входящих в работу», вложений и антивируса —
  диалог не заменяет триаж, а даёт переписку. Имя `MessengerDialog`, а не
  `Conversation`: `StaffConversation` уже занято чатом сотрудников.
- **Р-М-2. Один собеседник — один диалог.** Уникальность
  `(channel, peerRef)`: бот у платформы один, поэтому Telegram-пользователь
  не может «быть в двух компаниях». Компания у диалога появляется при
  автораспознавании, привязке сотрудником или **первом ответе** (ответивший
  забирает диалог в свою компанию — правило первого ответившего).
- **Р-М-3. Скоуп — как у «Входящих писем».** Сотрудник видит диалоги своей
  компании **плюс** общую очередь непривязанных (`companyId IS NULL`), и никогда
  чужой компании. Форма Prisma и in-memory-двойник держатся тестом
  эквивалентности (образец [inbound/scope.ts](../../../src/lib/services/inbound/scope.ts)).
- **Р-М-4. Флаг `inbound_messaging` становится поведенческим** (образец
  `Р-24` для `telephony_mango`): снимается с `FEATURE_PREFIXES`, закрывается
  страницами (`notFound`), меню и гардами роутов — все эти точки уже есть.
  Итог: один переключатель «Мессенджеры» в «Функциях платформы», сервер не
  трогаем. Нового флага не заводим — диалоги и входящие письма это одна
  функция «приём сообщений из мессенджеров».
- **Р-М-5. Экран «Мессенджеры» — у менеджера** (`/manager/messengers`,
  группа «Коммуникации»). Руководитель работает в нём через кабинет менеджера
  («играющий тренер»), администратор переписку не ведёт — исключение зеркала
  записывается с причиной, ровно как у «Входящих писем».
- **Р-М-6. Настройки: раздел «Подключение мессенджеров»** в группе
  «Интеграции» хаба (только администратор — там секреты, `Р-22`). Три формы
  мессенджеров **переезжают** из обзорной страницы в этот раздел (один объект —
  одно место, §0.2); обзор оставляет светофор и ссылку.
- **Р-М-7. Транспорт один.** Новый модуль `sendToMessenger(channel, peerRef,
  text)` роутит в существующие `send*Message`; сетевого кода не прибавляется.
  `replyToInbound` переводится на него (реюз, не дубль). Только текст:
  вложения в мессенджерах — вне объёма (см. §7).
- **Р-М-8. Написать первым — из списка диалогов.** Кнопка «Новый диалог» →
  выбрать человека → канал. Кандидаты: пользователи кабинетов с привязанным
  мессенджером и контакты компании с каналом мессенджера. В Telegram и MAX
  бот может писать только тому, кто уже нажал «Start» (chatId известен),
  поэтому кандидат без chatId не предлагается — честнее, чем кнопка с отказом.
- **Р-М-9. Менеджер узнаёт о входящем.** Новый тип уведомления
  `messenger_message` (аудитория `staff`) уходит менеджерам организации, к
  которой привязан диалог, со ссылкой на диалог. Непривязанные диалоги и так
  видны во «Входящих в работу».
- **Р-М-10. История не теряется.** Существующие `InboundMessage` из
  мессенджеров сворачиваются в диалоги скриптом `npm run backfill:messengers`
  (идемпотентно: сообщение попадает в диалог один раз по `inboundMessageId`).
  Тот же код чинит пропуски, если вебхук записал письмо, а диалог — нет.

## 3. Модель данных (миграция аддитивна и обратима)

```prisma
/// Диалог с клиентом в мессенджере (Р-М-1). Один собеседник — один диалог.
model MessengerDialog {
  id                   String   @id @default(cuid())
  createdAt            DateTime @default(now())
  updatedAt            DateTime @updatedAt
  channel              String            // telegram | max | whatsapp (MESSENGER_CHANNELS)
  peerRef              String            // chatId (telegram/max) или E.164 (whatsapp)
  peerDisplay          String?
  companyId            String?           // null — общая очередь непривязанных
  organizationId       String?
  contactId            String?
  userId               String?           // пользователь кабинета, если собеседник — он
  status               String   @default("open")   // open | closed
  lastMessageAt        DateTime @default(now())
  lastInboundAt        DateTime?
  lastMessagePreview   String?           // первые 200 символов последнего сообщения
  lastMessageDirection String?           // in | out
  unreadCount          Int      @default(0)        // входящих, не открытых сотрудником
  messages             MessengerMessage[]
  @@unique([channel, peerRef])
  @@index([companyId, lastMessageAt])
  @@index([organizationId])
  @@index([contactId])
}

/// Сообщение диалога — в обе стороны.
model MessengerMessage {
  id               String   @id @default(cuid())
  dialogId         String
  dialog           MessengerDialog @relation(fields: [dialogId], references: [id], onDelete: Cascade)
  direction        String            // in | out
  body             String
  authorId         String?           // сотрудник — у исходящих
  inboundMessageId String?  @unique  // связь с InboundMessage — у входящих
  externalId       String?  @unique  // идемпотентность входящих
  deliveryStatus   String   @default("sent")  // sent | failed — у исходящих
  createdAt        DateTime @default(now())
  @@index([dialogId, createdAt])
}
```

Связи на `Company`/`Organization`/`Contact`/`User` — `onDelete: SetNull`
(диалог переживает удаление привязки, как `InboundMessage`). Внешних ключей
на `authorId` не ставим намеренно: исходящее сообщение — исторический факт,
удаление сотрудника его не стирает.

## 4. Сервисы — `src/lib/services/messengers/`

| Файл | Что делает | Контракт |
|---|---|---|
| `channels.ts` | `MESSENGER_CHANNELS`, русские подписи, `isMessengerChannel`, `isMessengerAvailable` (креды + флаг канала) | чистый |
| `transport.ts` | `sendToMessenger(channel, peerRef, text)` → существующие клиенты | `{ ok }`, никогда не бросает |
| `scope.ts` | `dialogScopeWhere(session)` + `isDialogInScope(session, dialog)` | Р-М-3 |
| `appendInbound.ts` | вызывается из `ingestInboundMessage` после записи письма: upsert диалога по `(channel, peerRef)`, привязка при распознавании, `unreadCount+1`, переоткрытие закрытого, сообщение `in`, уведомление `messenger_message` | best-effort: сбой логируется, вебхук отвечает 200 |
| `recordOutbound.ts` | пишет исходящее в диалог (зовёт `sendInboundReply` после удачной отправки — история не теряется и из старого инбокса) | best-effort |
| `list.ts` | `listDialogs(prisma, session, {channel?, status?, page, pageSize})` — одна выборка, превью из колонок диалога | PII `messengers_list` |
| `get.ts` | `getDialog(prisma, session, id)` — диалог + последние 200 сообщений + собеседник/организация; `markDialogRead` | PII `messengers_view`; вне скоупа → `not_found` (не раскрываем существование) |
| `send.ts` | `sendDialogMessage(prisma, session, {dialogId, text})`: скоуп → длина ≤ 4000 → канал доступен → транспорт → правило первого ответившего → сообщение `out` (`sent`/`failed`) → аудит | `forbidden` · `not_found` · `invalid` · `text_too_long` · `channel_unavailable` · `reply_failed` |
| `bind.ts` | `bindDialog(prisma, session, {dialogId, organizationId, contactId?})`: те же гейты, что у `bindInboundMessage` (компания, `teamMode`, контакт своей компании), learn-on-link `captureChannel`, **привязка всех непривязанных `InboundMessage` того же собеседника** (очередь триажа очищается), аудит | `forbidden` · `not_found` |
| `start.ts` | `listDialogCandidates(prisma, session)` (люди с мессенджерами в скоупе) и `startDialog(prisma, session, {kind:'user'\|'contact', id, channel})` — `peerRef` берётся **с сервера** из привязки, не от клиента; upsert диалога с привязкой; чужая компания → `forbidden` | `forbidden` · `not_found` · `no_messenger_channel` |
| `status.ts` | `closeDialog` / `reopenDialog` + аудит | `forbidden` · `not_found` |
| `backfill.ts` | `backfillDialogsFromInbound(prisma)` — Р-М-10; скрипт `scripts/backfill-messenger-dialogs.ts` | идемпотентно |

Аудит: действия `messenger_dialog_bound`, `messenger_message_sent`,
`messenger_dialog_closed`, `messenger_dialog_reopened`, `messenger_dialog_started`;
сущность `messenger_dialog`; русские названия в `audit/labels.ts`.

Коды ошибок (новые) в `errors/messages.ts`: `text_too_long` («Сообщение
слишком длинное — не больше 4000 символов.»), `channel_unavailable»
(«Мессенджер не подключён. Проверьте раздел «Подключение мессенджеров».»),
`no_messenger_channel` («У этого человека нет привязанного мессенджера.»),
`dialog_not_found` («Диалог не найден.»).

- Крошки «Мессенджеры → <собеседник>» (`buildCabinetBreadcrumbs`).

- Форма ответа (Textarea + «Отправить»); если канал не подключён — вместо
  формы честная подсказка с ссылкой на настройки.

  `SourceIntakeActions` по последнему входящему письму; «Закрыть диалог» /

## 6. Инварианты приёмки

- Входящее из любого мессенджера попадает в диалог **ровно один раз**
  (повтор вебхука не двоит ни письмо, ни сообщение диалога; гонка двух
  вебхуков на новый диалог не падает — unique + повторный поиск).
- Ответ из диалога уходит тем же транспортом, что уведомления, и **виден в
  истории** — и когда отправлен из «Входящих писем» тоже.
- Менеджер компании A не видит и не может ответить в диалог компании B; в
  непривязанный — может, и диалог становится диалогом его компании (аудит).
- Привязка диалога закрывает непривязанные письма того же собеседника в
  «Входящих в работу» и обучает контакт каналу (следующее сообщение
  распознаётся само).
- «Новый диалог» не показывает людей без известного адреса в выбранном
  мессенджере; `peerRef` не принимается от клиента.
- Флаг `inbound_messaging` переключается из «Функций платформы»; страницы
  и роуты при выключенном флаге отвечают 404.
- Экраны проходят три вопроса §15 и 390 px; названия — из глоссария; раздел
  зеркален по правилу §0.2 или записан в исключениях.
- Все гейты зелёные: `typecheck`, `lint`, `test:unit`, интеграционные тесты
  затронутых сервисов на живом Postgres, покрытие новых файлов 100 %.

## 7. Вне объёма (не делаем в этой программе)

- Вложения (фото, файлы) из мессенджеров в диалоге — текст только;
  вложения по-прежнему живут во «Входящих письмах» с антивирусом.
- Новые адаптеры (VK, Viber): архитектура допускает — новый мессенджер =
  клиент + вебхук + строка в `MESSENGER_CHANNELS`; заводятся отдельной
  просьбой с кредами провайдера.
- Назначение ответственного за диалог, статусы сверх «открыт/закрыт»,
  шаблоны быстрых ответов.
- Зеркалирование переписки по заказу (`OrderThread`) в мессенджер клиента и
  обратно — отдельная спека, если понадобится.
- Диалог в карточке организации отдельной вкладкой: вкладка «Входящие письма»
  остаётся, диалоги фильтруются по организации из списка.
