# Единый план подготовки к боевому запуску (launch-readiness roadmap)

**Дата:** 2026-06-13
**Статус:** утверждён владельцем продукта (структура и приоритеты)
**Метод:** аудит по сквозным бизнес-процессам (6 параллельных агентов), не по ролям — баги логики в multi-role системе живут на стыках ролей.

## Контекст и цель

Code-backlog проекта исчерпан (фичи всех 6 ролей отгружены). Текущий этап — не «достроить недостающее», а **выровнять логику и подготовить к боевому запуску**: закрыть дыры на стыках ролей, убрать лишнее/расходящееся, сделать процессы предсказуемыми.

**Планка:** боевой запуск всех 6 ролей сразу (admin, руководитель, менеджер, партнёр, организация, слушатель).

## Ключевые решения владельца (зафиксированы)

1. **Волна запуска:** все 6 ролей сразу.
2. **Путь данных 1С:** приоритет — **прямая API-интеграция**; **Excel-выгрузка обязательна и постоянна** (не времянка); расширяемо под CSV/XML. → архитектурный принцип: подключаемые адаптеры-источники → один общий нормализованный контракт.
3. **Встречи с 1С не будет** — контракт обмена реализуем самостоятельно (сами решаем: ключ партнёра, перевод справочников-статусов, пагинацию). Внешнего блокера нет.
4. **Партнёр видит заказы/оплаты только через свои лиды** (не любой импорт) — переосмысляет F2.
5. **Лиды:** менеджер должен видеть/обрабатывать лиды в кабинете (сейчас пробел — лид уходит сразу в 1С).
6. **Заявки на обучение:** подаёт партнёр / организация / менеджер / руководитель / админ → **утверждение на нашей стороне** → провижн слушателя в LMS. **В первую волну.**
7. **Своя LMS** — будущий отдельный проект с двусторонней API-синхронизацией.
8. **Отчётность/экспорт** — для всех ролей по их функционалу.
9. **Домен текущей LMS слушателя:** `otsfera.cdoprof.com` (хардкод в коде верен; `.ru` в исходной формулировке был ошибкой — S1 снят).

Фундамент крепкий: **P0 по безопасности/изоляции не найдено.** Проверено и чисто: cross-company изоляция (C8), матрица гейтинга чата, безопасность bridge-JWT слушателя, защита от privesc суб-ролей, Model A, 0 TODO/FIXME в `src/`, нет мёртвых ссылок/флагов, реестр слушателей — корректный read-only из 1С (не полу-LMS).

## Дорожная карта (8 треков)

### 🔴 Launch-критичные

**T1. Единый контракт ингестии** *(фундамент)*
Подключаемые адаптеры-источники (1С API, Excel, расширяемо CSV/XML) → один нормализованный DTO (заказ/оплата/организация/документ) → валидация-гейт с **гарантией полноты** → доменный upsert. Полнота — свойство контракта, а не патч на адаптер: `financialStatus`, `partnerId`-резолв, `organizationId`, `isRefund` обязаны быть заполнены любым источником, иначе строка → карантин с видимым отчётом об импорте. Закрывает F1/F3/F4/F7 + гард размера/MIME (F5) + несведение KPI (F6). API-адаптер — эталон, Excel подтягивается к контракту.
Зависит: —

**T2. Живая 1С API-интеграция**
Включить `ONE_C_ADAPTER`, самостоятельно закрыть 3 «мины» (ключ партнёра, слой перевода справочников-статусов, пагинация), DOC-03 (download 1С-документов). Адаптер реализует контракт T1.
Зависит: T1

**T3. Лиды: партнёр → менеджер → заказ**
(a) **Новая фича:** менеджер видит/обрабатывает лиды в кабинете. (b) Цепочка лид→заказ→видимость партнёра «только через свои лиды» (F2 через `promotedOrderId`; F8). (c) Прозрачность статусов лида для партнёра (S5).
Зависит: —

**T4. Точечные блокеры**
DOC-01 (пин org-канала документов), C-01+C-05 (unique/период-гард ведомостей), C-02 (уведомление партнёра о ведомости).
Зависит: —

**T5. Заявки на обучение**
Подаёт партнёр / организация / менеджер / руководитель / админ → утверждение на нашей стороне → провижн слушателя в текущую LMS (`otsfera.cdoprof.com`; на старте провижн может быть ручным/полуавто). Закрывает входную сторону процесса слушателя.
Зависит: — (провижн-мост сцепляется с T6 в будущем)

### 🟢 После запуска / отдельные проекты

**T6. Своя LMS** — собственная LMS + двусторонняя API-синхронизация слушателей/обучения. T5 — её «кормилец».

**T7. Отчётность и экспорт по ролям** — отчёты/выгрузки каждой роли по её функционалу.

**T8. UX-полировка** — ~14 P2-находок (сообщения об ошибках, кнопки-флаги, unread-логика, AV-скан чат-вложений, консолидация гардов, float в суммах).

## Зависимости и порядок
- **T1 — фундамент**: всё финансовое стоит на нём.
- **T2** строится поверх T1 (адаптер реализует контракт).
- **T5 → T6** (заявки кормят будущую LMS).
- **T3 / T4 / T5 / T7 / T8** между собой независимы — параллелятся.

**Старт:** T1. Каждый трек проходит свой цикл спека → план → реализация (subagent-driven dev) с close-out `-DONE.md`.
