# Спека — Аудит семейства «Заказы»: логика действий и кросс-ролевая консистентность

**Дата:** 2026-06-21
**Статус:** дизайн утверждён, ждёт вычитки → план
**Тип:** UX/flow-аудит + точечная ремедиация (первый сабпроект трека D «Логика действий в приложении»)

## 1. Контекст и цель

Проект release-ready (v0.9.0), 6 кабинетов. Запрос владельца — чтобы «всё было логично по действиям». Трек D («логика действий») декомпозирован; это **первый сабпроект — семейство «Заказы»**, выбран как горизонтальный срез (один концепт, повторяющийся в нескольких ролях), потому что несогласованность по природе межкабинетная и видна только при сравнении ролей бок о бок.

**Цель:** выровнять **случайную** несогласованность экранов «заказов» между ролями (нейминг, заголовки, состояния, дубли, тупики), **сохранив намеренные ролевые различия** (RBAC, F2, Model A, C8).

**Не-цель:** редизайн, новые фичи, унификация под капотом без user-visible пользы, аудит других семейств (Финансы/Документы/Сообщения/Команда/Заявки — отдельные сабпроекты D2+).

## 2. Объём (scope)

Экраны «заказов» во всех ролях, где они есть — список и деталь:

| Роль | Список | Деталь | Пагинация (как есть) | Презентация |
|---|---|---|---|---|
| partner | `/partner/deals` (H1 «Заказы») | `/partner/deals/[id]` | offset (`take/skip`) + инлайн `Paginator` | `DealsTable` + `DealsCardList` |
| organization | `/organization/orders` | `/organization/orders/[id]` | offset + инлайн `Paginator` (дубль) | `OrgOrdersTable` + `OrgOrdersCardList` |
| manager | `/manager/orders` | `/manager/orders/[id]` | cursor (`nextCursor`) | `ManagerOrdersTable` |
| leader | `/leader/orders` | — (своей детали нет?) | cursor (`teamModeOverride`) | `ManagerOrdersTable` |
| admin | `/admin/orders` → `redirect('/admin/dashboard')` | `/admin/orders/[id]` | списка нет (Model A) | — |

**Жёсткая граница «намеренное vs случайное».** Аудит обязан различать:
- **Намеренные различия (НЕ трогать):** admin без списка заказов (Model A — управление через dashboard + деталь); partner видит только лид-промоутнутые заказы (F2, `promotedFromLead.partnerId`); manager/leader scope (C8, mode-aware). Это инварианты из CLAUDE.md §4/§5; нарушать нельзя.
- **Случайная несогласованность (выравниваем):** нейминг, заголовки/подписи, наличие карточного списка, дублирование кода, тупики навигации, отсутствие страницы детали, состояния empty/loading/error, подтверждения действий.

## 3. Рубрика аудита (6 осей × роли)

1. **Навигация** — нет тупиков; куда ведут строки/кнопки; back/хлебные крошки; есть ли страница детали и куда ведёт клик по строке.
2. **Доступность действий** — одинаковые действия присутствуют/активны консистентно; нет кнопок «в никуда».
3. **Обратная связь** — успех → `toast`, ошибка → inline/alert (CLAUDE.md §9); единообразие канала фидбека.
4. **Состояния** — `empty` / `loading` / `error` присутствуют и единообразны.
5. **Подтверждения** — модалки `Dialog` на необратимые действия (CLAUDE.md §9).
6. **Кросс-ролевая консистентность** — нейминг, расположение, паритет поведения одинаковых экранов.

## 4. Предварительные находки (grounded, до полного прохода)

Видны уже при чтении 5 страниц списка:

- **F1 (P2) — три модели пагинации** одного экрана: offset (partner, org) / cursor (manager, leader) / нет (admin). Под капотом, не user-blocking → см. открытый вопрос §6.
- **F2 (P2) — дублирование кода:** функции `Paginator` и `pluralize` дословно скопированы в [partner/deals/page.tsx](../../../src/app/partner/deals/page.tsx) и [organization/orders/page.tsx](../../../src/app/organization/orders/page.tsx).
- **F3 (P3) — карточный список** (`*CardList`, адаптив) есть у partner/org, нет у manager/leader.
- **F4 (P3) — заголовки/подписи расходятся:** partner «{N} заказов» + `font-bold`; org «{N} заказа · {имя орг}»; leader «Все заказы компании»; manager — без подзаголовка, `font-semibold`.
- **F5 — деталь заказа у leader:** своей `[id]`-страницы нет. Severity условная: **P1**, если клик по строке ведёт в тупик/404/чужой роут; **P3**, если ссылки на деталь нет вовсе (осознанно list-only). Что именно — определяется в фазе 1 (трассировка клика по строке `ManagerOrdersTable` в контексте leader).
- **F6 (intentional) — admin без списка** (`redirect`) — фиксируем как осознанное различие (Model A), НЕ баг.

Полный findings-лист (все 6 осей × список+деталь × 5 ролей, включая empty/loading/error и действия на детали) добивается в первой фазе плана.

## 5. Правила выбора «канона»

При расхождении правильным считаем то, что:
- **Приоритет — пользовательская логика действий**, не внутреннее устройство. Сначала: подписи/заголовки, карточный список, тупики, отсутствие детали, состояния, подтверждения.
- **Дубли убираем дёшево:** `Paginator` + `pluralize` → один презентационный примитив в `src/components/ui/` (CLAUDE.md §4 разрешает общий компонент, когда он строго презентационный и domain-agnostic; пагинатор именно такой). Подключить в partner/org.
- **Sibling-компоненты НЕ сливаем насильно** (§4): `*OrdersTable` по ролям остаются раздельными при ролевой специфике; выравниваем поведение, не насаждаем общий компонент.
- **Намеренные ролевые различия сохраняем** (см. §2 граница).

## 6. Открытый вопрос (решение зафиксировано: отложить)

**Унификация модели пагинации (cursor vs offset).** Обе работают; различие под капотом, user-visible пользы мало, а смена затрагивает сервисы + компоненты + тесты (высокая цена). **Решение: в этом проходе НЕ унифицируем.** Извлечение общего `Paginator` (F2) от модели пагинации не зависит — делаем его независимо. Унификацию выносим в потенциальный отдельный сабпроект, если позже появится user-visible причина.

## 7. Метод и формат результата

- **Метод:** основа — статическое чтение кода (страницы, компоненты, сервисы-резолверы, nav); живой прогон — точечно (спот-чек спорных мест), не как основной инструмент (dev-сервер из-под агента нестабилен — см. память `project-running-locally`).
- **Deliverable:** findings-таблица «ось × роль» с severity (P1 ломает флоу / P2 заметная несогласованность / P3 косметика) и рекомендованным каноном на каждый пункт; затем фиксы в этом же сабпроекте.

## 8. Тест-стратегия (CLAUDE.md §6)

- `typecheck` + `lint` + `test:unit` — обязательны.
- Извлечённый `ui/Paginator` — отдельный unit-тест (рендер веток: первая/средняя/последняя страница, границы).
- Если меняется раскладка экранов — `e2e:visual` с обновлением baseline (`e2e:visual:update`).
- Полный `build` как финальный чек.
- Сервисный слой не трогаем (пагинацию не унифицируем) → integration-слой не затрагивается; если внезапно потребуется — `test:integration` на живом PG.

## 9. Вне scope

- Другие семейства (Финансы, Документы, Сообщения, Команда, Заявки) — отдельные сабпроекты трека D.
- Унификация модели пагинации (см. §6).
- Любой редизайн/новые фичи.
- Изменение RBAC/F2/Model A/C8 инвариантов.
