## 1. Что требует ТЗ (§11 дословно)

- Настраивают **администратор и руководитель**.

## 3. Дизайн — модель данных

### 3.1 Типы полей: 5 → 12

`enum CustomFieldType` дополняется семью значениями (существующие пять не
трогаем — это сохранит данные и код):

| Значение enum | ТЗ | Хранение в `value String?` | Валидация |
|---|---|---|---|
| `text` (есть) | короткий текст | как есть | длина ≤ 500 |
| `textarea` | многострочный текст | как есть | длина ≤ 5000 |
| `number` (есть) | число | десятичная строка | `Number.isFinite` |
| `money` | денежная сумма | строка `"12345.67"` | регэксп `^-?\d+(\.\d{1,2})?$`, храним как строку (не float — иначе теряются копейки) |
| `date` (есть) | дата | ISO `YYYY-MM-DD` | парсится в дату |
| `datetime` | дата и время | ISO 8601 с временем | парсится в дату |
| `boolean` (есть) | Да/Нет | `"true"` / `"false"` | точное совпадение |
| `select` (есть) | выбор одного | значение из `options` | `options.includes(value)` |
| `multiselect` | множественный выбор | **JSON-массив строк** `["a","b"]` | парсится, все элементы ∈ `options`, без дублей |
| `phone` | телефон | нормализованная строка | цифры + `+`, 5–20 знаков |
| `email` | e-mail | как есть | простой RFC-lite регэксп, ≤ 254 |
| `url` | ссылка | как есть | `new URL()` парсится, схема только `http`/`https` |

> **Почему `multiselect` — JSON в той же колонке, а не отдельная таблица.**
> Колонка `value` уже строковая и полиморфная; отдельная таблица значений
> ради одного типа удвоит код чтения. Хранение фиксируем контрактом
> «`multiselect` ⇒ `value` — JSON-массив», парс/сериализация — в одном месте
> (`src/lib/services/customFields/coerce.ts`).

### 3.2 Новые поля определения

```prisma
model CustomFieldDefinition {
  // ... существующие
  helpText        String?        // подсказка под полем
  visibleToRoles  String[]       // пусто = видно всем, кому доступна карточка
  editableByRoles String[]       // пусто = правят admin/leader/manager
  isSystem        Boolean @default(false)  // системное — нельзя удалить/деактивировать
}
```

- Роли в массивах — строки из существующего `Role` + суб-роль руководителя:
  `admin`, `leader`, `manager`, `partner`, `organization`. `student` не участвует
  (у слушателя нет карточек — §14 ТЗ).
- **Пустой массив = «по умолчанию»**, а не «никому». Это важно для миграции:
  существующие поля заказа продолжают работать без правки данных.
- Дефолты по умолчанию **(решение Q1)**: `visibleToRoles = []` — видно всем, кто и
  так видит карточку; `editableByRoles = []` — правят **администратор и
  руководитель**. Менеджер и клиенты — только чтение, пока роль не отмечена явно.
- **Ловушка обратной совместимости.** У заказа сегодня значения пишет и менеджер
  (`resolveWritableOrder` пускает manager в скоупе). Если новый дефолт применить
  к уже созданным определениям, менеджеры молча потеряют право правки на
  боевых данных. Поэтому миграция **не оставляет старые строки пустыми**: всем
  существующим `CustomFieldDefinition` (все они `entityType='order'`)
  проставляется явный `editableByRoles = ['admin','leader','manager']` —
  поведение до и после миграции идентично. Новый дефолт действует только для
  полей, созданных после этапа.
- Миграция: четыре колонки с дефолтами + один `UPDATE` по существующим строкам
  (см. ловушку выше). Данные значений (`CustomFieldValue`) не трогаются.

### 3.3 `entityType`: свободная строка → закрытый список

Колонка остаётся `String` (менять на enum — дорогая миграция и лишний риск), но
допустимые значения фиксируются константой и валидируются в сервисе:

```ts
export const CUSTOM_FIELD_ENTITIES = ['order', 'organization', 'partner', 'student', 'document'] as const;
```

Попытка создать определение с чужим `entityType` → `invalid_entity_type` (новый код ошибки).

### 3.4 Системные поля (§11) — реестр, а не строки в БД

Перечисленные в §11 системные поля (название организации, тип, связанный
партнёр, ответственный менеджер, статус; ФИО сотрудника, организация, статус
карточки) — это **реальные колонки Prisma**, а не `CustomFieldDefinition`.
Городить их зеркала в таблице настраиваемых полей было бы дублированием
источника правды.

**Решение заказчика (Q2) — статический реестр:**
`src/lib/services/customFields/systemFields.ts` — список системных полей по
сущностям с русскими названиями. Он даёт:

1. **Экран настройки** показывает системные поля первым блоком, серым, с бейджем
   «системное» и без кнопок «Изменить/Деактивировать» — заказчик видит полную
   картину полей сущности, а не только добавленные.
2. **Защита ключей**: нельзя создать настраиваемое поле с ключом системного
   (`key` ∈ реестра ⇒ `reserved_key`) — иначе в карточке будет два поля «Статус».
3. Флаг `isSystem` в модели — задел на случай, если заказчик захочет
   «системные» настраиваемые поля (сейчас всегда `false`).

### 3.5 Значения: скоуп вместо хардкода заказа

`setValues` перестаёт быть заказо-специфичным. Новый резолвер
`resolveEntityAccess(prisma, session, entityType, entityId)` возвращает
`{ canRead, canWrite }`, опираясь на **существующие** политики:

| Сущность | Чтение | Запись |
|---|---|---|
| `order` | как сейчас (`canSeeOrder` + `teamMode`, org/partner — свои) | как сейчас + `editableByRoles` |
| `organization` | `canManagerAccessOrg` / `managerOrgScope`; партнёр — свои орг.; организация — себя | то же + `editableByRoles` |
| `partner` | admin/leader — все; менеджер — по видимым заказам партнёра; партнёр — себя | то же + `editableByRoles` |
| `student` | через организацию сотрудника (та же политика, что у карточки) | то же + `editableByRoles` |
| `document` | `canSeeDocument` | то же + `editableByRoles` |

Итоговое право = **скоуп карточки ∧ роль из `editableByRoles`**. Ни одно из двух
не ослабляет другое: если роль есть в `editableByRoles`, но карточка вне скоупа —
запрет (§4 CLAUDE.md, defense-in-depth не сокращаем).

`getValuesForEntity` получает аргумент `session` и **фильтрует по `visibleToRoles`**
на сервере — невидимое поле не должно приезжать в RSC-пропсы даже скрытым
(иначе утечёт в HTML).

## 4. Дизайн — интерфейс

### 4.1 Экран настройки (админ + руководитель)

- `/admin/custom-fields` — вкладки/селектор по пяти сущностям; таблица получает
  колонки «Подсказка», «Видят», «Правят», блок системных полей сверху.
- **Зеркало для руководителя**: `/leader/settings/custom-fields` — та же страница
  и тот же компонент, гейт `requireManagerLeader`. §4 ТЗ прямо даёт руководителю
  «Настройка полей и статусов», а Model A (§4 CLAUDE.md) запрещает пускать
  руководителя в `/admin/*`.
- API: `/api/admin/custom-fields` меняет гейт с «только admin» на
  **admin ∨ leader** (`requireAdmin` → `requireFieldsAdmin`). Менеджер — 403.
- Диалог поля: название · ключ · тип (12) · варианты (для `select`/`multiselect`) ·
  обязательность · подсказка · порядок · **видимость (чекбоксы ролей)** ·
  **право правки (чекбоксы ролей)** · активность.

### 4.2 Секция значений на карточках

Компонент `order-custom-fields.tsx` обобщается до
`components/custom-fields/entity-custom-fields.tsx` (`entityType` + `entityId` +
`fields` + `editable`), рендерит контролы для всех 12 типов:

- `textarea` → `Textarea`; `money` → `Input type=text inputMode=decimal` + суффикс «₽»;
- `datetime` → `Input type=datetime-local`; `multiselect` → группа чекбоксов;
- `phone` → `Input type=tel`; `email` → `type=email`; `url` → `type=url`;
- `helpText` → подпись под контролом (`text-xs text-gray-500`), она же в read-only.

Старый `order-custom-fields.tsx` остаётся тонкой обёрткой (сохраняем ~40 регрессов).
Sibling-паттерн §4 CLAUDE.md здесь **не применяется**: компонент строго
презентационный и принимает domain-agnostic тип `FieldWithValue`.

Точки монтирования — 4 новые сущности на карточках из таблицы §2. Карточка
партнёра для руководителя/менеджера **не создаётся** (решение Q4): настраиваемые
поля партнёра доступны в `admin/partners/[id]`.

### 4.3 Новая страница-карточка документа (решение Q3)

Сегодня документ живёт только строкой в списке. Заказчик выбрал полноценную
деталку, поэтому в объём этапа входит новый экран:

- **Маршрут:** `/{cabinet}/documents/[id]` для `admin`, `manager`, `leader`,
  `organization`, `partner` — пять тонких страниц поверх одного компонента
  `components/documents/document-detail-view.tsx` (документ — не доменно
  расходящаяся сущность, см. исключение sibling-паттерна в §4 CLAUDE.md:
  компонент презентационный, принимает `DocumentDetailView`-тип).
- **Сервис:** новый `src/lib/services/documents/detail.ts` —
  `getDocument(prisma, session, id)` поверх существующего `canSeeDocument`
  и клиентских скоупов (`counterpartyType`/`counterpartyId`, `order.organizationId`,
  `partnerId`). Возвращает `not_found` (не `forbidden`) при отказе — не раскрываем
  существование чужого документа.
- **Содержимое:** имя, тип, направление, номер, версия, размер, статус антивируса,
  кто и когда загрузил, связанный заказ/контрагент, кнопка скачивания
  (существующий download-роут с presigned URL — §10 CLAUDE.md, файл сам по себе
  через приложение не отдаётся), секция «Дополнительные поля».
- **Заражённый файл** (`scanStatus='infected'`): карточка открывается, но кнопка
  скачивания заменяется предупреждением — согласуется с 410 Gone у download-роута.
- Строки во всех пяти списках документов получают ссылку на карточку.

> **Честное предупреждение по объёму.** Это самая тяжёлая часть этапа: 5 страниц
> + сервис + компонент + их тесты под 100 % порог покрытия (§6 CLAUDE.md).
> Поэтому карточка документа вынесена в **отдельный PR-4**, а не подмешана к PR-3
> с остальными четырьмя сущностями — иначе PR-3 становится непроверяемым.

## 6. Тестовая стратегия

- **Unit (L2):** `coerce.ts` — таблица «тип × значение → валидно/нет» на все 12 типов,
  включая границы (`money` с тремя знаками, `multiselect` с дублем, `url` с `javascript:`);
  реестр системных полей (ключ занят → `reserved_key`); фильтрация по `visibleToRoles`.
- **Integration (L3, живой Postgres):** `resolveEntityAccess` по пяти сущностям ×
  пяти ролям — матрица чтения/записи; ключевой регресс — **партнёр компании A не
  пишет значения в карточку организации компании B** (в духе
  `security.idor-comments.integration.test.ts`).
- **Guard-тест:** значение поля с `visibleToRoles=['admin']` **не приходит** в
  пропсы страницы для менеджера (проверяем результат сервиса, а не CSS).
- **Coverage:** новые файлы попадают под 100%-порог (§6 CLAUDE.md) — компоненты
  через `@testing-library`, серверные страницы через `renderServerComponent`.
- **Миграция:** `prisma migrate status` зелёный; отдельный integration-регресс —
  определение заказа, созданное **до** миграции, после неё по-прежнему
  редактируется менеджером в скоупе (`editableByRoles` проставлен явно, см. §3.2),
  а поле, созданное **после**, менеджеру недоступно на запись.

## 7. Что этот этап НЕ делает

- Не трогает §10 (статусы) — это этап 2, отдельный PR.
- Из новых экранов создаёт **только карточку документа** (решение Q3). Карточка
  партнёра для менеджера и карточка сотрудника для администратора **не делаются**
  — там секция полей появится, когда/если появятся сами экраны.
- Не делает настраиваемые поля обязательными к заполнению на формах создания
  (валидация `required` — на сохранении секции, как сейчас у заказа).
- Не выносит системные поля §11 в редактируемый справочник — они остаются
  колонками БД (см. §3.4 и вопрос Q2).
