# Импорт оплат из 1С «Карточка счёта 51» — дизайн (ТЗ §7.2)

**Дата:** 2026-06-25
**Статус:** согласовано (брейнсторм) → spec self-review → ревью пользователя → план
**Связано:** [1c-file-import-design](2026-06-09-1c-file-import-design.md) (мультилистовой импорт — переиспользуем writer/UI-паттерны) · [organization-finance-hub-design](2026-06-04-organization-finance-hub-design.md) · ТЗ §7.2 (импорт выгрузки 1С) · §9.2 (возвраты в базе комиссии)

## Цель

Реализовать **парсер и импорт реального формата выгрузки 1С** — отчёта **«Карточка счёта 51»** (счёт 51 = расчётный счёт). Это основной канал автоматического внесения оплат по ТЗ §7.2; ручной ввод (§7.1) остаётся как fallback. После импорта партнёр и организация видят оплаты в **уже построенных** витринах `organization/finance` и `partner/finance` — этот слой не трогаем.

> **Важно (отличие от существующего импорта).** Мультилистовой импорт ([1c-file-import](2026-06-09-1c-file-import-design.md)) ждёт **чистый воркбук** (Контрагенты/Реализации/Поступления) с одной аккуратной строкой на запись. «Карточка счёта 51» — наоборот: **один шумный лист** с шапкой и итогами, многострочными ячейками, смешанными типами операций, и реальным сигналом (№ счёта, ИНН, НДС) в свободном тексте назначения платежа. Поэтому это **не новый `column-map.ts`**, а новый парсер + классификатор + матчер. Записываем оплаты через **существующий** writer (`upsertPaymentRecord`), а не дублируем write-логику.

## Реальность формата (определяет всю модель)

- Файл — Excel. Реальный образец — **legacy `.xls` (BIFF8)**; целевой — `.xlsx`. Оба поддерживаем (решение брейнсторма).
- Один лист, 12 колонок (индексы 0–11). Строки 0–6 — шапка отчёта. Строка 7 — заголовки. Строка 8 — подзаголовки. Строка 9 — «Сальдо на начало». Последняя — «Обороты за период и сальдо на конец» (итоги, **пропустить**). Операции — с ~строки 10.
- Раскладка колонок операции:
  - `col[0]` — **дата** (`ДД.ММ.ГГГГ`).
  - `col[1]` — **Документ** (многострочная): строка 1 = тип+номер+дата-время (`Поступление на расчетный счет 0000-001471 от 01.06.2026 17:00:00` / `Списание с расчетного счета ...`); строки 2+ = **назначение платежа**.
  - `col[2]` — Аналитика Дт (банковский счёт + статья).
  - `col[3]` — Аналитика Кт: строка 1 = **наименование контрагента** (иногда `… ИНН 9909676723`); строка 2 = договор/ДС; строка 3 = реализация.
  - `col[5]` — **сумма по дебету** (приход).
  - `col[7]` — **корр-счёт** (`62.01`, `62.02`, `60`, `91…`).
  - `col[8]` — сумма по кредиту (расход).

Проверено на реальном файле: 129 платежей / 198 исключений.

## Решения брейнсторма

1. **Очередь несопоставленных — отдельная таблица** (`PaymentImportRow`), а не nullable `Payment.organizationId`. Смэтченные строки пишутся как `Payment` через существующий writer; несмэтченные лежат в очереди с распарсенными полями + кандидатами + ссылкой на файл; оператор подтверждает в UI → промоушн в `Payment`. **`Payment.organizationId` остаётся NOT NULL** — все финвитрины сохраняют свой инвариант, риск утечки несмэтченных в KPI/комиссию нулевой.
2. **Матчинг по уровню уверенности:** точный (№ счёта→заказ→орг; ИНН→орг) → **авто-привязка**; fuzzy по наименованию → **в очередь** как предложенный кандидат, человек подтверждает. Финзаписи не привязываются к орг по нечёткому имени автоматически.
3. **Формат файла:** поддерживаем **оба** — `.xls` (SheetJS) и `.xlsx` (exceljs). Парсер **независим от чтения файла** (вход — `string[][]`), reader-слой выбирает библиотеку по расширению/magic-bytes.
4. **Объём:** вся фича в одной спеке/плане — парсер+классификатор → матчинг → запись+очередь → S3+журнал → UI загрузки → UI разбора очереди.
5. **Точки входа:** отдельные роуты `/admin/payments-import` + `/manager/payments-import` (не вкладка на `/import`).

## Архитектура и поток

```
[вход] /admin/payments-import (админ)  ·  /manager/payments-import (менеджер/руководитель)
        │  загрузка .xls / .xlsx (одна карточка счёта 51)
        ▼
[1] reader (format-agnostic)   .xls → SheetJS · .xlsx → exceljs   ⟶  string[][]
        ▼
[2] parser/oneCAccountCard/parser.ts   ⟶  ParsedRow[]   (вход: string[][], БЕЗ Prisma/HTTP)
        │   • срез строк-операций (между «Сальдо на начало» и «Обороты за период»)
        │   • классификация (62→платёж/возврат · 60/91/переводы→excluded(reason))
        │   • извлечение полей из col[1]/col[3]
        ▼
[3] matcher (read-only)   № счёта→Order→org · ИНН→Organization · fuzzy-имя→кандидат
        ▼
[4] DRY-RUN превью   ⟶  сводка (импорт / возврат / в очередь / исключено / ошибки парса)
        │   оператор подтверждает
        ▼
[5] commit ($transaction):
        ├─ точный матч  → upsertPaymentRecord (реюз writers.ts, дедуп по externalId)
        ├─ неточный/нет → PaymentImportRow (очередь, дедуп по externalId)
        ├─ excluded     → не пишем, считаем в сводке
        ├─ файл → S3 (prefix payments-import/) · PaymentImportBatch якорит файл+счётчики
        └─ SyncLog (entity=payment, direction=inbound, operation=import) + AuditLog
```

| `import-batch.ts` | Оркестратор: read→parse→match→план; commit ($transaction) точных в Payment + очереди в `PaymentImportRow`; S3-сохранение файла; SyncLog+Audit. | writers.ts, storage, log.ts |
| `index.ts` | barrel: `previewPaymentImport()` / `commitPaymentImport()` — публичный контракт (§3 Result-тип). | всё выше |

### Контракт сервиса (§3 Result-тип)

```ts
type PaymentImportError = 'invalid_file' | 'forbidden' | 'empty' | 'parse_failed';

function previewPaymentImport(
  prisma, session, args: { fileBuffer: Buffer; fileName: string }
): Promise<{ ok: true; plan: ImportPlan } | { ok: false; error: PaymentImportError }>;

function commitPaymentImport(
  prisma, session, args: { fileBuffer: Buffer; fileName: string }
): Promise<{ ok: true; result: ImportResult } | { ok: false; error: PaymentImportError }>;
```

`ImportPlan` несёт счётчики (платежи/возвраты к импорту, в очередь, исключено по причинам, ошибки парса) + per-row решения. Превью и commit парсят один и тот же буфер детерминированно — commit пересчитывает, не доверяя клиентскому плану.

## Модель данных (аддитивные миграции, `Payment` не трогаем)

| # | Миграция | Назначение |
|---|---|---|
| M1 | `model PaymentImportBatch { id, createdAt, importedById→User?, companyId?, fileKey String, fileName String, counts Json, status String }` | Один файл = один батч; якорь S3-файла и журнала. |
| M2 | `model PaymentImportRow { id, createdAt, batchId→PaymentImportBatch, externalId String @unique, paidAt DateTime, amount Decimal(14,2), isRefund Boolean, purpose String?, vatAmount Decimal(14,2)?, counterpartyName String?, counterpartyInn String?, accountCandidates Json, status String, candidateOrgId String?, candidateOrderId String?, matchMethod String?, rawRow Json, resolvedPaymentId String? }` | Очередь несопоставленных + контекст ручного разбора. |

- `status` ∈ `needs_review | resolved | dismissed`. `matchMethod` ∈ `name_fuzzy | none` (точные матчи в очередь не попадают — сразу `Payment`).
- `externalId @unique` на `PaymentImportRow` = идемпотентность очереди: повторный импорт того же документа не плодит дубль; уже `resolved`/`dismissed` строки не реанимируются.
- `accountCandidates` — массив строк (все извлечённые кандидаты № счёта, не только первый).
- `rawRow` — исходные ячейки строки (для ручного разбора и аудита).

`Payment` — без изменений (`organizationId String` NOT NULL, `externalId @unique`). Точные матчи пишутся как раньше через `upsertPaymentRecord`.

## Логика классификации (ТЗ, проверена на реальном файле)

Обрабатываем только строки-операции (между «Сальдо на начало» и «Обороты за период»). Для каждой:

1. **Платёж клиента** (`Payment`, `isRefund=false`): `col[1]` начинается с `Поступление` **И** corr `col[7]` начинается с `62` (62.01 постоплата / 62.02 аванс — оба). Сумма из `col[5]`.
2. **Возврат клиенту** (`Payment`, `isRefund=true`): `col[1]` начинается с `Списание` **И** corr `col[7]` начинается с `62`. Сумма из `col[8]`. (В образце таких нет, но логику реализуем — влияет на базу комиссии, §9.2.)
3. **Исключить** (`excluded` + счётчик по причине): всё прочее — оплаты поставщикам (corr `60`), комиссии/услуги банка (corr `91…`), внутренние переводы по тексту `col[1]` («Перевод собственных средств», «Внутреннее перемещение», «Перевод между своими счетами»).

|---|---|---|

| Сумма | `col[5]` (приход) / `col[8]` (возврат); толерантный парс к пробелам/запятым | `Payment.amount` |
| Номер документа 1С | строка 1 `col[1]` (`0000-001471`) | `Payment.externalId` — **ключ идемпотентности** |
| № платёжного поручения | тот же номер документа / «вх.д. N» из назначения | `Payment.paymentOrderNumber` |

| Кандидаты № счёта | назначение + строка 2 `col[3]` (запасной источник). Набор паттернов: `по счету № 260110-2805`, `СОГЛАСНО СЧЕТА 260509-1905`, `по сч № 260424РД`, `по счету № 251221А-6`, `счет № 260125-2605`, короткие `№ 26654`. Извлекать **все** кандидаты. | матчинг → заказ |

## Матчинг (matcher.ts) — точное авто, fuzzy в очередь

Порядок поиска для каждой `payment`/`refund`-строки:

1. **№ счёта** (любой из кандидатов) → `Order.orderNumber`/`externalId` → его `organizationId`. Приоритетный, точный → **авто-привязка** (`Payment` с `orderId`+`organizationId`).
2. **ИНН** контрагента → `Organization.inn`. Точный → **авто-привязка** (`Payment` org-level, `orderId=null`).
3. **Fuzzy-имя** → `Organization.name` (нормализованное сравнение; `Organization` несёт только `name`, без `legalName`) → **в очередь** `PaymentImportRow(status='needs_review', candidateOrgId, matchMethod='name_fuzzy')`. Не авто.
4. **Ничего** → в очередь `PaymentImportRow(status='needs_review', matchMethod='none')`.

> `Organization.inn` уже `@unique` (подтверждено схемой). Точный матч по ИНН безопасен. Нормализация имени: upper-case, схлопывание пробелов, унификация орг-форм (ООО/ИП и т.п.) — порог fuzzy лочится на образце.

## RBAC + scope (§4 defense-in-depth)

Три точки, как у существующего импорта:

1. **Middleware:** `/manager/payments-import` под `manager_cabinet`; `/admin/payments-import` под admin-гардом.
2. **Page/route:** `requireManager` / `requireRole('admin')`.
3. **Сервис:** точные авто-матчи проходят `orgInScope` существующего writer'а (менеджер = `managedOrgIds`, руководитель/админ = шире). Очередь `PaymentImportRow` стампится `companyId = session.companyId` импортёра; менеджер/руководитель видят очередь **своей компании**, админ — всю (Model A).

> **Тонкость C8 (write-scope ≠ read-visibility):** write-scope импорта = фактическое закрепление (`managedOrgIds`), не company-wide read-режим `managerTeamVisibility` — иначе при `teamMode=ON` рядовой менеджер перезаписал бы данные всей компании. Импорт никогда не пишет `OrganizationManager`.

## Хранение файла и журналирование (ТЗ §7.2)

- **S3:** исходный файл сохраняется в bucket `documents` под prefix `payments-import/<batchId>/<fileName>`; ключ → `PaymentImportBatch.fileKey`. Best-effort: сбой сохранения логируется, но не валит уже применённый импорт (degrade gracefully, §3).
- **SyncLog:** запись на каждый запуск — `entity='payment'`, `direction='inbound'`, `operation='import'`, `status`, `payload` = счётчики (создано/в очередь/исключено/ошибки). (Используем существующие значения direction проекта — `inbound`, не `in`.)
- **AuditLog:** `action='payment_import.commit'`, actor, имя файла, счётчики.

## Идемпотентность

- Дедуп `Payment` строго по `externalId` (= номер документа 1С) — существующий writer. Повторный импорт того же файла **не создаёт дубликатов** и не меняет подтверждённые вручную привязки.
- Дедуп очереди по `PaymentImportRow.externalId @unique`. Повторный импорт: если документ уже стал `Payment` (резолвнут) — пропускаем; если ещё `needs_review` — обновляем распарсенные поля, не плодим строку; `resolved`/`dismissed` не реанимируем.

## Обработка ошибок (§3, degrade gracefully)

- Нераспарсиваемая строка (нет суммы/даты) → помечается ошибкой в сводке (row + reason), **не валит весь файл**, остальные продолжают.
- `excluded`-строки → отдельный счётчик по причинам (не ошибки).
- Битый/нечитаемый файл / нет колонок карточки → `parse_failed`/`invalid_file`, транзакция не стартует.
- Пустой файл / нет строк-операций → `empty`.
- S3-сохранение / SyncLog → best-effort (логируем, не блокируем).
- **Атомарность:** commit в одной `$transaction` — частичный сбой откатывает импорт (всё-или-ничего), кроме явно excluded/ошибочных строк.

## UI

- **Загрузка** (`src/components/import/payment-import-form.tsx`): `<input accept=".xls,.xlsx">`, server-action → `previewPaymentImport` → сводка (платежи/возвраты к импорту, в очередь, исключено по причинам, ошибки) → подтверждение → `commitPaymentImport`. Переиспользует паттерны существующей `import-form.tsx` (preview→commit, ReasonsTable).
- **Очередь разбора** (`/admin/payments-import` + `/manager/payments-import`, раздел «Очередь»): список `PaymentImportRow(status='needs_review')` с распарсенными полями + кандидатами; действия: подтвердить привязку к org/order (→ промоушн в `Payment` через writer), исправить привязку, отклонить (`dismissed`). Промоушн идемпотентен (externalId).

## Тест-стратегия (§6, TDD)

- **Unit (без Postgres):**
  - Парсер на зафиксированных реальных строках: поступление 62.01 → платёж, сумма 14800, externalId `0000-001471`, счёт `260509-1905`, НДС 704.75, контрагент «ХОЛДИНГ ГЕФЕСТ ООО»; поступление 62.02 (аванс) → платёж; списание corr 60 / комиссия банка / «Перевод собственных средств» → excluded; синтетическое списание + corr 62 → возврат (`isRefund=true`); «НДС не облагается» → `vatAmount=0`.
  - Extractors: толерантный парс суммы, наборы паттернов № счёта (все кандидаты), НДС (сумма/ставка/«не облагается»), ИНН рядом с «ИНН».
  - Reader: `.xls` и `.xlsx` дают одинаковый `string[][]` на эквивалентных образцах.
  - Matcher (мок-Prisma): счёт→order, ИНН→org, fuzzy→очередь+кандидат, ничего→очередь.
- **Integration (живой PG, §6 L2.5/L3):** полный commit (точные→Payment, неточные→очередь); идемпотентность (повторный импорт = 0 новых Payment, 0 новых строк очереди); промоушн строки очереди → Payment (по externalId, без дубля); cross-scope инвариант (менеджер не пишет чужую орг даже при `teamMode=ON`); S3-сохранение и SyncLog-запись.
- **Manual перед merge:** реальный образец `.xls` → превью → commit на staging, сверка витрин + очереди.

## Не входит (YAGNI / отдельно)

- Изменение расчёта комиссии (§9.2) — только поставляем корректные `Payment` (сумма, дата, НДС, `isRefund`), на которых комиссия уже считается.
- Доходы из расчётного счёта по оплатам поставщикам/банку (corr 60/91) — исключаются по дизайну.
- Авто-расписание / подхват папки / webhook → ручная загрузка.
- Боевой REST-адаптер 1С (Трек A) → отдельный трек.
- Мультилистовой импорт (Контрагенты/Реализации/Поступления) → существующая фича, не трогаем.

## Открытые пункты (к началу реализации, не к спеке)

1. **Реальный образец `.xls`** лочит: точные индексы строк шапки/итогов (если в конкретной выгрузке сдвинуты), полный набор паттернов № счёта, порог fuzzy-нормализации имени. Парсер устойчив к мелким сдвигам (срез по маркерам «Сальдо на начало»/«Обороты за период», а не по фиксированным номерам строк).
2. **Порог fuzzy-матча** имени — настраиваемая константа, дефолт консервативный (лучше лишний раз в очередь, чем ошибочная авто-привязка — но мы и так fuzzy не авто-применяем).
3. **Подтверждение бухгалтерии** про `.xlsx`-выгрузку (заметка владельцу) — снимает зависимость от SheetJS, но поддержку `.xls` оставляем как страховку.

## Заметка владельцу (вне агента)
