## 1. Зачем

Это ответ на исходную жалобу: «организации не добавились». Главная причина
(П-1 ТЗ) — `pullOrganizations()` файлового адаптера **намеренно возвращает
пустой список**: лист «Контрагенты» честно парсится и молча выбрасывается.
Этапы 1–4 подготовили всё, чтобы включение прошло без 100% пропусков:
диагностика видна, файл распознаётся, партнёр необязателен.

## 2. Что в объёме (Т-15…Т-18, Т-21…Т-24)

| Требование | Суть |
|---|---|
| **Т-15** | `pullOrganizations()` возвращает DTO из уже парсящегося листа «Контрагенты»: `externalId`, `name`, `inn`, `kpp`, `partnerExternalId` |
| **Т-16** | Ключ синтезируется из ИНН: `synthOrgExternalId(inn) = '1c-inn:<ИНН>'` — одна экспортируемая функция (решение владельца №3); строка без ИНН ключа не получает |
| **Т-17** | Порядок батчей: **организации → заказы → оплаты** — заказ из того же файла находит свою организацию в live-режиме |
| **Т-18** | `ImportReport` = `{ orgs, orders, payments }`, в форме — карточка «Организации» |
| **Т-21** | Валидация ИНН: 10/12 цифр + контрольная сумма; невалидный → `invalid: 'bad_inn'`, батч продолжается |
| **Т-22** | Нормализация ИНН: пробелы, число из Excel → строка, ведущие нули (расширяется `oneCSync/inn.ts` этапа 4 — точка правды одна) |
| **Т-23** | Идемпотентность: повторная загрузка → `создано: 0, обновлено: N`, без P2002 |
| **Т-24** | Режим `shadow` не пишет **ничего** — включая backfill `externalId` в `resolveOrganizationRef` (сейчас там `update` без проверки режима — подтверждено разведкой) |

**Вне объёма:** привязка к компании — ветка создания в writer'е пока минтит
`Company` (дефект §0.2, этап 6, Т-41…Т-44); права руководителя (этап 7 — до
этапа 6 руководитель получает `out_of_scope` на создании, это ожидаемо и
описано в Т-26а); откат (этапы 8–9).

## 3. Разведка по коду (факт на `main` 1ebb0661)

- `adapter-file.ts` — `pullOrganizations()` действительно `return []`; лист
  `orgs` парсится и не используется (П-1).
- `resolve-org.ts` — backfill `externalId` выполняет `db.organization.update`
  **без проверки режима**: предпросмотр сегодня может писать в базу (Т-24
  подтверждён).
- `record-batch.ts`/`resilience.ts` — `invalids` заполняются из **Zod-ошибок**:
  текст первой issue становится `issue`, `externalId` берётся из сырой строки.
  Это готовый канал для `no_inn`/`bad_inn` без правки механики батча.
- `ORG_COLS` (этап 3) — `name`, `inn`, `partnerInn`; **колонки КПП нет**, хотя
  Т-15 требует поле `kpp` (и `OneCOrgSchema.kpp` уже есть).
- `upsertOrgRecord` (этап 4) — партнёр необязателен, ищется по ИНН/slug;
  найденной по ИНН организации **чужой `externalId` не перезаписывается** —
  ровно то, что просит Т-16 сохранить.

## 4. Решения

### 4.1. Валидация — файловой Zod-схемой, не общим writer'ом (Т-21, Т-16)

Сетевой `adapter-rest` шлёт организации через тот же `upsertOrgRecord`;
вшивать проверку контрольной суммы в writer значит менять поведение сетевого
обмена за рамками ТЗ. Вместо этого — **файловая схема**:

```ts
// oneCSync/schemas.ts
export const OneCOrgFileSchema = OneCOrgSchema.superRefine((org, ctx) => {
  if (!org.inn) ctx.addIssue({ message: 'no_inn', ... });
  else if (!isValidInn(org.inn)) ctx.addIssue({ message: 'bad_inn', ... });
});
```

`import/index.ts` гоняет батч организаций через неё — `parseRecords` сам
положит строку в таблицу ошибок с нужным кодом, батч продолжится (Т-21).
Сетевой путь остаётся на прежней `OneCOrgSchema`.

### 4.2. Строка без ИНН показывает наименование (Т-16)

Т-16: «в таблицу ошибок с наименованием контрагента, чтобы оператор завёл
вручную». У строки без ИНН синтетического ключа нет по определению — адаптер
заполняет `externalId` **наименованием контрагента**: до writer'а такая строка
не доходит (схема отрежет её с кодом `no_inn`), а в колонке идентификатора
таблицы ошибок оператор увидит имя, не прочерк.

### 4.3. `synthOrgExternalId` и рост `normalizeInn` (Т-16, Т-22)

В `oneCSync/inn.ts` (файл этапа 4):

```ts
export function normalizeInn(raw: string): string; // + число→строка уже строкой,
   // ведущие нули: длина < 10 → до 10 (юрлица); длина 11 → до 12 (физлица/ИП)
export function isValidInn(inn: string): boolean;  // 10/12 цифр + контрольная сумма
export function synthOrgExternalId(inn: string): string; // `1c-inn:${normalizeInn(inn)}`
```

Префикс `1c-inn:` отличает синтетический ключ от настоящего `externalId`
сетевого обмена (Т-16). Функция одна, её же будет использовать откат (этап 9).

### 4.4. `pullOrganizations` (Т-15)

`ORG_COLS` получает колонку `kpp: ['КПП']` (в тестовых книгах этапов 1–3 она
уже фигурировала как «нераспознанная»). Адаптер мапит строку листа в DTO:
`inn` нормализуется, `externalId = synthOrgExternalId(inn)` при валидном ИНН,
`partnerExternalId` — из «ИНН партнёра», `updatedAt = EPOCH` (как у
заказов/оплат: файл не несёт времени изменения).

### 4.5. Порядок и отчёт (Т-17, Т-18)

`run()` в `import/index.ts`: батч организаций — **первым** (orgs → orders →
payments), чтобы заказ из того же файла нашёл организацию в live. `ImportReport`
получает `orgs: BatchSummary`; проверка «файл пуст» считает все три. В форме —
карточка «Организации» и таблица причин, как у заказов и оплат.

### 4.6. `shadow` перестаёт писать (Т-24)

`resolveOrganizationRef` получает обязательный параметр `canWrite: boolean`;
оба вызова в writer'ах передают `isLive(ctx)`. Обязательный — чтобы ни один
будущий вызов не забыл решить. Backfill в shadow не выполняется, разрешение
организации работает как прежде.

### 4.7. Известное следствие, принятое порядком этапов

До этапа 6 ветка создания минтит `Company` на каждого нового контрагента
(§0.2) — включение импорта организаций делает этот дефект **видимым в
файловом пути**. Чинить его здесь нельзя (это Т-41 этапа 6, отдельный PR по
таблице §3 ТЗ); guardrail-тест «импорт не создаёт ни одной Company» (Т-44)
придёт там же. В integration-тестах этапа 5 уборка минтованных компаний — на
совести теста (как в тесте этапа 4).

## 7. Риски

Средний (по ТЗ). Главные: порядок батчей меняет `run()` — покрыт unit-тестом
на очерёдность; `canWrite` меняет сигнатуру `resolveOrganizationRef` — все
вызовы обновляются в одном PR, обязательность параметра не даст забыть; минт
`Company` в файловом пути (§4.7) — осознан, закрывается этапом 6.
