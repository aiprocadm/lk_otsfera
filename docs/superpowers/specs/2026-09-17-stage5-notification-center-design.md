# Этап 5 «Центр уведомлений» — дизайн

**Программа:** «CRM для отдела продаж — замена Битрикс24» (ТЗ 12.09.2026), этап 5 из 11.
**Требования:** `У-228`…`У-233` (6 шт.), приоритет MVP, кроме `У-230` — «Важно».
**Файл пакета:** [09_notifications.md](../../specs/09_notifications.md). **Оценка ТЗ:** 3 дня.
**База:** зависимостей нет (§5 индекса: этап независим). Этапы 1–4 закрыты.
**Сверка кода (§16):** 17.09.2026 против `main` `90422eba`.

## 0. Коротко

Уведомления в проекте **доставляются хорошо и читаются плохо**. Есть реестр из
40 типов с русскими подписями, четыре канала (кабинет, почта, Telegram, MAX,
WhatsApp), правила компании «событие × роль × канал», редактируемые шаблоны
писем, очередь доставки с защитой от повторов. И при этом:

1. **Читать негде.** Единственное окно — выпадающий колокольчик с последними
   пятьюдесятью. Страницы `/…/notifications` нет ни в одном из шести кабинетов
   (`У-228`).
2. **Настроить «что и куда» нельзя.** Человек может выключить Telegram целиком,
   но не «Telegram — только про оплаты» (`У-229`).
3. **Одинаковое сыплется поштучно.** Пять правок одного заказа за час — пять
   уведомлений (`У-231`).
4. **Заказчик получает по письму на событие.** Дайджеста нет (`У-230`).
5. **Руководителя уводят в чужой кабинет.** Все ссылки сотрудникам собраны как
   `/manager/…`, хотя у руководителя есть свои `/leader/orders/[id]` и
   `/leader/tasks/[id]` (`У-232`).

Пять PR. Схема БД меняется **аддитивно и обратимо**: одна новая модель
(`UserNotificationPreference`), три колонки у `Notification`, три у `User`.
Механизм доставки не переписывается — в него врезаются две проверки в одной
точке (`dispatchToRecipient`) и одна точка создания записи (`recordNotification`).

Главная работа этапа — не экраны, а **единственная точка создания
уведомления**: сейчас запись в `Notification` делают 27 вызовов в 20 файлах.
Без одной точки ни дедупликация, ни счётчик «×N», ни ссылки по ролям не
держатся — они разъедутся при первом новом продьюсере. Поэтому PR-3 сводит все
27 в один `recordNotification` и ставит стража, который не даст им расползтись
обратно (§3.5).

## 2. Модели

Все изменения аддитивные; ни одна колонка не удаляется, ни один тип не
переименовывается.

### 2.1. `Notification` — три колонки

| Поле | Тип | Зачем |
|---|---|---|
| `entityId` | `String?` | Ключ дедупликации вместе с `userId` и `type`. Продьюсер задаёт явно (`orderId`, `taskId`, `dialogId`, …); без него дедупа нет — это честнее, чем угадывать по `meta` |
| `dedupCount` | `Int @default(1)` | «×N» на экране |
| `lastOccurredAt` | `DateTime?` | Время последнего повтора; сортировка ленты — по нему, а не по `createdAt`, иначе задублированное уведомление тонет |

Индекс `@@index([userId, type, entityId, createdAt])` — поиск кандидата на
дедуп идёт ровно по этим полям.

### 2.2. `UserNotificationPreference` — новая модель

```
userId     String
eventType  String        // ключ реестра
channels   String[]      // ВКЛЮЧЁННЫЕ маршрутизируемые каналы: email | telegram | max | whatsapp
updatedAt  DateTime @updatedAt
@@unique([userId, eventType])
```

Хранятся **только отклонения** — тот же принцип, что у `NotificationRule`:
нет строки = «как решила компания». Пустая таблица ничего не меняет.
«В кабинете» в `channels` не хранится и не выключается (`У-229`; техническая
причина — запись в кабинете служит ключом защиты от повторов, см. `routing.ts`).

### 2.3. `User` — три колонки для дайджеста

`digestEnabled Boolean @default(false)`, `digestHourMsk Int @default(9)`,
`digestLastSentAt DateTime?`. Отдельная модель не нужна: это три поля одного
пользователя без истории.

### 2.4. Реестр типов — три поля

`icon: string` (обязательно; значок из семантического реестра значков, `У-5`…`У-9`),
`urgent?: true` (уходит письмом сразу, в дайджест не попадает),
`noDedup?: true` (каждое событие — отдельная строка). Срочные по пакету:
`document_published`, `invoice_paid`, `messenger_message`,
`client_request_status_changed`. Без дедупа: `messenger_message`,
`chat_message`.

### 2.5. Очередь и расписание

`notifications.digest` — ежечасно `0 * * * *` по Москве, `editable: true`
(правка из интерфейса, как у обмена с 1С и SLA). Час отправки — у каждого
пользователя свой, поэтому воркер ходит ежечасно и выбирает тех, у кого
`digestHourMsk` совпал с текущим часом.

## 3. Ключевые решения

### 3.1. `Р-Э5-1` — страница одна, кабинетов шесть, у слушателя она пустая

Один презентационный компонент `notifications-screen.tsx` (`Р-23`: общий
экран допустим, если данные и права даёт сервис роли), шесть серверных
страниц. Пункт меню `notifications` с `pinnedBottom: true` — над «Настройками»;
у слушателя «Настроек» нет, пункт встаёт над «Справкой». Значок `🔔`, подпись
«Уведомления» — из реестров `sectionLabels.ts`/`icons.ts`, зеркальные пары
(`staff`, `clients`) не нарушаются, исключений в `mirrorExceptions.ts` не
требуется.

У слушателя страница **всегда пустая**: ни один тип реестра ему не адресован.
Она нужна ради правила зеркала §0.2 («шесть кабинетов») и говорит честно:
«Пока ничего не произошло — здесь появятся события по вашим заказам и
обращениям» (текст из пакета). Фильтра по типам у него нет — нечего
показывать. `requireRole` в `api/notifications*` расширяется на `student`
(матрица `security.role-access-matrix` правится в том же PR).

### 3.2. `Р-Э5-2` — администратор видит только своё

Скоуп `{}` для администратора остаётся от времён паритета, когда лента была
служебной. Для личной страницы с кнопкой «Отметить все прочитанными» он
означает «пометить прочитанным чужое». Model A (§4 CLAUDE.md) — это
управление платформой через зеркало `/admin/*`, а не чтение чужих личных
уведомлений. Скоуп администратора становится `{ userId: session.sub }`;
остальные ветки (`organizationId`, `partnerId`, `meta.orderId` у сотрудников)
не трогаем — они про «уведомления моей организации / моих заказов» и
пережили два аудита. Тест `api.notifications.test.ts` «admin receives empty
scope» переписывается (§5.3).

### 3.3. `Р-Э5-3` — «Отметить все» бьёт по скоупу, а не по списку

`PATCH /api/notifications` с `{ all: true }` → `updateMany` по скоупу сессии
плюс `isRead: false`. Без выгрузки идентификаторов на клиент: нынешний предел
в 100 `ids` ровно для того и стоял, чтобы пометка не выходила из-под
контроля. Фильтры страницы (`unread`, `type`) на «все» не влияют — иначе
человек, стоя на фильтре «Задачи», думал бы, что пометил всё.

### 3.4. `Р-Э5-4` — личная настройка только сужает, и проверяется на сервере

`effective = routed ∩ preference(eventType)` — пересечение в **одной** точке,
`dispatchToRecipient`, до развилки inline/очередь. Получатель приезжает с
`notificationPreferences` в `CHANNEL_RECIPIENT_SELECT` — ноль лишних запросов
на рассылку. Нет строки настройки → `effective = routed`.

Гард на сервере, а не только в форме: сервис `savePreferences` сверяет
запрошенные каналы с правилом компании и отвергает включение запрещённого
кодом `channel_disabled_by_company` (§4, defense-in-depth). В матрице такой
канал показан серым с подсказкой «отключено вашей компанией». Каналы, не
привязанные пользователем (нет `telegramChatId` и т. п.), в матрице не
показываются — включать нечего.

### 3.5. `Р-Э5-5` — одна точка создания уведомления, дедуп живёт в ней

`recordNotification(prisma, input)` в `lib/notifications/core.ts` заменяет
все 27 прямых вызовов. Правило: если для `(userId, type, entityId)` есть строка
с `lastOccurredAt ?? createdAt` не старше 60 минут — `dedupCount += 1`,
`lastOccurredAt = now`, `isRead = false`, `title`/`body` обновляются на
свежие; возвращается `{ row, deduped: true }`, и продьюсер **не** дёргает
каналы — письмо и мессенджер не дублируются, как требует `У-231`. Иначе —
новая строка, `deduped: false`, каналы как прежде.

Исключения: `messenger_message`, `chat_message` (каждое сообщение важно) и
типы с `noDedup` в реестре. Без `entityId` дедупа нет.

Страж `notifications.single-create-point`: в `src/**` (кроме `core.ts` и
тестов) нет `notification.create(` — читается через `readSource`, чтобы
закомментированный вызов не считался живым. Без этого стража следующий
продьюсер обойдёт дедуп, и никто не заметит.

Известный предел, записанный честно: два события в одну миллисекунду проходят
проверку одновременно и дают две строки. Окно — защита от шума, а не
транзакционная гарантия; уникальный индекс здесь невозможен (третье событие
через час обязано создать новую строку).

### 3.6. `Р-Э5-6` — дайджест: не «отложить письмо», а «вычесть канал и собрать»

Держать письма в очереди сутки — значит хранить их содержимое где-то ещё и
рисковать потерять. Вместо этого: у пользователя с `digestEnabled` канал
`email` **вычитается** из веера в `dispatchToRecipient` для несрочных типов.
Запись в кабинете остаётся — она и есть содержимое дайджеста. Ежечасный
воркер выбирает пользователей, у кого `digestHourMsk` совпал с текущим
московским часом и `digestLastSentAt` старше 20 часов, **атомарно занимает**
их (`updateMany … where digestLastSentAt < порог` → `count === 0` → пропуск;
канон claim из `У-225`), собирает `Notification` за окно с прошлой отправки
(или 24 ч), **исключая срочные типы** (они уже ушли письмом), и шлёт одно
письмо `dailyDigest`. Пусто — не шлёт, `digestLastSentAt` всё равно
сдвигается (иначе завтра соберётся двое суток).

Срочные типы — флаг `urgent` в реестре, список из пакета дословно.
Дайджест — только `organization`/`partner` (пакет §3): галочка видна им, сервис
отвергает включение у прочих ролей. Шаблон `dailyDigest` — в реестре писем с
подстановками `recipient.name`, `period`, `count`, `items`; правится в
«Шаблонах писем» (`У-128`).

### 3.7. `Р-Э5-7` — ссылка считается от роли получателя, а не хранится с кабинетом

Новый `lib/notifications/routes.ts`: `notificationRoute(type, meta, role) →
path | null` — таблица «тип × роль → маршрут» по идентификаторам из `meta`
(`orderId`, `taskId`, `dialogId`, `documentId`, `leadId`, `dealId`,
`requestId`, `enrollmentId`, `contactId`, `noteId`). `notificationHref`
становится обёрткой над таблицей; `meta.url` остаётся **запасным** путём для
типов заказчика/партнёра (они уже пишут свой кабинет) и для внешних ссылок.

Продьюсеры сотрудников перестают писать `url` с кабинетом — пишут
идентификаторы; письмо получает `url` через `notificationRoute(type, meta,
recipient.role)` для каждого получателя (в `CHANNEL_RECIPIENT_SELECT`
добавляется `role`). Руководитель получает `/leader/orders/[id]` и
`/leader/tasks/[id]`; менеджер — `/manager/…`; администратор — `/admin/…`.
Для типов без объекта (`sync_error`, `ops_alert`) — путь в раздел кабинета
(`/admin/settings/system/health`), либо `null` только для роли, у которой
такого раздела нет — и такие пары перечислены в тесте явно.

Удалённый объект (пакет §9): ссылка ведёт на список раздела с параметром
`?missing=1`, страница показывает «объект недоступен» — не 404.

### 3.8. `Р-Э5-8` — флаг `notification_center`, поведенческий

Под флагом только НОВОЕ этапа: страница и пункт меню, ссылка «Показать все»
в колокольчике, матрица личных настроек, дайджест. Дедуп, единая точка
создания и маршруты по ролям — исправления существующего поведения, они
работают без флага (как задачи в этапе 4). Точки чтения: страницы
(`notFound()`), `cabinet.ts` (`flag`), server actions настроек, воркер
дайджеста (пропуск при выключенном), колокольчик (ссылка). Флаг выключен до
приёмки, включается из `/admin/settings/system/feature-flags`.

### 3.9. `Р-Э5-9` — два расхождения пакета с кодом, записанные, а не «поправленные»

1. Пакет §4: «флаги `urgent`, `noDedup`, `audiences` уже есть» — есть только
   `audience`. Флаги заводятся этим этапом (§2.4).
2. Пакет §5: у `Notification` есть `entity`, `entityId`, `readAt` — нет; есть
   `isRead` и `meta`. `entityId` заводится этим этапом, `readAt` не нужен:
   «когда прочитали» никто не спрашивал, а `isRead` держит индекс счётчика.

Требования выполняются по смыслу; пакет не правится (`Р-Б-10`: при
расхождении индекса с пакетом верен пакет — но здесь расходится пакет с

## 7. Вопросы заказчику

Ни один не блокирует этап; умолчания действуют, пока решения нет.

**`В-5-1`. Администратор видит только свои уведомления, а не всех.** Сейчас
видит все. **Умолчание: сужаем** (`Р-Э5-2`) — иначе «Отметить все» у
администратора помечает чужое.

**`В-5-2`. Дайджест — только заказчику и партнёру** (как в пакете); сотрудникам
не предлагаем. **Умолчание: как в пакете.** Добавить сотрудникам — одна
строка в проверке роли.

**`В-5-3`. Час дайджеста по умолчанию — 09:00 по Москве.** Человек меняет в
личных настройках. **Умолчание: 9.**

**`В-5-4`. Руководителю — ссылки в `/leader/…`.** Отменяет решение ТЗ
2026-08-17 «те же ссылки, что менеджеру». **Умолчание: действующее ТЗ
побеждает** (`У-232`, CLAUDE.md §14, ловушка 4).

**`В-5-5`. У слушателя страница есть, но всегда пустая.** Ни один тип ему не
адресован. **Умолчание: есть** — ради правила зеркала «шесть кабинетов»; убрать
— одна строка в реестре меню и запись в исключениях зеркала.
