## 1. Зачем

Строка банковской выписки с ИНН контрагента, которого нет в базе, попадает в
очередь ручного разбора — и сейчас оператору некуда её деть: организацию надо
заводить в другом экране руками и возвращаться. Т-30 добавляет кнопку «Создать
организацию и привязать» прямо в очереди. Автосоздание при этом остаётся
запрещённым (решение №5) и закрепляется тестом-стражем (Т-30а).

## 2. Что в объёме

| Требование | Суть |
|---|---|
| **Т-30** | Кнопка в `payment-queue-table.tsx` у строк с `counterpartyInn`: диалог с предзаполненными ИНН и наименованием (редактируемые), только по подтверждению создаётся `Organization` и платёж привязывается |
| **Т-30а** | Автосоздание запрещено: `matcher.ts` ветка `exact` требует существующую организацию, новый ИНН → `queue`. Тест-страж: «строка с новым ИНН → route `queue`, в БД 0 новых организаций» |
| **Т-31** (опция) | Подтяжка наименования/КПП/адреса по ИНН через существующий DaData-прокси; поля редактируемые, сохранение — только по кнопке |

**Вне объёма:** изменение матчера (он уже корректен — Т-30а только закрепляет),
права остальных кнопок очереди (staff, §8.2 спеки этапа 7).

## 3. Разведка по коду (факт на `main` a3257cf9)

- `matcher.ts` уже ведёт себя по Т-30а: `exact` по ИНН — только если
  организация **найдена в БД** (`if (org?.inn)`), иначе `route: 'queue'` —
  нужен только тест-страж с проверкой `organization.count()`.
- Привязка платежа из очереди уже есть: `resolveQueueRow` (гейт staff,
  company-скоуп строки по `row.batch.companyId`, платёж пишется через
  штатный writer). Новый сервис **композирует** его, а не дублирует.
- `PaymentImportBatch.companyId` может быть `null` (старые/админские батчи) —
  компанию новой организации надо решать по правилам этапа 6 (Т-41).
- DaData: сервис `suggestParty` + staff-прокси `/api/suggest/party` уже есть
  (этап 5 v1.0) — Т-31 не требует нового бэкенда.
- В реестре аудита уже есть `organization_created_manual` («ручное создание
  организации») — новое действие не нужно.
- `isValidInn`/`normalizeInn` — из `oneCSync/inn.ts` (этап 5).

## 4. Решения

### 4.1. Сервис `createOrgFromQueueRow` (Т-30)

`src/lib/services/import/oneCAccountCard/create-org.ts`:

```ts
createOrgFromQueueRow(prisma, session, {
  rowId, name, inn, kpp?, companyId?  // companyId — только для admin
}) → { ok: true; organizationId; paymentId } | { ok: false; error }
```

- **Права — `mayImportOneC`** (admin и руководитель): создание организации —
  импортная операция по духу решения №2; обычный менеджер страницу очереди и
  так не видит с этапа 7, сервис держит серверную границу.
- Строка: `needs_review` + company-скоуп строки (как в `resolveQueueRow`).
- ИНН: `normalizeInn` + `isValidInn` → иначе `bad_inn`. Организация с таким
  ИНН уже существует → `org_exists` (диалог подскажет «используйте
  „Привязать“») — молча привязывать к найденной не станем: оператор должен
  видеть, к чему привязывает.
- **Компания новой организации — правила Т-41**: руководитель → своя компания
  из скоупа (параметр игнорируется); admin → выбор в диалоге (селект как в
  Excel-форме, prefill компанией батча), не выбрана → `company_required`.
- `externalId` у новой организации **не ставится** (null): ключ `1c-inn:<ИНН>`
  принадлежит файловому импорту — при первой же загрузке Excel существующий
  backfill сам допишет ключ найденной по ИНН организации (логика этапа 5).
- После создания — **вызов `resolveQueueRow`** тем же сервисным путём: платёж
  пишется штатным writer'ом, строка очереди закрывается. Если привязка упала
  (гонка), организация уже создана — оператор жмёт штатную «Привязать»;
  сервис вернёт `bind_failed` с id организации (честно, без транзакции на два
  разнородных шага).
- Аудит: `organization_created_manual` с `after: { source: 'payment_queue',
  rowId, inn }` — существующее действие, реестр не трогаем.

### 4.2. UI (Т-30, Т-31)

В `payment-queue-table.tsx` у строки с `counterpartyInn` — вторая кнопка
**«Создать организацию»** (рядом с «Привязать»). Диалог (примитив `Dialog`):

- поля «Наименование» (prefill `counterpartyName`), «ИНН» (prefill
  `counterpartyInn`), «КПП» (пусто) — все редактируемые;
- admin дополнительно видит селект «Компания» (prefill компанией батча);
  страница передаёт список компаний так же, как Excel-форма;
- **Т-31**: кнопка «Подтянуть по ИНН» — запрос в существующий
  `/api/suggest/party` (DaData) с ИНН; ответ заполняет наименование/КПП,
  поля остаются редактируемыми; DaData не настроена/не нашла → тихая
  подсказка, ручной ввод работает как раньше;
- «Создать и привязать» → server action → успех: toast + refresh; ошибки —
  русским текстом в диалоге (`bad_inn`, `org_exists`, `company_required`,
  `bind_failed`, …).

### 4.3. Тест-страж автосоздания (Т-30а)

`import.no-autocreate-org.guardrail`: строка выписки с валидным, но
несуществующим ИНН → `matchPayment` даёт `route: 'queue'`, и
`organization.count()` до/после разбора равны. Живой Postgres — уровень
integration (через `commitPaymentImport`), плюс unit на матчер.

## 7. Риски

Низкий (по ТЗ). Создание — по явной кнопке с подтверждением; компания — по
проверенным правилам Т-41; привязка — через существующий проверенный путь
`resolveQueueRow`; автосоздание закрывается стражем.

## 8. Решения, требующие «ок» заказчика

Встроены в спеку, отдельного ответа не требуют — «ок» подтверждает:

1. **Права кнопки — `mayImportOneC`** (admin + руководитель), как у импорта
   (решение №2 по духу; Т-30 прав не оговаривает).
2. **Существующий ИНН → `org_exists`**, а не молчаливая привязка к найденной
   организации — оператор привязывает осознанно штатной кнопкой.
3. **Создание и привязка — два шага без общей транзакции**: упавшая привязка
   оставляет созданную организацию и честный `bind_failed` (штатная
   «Привязать» доводит дело), вместо отката созданного.
4. `externalId` новой организации пуст — ключ `1c-inn:` допишет первый же
   файловый импорт (существующий backfill этапа 5).
