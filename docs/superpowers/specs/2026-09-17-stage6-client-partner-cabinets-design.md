Программа — [ТЗ «CRM для отдела продаж — замена Битрикс24»](../../tz/2026-09-12-tz-crm-bitrix-replacement.md)
от 12.09.2026; пакет требований — [05_client_cabinet.md](../../specs/05_client_cabinet.md)

**Требования:** `У-234`…`У-241` (8 шт.), приоритет MVP, `У-234` и `У-236` — «Важно».
**Порядковые ограничения §5:** `У-212` (сервер канала `cabinet`, этап 3) до `У-234` —

## 0. Коротко

Кабинеты заказчика и партнёра уже покрывают ядро; этап закрывает то, ради чего
клиент всё ещё звонит менеджеру: **ответ на обращение** (`У-238`), **счета со
статусом оплаты** (`У-235`), **переписка в кабинете** (`У-234`), **кто мой
менеджер** (`У-240`), **с чего начать** (`У-239`), плюс два требования про
данные: **участник видит только свои заказы** (`У-236`) и **материалы для
партнёров** (`У-237`). `У-241` — зеркало, мобильные эталоны и стражи этапа.

Сверка кода (§16) показала, что **ни одно из семи содержательных требований не
реализовано** — есть только серверный канал `cabinet` из этапа 3, и у него
обнаружились две дыры, которые этап закрывает раньше остального (§1.1).

Пять PR: ответ на обращение + «Ваш менеджер» → счета + «Первые шаги» →
материалы для партнёров → переписка с менеджером + видимость `member` →
зеркало, стражи мутацией, эталоны, close-out.

## 1. Что показала сверка кода (§16)

### 1.1. Переписка с менеджером: сервер есть, экрана нет, заметки не защищены

- Канал `cabinet` — в реестре каналов диалога ([channels.ts](../../../src/lib/services/messengers/channels.ts));
  вопрос из кабинета (`submitCabinetQuestion`,
  [cabinetQuestion.ts](../../../src/lib/services/inbound/cabinetQuestion.ts)) идёт
  через общий приём `ingestInboundMessage` → `appendInboundToDialog` с
  `peerRef = userId`; ответ менеджера доставляется `deliverToCabinet`
  ([cabinet.ts](../../../src/lib/services/messengers/cabinet.ts)) уведомлением
  `inbound_reply` в кабинет и в привязанный бот.
- **Экрана диалогов у клиента нет**: `/organization/messages` и
  `/partner/messages` — это командный чат по заказам (`OrderThread`) под флагом
  `chat`; никакого `api/organization/messages` не существует. Клиент видит
  ответ только как строку уведомления и не может ответить на него.
- **Заметки сотрудников не защищены выборкой.** Единственный сервис чтения
  диалога — сотрудничий ([get.ts](../../../src/lib/services/messengers/get.ts)),
  он отдаёт `direction: 'note'`. Страж
  `messengers.note-not-leaked` требует, чтобы любой запрос `messengerMessage.*`
  в клиентских каталогах нёс `direction` внутри вызова, — клиентских запросов
  пока нет, поэтому он ничего не охраняет. Этап заводит их правильно с первого
  раза.
- Реестр помечает `inbound_reply` аудиторией `staff`, хотя получают его клиенты
  (записано в close-out этапа 5): у клиента по таблице маршрутов нет ссылки.
  Этап исправляет аудиторию и маршрут.

### 1.2. Счета: признак оплаты есть, раздела нет

`/organization/finance` показывает только KPI и платежи
([finance/page.tsx](../../../src/app/organization/finance/page.tsx)); блока «Счета»
нет, экспорт (`paymentsExport.ts`) счетов не содержит. Признак оплаты счёта
**уже вычисляется** — `invoicePaymentState`
([invoicePayment.ts](../../../src/lib/documents/invoicePayment.ts)): по платежам
заказа с привязкой «платёж → счёт» через назначение платежа (`У-148`),
состояния `unpaid | partially_paid | paid` — его и переиспользуем, а не
заводим второй расчёт.

### 1.3. `member` ничем не ограничен

`canSeeOrder` в [organizationPolicy.ts](../../../src/lib/auth/organizationPolicy.ts)
проверяет только членство в организации; `listOrgOrders` фильтрует по
`organizationId`. Роль `roleInOrg` — строка `admin | leader | member`, настройки
«участники видят только свои» нет. У заказа нет поля «инициатор»: есть
`Order.primaryContactId → Contact`, а у контакта — `Contact.userId` (этап 1); связь
«обращение → заказ» — через лид (`ClientRequest.convertedLead ↔
Order.promotedFromLead`).

### 1.4. Материалов для партнёров нет вовсе

Ни модели, ни раздела, ни пункта меню. Есть всё, из чего это собирается:
хранение с антивирусом (`upload-core.ts`, свой `kind` в очереди
`docs.scanDocument`, образец — брендинг компании
[companyBranding.ts](../../../src/lib/services/admin/companyBranding.ts)), реестр
разделов хаба ([settings.ts](../../../src/lib/navigation/settings.ts)), реестр
исключений зеркала ([mirrorExceptions.ts](../../../src/lib/navigation/mirrorExceptions.ts)),
presigned-скачивание только для `clean`.

### 1.5. Обращение: ответа нет

`ClientRequest` — только `status`, `rejectedReason`; сервисов ответа нет
([triage.ts](../../../src/lib/services/clientRequests/triage.ts) — взять, конвертировать,
отклонить). Карточка у заказчика и партнёра — один компонент
`client-request-detail-view.tsx`, показывает только причину отказа. Письмо
`client_request_status_changed` содержит статус и причину.

### 1.6. «Первые шаги» и «Ваш менеджер»: нет

Одноразовый welcome-блок когда-то был и **удалён** (комментарий в
[quickTasks.ts](../../../src/lib/quickTasks.ts)); полей «скрыть навсегда» нигде нет.
Активных менеджеров у организации — **множество** (`OrganizationManager`, без
признака «главный»); у партнёра ответственного менеджера нет; контакты
менеджера клиенту сейчас не отдаёт никто.

### 1.7. Зеркало главных страниц уже держится

Главные заказчика и партнёра состоят из пяти одинаковых блоков в одном
порядке; страж зеркала читает реестр меню, а не картинку. Новые блоки
вставляются в обе страницы на одну позицию.

## 2. Модели

Все изменения аддитивные; ни одна колонка не удаляется.

### 2.1. `ClientRequest` — ответ сотрудника (`У-238`)

`staffReply String?`, `staffRepliedAt DateTime?`, `staffRepliedById String?`
(→ `User`, `onDelete: SetNull`). Ответ не меняет статус; отказ по-прежнему
несёт `rejectedReason`, ответ — дополнительно.

### 2.2. `Partner.managerId` (`У-240`)

`managerId String?` → `User` (`onDelete: SetNull`), индекс. Правится в карточке
партнёра у администратора (`/admin/partners/[id]`; у руководителя карточки
партнёра нет — записанное исключение зеркала кабинетов ЦО, как и сейчас).

### 2.3. `Organization.membersSeeOwnOrdersOnly` (`У-236`)

`Boolean @default(false)`. Правит `roleInOrg = admin` на вкладке «Настройки»
карточки «Моя организация»; хранится на организации, а не на пользователе —
это правило компании-заказчика, а не личная настройка.

### 2.4. `OrganizationUser.onboardingDismissedAt`, `PartnerUser.onboardingDismissedAt` (`У-239`)

`DateTime?` — «Закрыть навсегда». Выполненность пунктов **не хранится**,
считается по данным при каждом показе.

### 2.5. `PartnerMaterial` (`У-237`)

```
id, companyId → Company, title, description?, category (enum PartnerMaterialCategory:
price_list | presentation | template | instruction | other), documentId? → Document,
externalUrl?, isActive @default(true), publishedAt?, sortOrder @default(0),
replacesDocumentId?, updatedById → User, createdAt, updatedAt
@@index([companyId, isActive, publishedAt])
```

Файл **или** ссылка (проверка формы и сервиса: ровно одно из двух). Файл живёт
в `Document` (S3, антивирус — свой `kind: 'partner_material'` в очереди
проверки); публикация возможна только при `scanStatus = clean`. Замена файла
— новый `Document`, старый уходит в `replacesDocumentId` и у партнёра не
показывается.

### 2.6. Реестр уведомлений

- `partner_material_published` — новый тип, аудитория `partner`, значок, маршрут
  `/partner/materials`.
- `inbound_reply` — аудитория расширяется до `['staff', 'organization', 'partner']`;
  маршрут для клиентов — `/{organization,partner}/messages?tab=manager&dialog=<id>`.

## 3. Ключевые решения

### 3.1. `Р-Э6-1` — «Переписка с менеджером»: одна лента, писать — в диалог кабинета

Вкладка «Переписка с менеджером» в «Сообщениях» заказчика и партнёра показывает
**все диалоги, где `MessengerDialog.userId` = текущий пользователь** — канал
`cabinet` и мессенджеры/почта единой лентой, свежие сверху. Внутри диалога —
реплики `in`/`out`; **`note` не отдаётся никогда**: фильтр `direction: { in:
['in', 'out'] }` стоит внутри каждого запроса `messengerMessage` в клиентских
сервисах (страж `messengers.note-not-leaked` это проверяет по тексту,
интеграционный тест — по данным).

Писать из кабинета можно **в диалог кабинета** — он у пользователя один
(`channel = 'cabinet'`, `peerRef = userId`); сообщение идёт тем же путём, что
вопрос «Задать вопрос»: `ingestInboundMessage` → `appendInboundToDialog` →
`notifyManagersMessengerMessage`. Так менеджер видит его в том же диалоге, с тем
же ответственным и SLA. Диалоги других каналов (Telegram, MAX, WhatsApp, почта)
в кабинете **читаются**, а поле ответа ведёт в диалог кабинета с подсказкой
«ответить можно здесь или в Telegram» — отвечать в чужой канал из кабинета
нельзя (правило «первым в кабинет не пишут» и контракт исходящих файлов
`Р-Б-16` остаются).

Ответ сотрудника (`deliverToCabinet`) — как сейчас: уведомление в кабинет всегда,
в бот — если привязан; ссылка уведомления ведёт в диалог вкладки.

Кнопка «Задать вопрос» остаётся быстрым входом в тот же диалог.

Гейт: вкладка и пункт меню «Сообщения» у заказчика и партнёра — под
существующим флагом `cabinet_questions` (канал кабинета); вкладка «По заказам»
(командный чат) — по-прежнему под `chat`. Страница живёт, если включён хотя бы
один из двух; без обоих — `notFound()`, как сейчас. Новый флаг не заводится:
переписка — это экран над уже работающим каналом, а не новая функция.

### 3.2. `Р-Э6-2` — `member` видит заказ, если он его контакт или инициатор

При `Organization.membersSeeOwnOrdersOnly = true` пользователь с
`roleInOrg = member` видит заказ, если выполнено хотя бы одно:

1. `Order.primaryContact.userId = session.sub` (контакт заказа — он);
2. заказ рождён из обращения или заявки на обучение, которые он подал
   (`Order.promotedFromLead.clientRequest.submittedByUserId = session.sub`;
   `EnrollmentRequest.submittedByUserId = session.sub` с заказом по заявке).

`admin` и `leader` организации видят всё; при выключенной настройке — как
сейчас. Скоуп живёт в **одном** месте — `memberOrderScope(session, org)` в
`organizationPolicy.ts`, его зовут `listOrgOrders`, `getOrgOrder`, счётчики
главной и экспорт; `canSeeOrder` получает флаг организации и роль, а не только
`organizationId`. Чужой заказ — `?missing=1` (как после этапа 5), не отдельный
«403»: разница ответов выдала бы существование заказа. Страж
`security.org-member-scope` + интеграционный IDOR-тест.

Подсказка у роли `member` в «Доступе в кабинет» меняет текст в зависимости от
настройки (пакет 05 §11).

### 3.3. `Р-Э6-3` — материалы: издатель — компания, читатель — партнёр с её организациями

Партнёр видит материалы **компаний, у которых есть хотя бы одна его
организация** (`Organization.partnerId = partner AND companyId = company`);
пользователь партнёра с ролью `manager` — только компаний своих
`assignedOrgIds`. Материалы разных компаний подписаны издателем. Публикует
администратор или руководитель **своей** компании из хаба «Конфигурация
процессов → Материалы для партнёров» (раздел `catalogs.partnerMaterials`,
право `settings.catalogs.manage`, кабинеты `admin`/`leader`); загрузка — API-роут
(CLAUDE.md §11), не server action.

Скачивание партнёром — presigned URL только для `clean`; каждое скачивание —
аудит `partner_material_downloaded` (кто, что); в хабе у материала виден
счётчик и список «кто скачал». Уведомление `partner_material_published` — всем
пользователям партнёров-читателей по правилам компании, единой точкой
`recordNotification` (дедуп по материалу).

Раздел `/partner/materials` — пункт меню между «Портфель» и «Сообщения»;
исключение зеркала с причиной «материалы адресованы агентам; у заказчика
аналога нет». Пустое состояние — «Материалов пока нет» с объяснением, откуда
они появляются.

### 3.4. `Р-Э6-4` — ответ на обращение: отдельно от статуса, видим клиенту дословно

Сотрудник (`admin`/`leader`/`manager` в скоупе обращения) пишет ответ в
деталке обращения — вместе со сменой статуса или отдельно; сервис
`replyToClientRequest` пишет три поля и аудит. Клиент и партнёр видят блок
«Ответ менеджера» (текст, имя, дата) в карточке обращения; уведомление
`client_request_status_changed` расширяется текстом ответа (у шаблона —
подстановка `reply`). Ответ после `converted` допустим. Заявка с сайта без
пользователя (`submittedByUserId = null`) уведомления не получает — как сейчас.

### 3.5. `Р-Э6-5` — «Первые шаги» считаются по данным

Чек-лист заказчика: реквизиты заполнены (ИНН и адрес) → сотрудники добавлены
→ бот привязан (Telegram или MAX) → первое обращение или заявка. Партнёра:
реквизиты партнёра → первая организация в портфеле → бот привязан → команда
приглашена (только у `admin` партнёра). Каждый пункт — ссылка на экран.
Блок показывается, пока не выполнено всё и не нажато «Закрыть»; «Закрыть» —
`onboardingDismissedAt` на членстве (в организации / у партнёра), не на
`User`: один человек в двух организациях закрывает блок в каждой отдельно
(пакет 05 §14). Один презентационный компонент с view-моделью на оба
кабинета (`Р-23`).

### 3.6. `Р-Э6-6` — «Ваш менеджер»: имя и почта, без телефона

У заказчика — первый активный менеджер организации по `assignedAt` (плюс
«и ещё N» без контактов); у партнёра — `Partner.managerId`, иначе менеджер
первой организации портфеля. Показываются **имя и e-mail**; телефона у
сотрудника в модели нет (`Р-Б-17`), внутренний номер (`internalPhone`) —
служебный, клиенту не показывается. Кнопка «Написать» ведёт на вкладку
«Переписка с менеджером» (`У-234` в этом же этапе; до PR-4 — «Задать вопрос»).
Нет менеджера — «Менеджер назначается; напишите нам» с той же кнопкой.

### 3.7. `Р-Э6-7` — зеркало и эталоны

Новые блоки главных («Первые шаги», «Ваш менеджер») и карточек обращений —
один компонент с view-моделью на оба кабинета; «Материалы» — записанное
исключение зеркала; «Счета» — только у заказчика (партнёр оплаты и
задолженность клиента не видит, пакет 06 §12) — исключение записывается.
Мобильные эталоны 390×844 новых экранов снимаются в PR-5 на локальном dev с
сид-базой; если стенд не поднимется на этой машине — записывается честно
как хвост, а не подменяется.

### 3.8. Что этап не делает

ZIP документов и версии файлов (`У-251`, `У-252` — этап 8); ответ из кабинета
в чужой канал; телефон менеджера; ручная отметка оплаты счёта (только
1С/выписка, ADR-0004); материалы без файла и без ссылки.

## 5. Тестовая стратегия

### 5.1. Стражи этапа (каждый проверяется мутацией)

| Страж | Что держит | Мутация → красный |
|---|---|---|
| `security.org-member-scope` | при включённой настройке `member` не видит чужой заказ ни списком, ни карточкой, ни счётчиком; `admin`/`leader` видят всё; выключено — как раньше | снять условие роли / снять флаг из скоупа |
| `messengers.cabinet-notes-not-served` | клиентские сервисы диалогов несут `direction: { in: ['in','out'] }` в каждом запросе (страж по исходнику) + интеграционный тест на данных | убрать фильтр в одном запросе |
| `partner.materials-scope` | партнёр видит материалы только «своих» компаний; `manager` партнёра — только компаний `assignedOrgIds`; неопубликованные и заражённые не отдаются | снять фильтр компаний / отдать `pending` |
| `partner.materials-download-audited` | каждое скачивание пишет аудит; presigned только для `clean` | убрать `recordAudit` / отдать `infected` |
| `client-requests.reply-visible` | ответ виден клиенту и партнёру, письмо содержит текст; ответ не меняет статус | не класть `reply` в тело письма |
| `dashboard.first-steps` | пункт исчезает при выполнении по данным; «Закрыть» — на членстве, не на `User` | хранить выполненность |
| `navigation.mirror` (существующий) | «Материалы» и «Счета» — записанные исключения, остальное зеркально | убрать исключение |

### 5.2. Интеграционные тесты (живой Postgres)

- `security.org-member-scope.integration` — два `member`, `admin`, заказ с
  контактом, заказ из обращения: видимость при включённой и выключенной
  настройке; чужой заказ — `not_found`.
- `messengers.cabinet-dialogs.integration` — диалог кабинета с `in`/`out`/`note`:
  клиент получает две реплики из трёх; ответ из кабинета доходит менеджеру
  тем же диалогом.
- `partner.materials.integration` — две компании, партнёр с организацией одной
  из них: видит только её материалы; скачивание пишет аудит.

### 5.3. Понятность и мобильный экран (§15)

Каждый новый экран — заголовок, подзаголовок в одну строку, главное действие;
пустые состояния с объяснением и кнопкой; на 390×844 таблица счетов и
материалов превращается в карточки. Термины — в глоссарий: «Переписка с
менеджером», «Материалы для партнёров», «Ответ менеджера», «Первые шаги».

## 6. Риски

| Риск | Что делаем |
|---|---|
| Заметка сотрудника утечёт клиенту через новый экран | фильтр внутри каждого запроса + страж по тексту + интеграционный тест на данных; `lastMessagePreview` заметки уже не пишется (этап 3) |
| `member` увидит чужой заказ через счётчик, экспорт или ленту событий главной | скоуп в одном месте, все читатели заказов заказчика идут через него; IDOR-тест по списку, карточке, счётчику, экспорту |
| Материал опубликуют до проверки антивирусом | публикация — только при `clean`, страж; в хабе статус «проверяется» |
| Ответ из кабинета в диалог Telegram заведёт вторую переписку | из кабинета пишут только в диалог кабинета; менеджер видит оба диалога одного человека с одним `userId` |
| Контакты менеджера утекут дальше блока | отдаются только именем и e-mail в блоке главной; телефона нет в модели |
