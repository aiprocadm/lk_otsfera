# Спека: связь «заказ ↔ сделка» со стороны заказа

Дата: 2026-08-19 · Статус: **к реализации** (задача взята из «Задела на
будущее» [STATUS.md](../../tz/STATUS.md) по прямой просьбе заказчика 19.08.2026)

## 1. Задача

Заказчик: «сделай связь заказ и сделка».

## 2. Что уже есть (разведка по коду)

| Часть связи | Состояние |
|---|---|
| В базе | `Deal.orderId @unique` ↔ обратная ссылка `Order.wonDeal` — связь один-к-одному **есть** |
| Сделка → заказ | ✅ работает: в диалоге сделки на доске ссылка `/manager/orders/{orderId}` ([deal-dialog.tsx](../../../src/components/deals/deal-dialog.tsx)) |
| Заказ → сделка | ⚠️ только у менеджера и только хлебными крошками: `loadOrderDealChain` + `buildOrderBreadcrumbs` рисуют «Сделки → <название>», но **обе крошки ведут на общий список** `/manager/deals` |
| Заказ → сделка у руководителя и админа | ❌ нет ничего |
| `Order.wonDeal` | не читается в боевом коде **нигде** |

Вывод: миграция `Order.dealId` (как буквально предлагал §6 ТЗ v1.0) **не
нужна** — `Deal.orderId @unique` даёт ровно ту же связь 1:1, переворот
направления был бы миграцией ради формулировки. Недостающая половина — не
поле в базе, а **видимость связи со стороны заказа**.

## 3. Ключевое ограничение, найденное разведкой

Заказ появляется **при выигрыше** сделки, то есть интересная нам сделка почти
всегда `status = won`. На доске карточку такой сделки **нельзя открыть**:
`openEdit` в [deal-board.tsx](../../../src/components/deals/deal-board.tsx)
выходит на `card.status !== 'open'` (редактируются только открытые, завершённые
сервис отклоняет). Отдельной страницы сделки в природе нет.

**Следствие для дизайна:** ссылка «открыть сделку» вела бы в никуда — человек
попал бы на доску и искал карточку глазами. Поэтому блок на карточке заказа
делаем **самодостаточным**: он сам показывает, из чего вырос заказ, и не
требует перехода. Это же отвечает на вопрос §15 «где я и что здесь».

## 4. Решение

### 4.1. Сервис

`loadOrderDealChain` → переименовать в **`loadOrderDeal`**
([services/manager/orderDetail.ts](../../../src/lib/services/manager/orderDetail.ts))
и расширить селект полями для панели: `id`, `amount`, `status`, `wonAt`,
`stage.name`, `manager.name`. Один запрос обслуживает и крошки, и панель —
второй запрос на ту же страницу не добавляем (§13: узкие селекты).

**Изоляция компании (§4, C8):** заказ страница уже проверила политикой, но
связь 1:1 не доказывает совпадение компаний — данные могли разъехаться
импортом. Поэтому граница передаётся явно, типом-union:

```ts
export type OrderDealScope = { allCompanies: true } | { companyId: string };
```

Union, а не `string | null`, — по итогу собственной ошибки при реализации.
Первая версия принимала `companyId: string | null` и звалась
`session.companyId ?? null`; у сотрудника без компании это молча означало
«смотреть без границы», то есть деградацию в **«видно всё»** вместо «ничего» —
ровно наоборот к канону проекта (sentinel-ветки `managerPolicy` и
`chat/policy.ts`). С union «все компании» надо попросить словом, а кабинеты
сотрудников при пустой компании просто не читают сделку. Держится стражем и
проверено мутацией.

### 4.2. Компонент

`components/orders/order-deal-panel.tsx` — **строго презентационный**, принимает
domain-agnostic тип (§4 sibling-pattern это разрешает; ролевой логики внутри
нет). Показывает: название сделки, бейдж статуса (Выиграна / В работе /
Проиграна), стадию, сумму, ответственного, дату выигрыша и цепочку
происхождения — лид и исходное обращение. Заголовок блока — «Сделка» (термин
из [глоссария](../../glossary.md): переговоры со стадиями на канбане).

Пустого состояния у блока нет: **нет сделки — нет блока**. Заказ, заведённый
руками или пришедший из 1С, сделки не имеет, и пустая рамка «сделки нет» была
бы шумом на каждой такой карточке.

### 4.3. Где монтируем

| Кабинет | Решение |
|---|---|
| Менеджер `/manager/orders/[id]` | ✅ панель (данные уже читаются) |
| Руководитель `/leader/orders/[id]` | ✅ панель — та же `ManagerOrderDetailView`, сейчас чтения нет вовсе |
| Админ `/admin/orders/[id]` | ✅ панель — своя разметка страницы; доски сделок у админа нет, поэтому блок справочный, ссылок наружу не даёт |
| Заказчик `/organization/orders/[id]` | ❌ **намеренно нет.** Сделка — внутренняя кухня продаж (сумма переговоров, ответственный, причина проигрыша). Клиенту это не показываем |
| Партнёр | ❌ нет: `/partner/deals` — это его **заказы** (историческое имя адреса), модели `Deal` партнёр не касается |

Флаг `deals_pipeline` (opt-in) уважается: выключен — панель не читается и не
рендерится, как сейчас у крошек.

## 5. Тестовая стратегия

- unit сервиса: селект зовётся с фильтром компании; админ без фильтра; нет сделки → `null`;
- unit компонента: три статуса, отсутствие необязательных полей (сумма/стадия/ответственный/лид), экранирование;
- страницы: панель есть у менеджера/руководителя/админа при включённом флаге и исчезает при выключенном;
- **страж** `security.order-deal-visibility.guardrail`: панель не смонтирована в клиентских кабинетах (organization/partner). Проверяется мутацией (§16).

Покрытие новых файлов — 100 % (§6, гейт не понижаем).

## 6. Чего эта работа НЕ делает

- не добавляет `Order.dealId` и вообще не трогает схему и миграции;
- не делает страницу сделки и не учит доску открывать выигранные сделки — это отдельный объём, здесь не нужен;
- не меняет права, флаги и существующие крошки.
