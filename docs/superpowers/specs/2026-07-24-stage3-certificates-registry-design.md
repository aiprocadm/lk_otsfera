## 1. Цель и критерий приёмки (§9 ТЗ)

«Организация видит все свои удостоверения со сроками и скачивает скан ≤ 3 кликов
от дашборда; партнёр — по своим организациям; выгрузка в Excel работает».

Сейчас: удостоверения видят только сотрудники (карточка слушателя
`/manager/students/[id]`); у клиентов есть лишь точечные ссылки из деталки
заявки на обучение (этап 2). Реестров, фильтров, экспорта и дашборд-карточек нет.

## 2. Существующий задел в `main` (переиспользуем, не делаем заново)

- **Модель `Certificate`** — полная: student/organization/direction FK, `number`,
  `issuedAt`, `validUntil?`, `documentId?` (скан), `orderItemId?`, индексы по
  `organizationId`/`validUntil`/`directionId`. Миграций НЕ требуется.
- **`listCertificates`** (`src/lib/services/training/certificates.ts`) — уже
  скоупит все 4 роли (admin/manager/partner/organization) и пишет
  `PiiAccessEvent` context `certificates_list`. Расширяем аргументы, скоуп-ядро
  не трогаем (кроме одной правки — §5.2 про partner-manager).
- **Скачивание скана** — generic `POST /api/documents/[id]/download` (presigned,
  `canReadDocument`, антивирус-карантин → 410) + готовая кнопка
  `CertificateDownloadButton` (этап 2).
- **Экспорт-инфраструктура** — `commission/xlsx.ts`: exceljs, брендированная
  шапка, `safeText` против формула-инъекций, числовые форматы. Образец роутов —
  `api/partner/finance/statements/[id]/xlsx`.
- **Сроки/напоминания** — `training/expiry.ts` (пороги 90/60/30/7) +
  воркер-джоб `CertificateReminder`. Не трогаем; статусная модель реестра
  согласована с порогом 60 из ТЗ.
- **Компонент `CertificateList`** (карточка слушателя менеджера) — берём за
  основу клиентских таблиц.

## 3. Модель данных

Новая модель — только для метки «новый» у документов (ФТ-6.6):

```
model DocumentViewMark {
  id         String   @id @default(cuid())
  documentId String   // FK → Document (Cascade)
  userId     String   // FK → User (Cascade)
  viewedAt   DateTime @default(now())
  @@unique([documentId, userId])
}
```

`Certificate` не меняется. Данные не мигрируются.

## 4. Статусная модель реестра (ФТ-6.1)

Статус вычисляется на лету от `validUntil` (не хранится):

- **действует** — `validUntil` > сегодня + 60 дней, ИЛИ `validUntil = null`
  (бессрочное; в колонке срока — «бессрочно»);
- **истекает** — осталось ≤ 60 дней (порог из ТЗ), жёлтый бейдж;
- **истекло** — `validUntil` < сегодня, красный бейдж.

Отдельно от статуса: строка без скана (`documentId = null`) — пометка
«скан готовится» вместо кнопки скачивания.

## 5. Страницы и API

### 5.1 `/organization/certificates` (ФТ-6.1)

Реестр в `OrgAppShell`: сотрудник (ссылка на карточку §5.3), направление,
номер, выдано, действует до, статус-бейдж, «Скачать скан» /«скан готовится».
Фильтры: направление (селект из справочника), статус (действует/истекает/истекло);
поиск по ФИО; пагинация как на `/organization/students` (take/skip, лимиты 50/200).
`listCertificates` расширяется опциями `{ directionId?, status?, search?, take?, skip? }`
(фильтрация по статусу — в SQL через границы `validUntil`, не в JS).

### 5.2 `/partner/certificates` (ФТ-6.2)

Sibling-версия: + колонка и фильтр «Организация» (селект по организациям
партнёра). Скоуп — организации партнёра; **для partner-manager — с учётом
`assignedOrgIds`**: сейчас partner-ветка `scopeOrgIds` в `certificates.ts` берёт
все организации по `partnerId` и игнорирует `assignedOrgIds` — дополняем
(пересечение), это единственная правка существующего скоупа.

### 5.3 Карточка сотрудника `/organization/students/[id]` (ФТ-6.3)

По образцу `/manager/students/[id]`: шапка (ФИО, email, должность), блок
«Удостоверения» (та же строка, что в реестре), блок «История обучения» —
позиции заказов (`OrderItem` по `studentId`): заказ, направление,
`trainingStatus`, даты. Доступ — только своя организация (скоуп membership,
чужой id = notFound). Ссылки на карточку — из реестра §5.1 и из таблицы
`/organization/students`.

### 5.4 Дашборд-карточки (ФТ-6.4)

- Организация: 5-я карточка в `OrgKpiGrid` — «Истекают удостоверения: N»
  (≤ 60 дней, включая уже истёкшие? — нет: только истекающие; истёкшие видны
  фильтром) → `/organization/certificates?status=expiring`.
- Партнёр: аналогичная карточка в `KpiGrid` →
  `/partner/certificates?status=expiring`. Счётчики — в существующих
  `kpis()` дашборд-сервисов (одним `count`).

### 5.5 Экспорт в Excel (ФТ-6.5, ФТ-12.1, часть ФТ-12.2)

- Роуты: `GET /api/organization/certificates/export`,
  `GET /api/partner/certificates/export` (у партнёра + колонка «Организация»).
- Общий рендерер `src/lib/services/certificates/xlsx.ts` по образцу
  `commission/xlsx.ts` (шапка-бренд, `safeText`, автофильтр, frozen row).
- Правила ФТ-12.1: выгрузка строится **тем же `listCertificates`** с теми же
  фильтрами из query (RBAC не обходится); лимит 10 000 строк (при превышении —
  первые 10 000 + строка-предупреждение в файле); клиентские выгрузки
  собственных данных в `PiiAccessEvent` НЕ пишутся (журнал и так no-op для
  не-staff ролей — поведение фиксируется тестом).
- Остальные кнопки ФТ-12.2 (экспорты у сотрудников, платежи, сотрудники
  организации) — этап 9 («остаток Модуля 12»), в этот этап не входят.

### 5.6 Документы: «новый» и группировка (ФТ-6.6)

- В списках `/organization/documents` и `/partner/documents`: бейдж «новый» у
  документов без `DocumentViewMark` текущего пользователя; отметка о просмотре
  ставится при скачивании (кнопка «Скачать» уже есть) и при открытии деталки.
- Группировка по заказу: секции «Заказ №…» + «Без заказа» (сортировка внутри
  прежняя).
- Доставка `document_uploaded`: аудит цепочки «менеджер загрузил → клиент
  получил письмо с прямой ссылкой» — покрывается тестами (unit по
  upload-core → notify; в письме прямая ссылка на документ, не на список);
  найденные разрывы чинятся в этом же PR.

## 6. Feature-флаг и RBAC

- Новый opt-in флаг **`certificates_registry`** (default OFF, как
  `enrollment_requests`): гейтит обе страницы реестра, карточку сотрудника
  §5.3, KPI-карточки и экспорт-роуты (`notFoundIfDisabled`). Метка «новый» и
  группировка документов (§5.6) флагом не гейтятся (низкорисковый UI).
- Роли: organization (только свои организации-membership), partner
  (свои организации, partner-manager — `assignedOrgIds`). Сотрудники продолжают
  пользоваться существующей карточкой слушателя; staff-реестры в этот этап не
  входят.
- Скачивание — только через generic download-роут (`canReadDocument`);
  прямых presigned-ссылок в разметке нет.
- ПДн: просмотр реестра клиентом в `PiiAccessEvent` не пишется (не-staff),
  существующая запись `certificates_list` для staff остаётся как есть.
