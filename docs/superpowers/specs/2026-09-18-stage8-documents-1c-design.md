## 0. Коротко

Документы в системе выпускаются, нумеруются, подписываются и уезжают в 1С — но
как **файловый шкаф** раздел не доделан: у загруженного файла нельзя заменить
версию, нельзя скачать десять документов разом, в карточке организации с сотней
файлов нет ни группировки, ни поиска по номеру, и не видно, кто что скачивал.
Со стороны 1С не хватает двух вещей: контактов контрагента и сверки долгов.

Сверка кода (§16) показала: **семь требований этапа не реализованы**, но два из
них сделаны наполовину — и именно эта половина меняет проект. Подробности — §1.

Три PR: версии и журнал скачиваний → пакетное скачивание ZIP → группировка,
поиск, источник, контакты и сверка долгов из 1С, close-out.

## 1. Что показала сверка кода (§16)

Проверялось поведение, а не наличие файлов: где гард, где скоуп, что видит
человек в краевом случае.

### 1.1. Журнал скачиваний уже есть — и его нельзя заводить второй раз

Пакет предлагает завести событие аудита `document_downloaded`. В коде **уже
пишется** `document_download_signed_url` — во всех трёх роутах выдачи ссылки
([documents/[id]/download](../../../src/app/api/documents/%5Bid%5D/download/route.ts),
[manager](../../../src/app/api/manager/documents/%5Bid%5D/download/route.ts),
[organization](../../../src/app/api/organization/documents/%5Bid%5D/download/route.ts)),
заведено в `AUDIT_ACTIONS` и имеет русское название «Скачивание документа»
([labels.ts:83](../../../src/lib/audit/labels.ts)).

Завести рядом второе имя для того же факта — значит **разрезать журнал надвое**:
половина скачиваний под одним словом, половина под другим, и «кто скачивал»
покажет неполную правду. Поэтому (`Р-Э8-1`) переиспользуем существующее событие,
а не заводим новое.

**Чего в событии не хватает:** версии документа и роли читателя в разборном виде
(сейчас `after: { ttl, viewer: 'manager' }` — строка `viewer` есть только у двух
роутов из трёх). Это и есть работа `У-254` на стороне данных.

### 1.2. Источник документа вычисляется из того, что уже лежит в базе

Пакет предлагает новое поле `Document.uploadedByRole` с бэкфиллом по аудиту.
Сверка показала, что **все шесть источников различимы существующими полями**:

| Источник | Как отличить | Кто ставит |
|---|---|---|
| Из Битрикса | `bitrixId != null` | [bitrix/writers/files.ts](../../../src/lib/services/bitrix/writers/files.ts) |
| Из 1С | `externalId != null` | [oneCSync/writers.ts](../../../src/lib/services/oneCSync/writers.ts) |
| Выпущен в ЛК | `generatedBy = 'system'` без двух предыдущих | [documents/generate.ts](../../../src/lib/services/documents/generate.ts) |
| Загружен клиентом | `generatedBy = 'user'`, `uploadedBy.role = 'organization'` | роуты загрузки |
| Загружен партнёром | то же, `role = 'partner'` | роуты загрузки |
| Загружен сотрудником | то же, `role` из менеджерского контура или `admin` | роуты загрузки |

Поле `uploadedById` (FK на `User`) **уже есть** в модели. Новая колонка не нужна,
бэкфилл не нужен, миграции в этапе нет вовсе (`Р-Э8-2`).

**Оговорка записана честно:** роль читается у пользователя сейчас, а не на момент
загрузки. Внутри staff-контура это ничего не меняет — менеджер и руководитель
попадают в одно ведро «сотрудник». Переход клиента в сотрудники в продукте не
предусмотрен. Если такой переход когда-нибудь появится, денормализация роли в
момент загрузки станет оправданной — тогда и заводить.

### 1.3. Поиск по документам ищет не то, что обещает

[listDocuments](../../../src/lib/services/manager/documents.ts) принимает
`search` и ищет **только по имени файла**: `{ name: { contains } }`. Человек,
который вводит в поиск номер счёта, не находит ничего и делает вывод, что счёта
нет. Номер лежит в отдельном поле `number` и в поиск не входит.

Это расхождение с `У-253` («поиск по номеру и названию файла») — чинится этапом.

### 1.4. У списка документов нет общего числа

Тот же сервис возвращает `{ rows, nextCursor }` — постраничность курсорная, а
`total` нет. Человек не знает, сколько всего документов: «показано 50» без «из
340» читается как «их пятьдесят». `У-253` требует `total`.

**Отступление записано:** курсорную постраничность не меняем (она правильная для
больших списков и стоит на стабильном порядке — страж
`services.stable-pagination-order`). `total` считается **отдельным** `count` по
тому же `where` — это второй запрос, но он дешёвый и не ломает курсор.

### 1.5. Партнёр скачивает документы общим роутом — и это хорошо для ZIP

Своего роута скачивания у партнёра нет: он идёт в
`/api/documents/[id]/download`, а скоуп там держит **единая** функция
[getDocumentForSignedDownload](../../../src/lib/services/documents/download.ts),
которая зовёт `canReadDocument(session, doc)` по каждому документу.

Значит, ZIP (`У-252`) обязан собираться **через ту же проверку на каждый
документ**, а не через самописный `where` по ролям: второй набор правил доступа
разъедется с первым на первой же правке. Решение `Р-Э8-3`.

### 1.6. Готовые куски для части 1С

- `resolveContactByChannel.ts` с `normalizeChannelValue` — из этапа 1, готов для
  `У-256` (поиск контакта по нормализованному телефону/почте).
- `jszip` уже в зависимостях (используется пакетом для бухгалтера, `У-173`).
- Страж [docs.onec-contract-fields](../../../src/__tests__/docs.onec-contract-fields.guardrail.test.ts)
  сверяет контракт с кодом — новые поля схемы обязаны попасть в
  `docs/integrations/1c-contract.md` тем же PR, иначе гейт красный.

### 1.7. Что НЕ реализовано (подтверждено проверкой)

`У-251` — роуты загрузки не принимают `replacesDocumentId`; версии есть только у
генерируемых документов (перевыпуск `У-151`). `У-252` — общего ZIP нет.
`У-256` — в `OneCOrgSchema` нет поля `contacts`. `У-257` — очереди
`oneCSync.reconcileDebts` нет, кода сверки долгов нет.

## 2. Объём этапа и что в него НЕ входит

**Входит:** `У-251`, `У-252`, `У-253`, `У-254`, `У-256`, `У-257`, `У-258`.

**Не входит `У-255` (номенклатура ↔ каталог).** Пакет помечает его «Позже»:
требуется метод `GET /api/nomenclature` на стороне 1С, которого нет и о котором
ещё не договорились. Проектировать экран сопоставления под несуществующий ответ —
способ сделать работу дважды. В `AUDIT.md` требование остаётся `⏳`, в close-out
записывается явно.

## 3. Решения

- **`Р-Э8-1`. Журнал скачиваний строится на существующем событии**
  `document_download_signed_url`, а не на новом `document_downloaded`. Второе имя
  для того же факта разрезало бы журнал надвое (§1.1). Событие дополняется
  версией документа и ролью читателя в разборном виде; третий роут получает
  `viewer` наравне с двумя другими.
- **`Р-Э8-2`. Новой колонки под источник не заводим.** Шесть источников
  вычисляются из `bitrixId`, `externalId`, `generatedBy` и роли `uploadedBy`
  (§1.2). Миграции в этапе нет.
- **`Р-Э8-3`. ZIP проверяет каждый документ той же функцией, что и скачивание.**
  `canReadDocument` по каждому id; чужой id **молча пропускается** и считается в
  ответе «не включено: N» — без ответа «такого документа нет», чтобы не
  подтверждать существование чужого документа.
- **`Р-Э8-4`. Предел ZIP — отказ до сборки, а не усечение.** 50 файлов или
  500 МБ; проверяется по метаданным **до** скачивания из хранилища. Молча
  срезанный архив человек примет за полный — та же логика, что у предела отчётов
  (`Р-Э7-5`, этап 7).
- **`Р-Э8-5`. Версия загруженного файла — новая строка `Document`,** а не
  перезапись файла: `replacesDocumentId` на прежний, `version + 1`, прежний
  получает `supersededAt` и уходит из списков по умолчанию. Тот же механизм, что
  у перевыпуска (`У-151`) — второго способа «заменить документ» в системе не
  появляется.
- **`Р-Э8-6`. Сверка долгов ничего не правит.** `У-257` только показывает
  расхождение: ЛК не двигает суммы заказов по данным 1С и наоборот. Автоправка
  денег по внешнему источнику — это решение заказчика, а не фоновая задача.
- **`Р-Э8-7`. Контакты из 1С не затирают заполненное пустым** — то же правило,
  что у реквизитов организации (`У-171`). Конфликт канала с контактом ДРУГОЙ
  организации не пишется вовсе: строка `warn` в `SyncLog` со ссылкой на
  объединение контактов, импорт не падает.
- **`Р-Э8-8`. Общее число в списке — отдельный `count`,** курсорная
  постраничность сохраняется (§1.4).

## 4. Открытые вопросы заказчику (умолчания действуют)

- **`В-8-1`.** Предел ZIP 50 файлов / 500 МБ — умолчание из пакета. Если в
  практике архивы больше, число меняется одной строкой.
- **`В-8-2`.** «Кто скачивал» показывает последние 20 записей. Больше — по
  ссылке в журнал аудита.
- **`В-8-3`.** Порог расхождения дебиторки — 1 рубль (из пакета). Копеечные
  расхождения округления в отчёт не попадают.
- **`В-8-4`.** Частота сверки долгов — раз в сутки, расписание из интерфейса по
  механизму `У-125`. Умолчание — 04:00 МСК, когда 1С свободна.
- **`В-8-5`.** Группировка списка запоминается в сессии на человека, а не на
  компанию: это привычка конкретного сотрудника.
- **`В-8-6`.** Массовая отправка клиенту (`У-258`) шлёт **одно письмо на
  организацию** со списком документов, а не письмо на документ.

## 5. Версии загруженных файлов (`У-251`)

Кнопка «Загрузить новую версию» в карточке документа, у которого
`generatedBy = 'user'` (у генерируемых работает перевыпуск `У-151` — второй
кнопки там не появляется).

- Роуты загрузки принимают необязательный `replacesDocumentId`; сервис
  `documents/versions.ts` проверяет: документ существует, в скоупе роли, это
  **загруженный** документ, он ещё не заменён, тип и контрагент совпадают.
- Новая строка: `version = прежняя + 1`, `replacesDocumentId`, тот же тип,
  направление, контрагент, заказ. Прежняя получает `supersededAt = now()`.
- Клиент и партнёр видят только последнюю версию — списки уже фильтруют по
  `supersededAt = null`.
- Блок «История версий» в карточке у сотрудников: версия, дата, кто загрузил.
- Аудит `document_version_uploaded` (новое действие + русское название).
- **Краевой путь:** прежняя версия уже выгружена в 1С → в карточке пометка «в 1С
  ушла версия N» и кнопка «Выгрузить повторно» (механизм `У-169`); молча
  подменять выгруженный документ нельзя.

## 6. Пакетное скачивание (`У-252`)

`GET /api/documents/zip?ids=a,b,c` — все роли, скоуп по `canReadDocument`.

Порядок проверок (важен): разбор списка id → предел по числу **до** обращения к
хранилищу → по каждому id `canReadDocument` → отсев `scanStatus != 'clean'` →
суммарный размер по метаданным → сборка.

Ответ при отказе — 413 с русским текстом и числами: «выбрано 80 файлов, предел
50 — снимите лишние». Ответ при успехе — поток ZIP; имена внутри по правилу
`У-154`; дубль имени получает суффикс `(2)`.

В ответе-заголовке `X-Zip-Skipped` (или в теле отказа) — сколько документов не
вошло и почему: «не включено: 2» (чужие), «ожидает проверки: 1» (`pending`).
Чужой id не отличим от несуществующего — оба просто «не включено».

Аудит `documents_zip_downloaded` с перечнем id.

Кнопка «Скачать выбранные (ZIP)» + чекбоксы: экран «Документы» сотрудника,
вкладка карточки организации, карточка заказа, «Документы» заказчика,
«Документы» партнёра и вкладка организации в портфеле партнёра.

## 7. Группировка, поиск, источник (`У-253`, `У-258`)

`listDocuments` расширяется: `year`, `direction`, `status`, `source`, поиск по
**номеру И имени** (`OR`), `total` отдельным `count`.

Группировка «по типу» / «по году» / «по заказу» — переключатель над списком,
запоминается в сессии (`В-8-5`). Группировка считается на уже полученной
странице, а не отдельными запросами: иначе счётчики разъедутся с постраничностью.

Источник вычисляется функцией `documentSource(doc)` в `lib/documents/source.ts`
по правилам §1.2; у неё же русские названия шести источников — один словарь на
фильтр, колонку и подпись (правило зеркала §0.2).

Массовые действия на экране сотрудника: «Выгрузить в 1С» (есть), «Скачать ZIP»
(`У-252`), «Отправить клиенту» — по одному письму на организацию (`В-8-6`),
только для выпущенных документов, механизм `У-149`.

## 8. Контакты контрагента из 1С (`У-256`)

`OneCOrgSchema` получает необязательное поле
`contacts: [{ name, position?, phone?, email? }]` — аддитивно, старые ответы 1С
остаются валидными.

`writers.ts` для каждого контакта: нормализует канал, ищет контакт организации
через `resolveContactByChannel`; нашёлся — дополняет пустые поля (пустое из 1С
не затирает заполненное, `Р-Э8-7`); не нашёлся — создаёт; канал занят контактом
другой организации — **не пишет**, строка `warn` в `SyncLog` со ссылкой на
объединение контактов.

Повторный запуск не создаёт дублей — это и есть критерий приёмки.

Контракт `docs/integrations/1c-contract.md` §1 дополняется полем; фикстуры
`mock-1c` — контактами; страж `docs.onec-contract-fields` обязан остаться
зелёным. Клиенту контакты не видны (они во внутреннем контуре).

## 9. Сверка дебиторки (`У-257`)

Метод контракта `GET /api/debts?since=` (ИНН контрагента, `externalId` заказа,
сумма долга на дату) — **с пометкой «ожидает реализации на стороне 1С»**.
Очередь `oneCSync.reconcileDebts`, расписание из интерфейса (`У-125`), умолчание
04:00 МСК (`В-8-4`).

Сравнение: долг в ЛК (`totalAmount − paidAmount`) против суммы из 1С по
`externalId` заказа. Расхождение больше 1 ₽ (`В-8-3`) → строка в отчёт
«Расхождения по дебиторке»: вкладка «История» → канал «Дебиторка», выгрузка XLSX,
кнопка «Повторить сверку». Алерт по порогу — механизм `У-126`.

**ЛК ничего не правит** (`Р-Э8-6`). Новый код ошибки `debt_mismatch` + русская
строка.

**Краевой путь:** метод в 1С не реализован → экран показывает «метод не
подключён», а не ошибку; задача не падает и не копит DLQ.

| Кто | Версии | ZIP | Кто скачивал | Источник | Сверка долгов |
|---|---|---|---|---|---|
| Админ | да | да | да | да | да |
| Руководитель | да | своя компания | да | да | своя компания, чтение |
| Менеджер | да | свой скоуп | да | да | нет |
| Заказчик | свои загруженные | свои | **нет** | **нет** | нет |
| Партнёр | свои загруженные | свои | **нет** | **нет** | нет |

## 11. Стражи этапа

- `security.documents-zip-scope` — партнёр не получает документ чужой
  организации; чужой id не раскрывается; `infected` и `pending` не попадают в
  архив. Мутации: снять `canReadDocument` из цикла; вернуть отсев по `where`
  вместо проверки на документ; впустить `pending`.
- `documents.version-chain` — новая версия не создаётся у генерируемого
  документа; прежняя получает `supersededAt`; клиенту видна только последняя.
  Мутация: убрать `supersededAt` у прежней.
- `documents.source-complete` — шесть источников различимы и у каждого русское
  название; новый источник без названия роняет тест.
- `audit.download-single-action` — **нет второго действия** для скачивания:
  в коде не появилось `document_downloaded` рядом с
  `document_download_signed_url`. Мутация: завести второе имя → красный.
- `docs.onec-contract-fields` (существующий) — поле `contacts` описано в
  контракте.

Каждый страж проверяется мутацией: сломать → тест красный → вернуть файл из
копии (не `git checkout`).

## 12. Производительность

- ZIP собирается потоком, без временного файла; предел 500 МБ проверяется по
  метаданным до чтения.
- `total` — отдельный `count` по тому же `where`; на списке документов индексы
  есть (`@@index([companyId])`, `[orderId, type]`).
- Аудит на каждое скачивание увеличивает `AuditLog` — индексы под фильтры уже
  заведены (трек F, хотфикс №17). Новых запросов в цикле нет; блок «Кто
  скачивал» — один `findMany` с `take: 20`.

## 13. Разбивка по PR

| PR | Что | Требования |
|---|---|---|
| **PR-1** | Версии загруженных файлов (`replacesDocumentId` в роутах, сервис, история в карточке, аудит); журнал скачиваний на существующем событии (версия + роль, третий роут), блок «Кто скачивал» | `У-251`, `У-254` |

## 14. Критерии приёмки этапа

- [ ] Новая версия загруженного файла скрывает старую у клиента, показывает
      историю сотруднику, пишет аудит; у генерируемого документа кнопки нет.
- [ ] ZIP собирается только из документов скоупа и только `clean`; предел — отказ
      с числами; чужой id не раскрывается; имена человеческие.
- [ ] Поиск находит документ **по номеру**; в списке есть общее число.
- [ ] Шесть источников различаются без новой колонки; у каждого русское название.
- [ ] «Кто скачивал» показывает скачивания клиента и сотрудника; клиент блока не
      видит; второго действия аудита в коде нет.
- [ ] Контакты из фикстуры 1С появляются у организации, повтор не дублирует,
      пустое не затирает, конфликт — предупреждение, а не падение.
- [ ] Сверка находит искусственное расхождение, показывает в истории и XLSX,
      данные заказов не изменены; без метода в 1С — «метод не подключён».
- [ ] Восемь гейтов зелёные; стражи проверены мутацией; `У-255` остаётся `⏳` с
      записанной причиной.
