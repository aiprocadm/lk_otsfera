# Спека: загрузка документов партнёра и организации через API-роут

**Дата:** 2026-08-17 · **Источник объёма:** задача из «Задела на будущее»
(STATUS.md, строка «Загрузка документов режется общим пределом тела запроса»),
взята по явному выбору заказчика 17.08.2026. Требования `У-N` под неё нет —
это точечная починка молчаливого дефекта, зафиксированного разведкой ещё
05.08.2026.

## 1. Проблема

Партнёр и организация загружают документы через **server actions**, а на все
server actions действует общий предел тела запроса
`bodySizeLimit: '25mb'` ([next.config.mjs:66-72](../../../next.config.mjs)).
Файл больше 25 МБ Next отбрасывает **до входа в action**: форма не получает
результата и молчит — ни ошибки, ни успеха. При этом:

- приложение обещает **200 МБ** (`DOCUMENT_MAX_FILE_SIZE_MB`, дефолт в
  [lib/config/upload.ts:2](../../../src/lib/config/upload.ts));
- формы организации честно пишут «Максимум 200 МБ» (недостижимо);
- форма партнёра и обе формы менеджера пишут «Максимум 20 МБ» — третья цифра,
  не совпадающая ни с чем (хардкод).

У менеджера транспорт уже правильный: **API-роут**
([api/manager/documents/[id]/upload/route.ts](../../../src/app/api/manager/documents/%5Bid%5D/upload/route.ts)),
на который лимит server actions не действует; честные 200 МБ проверяет сервис
(`validateUploadFile` в
[services/documents/upload-core.ts:30](../../../src/lib/services/documents/upload-core.ts)).

Поднимать общий `bodySizeLimit` до 200 МБ нельзя: он синхронизирован с
`IMPORT_MAX_FILE_MB = 25` (связку держит тест `lib.config.import-limits`) и
действует на **все** действия форм приложения.

## 2. Решение (подтверждено заказчиком при выборе задачи)

Перевести загрузку документов партнёра и организации на API-роуты по образцу
менеджера. **Сервисный слой не меняется** — `createPartnerDocument` и
`createOrganizationDocument` готовы; меняется только транспорт.

### 2.1 Два новых роута

| Роут | Гард | Флаг | Поля формы |
|---|---|---|---|
| `POST /api/partner/documents/upload` | `requirePartner()` (redirect-стиль, как у менеджера) | нет (флага партнёрского кабинета не существует) | `file`, `orderId` (обязателен), `docType` |
| `POST /api/organization/documents/upload` | `requireOrganization()` | `notFoundIfDisabled('organization_cabinet')` | `file`, `organizationId` (обязателен), `orderId` (опционален — без него order-less ветка), `docType` |

Разбор формы — общие помощники `readMultipart`/`formFields`/`readFile` из
[lib/api/multipart.ts](../../../src/lib/api/multipart.ts). `withAuth` не
используется намеренно: он принимает только JSON-тело и Result-гарды
([lib/api/README.md](../../../src/lib/api/README.md) предписывает файловым
роутам ровно этот набор помощников).

Маппинг кодов сервиса → HTTP (как у эталона): `forbidden→403`,
`not_found→404`, `too_large→413`, `invalid_mime→415`, `storage→500`;
кривая форма/нет файла → `400` (`validation`/`no_file`). Успех —
`201 { ok: true, documentId }`. `organizationId` проверяется сервисом по
членству в БД — роут прав не расширяет.

### 2.2 Три формы переходят на `useFetchSubmit`

`partner-document-upload-form`, `organization-document-upload-form`,
`organization-order-less-upload-form` меняют `useFormAction(action)` на
`useFetchSubmit({ url, body: () => FormData })` — ровно как
`manager-doc-upload-form`. Контракт ошибок тот же (`ActionResult`), тексты —
из `errors/messages.ts`, все нужные коды уже переведены.

Плюс два пре-чека до отправки (паттерн `guardedAction` менеджерской формы +
пре-чек размера из `import-form.tsx`):

- файл не выбран → «Файл не выбран.» без похода на сервер;
- файл больше лимита → сразу понятная ошибка, без заливки сотен мегабайт.

`revalidatePath` из server actions заменяется уже используемым
`refresh: true` (обновление данных страницы после успеха).

### 2.3 Честные подсказки о размере

Все документные формы показывают цифру из константы
`DEFAULT_MAX_FILE_SIZE_MB`, хардкоды «20 МБ» удаляются:
`partner-document-upload-form` (:56), `manager-doc-upload-form` (:84),
`manager-order-less-upload-form` (:107), плюс устаревший JSDoc «413 — file
exceeds 20 MB» в manager-роуте. Формы организации уже используют константу.

**Тест-страж** (новый): в `src/components/**` файл с file-input не может
содержать литерал вида «Максимум/до N МБ» с захардкоженной цифрой — цифра
обязана приходить из константы. Страж проверяется мутацией (§16).

### 2.4 Старые server actions удаляются

`server-actions/partner/documents.ts` и
`server-actions/organization/documents.ts` вместе с их тестами — иначе knip
уронит сборку на мёртвых экспортах. Других потребителей нет (проверено grep).

## 3. Что НЕ входит

- Изменения сервисов и `upload-core` — не нужны.
- Поднятие `bodySizeLimit` — запрещено (общий предел, связка с импортом).
- Перевод прочих server actions на роуты — только документы.
- Редизайн форм организации (сырые кнопки вместо примитивов `ui/`) — не
  трогаем, объём не расширяем.
- Перегенерация e2e-эталонов — все 38 устарели ещё с этапов 4–9, решение за
  заказчиком (смена «20 МБ»→«200 МБ» попадёт в ту же перегенерацию).

## 4. Тестовая стратегия

- **Роуты** — по эталону `api.manager.documents.upload.test.ts` (mock-паттерн
  `vi.hoisted`): все ветки маппинга статусов, redirect чужой роли,
  не-multipart, нет файла, пустой `orderId`/`organizationId`, 404 по флагу
  `organization_cabinet`, order-less ветка. Покрытие 100 % (гейт).
- **Формы** — существующие компонентные тесты переписываются с мока server
  action на мок `fetch`; новые кейсы: оба пре-чека.
- **Страж хинтов** — п. 2.3, с проверкой мутацией.
- Интеграционные тесты сервисов не меняются (сервисы не тронуты).

## 5. Риски

- Стенд: nginx уже пропускает 200 МБ (`client_max_body_size 200m` в двух
  местах конфига) — после фикса путь свободен. На проде проверить то же
  значение (заметка заказчику в PR).
- Снапшоты e2e с текстом «20 МБ» перестанут совпадать — уже устаревшие,
  см. п. 3.
- `security.role-access-matrix.guardrail` не задет: новые предикаты в
  `guard.ts`/`managerPolicy.ts` не добавляются (гарды берутся готовые из
  `requireRole.ts`).
