# Spec — 100% покрытие кода тестами

**Дата:** 2026-06-15
**Статус:** дизайн на ревью
**Автор-агент:** brainstorming → writing-plans

## 1. Цель

Довести покрытие кода `src/**` тестами (Vitest) до **100%** по всем четырём метрикам v8
(statements / branches / functions / lines) для всего кода, **несущего логику**, и закрепить
это порогом-гейтом, чтобы покрытие не деградировало.

Решение пользователя (2026-06-15): «100% буквально на всём», с границей denominator =
«всё, где есть логика» (см. §3).

### Non-goals

- Не гоняемся за 100% на беслогичных фреймворк-шеллах Next и чистых барелях (см. §3 exclude).
- Не заменяем Playwright visual / e2e — UI-регрессии верстки остаются за ними; coverage-тесты
  на компоненты проверяют **поведение и ветки**, а не пиксели.
- Не меняем рантайм-код ради тестируемости без отдельного согласования (рефактор «под тест» —
  только если файл иначе непокрываем, и точечно).

## 3. Граница denominator (exclude)

Под 100% — **весь код с логикой**. В `coverage.exclude` уходит:

```
src/**/__tests__/**
src/**/*.test.{ts,tsx}
src/e2e/**                                    // Playwright, не исполняется Vitest
src/**/*.d.ts
src/**/{layout,loading,error,not-found,global-error,template}.tsx   // фреймворк-шеллы Next
```

Дополнительно:

- **Чистые барели ре-экспорта** (`index.ts`, состоящие только из `export … from`) — помечаются
  построчно `/* v8 ignore file */` с комментарием, а не глоб-исключением (чтобы не вычистить
  случайно барель с логикой). Барель, который импортирует хоть один тест, и так покрыт.
- **Конфиги и генерёнка** (`next.config.*`, `tailwind.config.*`, Prisma client) уже вне
  `include: src/**`, отдельного exclude не требуют.
- **Чисто типовые модули** (`type`/`interface`, 0 исполняемых строк) v8 рапортует как 100%/NA
  автоматически — exclude не нужен. `lib/jobs/types.ts` (0/36) проверить: если там zod/const —
  это логика, покрываем; если только типы — в исключение.

Любое точечное исключение строки/файла — только через `/* v8 ignore */` с комментарием-обоснованием
рядом, чтобы исключения были видимы в diff и ревью.

## 4. Программа работ (фазы)

### Фаза 0 — Фундамент ✅ (выполнено в этой сессии)

- `@vitest/coverage-v8` установлен, `vitest.config.ts` сконфигурирован.
- `scripts/coverage-by-layer.mjs` — агрегатор покрытия по слоям (карта дыр).
- Baseline снят (§2).
- **Осталось:** добавить npm-скрипты `test:coverage` (полный) и `test:coverage:unit`;
  применить exclude из §3; убрать `coverage-full-run.log` из git (gitignore).

### Фаза 1 — Хвост логики → 100% (высокая отдача)

Цель: 100% на `lib/**`, `worker/**`, `server-actions/**`, `app/api/**`, `middleware.ts`, `hooks/**`.

- Расширяем существующие тест-паттерны (см. CLAUDE.md §6: `vi.hoisted` + `vi.mock`, integration
  через живой Postgres). Никакой новой инфраструктуры.
- Приоритет по объёму: `leadAttachments.ts` (350), `worker/index.ts` (101), `partner/finance.ts`
  (82), `orgPageContext.ts` (59), затем ветки в `manager/*`, `enrollments`, `oneCSync/adapter`.
- `worker/index.ts` (bootstrap) — либо unit с моками очередей/процессоров, либо вынести логику
  регистрации в тестируемый модуль, оставив тонкий entrypoint в exclude (решить при планировании).
- Edge-/error-ветки сервисов добиваем там, где integration их не трогает (forbidden/not_found/
  too_large/invalid_mime и пр. из Result-контракта §3 CLAUDE.md).

### Фаза 2 — Компоненты → 100% (средняя отдача, основная масса)

Цель: 100% на `components/**` (~10k строк).

**Ключевое техническое решение (главный риск, §6):** как рендерить React под Vitest.
Сейчас `environment: 'node'`. Варианты:

- **renderToString (node)** — дёшево, без новых зависимостей, но только initial render;
  ветки по интерактиву (onClick/effect/состояние) недостижимы. Помнить gotcha: classic-JSX
  transform → каждый тест-файл с JSX обязан `import React` (см. memory `project-vitest-classic-jsx`).
- **jsdom + @testing-library/react** — полный интерактив (события, состояние, эффекты), новые
  devDeps + `environment: 'jsdom'` per-file (`// @vitest-environment jsdom`).

Рекомендация: **гибрид** — `renderToString` для презентационных, `jsdom`+`@testing-library/react`
для интерактивных (форм, чат, инсталлер). Точную раскладку утвердить в начале фазы 2 (отдельный
mini-design), т.к. это определяет объём.

Работа бьётся по доменам (sibling-паттерн CLAUDE.md §4): partner / admin / manager / organization /
chat / enrollment / auth / documents / dashboard / import / leader / pwa-installer.

### Фаза 3 — `app/*` страницы → 100% (низкая отдача, дублирует e2e)

Цель: 100% на `app/**` (кроме шеллов из §3), ~7k строк серверных компонентов.

- Серверные компоненты = async-функции; тест вызывает их с замоканными `next/headers` (cookies),
  Prisma, `requireRole`/`getSession`, и проверяет возвращённый JSX-дерево/редиректы/`notFound()`.
- Бьётся по кабинетам: admin → partner → organization → manager → leader → student → auth.
- Самая дорогая и наименее ценная фаза (ветки в основном — права доступа и наличие данных, и они
  уже покрыты на уровне middleware/service). Делаем последней; кандидат на пересмотр объёма после
  фаз 1–2 (см. §7 открытый вопрос).

### Фаза 4 — Гейт 100%

- `coverage.thresholds = { lines: 100, branches: 100, functions: 100, statements: 100 }`.
- Включаем поэтапно (ratchet): после каждой фазы поднимаем порог по затронутым слоям через
  `coverage.thresholds['src/lib/**']` и т.п. (per-glob пороги), а не глобально сразу — иначе
  весь набор красный до самого конца.
- Встраиваем в pre-push / `npm run gate` (CLAUDE.md §6). Учесть: coverage-прогон требует
  integration (живой Postgres) для честной цифры по сервисам — гейт 100% не может быть unit-only.

## 5. Тестовая стратегия и качество

«100%» измеряет исполнение, не качество проверок. Чтобы не получить пустые тесты ради цифры:

- Каждый новый тест содержит осмысленный `expect` на результат/побочный эффект, не просто вызов.
- Для сервисов — проверяем оба исхода Result-контракта (`ok:true` data + каждый `error`-код).
- Для компонентов — проверяем условный рендер/ветки пропсов, а не факт «отрендерилось без ошибок».
- Ревью каждой фазы — `superpowers:requesting-code-review` + (для крупных) adversarial-проход.

## 6. Риски

1. **Фаза 2 — выбор рантайма рендера** (node/renderToString vs jsdom/testing-library) определяет
   объём и стоимость; недооценка = взрыв сроков. Митигируем mini-design в начале фазы 2.
2. **Интерактивные ветки компонентов** (эффекты, async-состояние) могут быть недостижимы без
   jsdom — часть строк потребует либо jsdom, либо обоснованного `/* v8 ignore */`.
3. **`worker/index.ts` и подобные bootstrap-файлы** плохо unit-тестируются; решение (тест vs
   вынос логики vs exclude) принимается пофайлово и фиксируется.
4. **Гейт 100% хрупок:** любая новая строка без теста валит push. Нужна культура «тест в том же
   PR» и понятное сообщение гейта.
5. **Стоимость прогона:** полный coverage-ран (unit+integration) ~23 мин на этом боксе. Гейт не
   может гонять его на каждый commit — только pre-push/manual, как уже устроено L2.5/L3.

## 7. Открытые вопросы

- **Фаза 3 объём:** оставляем буквальные 100% на `app/*`, или после фаз 1–2 пересматриваем и
  выносим тонкие страницы в exclude (как шеллы)? Решить по факту, когда останется только хвост.
- **Фаза 2 рантайм:** финализируется отдельным mini-design перед стартом фазы 2.
- **Гейт per-glob vs глобальный:** подтвердить, что Vitest v2 поддерживает per-path thresholds в
  нужной форме (проверить при реализации фазы 4).
