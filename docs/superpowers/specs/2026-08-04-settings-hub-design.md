# Хаб «Настройки» в кабинетах сотрудников + русификация аудита — дизайн

**Дата:** 2026-08-04
**Источник:** ТЗ заказчика «Консолидация служебных разделов в „Настройки“ (кабинет
администратора) + русификация журнала аудита», версия 1.0.
**Область:** только `/admin` и `/leader`. Клиентские кабинеты (organization,
partner, student) не затрагиваются.

---

## 1. Цель

Убрать из основной навигации администратора девять служебно-конфигурационных
разделов и собрать их под единым хабом `/admin/settings` с четырьмя группами.
Плюс — перевести журнал аудита полностью на русский (слой представления, без
миграций данных).

Бизнес-логика, схема БД и контракты API не меняются: страницы переезжают «как
есть».

**Расхождения зафиксированы** (требование ТЗ §9.1): три пути из таблицы ТЗ в
коде называются иначе (`order-statuses`, `pii-access`, `import`/`payments-import`),
маршрута `/admin/1c` нет вовсе.

### 2.2. Главное расхождение: `/admin/settings` уже занят

ТЗ исходит из того, что `/admin/settings` свободен. В коде это **работающая
страница личных настроек** администратора: привязка Telegram, каналы
уведомлений, коды восстановления 2FA, карточка безопасности (сессии), реквизиты
исполнителя (Company) и матрица feature-флагов. Аналогично занят
`/leader/settings`.

Решение (см. §4.1) — разложить её содержимое по группам хаба, ничего не потеряв.

### 2.3. Модель прав

`AccessProfile` (Prisma) = матрица охватов (`*Scope: ScopeLevel`) + `capabilities: String[]`.
Единый источник кодов — Zod-энум `capabilitySchema`
([src/lib/auth/accessProfileSchema.ts](../../../src/lib/auth/accessProfileSchema.ts)):
сегодня шесть кодов (`see_commission`, `import_1c`, `export`, `manage_catalog`,
`manage_users`, `assign_orders`). Профиль денормализуется в JWT при логине;
проверка — `can(session, capability)`
([src/lib/auth/accessProfile.ts](../../../src/lib/auth/accessProfile.ts)):
admin → всегда `true` (Model A), есть профиль → default-deny, нет профиля →
legacy-ветка.

### 2.4. Журнал аудита

- `AuditLog.action` и `AuditLog.entity` — **свободные строки**, не Prisma-enum.
  Тест полноты «по всем значениям enum» в формулировке ТЗ §6.4.2 буквально
  неисполним: enum'ов нет.
- `entity` типизирован TS-объединением `AuditEntity` (43 значения,
  [src/lib/auth/audit.ts](../../../src/lib/auth/audit.ts)) — но только на уровне
  типов, в рантайме списка нет.
- `action` не типизирован вообще: ~150 вызовов `recordAudit` с произвольными
  строковыми литералами.
- Уже существует частичный словарь
  [src/lib/i18n/auditActions.ts](../../../src/lib/i18n/auditActions.ts) — но он
  покрывает только ленту «Последние события» на дашборде (17 кодов) и даёт
  глагольные фразы («утвердил отчёт»), а не названия действий.
- Английское в UI аудита: заголовки колонок `Actor / Action / Entity / ID / Detail`,
  сырые значения `action` и `entity` в ячейках и в фильтрах, заголовок диалога
  `«<action> · <entity>»`, ключи полей в диффе «До/После».
- `meta.status` = `'success' | 'denied'` пишется всегда (`recordAudit`), в UI не
  показывается.

### 2.5. Прочее

- Навигация — статический канон `navByRole`
  ([src/lib/navigation/cabinet.ts](../../../src/lib/navigation/cabinet.ts)),
  группировка по полю `group` (`groupNavItems`). Пункт «Настройки» у админа уже
  есть (ведёт на личные настройки).
- Гейт маршрута — `middleware.ts` (`protectedPrefixes` + `FEATURE_PREFIXES`) +
  серверный гард на странице (`requireAdmin` / `requireManagerLeader`).
- `/forbidden` уже полностью на русском («Доступ запрещён», 403).
- Порог покрытия **100/100/100/100** на `src/app/**/*.tsx` и `src/components/**`
  (CLAUDE.md §6): каждая новая страница и каждый новый компонент обязаны прийти
  со своим тестом.

## 3. Архитектура решения

### 3.1. Единый реестр разделов — `src/lib/navigation/settings.ts`

Один источник правды, из которого выводится всё: карточки хаба, боковая
навигация, хлебные крошки, проверка прав, карта редиректов и тесты.

```ts
export type SettingsSection = {
  id: string;                 // 'integrations.sync'
  group: SettingsGroupId;     // 'integrations' | 'catalogs' | 'access' | 'security'
  title: string;              // «Синхронизация»
  description: string;        // одна строка для карточки
  icon: string;               // emoji, как в navByRole
  href: string;               // '/admin/settings/integrations/sync'
  leaderHref?: string;        // '/leader/settings/access/roles' — если раздел есть у руководителя
  capability: SettingsCapability;
  flag?: FeatureFlag;         // раздел скрыт при выключенном флаге (role_constructor)
  legacyHrefs: string[];      // старые пути → редиректы (['/admin/sync'])
};
```

### 3.2. Слой прав — `src/lib/auth/settingsAccess.ts`

Семь новых кодов добавляются в `capabilitySchema` (имена — из ТЗ §5.2 дословно):
`settings.integrations.view`, `settings.integrations.manage`,
`settings.catalogs.manage`, `settings.access.manage`, `settings.audit.view`,
`settings.personal_data.view`, `settings.system.view`.

Правило разрешения (`canAccessSettingsSection`):

1. `role === 'admin'` → **разрешено всегда** (Model A, тождественно `can()`).
2. Профиля нет (`accessProfileId = null`) → **legacy-поведение**: разрешено то,
   что роль могла раньше (руководителю — роли, доп-поля, статусы, личные
   разделы). Байт-в-байт как до изменений (критерий приёмки 5).
3. Профиль есть, но **ни одного** `settings.*`-кода в нём нет → тоже
   legacy-поведение («дедушкина оговорка»). Иначе включение новой модели прав
   молча отняло бы доступ у уже заведённых профилей — это и есть «наслоение без
   ломки legacy» из ТЗ §5.2.
4. Профиль есть и хотя бы один `settings.*`-код в нём объявлен → **default-deny**:
   нужен именно код этого раздела.

Проверка вызывается **на каждый запрос** в layout-е раздела (серверный слой), а
не только скрытием карточки. Отказ → `redirect('/forbidden')` (существующая
русская страница 403).

### 3.3. Флаг раскатки `settings_hub`

- Выключен → сайдбар прежний; старые маршруты рендерят свои страницы на месте.
- Включён → сайдбар с одним пунктом «Настройки»; старые маршруты редиректят на
  новые.

Новые маршруты **не гейтятся флагом**: при выключенном флаге они просто
недостижимы из меню. Так флаг остаётся честным двусторонним рубильником, а
редирект не может увести на 404.

**Отклонение от ТЗ §5.1 (осознанное).** Редиректы делаются временными (307,
`redirect()`), а не постоянными (308, `permanentRedirect()`), пока живёт флаг:
308 браузер кэширует навсегда, и откат флага оставил бы пользователей с мёртвой
навигацией. Перевод на 308 — шагом снятия флага после приёмки.

### 3.4. Размещение существующего содержимого `/admin/settings`

Ничего не выбрасывается, всё раскладывается по четырём группам ТЗ:

| Что было на `/admin/settings` | Куда переезжает | Группа ТЗ |
|---|---|---|
| Привязка Telegram + каналы уведомлений | `/admin/settings/integrations/notifications` | 3.1 «Каналы уведомлений» (ТЗ прямо просит) |
| Реквизиты исполнителя (Company) | `/admin/settings/catalogs/requisites` | 3.2 конфигурация |
| Матрица feature-флагов | `/admin/settings/system/feature-flags` | 3.4 система |
| Коды восстановления 2FA + сессии | `/admin/settings/security/personal` | 3.4 безопасность |

Аналогично для `/leader/settings`.

### 3.5. Русификация аудита

Модуль `src/lib/audit/labels.ts` — **только представление**, БД не трогаем.

Чтобы тест полноты был возможен (§2.4: enum'ов нет), вводятся рантайм-реестры в
`src/lib/auth/audit.ts`:

- `AUDIT_ENTITIES` — `const` массив, `AuditEntity` выводится из него (`typeof [number]`);
- `AUDIT_ACTIONS` — `const` массив всех кодов действий, `AuditAction` выводится
  из него, и поле `AuditRecord.action` типизируется этим объединением.

Тогда **TypeScript сам** становится защитой: новый код действия, не внесённый в
реестр, не компилируется; тест полноты требует перевод для каждого элемента
реестра. Это сильнее, чем просил ТЗ, и закрывает его цель («защита от
англоязычных значений при добавлении новых типов событий»).

Fallback (ТЗ §6.4.1): нет перевода → показать исходное значение + `log.warn`.

## 4. Что НЕ входит

Строго по ТЗ §7: бизнес-логика переносимых разделов, схема БД (кроме новых
кодов прав), клиентские кабинеты, доработка функционала доп-полей и статусов,
полноценная i18n-инфраструктура.

Дополнительно: `/admin/import` и `/admin/payments-import` **не сливаются** в одну
страницу — у них разная логика (ТЗ §10 прямо разрешает не объединять); они
становятся двумя вкладками одного подраздела «Обмен с 1С», каждая на своей
странице.

## 5. Тестовая стратегия

| Слой | Что проверяем |
|---|---|
| unit (lib) | реестр разделов: у каждого раздела уникальный `id`/`href`, все `legacyHrefs` уникальны; матрица прав `canAccessSettingsSection` по четырём веткам §3.2 |
| unit (components) | хаб: четыре группы, фильтр поиска, скрытие карточек без прав; боковая навигация: активный пункт, мобильный `<select>`; крошки |
| unit (pages) | каждая новая страница рендерится (helper `renderServerComponent`); старые маршруты: флаг ON → `redirect` на новый, флаг OFF → рендер прежнего содержимого |
| unit (audit) | полнота словаря по `AUDIT_ACTIONS`/`AUDIT_ENTITIES`; fallback + `log.warn`; формат даты `ДД.ММ.ГГГГ ЧЧ:ММ:СС` |
| integration | 403 при заходе в чужой раздел с профилем; полный доступ при `accessProfileId = null` |
| гейты | `typecheck`, `lint`, `boundaries`, `deadcode`, `dup:check`, `format:check` |

## 6. Открытые вопросы заказчику (не блокируют работу)

1. **Постоянные редиректы (308).** Сделаны временными на время жизни флага —
   см. §3.3. Переключить на 308 при снятии флага?
2. **Пункт «Отчёты»** из «остаётся в основном меню» (ТЗ §2) в админском меню
   отсутствует как таковой — ничего не трогали.
3. **Профили доступа**, заведённые до этой задачи, попадают под «дедушкину
   оговорку» (§3.2, п. 3) и сохраняют прежний доступ. Если нужно жёстко
   default-deny — это отдельное решение и видимое изменение поведения.
