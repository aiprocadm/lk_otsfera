# Этап 2 «Реестр значков + единый шелл» — дизайн

- **ТЗ:** [Понятность интерфейса и функциональные пробелы](../../tz/2026-08-08-tz-usability-and-core-gaps.md)
- **Требования:** `У-5`…`У-12` (блок B «Единый визуальный язык»)
- **Статус:** 📝 спека, ждёт «ок» заказчика. Код не начат (CLAUDE.md §8)
- **Факт кода:** ветка `stage2-nav-icons-shell` от `main` `270d3a5e` (этап 1 влит)

## 1. Зачем

Меню — единственное, по чему человек понимает, что вообще есть в системе. Сейчас
оно разное в каждом кабинете, а значки подобраны на глаз, поэтому один и тот же
значок означает разное, а один и тот же раздел выглядит по-разному в двух ролях.
Плюс интерфейс собран из **пяти отдельных каркасов**, и любая правка (мобильная
версия этапа 3, хлебные крошки этапа 9) означает пять одинаковых правок и пять
источников расхождений.

## 2. Что в объёме

`У-5` реестр значков · `У-6` `iconKey` вместо `icon` · `У-7` значки партнёру и
слушателю · `У-8` разведение конфликтов · `У-9` тест-страж · `У-10` шелл рисует
значок вместо серой точки · `У-11` пять шеллов → один · `У-12` ширина `w-60`.

**Не в объёме:** мобильная версия (этап 3 — но `У-11` делается ради неё),
хлебные крошки и «Частые задачи» (этап 9), перестановки пунктов партнёрского
кабинета (этап 4), объединение экранов 1С (этап 7). Состав меню не меняем —
только значки, названия из таблицы §4.2 и каркас.

## 4. Решения

### 4.1. Реестр значков (`У-5`, `У-6`)

Новый файл `src/lib/navigation/icons.ts`:

```ts
export const NAV_ICONS = { dashboard: '⌂', orders: '📦', ... } as const;
export type IconKey = keyof typeof NAV_ICONS;
```

В `NavItem` поле `icon?: string` заменяется на `iconKey: IconKey`
(**обязательное** — иначе «забыл значок» снова станет нормой, как у партнёра).
Сайдбары читают `NAV_ICONS[item.iconKey]`.

Значки остаются **эмодзи** — как сейчас. Переход на SVG-набор потянул бы новую
зависимость и правку всех шести кабинетов; в объёме `У-5` этого нет.

### 4.2. Разведение конфликтов (`У-8`) — предлагаемая карта

**Меняется только значок** (названия те же):

| Раздел | Было | Стало | Почему |
|---|---|---|---|
| «Организации» (admin) | `🏛` | `🏢` | один раздел — один значок во всех ролях |
| «Партнёры» (admin) | `🏢` | `🤝` | `🏢` занят «Организациями» |
| «Команда» (3 роли) | `⚙` | `👥` | `У-8`: «Настройки» ≠ «Команда» |
| «Кабинет руководителя» (manager) | `⚙` | `🧭` | `У-8`: третий смысл у `⚙` |
| «Кабинет слушателя» (organization) | `🎓` | `👤` | `🎓` — про заявки на обучение |
| «Импорт оплат» (manager) | `📥` | `💳` | `📥` — «Входящие в работу» |
| «Загрузка из 1С» (admin, manager) | `📥` | `📤` | там же |

**Меняется название** — это требует вашего «ок» отдельно (см. §8):

| Роль | Было | Стало | Почему |
|---|---|---|---|
| leader | «Сводка» | «Главная» | тот же экран, что «Главная» у трёх других ролей; страж `У-9` запрещает одному значку два названия |
| manager, leader | «Обращения клиентов» | «Обращения» | один объект — одно имя во всех кабинетах (`У-76`) |
| organization | «Мои заявки» | «Обращения» | то же самое обращение, вид со стороны клиента |
| manager | «Обращения» (`/manager/inbox`) | «Входящие письма» | это **другой** раздел — входящая почта; сейчас название совпадает с обращениями и путает |
| admin | «Загрузка Excel» | «Загрузка из 1С» | тот же раздел, что у менеджера |

### 4.3. Тест-страж (`У-9`)

Unit-тест по всему `navByRole`: одинаковый `label` ⟹ одинаковый `iconKey`, и
одинаковый `iconKey` ⟹ одинаковый `label`. Плюс: у каждого пункта `iconKey` есть
в реестре, и в реестре нет ключей, которыми никто не пользуется.

### 4.4. Единый шелл (`У-11`)

`src/components/shell/app-shell.tsx` + `src/components/shell/sidebar.tsx`.
Роль-специфичное уезжает в пропсы:

| Проп | Что закрывает |
|---|---|
| `title` / `subtitle` | «Админ», «Менеджер» + «Промтехносфера», «Заказчик» + название организации |
| `items` | готовый список (фильтрация прав остаётся **на сервере**, как сейчас) |
| `headerLeft` | e-mail, «Кабинет менеджера · e-mail», название организации |
| `bellRole` | `admin` · `manager` (в том числе для leader) · `organization` · `partner` · у слушателя колокольчика нет |
| `showAskQuestion` | партнёр и организация, под флагом `cabinet_questions` |
| `sidebarTop` | слот для переключателя организаций (клиентский кусок остаётся отдельным компонентом) |
| `theme` | `dark` (партнёр/слушатель) · `light` (остальные) — тёмную шапку сохраняем, чтобы не менять внешний вид кабинета вне объёма |

Возможности сайдбара — объединение того, что уже есть: группы, закреплённые
внизу пункты, счётчики `NavBadge`, значок, подсветка активного пункта,
`disabled` со значком «скоро». Партнёр и слушатель **получают подсветку
активного пункта**, которой у них не было, — это следствие объединения, а не
отдельная работа.

**Гарды не переезжают.** `requireAdmin`, `hasAnySettingsAccess`, `isManagerLeader`,
`orgAdminOrLeaderOnly` остаются там же, где сейчас, — шелл получает готовый
список. Иначе объединение каркасов молча превратилось бы в правку прав (§4).

### 4.5. `У-10`, `У-12`

Серая точка заменяется значком; ширина партнёрского/слушательского сайдбара
`w-56` → `w-60`.

## 6. Тесты

- страж `У-9` (пары «название ↔ значок» по всем ролям);
- реестр: каждый `iconKey` пункта есть в `NAV_ICONS`, неиспользуемых ключей нет;
- общий шелл: тёмная и светлая шапка, колокольчик по роли, «Задать вопрос» под
  флагом, переключатель организаций, группы, закреплённые пункты, счётчики,
  подсветка активного, `disabled` со «скоро»;
- у партнёра и слушателя в меню есть значки и нет серой точки;
- ширина `w-60` во всех кабинетах.

Гейты перед PR: `typecheck` · `lint` · `format:check` · `test:ci`; `knip`,
`depcruise`, `jscpd` — на CI (локально отсутствуют).

## 7. Риски

| Риск | Что делаем |
|---|---|
| Объединение каркасов молча меняет права | гарды и фильтры остаются на сервере, шелл получает готовый список; тесты прав не переписываем, они должны продолжать проходить |
| Переключатель организаций — клиентский, а шеллы серверные | остаётся отдельным клиентским компонентом, вставляется слотом `sidebarTop` |
| Ломается визуальная приёмка (38 эталонов Playwright) | после правок прогнать `npm run e2e:visual`, при осознанных отличиях обновить эталоны и сказать об этом в PR |
| `iconKey` обязателен — большой единовременный diff по 92 пунктам | иначе «забыл значок» повторится; страж `У-9` держит инвариант дальше |
| Тёмная шапка партнёра «уедет» в светлую | тема пропом, внешний вид кабинетов не меняем |

## 8. Решения, требующие «ок» заказчика

1. **Переименования пунктов меню** (таблица §4.2, вторая часть): «Сводка» →
   «Главная» у руководителя; «Обращения клиентов» и «Мои заявки» → **«Обращения»**
   во всех кабинетах; `/manager/inbox` → **«Входящие письма»**; «Загрузка Excel» →
   «Загрузка из 1С». Без переименований страж `У-9` невозможен: одно и то же
   название с разными значками (или наоборот) — это ровно то, что он запрещает.
2. **Значки остаются эмодзи** (а не набор SVG-иконок). Дешевле и без новых
   зависимостей; в `У-5` формат не задан.
3. **Партнёр и слушатель получают подсветку активного пункта** и светлые
   значки вместо серых точек, но **тёмная шапка их кабинета сохраняется**.
   Альтернатива — привести все кабинеты к светлой шапке; это заметное изменение
   внешнего вида, поэтому по умолчанию не делаю.
