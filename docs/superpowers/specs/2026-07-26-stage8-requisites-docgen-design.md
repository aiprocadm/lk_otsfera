# Этап 8 ТЗ — реквизиты и автогенерация документов (Модуль 9, ФТ-9.1–9.7)

Дата: 2026-07-26 · Статус: **📝 ждёт подтверждения заказчика** (4 вопроса — §9) ·
ТЗ: [docs/tz/2026-07-23-tz-lk-otsfera-v1.md](../../tz/2026-07-23-tz-lk-otsfera-v1.md) §Модуль 9, §9 этап 8.

**Решения §10 ТЗ** (заказчик, 26.07.2026): вопрос 2 — документы v1: **счёт,
акт, договор, доп. соглашение**; номер счёта — **с префиксом года**. Вопрос 3 —
документы платформы **оперативные**, бухгалтерский канон — 1С (`externalId`
обеспечивает матчинг, конфликтов с текущим 1С-обменом нет: сгенерированные
документы синк не трогает — у них `externalId=null`, как у promoteLead-заказов).

## 1. Цель и критерий приёмки (§9 ТЗ)

«Менеджер формирует счёт и акт по заказу в 1 клик при полных реквизитах; при
неполных — понятный список недостающего; нумерация без дублей под конкуренцией».

## 2. Контекст кода (разведка)

- PDF уже генерится: `@react-pdf/renderer` (PDF комиссии, воркер
  `docs.generateCommissionPdf`). **Кириллического шрифта нет** (Helvetica) —
  нужен TTF в репозитории + `Font.register`.
- **Docx-стека нет вообще** (ни docxtemplater, ни LibreOffice/конвертера
  docx→PDF на сервере) — «docx-шаблон → PDF» из ФТ-9.3 в лоб нереализуем
  без тяжёлой новой инфраструктуры (вопрос §9-1).
- `Document` готов: `type` (invoice/act/contract/extra_agreement уже в enum),
  `generatedBy(system)`, `direction`, `version`, `replacesDocumentId`
  (поле-сирота — версии построим на нём). Счётчиков в БД нет; эталон
  атомарности — upsert+increment в транзакции.
- Реквизиты: Organization — только ИНН/КПП; Partner — legalName/ИНН;
  **Company — ничего**. Формы: admin-редакторы орг/партнёра есть (узкие),
  /organization|partner|admin/settings — только Telegram+каналы.
  DaData-прокси уже отдаёт **ОГРН и адрес** — автозаполнение готово.
- Деталка заказа менеджера: блок «Документы» есть, action-кнопок нет;
  «условия завершения» (`completion.ts` + панель) — готовый образец для
  «кнопка неактивна + список недостающего» (ФТ-9.5).
- Скан: пользовательские файлы сканируются; для сгенерированных нами байтов
  ставим `scanStatus='clean'` сразу (антивирус для своих байтов бессмыслен).

## 3. Модель данных (ФТ-9.1; все миграции аддитивные)

Единый набор реквизитов (nullable) для **Organization / Partner / Company**:
`ogrn`, `legalName` (орг; у партнёра есть), `kpp` (партнёру добавить),
`legalAddress`, `bankName`, `bankAccount` (р/с), `corrAccount` (к/с), `bic`,
`signerName`, `signerPosition`, `signerBasis` (устав/доверенность №…).
Company дополнительно: `inn`, `phone?`, `email?` (шапка документов).

- **`DocumentCounter`**: `@@id([companyId, year, docType])`, `lastNumber Int` —
  атомарный `upsert + increment` в транзакции генерации (без дублей под
  конкуренцией; вопрос §9-2 о формате).
- **`Document`**: `+number String?` (человекочитаемый номер документа).
- **`OrderItem`**: `+amount Decimal?` (цена позиции; вопрос §9-3).
- Новые реквизитные ключи — в скраббер логов (НФ-2) и `recordPiiAccess`
  не требуется (реквизиты юрлиц — не ПДн физлиц; подписант ФИО — пишем в
  скраббер).

## 4. Формы «Реквизиты» (ФТ-9.2)

- `/organization/settings` и `/partner/settings` — карточка «Реквизиты»
  (самообслуживание): все поля §3 + `PartyAutocomplete` по ИНН
  (автозаполнение названия/КПП/ОГРН/адреса из DaData, деградация до ручного
  ввода). Сервисы organization/partner + аудит `requisites_changed`.
- Сотрудники: расширение admin-форм (`OrganizationEditForm`,
  `PartnerEditForm` — партнёру заодно добавить отсутствующие legalName/ИНН)
  + read-only таб «Реквизиты» карточки организации менеджера показывает
  полный набор.
- Реквизиты исполнителя: карточка «Реквизиты компании» на `/admin/settings`
  (Company, admin-only).

## 5. Генерация документов (ФТ-9.3/9.4/9.6; вопрос §9-1)

- **v1 — встроенные шаблоны** на существующем PDF-движке: счёт, акт,
  договор, допсоглашение (кириллический TTF — в репозиторий). Данные:
  стороны (Company ↔ Organization, реквизиты полностью), номер+дата,
  позиции (§9-3), итог, НДС из `Order.vatIncluded/vatRate`, подписанты.
  Управление собственными docx-шаблонами из админки — **отложить** (§9-1):
  честная реализация требует docx→PDF конвертера (LibreOffice), которого
  нет; предлагаю отдельным PR после этапа при подтверждении потребности.
- Кнопки «Сформировать: счёт / акт / договор / доп. соглашение» — блок
  «Документы» деталки заказа менеджера (+ зеркало admin-деталки заказа).
- Транзакция: номер из `DocumentCounter` → рендер PDF → S3
  (`orders/{orderId}/generated/...`) → `Document` (`generatedBy='system'`,
  `direction='outgoing'`, `type`, `number`, `scanStatus='clean'`).
  Повторная генерация того же типа → новый документ `version+1` +
  `replacesDocumentId` (старый остаётся скачиваемым, в списке — бейдж
  версии). Аудит `document_generated`; клиенту — существующее
  `document_published` со ссылкой.
- **Синхронно, без очереди** (ФТ-9.6): рендер комиссионного PDF тем же
  движком — доли секунды; замер фиксируем unit-тестом (порог ~2 с). Очередь
  `docs.generateOrderDocument` заводим только если замер провалится.
- Feature-флаг **`document_generation`** (opt-in): гейтит кнопки и
  action/route генерации. Формы реквизитов — без флага (самообслуживание
  полезно само по себе и ничего не ломает).

## 6. Валидация полноты (ФТ-9.5)

- Чистая функция `listMissingRequisites(company, counterparty, docType)` →
  русские названия недостающих полей (образец `completion.ts`).
- Кнопки генерации неактивны при неполных реквизитах, рядом список
  недостающего + кнопка «Запросить у клиента» → уведомление организации
  `requisites_requested` (новая ветка `notifyOrgUsers`, url →
  `/organization/settings`); повторный запрос — не чаще 1 раза в сутки
  (просто disabled по последнему аудиту, без новой модели).

## 7. Тестовая стратегия (порог 100%)

- Миграции/модели: аддитивность; счётчик — конкурентный integration-тест
  (параллельные генерации → номера без дублей и пропусков).
- Сервисы: валидатор полноты (матрица docType×поля), генерация (транзакция,
  версия+replaces, номер, scanStatus=clean, аудит), реквизит-формы
  (валидация ИНН/БИК/р-с длины, идемпотентность, аудит), requisites_requested.
- PDF-рендеры: unit — renderToBuffer не падает, содержит номер/стороны
  (parse текстового слоя не делаем — проверяем данные пропсов), замер < 2 с.
- RBAC: клиентские роли не генерируют (403/404), формы чужих орг → forbidden.
- UI: карточки реквизитов ×3, кнопки генерации (disabled + список
  недостающего), бейдж версии; страницы через renderServerComponent.
- Integration: полный путь «заполнили реквизиты → счёт+акт сгенерированы →
  Document со скачиваемым presigned» на живом Postgres (S3 — мок-порт).

## 8. Разбивка (вопрос §9-4)

- **PR-1 «Реквизиты»**: §3 (кроме счётчика) + §4 + скраббер.
- **PR-2 «Счёт и акт»**: шрифт, движок генерации, счётчик, кнопки,
  валидация полноты + «Запросить у клиента», версии, флаг.
- **PR-3 «Договор и допсоглашение»**: два текстовых шаблона на том же
  движке (+ настройка текстовых блоков договора — если попросите).

## 9. Вопросы заказчику (до кода)

1. **Шаблоны v1**: генерируем PDF по встроенным шаблонам с автоподстановкой
   реквизитов (надёжно, кириллица, 1 клик). Загрузку СВОИХ docx-шаблонов
   через админку отложим (нужен docx→PDF конвертер — тяжёлая
   инфраструктура) — ок? Если свои шаблоны критичны для v1 — скажите, тогда
   вместо PDF будем отдавать заполненный DOCX (его конвертер не нужен).
2. **Формат номера**: свой счётчик на каждый тип в рамках года, номер вида
   **«С-2026-17» / «А-2026-17» / «Д-2026-17» / «ДС-2026-17»** (префикс типа +
   год + сквозной номер) — ок? Альтернатива: акт наследует номер счёта
   (пара «счёт С-2026-17 → акт А-2026-17 с тем же 17»).
3. **Позиции счёта/акта**: у позиций заказов сейчас нет цен — v1 печатает
   одну строку «Услуги по заказу №X: <название>» на сумму заказа (НДС по
   заказу); заодно добавляем поле «цена» позиции — когда менеджеры начнут
   его заполнять, счёт автоматически станет попозиционным. Ок?

## 10. Вне скоупа этапа 8
