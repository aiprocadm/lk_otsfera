# Runbook — автообновление стенда lk.ptsfera.online

**Owner**: ops (сервер `ubuntu`, пользователь `aiproc`)
**Scope**: непрерывное развёртывание свежей `main` на боевой стенд. **Не-цель** — большой релиз с флипом флагов и переводом 1С в live, это [runbook-launch-deploy.md](runbook-launch-deploy.md).

Скрипт: [`scripts/deploy-stand.sh`](../scripts/deploy-stand.sh) · команда: `npm run deploy:stand`

---

## 1. Как устроено

Стенд — **отдельная рабочая копия репозитория**, не та, в которой ведётся разработка. Это принципиально: раньше службы были запущены из рабочего каталога разработчика, и однажды `next dev`, забытый в фоне, занял порт 3000 — боевая служба ушла в бесконечный цикл перезапуска, а сайт полдня отдавал dev-сборку.

| Что | Где |
|---|---|
| Каталог стенда | `/home/aiproc/stands/lk_otsfera` (ветка `main`) |
| Службы | `lk-otsfera-web` (Next.js, :3000), `lk-otsfera-worker` (BullMQ) |
| Секреты | `.env.production` внутри каталога стенда (в git не хранится) |
| Журнал обновлений | `/home/aiproc/stands/logs/lk-update.log` |
| Файл блокировки | `/home/aiproc/stands/lk-update.lock` |
| Расписание | cron пользователя `aiproc`, раз в 10 минут |

Все пути переопределяются переменными окружения (`LK_STAND_DIR`, `LK_UNITS`, `LK_LOG_DIR`, `LK_LOCK_FILE`, `LK_NODE_BIN`, `LK_BRANCH`, `LK_HEALTH_URL`) — значения по умолчанию описаны в шапке скрипта.

**sudo не нужен нигде.** Службы работают от `aiproc`, поэтому перезапуск делается через `kill` главного процесса: systemd с `Restart=always` поднимает его сам.

## 2. Порядок шагов

1. `git fetch origin main` → если коммит не изменился, скрипт молча выходит (обычный случай, 143 из 144 запусков в сутки).
2. Снимок текущей сборки: `.next` → `.next.bak`.
3. `git reset --hard origin/main`.
4. `npm ci` — **только если изменился `package-lock.json`**, иначе это лишние минуты на каждом прогоне.
5. `npx prisma generate`.
6. `npm run build` + проверка, что появился `.next/BUILD_ID`.
7. `npx prisma migrate deploy` — **строго после успешной сборки**: база общая с разработкой, и трогать её из-за кода, который даже не собрался, нельзя.
8. Перезапуск служб, затем проверка, что сайт отвечает по HTTP (до 60 с).

**На любой осечке шагов 4–7 срабатывает откат**: код возвращается на предыдущий коммит, `.next.bak` — на место `.next`, службы не трогаются. Стенд продолжает работать на прошлой рабочей версии.

## 3. Три вещи, которые легко сломать

**Скрипт обновляет репозиторий, в котором сам лежит.** `git reset --hard` перезаписывает файл скрипта, а bash дочитывает его с диска по мере выполнения — и может исполнить обрывок новой версии. Поэтому скрипт первым делом копирует себя во временный файл и продолжает работу оттуда. Не убирайте этот блок.

**Порядок «сборка → миграции».** Обратный порядок означает изменённую схему базы под кодом, который не собрался.

**Проверка `BUILD_ID`.** Без неё «сборка прошла, но результата нет» превращается в цикл перезапуска службы, который со стороны выглядит как «сайт просто лежит».

## 4. Ручные операции

```bash
cd /home/aiproc/stands/lk_otsfera

npm run deploy:stand                 # обычный прогон
npm run deploy:stand -- --dry-run    # показать, что будет сделано
npm run deploy:stand -- --force      # пересобрать текущий коммит заново
npm run deploy:stand -- --no-restart # обновить код и сборку, службы не трогать
npm run deploy:stand -- --help       # справка
```

При ручном запуске лог дублируется на экран; из cron пишется только в файл.

## 5. Если что-то пошло не так

```bash
tail -50 /home/aiproc/stands/logs/lk-update.log   # что делал скрипт
systemctl status lk-otsfera-web                    # почему не поднялась служба
ss -tlnp | grep :3000                              # кто занял порт
```

- **Служба падает с `EADDRINUSE`** — порт 3000 занят чужим процессом (чаще всего забытый `next dev`). Найдите его через `ss` и остановите.
- **Служба падает с «Could not find a production build»** — в каталоге стенда нет `.next/BUILD_ID`. Лечится `npm run deploy:stand -- --force`.
- **Нужно откатиться вручную** — `git reset --hard <коммит>` в каталоге стенда, затем `npm run deploy:stand -- --force`.

## 6. Связь с cron

В cron остаётся тонкая обёртка `/home/aiproc/stands/update-lk.sh`, которая вызывает версионируемый скрипт из каталога стенда:

```bash
#!/usr/bin/env bash
exec /home/aiproc/stands/lk_otsfera/scripts/deploy-stand.sh "$@"
```

Так расписание не зависит от содержимого репозитория, а сама логика развёртывания живёт в git — её видно в истории и можно ревьюить в PR.
